# Gotchas / footguns

Things that have bitten us, so they don't bite again. **Read before debugging; append when something costs you more than a few minutes.** Each entry: the trap, why it happens, what to do instead.

---

## Repo / build

- **TanStack Router: an object `search` in `navigate()` REPLACES the whole query string.** `navigate({ to: "/contacts", search: { action: "new" } })` silently wipes an existing `?type&id` selection. When adding one param on a route that carries others, use the functional updater: `search: (prev) => ({ ...prev, action: "new" })`. Bit FX-1 (the palette's New-contact wiped the open contact's selection); `/contacts` is the app's first search-param route, so every future `navigate` targeting it must think about this.

- **`preview_start` in a `.claude/worktrees/*` session has two failure stages — only the first is fixable.** (1) `Port 8081 is in use by another chat's dev server` → fixed for good 2026-07-02: `.claude/launch.json`'s "web" config uses `autoPort: true` + a port-flag-free command, and `rsbuild.config.ts` honors an assigned `PORT` env (default stays 8081). (2) `EPERM: uv_cwd` → **not fixable from the session**: the preview sandbox binds to whichever worktree owns the currently *active* dev server, so while another chat serves :8081 the sandbox can't even `cwd` into yours. Do not kill the other session's rsbuild (that trap already bit us — Session 10). Workaround: `bun install` in the worktree, run `MODUO_TARGET=web ./node_modules/.bin/rsbuild dev --host 127.0.0.1 --port <free>` via Bash background, drive with the Chrome MCP, kill by the **exact port-specific** pattern when done.
- **Never import a bare `{ runtime }`.** Always resolve via `getRuntime()`. The bare export was an always-null const footgun; grep `./runtime` when auditing lib exports. → [data-layers.md](./data-layers.md)
- **A "reset local cache" that clears `moduo.appearance` also nukes the device-local display prefs (density / text-size / tab style) that deliberately never sync to cloud** — so on reload they snap back to defaults while theme/accent/font re-adopt from cloud. They ride *inside* the same `moduo.appearance` localStorage blob (appearance.ts: "per-device fields never leave localStorage"), so a key-prefix clear can't spare them. DF-19g's reset owns this by **disclosing it in the confirm copy** ("device-only display settings reset to defaults"), not by silently dropping them — the designer treats density as a first-class customization axis. Any future cache-wipe that touches `moduo.appearance` must either preserve the device subset or say so. → [advanced-section.tsx](../src/features/settings/sections/advanced-section.tsx)
- **Deleting the Notes IndexedDB is only safe once the outbox is empty — and the guard must count BOTH outboxes across ALL workspaces.** The per-note y-indexeddb doc DBs (`moduo:notes-v2:doc:*`) hold local CRDT state; `deleteDocOutboxEntries` runs only *after* a successful `pushUpdates` (engine-v2), so an empty `docOutbox`+`metaOutbox` provably means every local edit reached the cloud and the doc DBs can be dropped losslessly. DF-19g's reset gates on `countPendingOutbox()` (idb.ts) which counts globally because the delete is global; the blocked-dialog path removes the reset button entirely (not just disables it) so there's no code path from pending>0 to a delete. Caveat it can't cover: an edit stranded in the engine's in-memory `memOutbox` (a transient IDB-write failure) is invisible to a durable-store count. Also `indexedDB.databases()` is unsupported on Firefox/older Safari → there only the named `moduo-notes-v2` is deleted, per-note doc DBs survive (harmless: outbox empty, cloud is truth). → [advanced-section.tsx](../src/features/settings/sections/advanced-section.tsx), [idb.ts](../src/features/notes/sync/idb.ts)
- **redb is paused — never make it load-bearing** for a new feature. New models are Supabase-first; redb is kept only for the future offline/"lite" version and not-yet-migrated legacy modules. → [data-layers.md](./data-layers.md)
- **Vitest has no `@/` alias — VALUE imports from `lib/` in a test's graph must be relative.** `vitest.config.ts` defines no `resolve.alias`, so a runtime (value) import like `import { deriveLinkKey } from "@/lib/entity-links"` fails to resolve under `bun run test` ("Failed to resolve import @/lib/…"), even though `tsc` (which reads tsconfig `paths`) is happy. **Type-only** `@/` imports are fine — they're erased before resolution, which is why existing tests (`mention.test.ts`, `rollup.test.ts`) use `@/` for types and still pass. The rule: anything reachable from a `*.test.ts(x)` via a *value* import must use a **relative** path for `lib/*` (see `spine/activity.ts` → `../../lib/entity-links`, `spine/suggest.ts`). Components/hooks bundled only by rsbuild may use `@/` values (rsbuild resolves it); the trap is strictly the vitest graph. Standalone `bunx vitest` resolves `@/` even less than `bun run test` — always verify with the project script.
- **Corollary: a unit test must NOT import a component `.tsx` — extract the pure logic to a `.ts` and test that.** Every `src/components/ui/*` primitive imports `@/lib/utils`, so importing any `.tsx` that renders one (e.g. a settings section using `Badge`) drags `@/lib/utils` into the vitest graph → `Failed to resolve import "@/lib/utils" from ui/badge.tsx`, failing the whole suite even when you only wanted a pure exported helper. DF-19d hit this testing `keyScope` by importing `api-keys-section.tsx`; fixed by moving `keyScope` into a pure `api-keys.ts` (the `account.ts`/`billing.ts` pattern — pure logic in `.ts` is unit-tested, the `.tsx` component is live-verified). (2026-07-11.)
- **The local done-check is `bun run verify`** (typecheck + lint:tw + lint:css + unit tests) — it mirrors CI's gate. CI does **not** run the e2e / visual-snapshot / billing suites (those stay local/manual), so a green PR doesn't cover them.
- **Dead-code sweeps: "is it mounted?" is not "is it alive?" — trace the OUTPUT, not just the importers.** `useSlotBookingsSync` was mounted in `app-gate.tsx` (so import-graph tools call it live) yet its entire effect was writing a localStorage key with zero readers — and it PATCHed `slot_bookings.calendar_synced=true` server-side for rows that surfaced nowhere, actively corrupting the "unsynced" signal for any future re-implementation. When sweeping, follow each candidate's *sinks* (storage keys, tables, events) to a real consumer before calling it live. Also: `bun run verify` catches zero Rust breakage — any sweep touching `src-tauri` needs its own `cargo check` (CLEAN-1, 2026-07-03).
- **A code-graph / import-graph "isolated, prune-safe" verdict can miss a compile-only coupling into a load-bearing module — re-verify with `rg` before deleting.** Graphify (and the backend memo it fed) reported `graph_helix`/`embeddings` as "isolated, in no coupling hotspot, touches zero feature code." They were **runtime-dead** but **compile-coupled**: `graph_helix` was woven into the **live email engine** via `commands/email/graph_outbox.rs`, called from ~11 sites across `email.rs`/`sync.rs`/`realtime.rs`, and `queue_graph_upsert_for_envelope` wrote an `email_graph_outbox` redb row on *every* envelope sync (only the *flush* was gated behind `graph.is_enabled()`, false without `HELIX_SIDECAR_PATH`). Removing `helix-rs` therefore required excising that dead tendril from email — not the "zero feature code" the graph claimed. The graph counts *edges it saw*; a subsystem whose outputs nothing reads (dead) can still be *written to* from live code (coupled). When a graph says "safe to delete," still `rg` every symbol (types, redb tables, command fns) for writers, not just readers, before cutting (proposal C, 2026-07-11). → [docs/decisions.md](./decisions.md)
- **`src-tauri` has a `lite` Cargo feature (off by default) — the redb↔Supabase `sync` worker compiles only under `--features lite`.** `cargo check`/`build` in the **default** (cloud) config does NOT compile `src/sync/mod.rs` or the `AppState.sync_worker` field / `auth.rs` start-stop paths (all `#[cfg(feature = "lite")]`). If you edit `sync/` or anything gated for the future offline/"lite" build, a default `cargo check` won't catch breakage there — run `cargo check --features lite` too (proposal C, 2026-07-11). → [src-tauri/Cargo.toml](../src-tauri/Cargo.toml)
- **Visual-snapshot PNG baselines are NOT generated in CI** and are platform-suffixed (`*-visual-darwin.png`). Capture is a deliberate human `bun run e2e --update-snapshots` run on the canonical env. A visual diff means **stop and ask**, never auto-accept/regenerate.
- **macOS Liquid Glass app icon has been lost in merges twice.** It lives in-repo at `scripts/icons/source/Moduo.icon`; regenerate with `bun run icon:liquid` (needs full Xcode for `actool`). Don't let a merge drop it.

## Supabase / migrations

- **A new migration is NOT applied by `bun run verify`.** `verify` only runs typecheck/lint/unit-tests; it never touches Postgres. A green PR with a new `supabase/migrations/*.sql` means the SQL *parsed in your head*, not that it deployed — server invariants (RLS, RPCs, FKs, generated columns) are unproven until the migration is applied to a Supabase instance and exercised by an authenticated round-trip (the manual-test layer). Apply the migration and regenerate `src/types/supabase.ts` before any code *depends* on the new tables/RPCs. Don't apply to the shared/prod project without authorization.
- **The Supabase JS client is untyped (`SupabaseClient`, no `Database` generic).** So `supabaseClient.from("a_table_that_doesnt_exist_yet")` and `.rpc("an_unmigrated_fn", …)` both **typecheck fine** — TS can't catch a table/RPC-name typo or an arg-shape mismatch against an unmigrated schema. New runtime methods for new tables pass `verify` even if the migration is wrong or unapplied; the only real check is the live round-trip. (Mappers take `r: any`, so column renames are silent too.)
- **`runtime.workspace.joinInvite(token)` returns the accepted *invite* row, NOT a workspace** — `{ id: <invite id>, workspace_id, role, email, status, … }`. Its return type is `Promise<any>` (untyped, see above), so `mapWorkspace(inviteRow)` typechecks and passes `verify` while producing a garbage `WorkspaceSummary`: `id` = the invite id, `name` = `undefined`, `role` derived from the invite. The joined workspace's real id is `invite.workspace_id`; resolve the actual summary from a refreshed workspace list (`refreshWorkspaces()` now returns the fresh list for exactly this) and select *that*. Never `selectWorkspace(inviteRow.id)` either — it selects a non-existent workspace (→ `selectedWorkspace` goes `null`, the switcher unmounts). Bit `joinWorkspace` pre-DF-24; it only hid because its one consumer used the return value as a truthiness check. → [workspace-provider.tsx](../src/providers/workspace-provider.tsx)
- **Direction-agnostic link dedupe must use a collation that matches JS.** `entity_links.pair_key` (the unordered `least/greatest(type:id)` key) compares with `COLLATE "C"` (byte order) so it provably matches the TS `deriveLinkKey` (JS `<=` code-unit order). Plain `least/greatest` on `text` uses the DB's *default* collation (a locale on standard Supabase), which can order non-ASCII tokens differently than JS → the server-side and client-side dedupe keys silently disagree. Keep `spine_pair_key()` (SQL) and `deriveLinkKey()` (TS) in lockstep. → [src/lib/entity-links.ts](../src/lib/entity-links.ts)
- **A plpgsql function returning a composite type returns an all-NULL *row*, not SQL NULL, after a `SELECT … INTO` that finds nothing.** `RETURN v_row;` when `v_row` is unset serializes (via PostgREST) as `{id:null,…}`, not `null` — callers expecting `null` get a truthy object. Guard with `IF v_row.id IS NULL THEN RETURN NULL; END IF;` (see `links_op_delete`, `contacts_op_unlink`).
- **Wiring a brand-new RPC into a live read path breaks that surface until the migration is deployed.** `verify` never applies migrations, and the prod apply is a separate step — so between merging code that calls `runtime.x.newRpc()` and deploying its migration, the call 404s and can break the feature for everyone (e.g. the notification bell). For a *new* RPC consumed on a hot read path, wrap the call in try/catch and **degrade gracefully** (fall back to the prior behavior / empty) so the app survives the gap; the new data simply appears once the migration lands. (See `workspace-provider.refreshNotifications` wrapping `spine.listNotifications`.) Mutations the user explicitly triggers can surface the error instead.
- **A plpgsql/SQL function with `RETURNS TABLE(...)` whose out-columns share names with a table in its body (e.g. `workspace_id`, `id`, `payload`) is an ambiguity trap.** It only works while *every* column reference in the body stays table-qualified (`ma.workspace_id`); a single later unqualified ref silently resolves to the out-param instead of the column. Keep refs qualified (or prefix out-params `o_`). (See `notifications_list`.)

## Supabase / Realtime (NO-6)

- **`channel.send()` on a Realtime channel that isn't JOINED does NOT drop — it silently REST-falls-back with a `console.warn`.** The notes broadcast relay assumed `send()` was a no-op while joining/torn-down; in `@supabase/realtime-js` it POSTs to the broadcast REST endpoint instead (plus a deprecation warning), so early keystrokes (before SUBSCRIBED) or a flush after teardown spam REST + the console. Gate the outbound path on a `pushable` boolean set true only on `status==='SUBSCRIBED'` and back to false on cleanup / CLOSED / CHANNEL_ERROR / TIMED_OUT; drop the buffer while not pushable (durability rides the outbox + pull, not broadcast). → [use-note-realtime.ts](../src/features/notes/hooks/use-note-realtime.ts)
- **`WorkspaceMember` carries NO display name or avatar — only `userId`/`role`/`isActive`.** ~~Any "who" UI can't resolve a name from the members list.~~ **UPDATED DF-24 (2026-07-11):** `mapMember` now surfaces `displayName`/`avatarUrl` from the `profiles(*)` join `listMembers` already does — the modal renders real names. The join was always fetched; the mapper just threw it away. Presence/comments elsewhere still use the current user's email local-part + `useMentionSearch` for a searchable people source. → [workspace-mappers.ts](../src/features/workspaces/workspace-mappers.ts)
- **`workspace_members` uses a DIFFERENT role/permission vocabulary than the app and than `workspace_invites` — and the untyped client can't catch it.** The members table's CHECK constraints only accept **role ∈ {owner,admin,member,viewer}** and **permissions_{notes,tasks} ∈ {read,write,none}** (verified live: `editor`/`view`/`edit`/`admin` all 400 the insert). But the app's `WorkspaceRole` is `{owner,admin,editor,viewer}` and `ModulePermission` is `{none,view,edit,admin}`, and `workspace_invites` happily stores the app vocabulary. So `joinInvite` copying `invite.role`/`invite.permissions_*` straight into the `workspace_members` insert made **every** real redemption 400 on a CHECK — the invite loop was silently data-broken (nobody had ever completed a join, so it never showed). **Any write to `workspace_members` must go through the bridges** `toMemberRole`/`toMemberPerm` ([workspace-mappers.ts](../src/features/workspaces/workspace-mappers.ts)); reads normalize back via `normalizeMemberRole` (`member`→`editor`). Also: `mapWorkspace` had `row.role ?? "owner"` but `workspaces` has **no `role` column**, so every workspace read as owner/edit — the caller's real role/perms live in the nested `workspace_members(*)` row and must be derived from it (DF-24 passes `currentUserId` in). `verify` catches none of this — only a live authed insert does. → [runtime.web.ts](../src/lib/runtime.web.ts) `joinInvite`/`updateMemberPermissions`, [workspace-mappers.ts](../src/features/workspaces/workspace-mappers.ts) `mapWorkspace`
- **Managing ANOTHER member's `workspace_members` row (role change, remove, transfer ownership) can't be a client-direct write — the base RLS is own-row.** A direct `.from("workspace_members").update(...).eq("id", <someone-else>)` silently affects 0 rows (RLS filters it out) — which reads as a no-op success, not an error. `updateMemberPermissions` shipped this way and role changes for other members quietly did nothing. Every cross-member management op must be a **SECURITY DEFINER RPC** that re-checks the caller: `workspace_op_set_member_role` / `workspace_op_remove_member` / `workspace_op_transfer_ownership` (2026-07-11 role-hierarchy work). The **role hierarchy rules live in TWO places that must stay in lockstep**: the SQL ops AND the client mirror [`member-permissions.ts`](../src/features/workspaces/member-permissions.ts) (`canManageMember`/`assignableRolesFor`/`canTransferOwnership`) — the client is UX-only (filters menus), the SQL is the real gate. Rule: owner manages everyone incl. admins; an admin manages only editors/viewers (never a peer admin, never grants admin); the owner is never removed/role-changed (hands off via transfer). Determine "is caller the owner" from `workspaces.owner_id`, never a role string. → [supabase/migrations/20260711180000_workspace_roles_transfer.sql](../supabase/migrations/20260711180000_workspace_roles_transfer.sql)

## Routes / app chrome

- **A new top-level route needs FIVE wirings, and the compiler catches none of them:** (1) `src/app/router/route-tree.tsx` (the route), (2) `app-chrome-constants.ts` (the nav tab) + the permission filter in `app-chrome.tsx`, (3) **`routeToFeatureLayout` in `src/features/layout/panel-events.ts`** — miss this and the top-bar panel toggles silently mutate ANOTHER feature's persisted panel state (the fallthrough returns `"notes"`) while the page's own `FeaturePanelsShell` ignores them, (4) the `module-N` shortcut count (`src/lib/shortcuts.ts` + the fixed `useShortcut` calls in app-chrome — the Nth tab past the list loses its ⌘N silently), (5) the command palette's `navActions` (`global-command-palette.tsx`). CAL-1 hit 3–5; a validator agent caught #3 pre-ship.
- **HIDING a route (nav tab removed but route kept) has a SIXTH wiring the add-a-route gotcha doesn't list: the app-chrome redirect guard.** `app-chrome.tsx` runs `if (!isSettingsRoute && !modulesNavItems.some(t => t.href === pathname)) navigate({to: modulesNavItems[0].href, replace:true})` — it bounces ANY pathname not in the visible nav to the first tab. So dropping a tab from `baseModulesNavItems` silently makes that route **unreachable even by direct URL** (it redirects to Home), even though the route + its `routeToFeatureLayout` entry are intact. DF-4 hit this hiding Mindmap: `/mindmap` bounced to `/` until the guard was taught to exempt it. Fix pattern: keep an explicit `hiddenReachableRoutes` allowlist (in `app-chrome-constants.ts`) and skip the bounce for those paths. Live-caught (path came back `/` after navigating to `/mindmap`), not test-caught — no test covers the guard.
- **Setting `scrollbar-width` (e.g. Tailwind's `scrollbar-thin`) makes Chromium ignore all `::-webkit-scrollbar` rules for that element** — the native thin scrollbar renders, colored by `color-scheme`, i.e. WHITE on our dark surfaces. Pair it with `scrollbar-color: var(--border) transparent` (done app-wide in `.scrollbar-thin`, global.css). Editing the webkit block does nothing while scrollbar-width is set.

- **A "new" table may already exist in prod from the pre-migrations era — check `src/types/supabase.ts` BEFORE writing `CREATE TABLE IF NOT EXISTS`.** The legacy exploratory calendar created `calendar_events` straight from the dashboard (no migration file), owner-scoped with client-direct writes. A `CREATE TABLE IF NOT EXISTS` for the Wave-2 shape would have silently no-op'd and left every new column missing at runtime (untyped client = no compile error, per the gotcha above). CAL-2 extends it in place instead (ALTER + drop-all-policies loop via `pg_policies`, since dashboard-era policy names are unknown). Grep the generated types for the table name first, always.
- **Radix dismiss (Esc) runs on a document-level CAPTURE listener — it fires before your input's onKeyDown, and `onOpenChange(false)` can't tell Esc from click-away.** The quick-create popover initially committed the event on Esc because the dismiss path ran commit-on-close before the input's Esc handler could cancel. Handle `onEscapeKeyDown` on the Content with `event.preventDefault()` + your own cancel, and `onPointerDownOutside` for the click-away path; keep `onOpenChange` only as a discard fallback. → [src/features/calendar/ui/event-quick-create.tsx](../src/features/calendar/ui/event-quick-create.tsx)
- **`<input type="datetime-local">` fires change per keyboard segment edit** — committing in `onChange` writes garbage intermediates (year "0002") to the server, one RPC per keystroke. Draft-state + commit on blur/Enter, like the title-field pattern. → [event-detail-panel.tsx](../src/features/calendar/ui/event-detail-panel.tsx)
- **Custom pointer-drag engines need three exits, not one:** `pointerup` alone loses the gesture when the button releases outside the window/over an iframe (sticky ghost + a surprise commit on the next click). Also handle `pointercancel`, self-heal on `pointermove` with `e.buttons === 0`, and re-measure cached rects per move (wheel-scroll mid-drag shifts them). NOTE for synthetic testing: dispatch moves with `buttons: 1` or the self-heal cancels your test gesture. → [calendar-grid.tsx](../src/features/calendar/ui/calendar-grid.tsx)
- **SettingsModal (anything inside AppChrome) mounts → unmounts → remounts SEVERAL times during boot** (workspace-loading churn; three mounts observed live in one cold load, DF-3 2026-07-10 — and a workspace switch remounts AppChrome the same way via `WorkspaceGate`'s `loading → null`). Consequences: (1) a `window` CustomEvent dispatched during boot (e.g. the `/settings?section=…` redirect page's `dispatchOpenSettings`) is heard by a listener that unmounts moments later — the event is effectively lost; (2) a one-shot "pending" buffer consumed on mount is wiped the same way. Component state in AppChrome's subtree does NOT survive boot. Fix pattern (validator-hardened): a module-level **sticky** buffer that ONLY the deep-link path arms (`dispatchOpenSettings(detail, {sticky:true})`), every modal mount inside a 30s TTL re-applies, and a **user close disarms** (`clearPendingOpenSettings` from `onOpenChange(false)`/the ⌘, toggle) — buffering EVERY dispatch re-opens a modal the user explicitly closed on the next remount. Any future boot-time event → AppChrome-subtree consumer needs the same treatment (or the remount churn itself fixed — CC-13 boot-storm neighborhood). → [settings-events.ts](../src/features/settings/settings-events.ts)
- **supabase-js reports PostgREST/REST failures via the result's `error` field — it does NOT throw.** A `catch` around `await supabaseClient.from(...).select(...)` only sees network-level rejections; destructuring just `{ data }` silently coerces a 500/expired-JWT-401/RLS error to "no rows", which reads as "no subscription"/"empty" downstream. If the distinction between *absent* and *failed* matters (it did in the SubscriptionGate — a paying user would have been paywalled on a transient error), check `error` and route it explicitly (`if (error) throw …`). Bit DF-3's gate fail-open (2026-07-10). → [app-gate.tsx](../src/routes/layouts/app-gate.tsx)
- **`window.location.origin` inside the Tauri webview is `tauri://localhost` (macOS/Linux) or `http://tauri.localhost` (Windows) — never send it to an external service as a return/redirect URL.** Stripe rejects non-http(s) return_urls (and even if accepted, the link would dead-end in a normal browser). On desktop omit the URL and let the server-side fallback (`APP_URL`) win, or use the hosted web origin (`PUBLIC_WEB_ORIGIN`). Also: platform forks for "open this URL" should detect the desktop **shell** (`"__TAURI_INTERNALS__" in window`), not `getRuntime()?.capabilities` — the runtime singleton is null before init, and the web fallback (`window.location.href = url`) would navigate the whole Tauri webview to the external site with no way back. Both bit DF-3's Manage-billing button (validator, 2026-07-10). → [use-entitlement.ts](../src/hooks/use-entitlement.ts) `openStripeUrl`/`isDesktopShell`
- **A command palette that mixes server-filtered results with cmdk items MUST run `shouldFilter={false}`.** cmdk's default filter scores every `CommandItem`'s `value` against the input — so a search result whose `value` is an id-based key (`entity:task:<uuid>`, needed for a stable/unique key) scores 0 against "water" and cmdk **hides it**, even though the server already matched it. DF-10's palette turns cmdk filtering off and filters the *static* nav/create actions itself (label-substring); entity results come pre-filtered from `searchEntities`'s `ilike`. Setting the result `value` to the label instead would re-enable cmdk filtering but collides on duplicate labels (cmdk uses `value` for selection/highlight) — the mention-picker hit this first and also runs `shouldFilter={false}`. Also: the shared **`CommandDialog` does NOT forward arbitrary props to its inner `Command`** — it spreads `...props` onto the Radix `Dialog`, not cmdk. DF-10 added an explicit `commandProps` pass-through (spread onto `Command`, className cn-merged) to reach `shouldFilter`. → [src/components/app/global-command-palette.tsx](../src/components/app/global-command-palette.tsx), [src/components/ui/command.tsx](../src/components/ui/command.tsx)
- **Live-verify caveat: in the preview pane a Radix Dialog can look "stuck open" after `setOpen(false)`.** The palette (a Radix `Dialog`) closed correctly on select in code, but `document.querySelector('[cmdk-input]')` still returned it in back-to-back `javascript_tool` reads — the pane's rAF/chained-timer throttle (already noted under Storybook/live-verify) defers Radix's close transition/state flush. A `computer{screenshot}` **forces progress** and the dialog then reads closed. Don't diagnose a close-on-select "regression" from DOM polling alone in the preview pane — force a repaint first, or verify in real Chrome. (DF-10, 2026-07-11.)

- **A page overrides a GLOBAL keyboard shortcut by claiming the key in the CAPTURE phase, not by registering "later".** `useGlobalShortcuts` (app-chrome) is a **bubble**-phase `window` keydown listener mounted once at boot; a page-level bubble listener mounted later STILL fires after it (same target+phase → registration order, and AppChrome always mounts first), so it can't win by ordering. To let a page's plain key beat a global one — DF-16's email `?` triage legend vs the app-wide `?` shortcuts sheet — register the page's listener in **capture** (`window.addEventListener('keydown', fn, true)`; the capture flag MUST match on `removeEventListener`) and `preventDefault()` what it handles; the global bubble handler reads `event.defaultPrevented` and bails. Guard the capture listener on modifiers (`metaKey||ctrlKey||altKey`) + typing targets so it only claims its own plain keys and every global ⌘-combo still passes through. → [src/features/email/ui/email-page-view.tsx](../src/features/email/ui/email-page-view.tsx), [src/lib/shortcuts.ts](../src/lib/shortcuts.ts)
- **A `?` / Shift+/ key matcher must accept BOTH `key==='?'` and `shiftKey && key==='/'`.** Most layouts resolve Shift+/ to `event.key==='?'`, but some keyboard layouts — and synthetic key events (the live-verify automation's `shift+/` did exactly this) — deliver `key==='/'` with `shiftKey` set. ## Calendar / CalDAV + ICS (CAL-8)

- **A provider mapper that swallows parse errors and returns `[]` can MASS-TOMBSTONE the whole account.** The CAL-6 sync loop diffs "what the fetch returned" against "what we last mirrored" and deletes the difference. An ICS feed URL that expired and now serves an HTML login page under **HTTP 200** (common) would map to `[]` → the diff tombstones every event → the account is then written `status:'ok'`, so the user's whole external calendar silently vanishes for all workspace members. Fix (CAL-8): `mapIcsEvents` **throws** when non-empty input parses to zero VCALENDARs (a valid-but-empty calendar still returns `[]`); the per-account catch flips `error` and keeps the last mirror. - **Expanded-occurrence mirror ids must key on the ORIGINAL recurrence slot, never the moved/instant start.** Keying `uid::<movedStartIso>` churns the id when an occurrence is rescheduled (tombstone+recreate instead of update), collides when an override is moved onto another occurrence's slot, and — because a local-midnight all-day `toISOString()` embeds the machine zone — churns **every all-day id** on an OS-timezone change. Key on the recurrence-id wall fields (`uid::YYYY-MM-DDThh:mm:ss`) instead: stable, collision-free, tz-independent. Also: the monotonic-window `break` in the expansion loop drops an override moved *backward* into the window from a base slot past the break — handle overrides in a separate post-loop pass. → [src/features/calendar/ics-mirror.ts](../src/features/calendar/ics-mirror.ts)
- **ical.js `TimezoneService` is a global singleton — `register` is first-wins and state leaks across resources.** Registering a VTIMEZONE whose TZID is already present is skipped, so a second CalDAV resource that defines the *same non-IANA TZID name* with *different rules* converts with the first resource's zone. Reset (`ICAL.TimezoneService.reset()`) around **each** resource, not once per batch. Also cache the per-zone `Intl.DateTimeFormat` (a recurring expansion converts start+end per occurrence — the repo's cached-formatter posture). → [src/features/calendar/ics-mirror.ts](../src/features/calendar/ics-mirror.ts)

- **A CalDAV/ICS account's credentials live only in the CONNECTING machine's keychain — a second desktop must not flip the shared row to `error`.** Every desktop in the workspace runs the 15-min sync loop over all accounts, but only the machine that connected holds the CalDAV password / ICS feed URL. ## React effects

- **An effect that owns a debounce timer must NOT list an inline callback prop in its deps** — every parent re-render (a sync-status flip, any state change) re-runs the effect, and the cleanup clears the pending timer, so the debounced call can starve FOREVER under steady re-render pressure. The notes editor's first-line-title derivation never fired because `onTitleDerived` was an inline arrow: each CRDT flush toggled status → re-render → timer killed. - **A `useCallback` that BOTH sets a piece of state AND lists that state in its deps, fired from its own effect, is a self-cascade — it re-fetches on boot.** `WorkspaceProvider.refreshWorkspaces` depended on `selectedWorkspaceId` (to preserve the current selection) and *set* it; its boot effect listed `[refreshWorkspaces, …]`, so the `null → resolved` selection change recreated the callback → re-ran the effect → a second `workspace.list()`. Worse, each run toggled the provider's `loading`, and `WorkspaceGate` returns `null` while loading → **AppChrome unmounted+remounted**, re-firing every downstream boot read (`dashboard_layouts`, notifications, members) — the bulk of the DF-12 fetch storm was this ONE cascade, not N missing caches. ## Boot-time read caching (DF-12)

- **`supabaseClient.auth.getUser()` is a network round-trip to `/auth/v1/user`, and ~16 runtime methods called it independently** (every user-scoped read/write resolves the user first). That's why one boot fired it ×8. It's now deduped through `getAuthedUser()` ([runtime.web.ts](../src/lib/runtime.web.ts)) over the shared [`request-cache`](../src/lib/request-cache.ts). Any NEW runtime method that needs the current user must call `getAuthedUser()`, **never** `supabaseClient.auth.getUser()` directly, or it reintroduces a per-call `/auth/v1/user` hit.
- **Caching an auth/identity read at Infinity TTL is a session-brick trap unless you cache ONLY success.** `getUser()` returns `{data:{user:null}, error}` (it does NOT throw) on BOTH a transient failure (offline / mid-refresh 401 / 5xx) AND a genuine sign-out. If you cache that `null` at a long TTL, one boot blip pins `null` for the whole session → every read returns empty and every write fails RLS (`owner_id=""`), recoverable only by a real sign-in. `getAuthedUser` avoids it by **throwing** inside the fetcher on error-or-null (so `request-cache` never retains it) and returning `null` from an outer catch — same graceful `User | null` at call sites, but failures self-heal on the next call. Mirror this for any future Infinity-TTL cache: retain only a positive result.
- **A shared read-cache must clear its in-flight repopulation on invalidate, or a sign-out races back the old user.** `request-cache` guards this with a module `epoch` bumped on `invalidate`/`clear`; a fetch only writes back if `epoch` is unchanged since it started. Without it, a `getUser` in flight when `SIGNED_OUT` clears the cache would resolve after and re-cache the signed-out user.
- **A boot read-cache keyed by a fixed string (not the userId) leaks across a fast account switch on a shared browser.** `getCloudPrefs` cached prefs under a single `"prefs"` key; within its TTL a `SIGNED_OUT`→`SIGNED_IN(B)` would serve A's cached prefs to B (B adopts A's theme/accent, re-stamped as B's). Key any user-scoped cache by `userId` (`prefs:${userId}`) so a different user is a cache miss. → [src/lib/prefs-sync.ts](../src/lib/prefs-sync.ts)
- **A pure read path must not issue a write.** `layout-repo.load()` used to fire-and-forget a `dashboard.save()` to reconcile a cache-wins load up to the cloud — a `POST` on every boot that resolved to the local cache. Removed for DF-12: the local cache is the device's truth and a cut-off edit rides up on the next `save`, so cross-device propagation is delayed at most one edit, never lost. When adding a "reconcile on load" convenience, route it through the explicit save lifecycle, not the read. → [src/features/dashboard/data/layout-repo.ts](../src/features/dashboard/data/layout-repo.ts)

## Tasks data

- **`tasks.due_date` is a `timestamptz`, not a `YYYY-MM-DD` date.** The Tasks UI writes it from local midnight via `new Date(`${v}T00:00:00`).toISOString()` (e.g. `"2026-06-25T15:00:00.000Z"` for a JST user). - **An app-level accrual store that flushes through a *mounted-only* module sink loses time if it flushes against the not-yet-loaded bundle.** DF-11 lifted the Focus timer into a module store that keeps ticking while `/tasks` is unmounted; it flushes tracked seconds through `useTasksModule.addTimeSpent`, registered as a sink while /tasks is mounted. ## Notes / publish + MCP connector (NO-9/NO-10)

- **Supabase Edge Functions CANNOT serve rendered HTML — a `GET` returning `text/html` is rewritten to `text/plain` by the platform** (anti-abuse; [docs: Functions → Development tips](https://supabase.com/docs/guides/functions/development-tips) "HTML not supported"). The body is delivered intact but the browser shows raw source, not a page. Confirmed on `notes-public`: HEAD reported `text/html`, GET was forced to `text/plain`; custom headers (`x-robots-tag`) DO pass through, only the content-type is rewritten. **Consequence: NO-9's "edge function renders the published page from body_md" (spec assumption 8) is not viable as-is.** HTML must come from **Supabase Storage** (a public bucket serves the content-type you upload with — not rewritten) or from a **client-rendered app route** (the SPA is served with a real content-type; the edge fn returns JSON the page renders). Edge functions returning JSON (`application/json`) are fine. Don't build an edge-fn HTML renderer for a public page. → [supabase/functions/notes-public/index.ts](../supabase/functions/notes-public/index.ts)

The `notes-public` edge fn overrides the renderer: `html()` → `escapeHtml` (block + inline raw HTML both flow there), `link()`/`image()` → `safeHref` allow-lists **only** `http(s):`/`mailto:` (a `moduo://` chip or `javascript:`/`data:` degrades to a plain escaped label). `marked.parse()` is synchronous unless `async:true` (the `as string` cast is valid). ## Email engine (EM-1)

- **lettre's `MessageId` / `in_reply_to` / `references` headers emit the value VERBATIM — they do NOT add angle brackets.** lettre's *own* default Message-ID is `format!("<{}@{}>", …)` (already bracketed), so `.message_id(Some(id))` expects the bracketed form and passes it through. Stripping brackets (the instinct that "lettre re-wraps") emits `Message-ID: id@host` — RFC-invalid, and it breaks threading + the Sent-copy match the follow-up tracker relies on. Pass `<id@domain>`; and skip blank ids (an empty string → a malformed `<>` token). Confirmed by unit test on `message.formatted()` bytes (the only way to assert lettre header shape). → [src-tauri/src/commands/email/smtp.rs](../src-tauri/src/commands/email/smtp.rs)
- **Never construct a lettre recipient header via the tuple `header::To(mboxes)` — the field is `pub(crate)`.** From outside lettre, use `header::To::from(mboxes)` (the `From<Mailboxes>` impl); `Mailboxes::new()` + `.push()` builds the list. Also: `MultiPart::mixed()` returns a *builder* — its first `.singlepart`/`.multipart` finalizes to a `MultiPart` that further parts chain onto (don't reassign a `MultiPart` to a `MultiPartBuilder` binding). `.singlepart`/`.multipart` return `Result` (missing From/Date), so `?` them. → [src-tauri/src/commands/email/smtp.rs](../src-tauri/src/commands/email/smtp.rs)
- **The email secret keychain scope is `email_{user_id}_{account_id}` — NEVER migrate/wipe a legacy secret without an authenticated session.** Legacy secrets were stored un-scoped in redb (`secret::{account_id}`). The lazy migration writes them into the *current user's* keychain scope and wipes redb; if the session is momentarily absent, `session_user_id` is `None` and migrating under a fallback scope would strand the secret once a real user id returns (the account would falsely flip to `reauth_required`, orphaning a keychain item). `resolve_secret(user_id: Option<&str>, …)` returns the legacy secret **read-only** (no keychain write, no wipe) when there's no session; migration waits for a real user id. Same "never drop a secret" rule as the locked-keychain case (`get_secret` maps a locked keychain to `Ok(None)`). → [src-tauri/src/commands/email/secrets.rs](../src-tauri/src/commands/email/secrets.rs)
- **The email accounts list is an unlocked read-modify-write** (`read_accounts` → mutate one row → `write_accounts` the whole vec). Two concurrent sends, or a send racing the IDLE worker's `patch_account_sync_state`, can interleave and clobber a `status`/`last_sync_at`/`last_error` update. **Pre-existing** (the legacy `email_send_saved` + `patch_account_sync_state` do the same); `email_send_message` inherits it.
