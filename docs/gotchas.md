# Gotchas / footguns

Things that have bitten us, so they don't bite again. **Read before debugging; append when something costs you more than a few minutes.** Each entry: the trap, why it happens, what to do instead.

---

## Repo / build

- **TanStack Router: an object `search` in `navigate()` REPLACES the whole query string.** `navigate({ to: "/contacts", search: { action: "new" } })` silently wipes an existing `?type&id` selection. When adding one param on a route that carries others, use the functional updater: `search: (prev) => ({ ...prev, action: "new" })`. Bit FX-1 (the palette's New-contact wiped the open contact's selection); `/contacts` is the app's first search-param route, so every future `navigate` targeting it must think about this.

- **`preview_start` in a `.claude/worktrees/*` session has two failure stages — only the first is fixable.** (1) `Port 8081 is in use by another chat's dev server` → fixed for good 2026-07-02: `.claude/launch.json`'s "web" config uses `autoPort: true` + a port-flag-free command, and `rsbuild.config.ts` honors an assigned `PORT` env (default stays 8081). (2) `EPERM: uv_cwd` → **not fixable from the session**: the preview sandbox binds to whichever worktree owns the currently *active* dev server, so while another chat serves :8081 the sandbox can't even `cwd` into yours. Do not kill the other session's rsbuild (that trap already bit us — Session 10). Workaround: `bun install` in the worktree, run `MODUO_TARGET=web ./node_modules/.bin/rsbuild dev --host 127.0.0.1 --port <free>` via Bash background, drive with the Chrome MCP, kill by the **exact port-specific** pattern when done.
- **Never import a bare `{ runtime }`.** Always resolve via `getRuntime()`. The bare export was an always-null const footgun; grep `./runtime` when auditing lib exports. → [data-layers.md](./data-layers.md)
- **A "reset local cache" that clears `moduo.appearance` also nukes the device-local display prefs (density / text-size / tab style) that deliberately never sync to cloud** — so on reload they snap back to defaults while theme/accent/font re-adopt from cloud. They ride *inside* the same `moduo.appearance` localStorage blob (appearance.ts: "per-device fields never leave localStorage"), so a key-prefix clear can't spare them. DF-19g's reset owns this by **disclosing it in the confirm copy** ("device-only display settings reset to defaults"), not by silently dropping them — the designer treats density as a first-class customization axis. Any future cache-wipe that touches `moduo.appearance` must either preserve the device subset or say so. → [advanced-section.tsx](../src/features/settings/sections/advanced-section.tsx)
- **Deleting the Notes IndexedDB is only safe once the outbox is empty — and the guard must count BOTH outboxes across ALL workspaces.** The per-note y-indexeddb doc DBs (`moduo:notes-v2:doc:*`) hold local CRDT state; `deleteDocOutboxEntries` runs only *after* a successful `pushUpdates` (engine-v2), so an empty `docOutbox`+`metaOutbox` provably means every local edit reached the cloud and the doc DBs can be dropped losslessly. DF-19g's reset gates on `countPendingOutbox()` (idb.ts) which counts globally because the delete is global; the blocked-dialog path removes the reset button entirely (not just disables it) so there's no code path from pending>0 to a delete. Caveat it can't cover: an edit stranded in the engine's in-memory `memOutbox` (a transient IDB-write failure) is invisible to a durable-store count. Also `indexedDB.databases()` is unsupported on Firefox/older Safari → there only the named `moduo-notes-v2` is deleted, per-note doc DBs survive (harmless: outbox empty, cloud is truth). → [advanced-section.tsx](../src/features/settings/sections/advanced-section.tsx), [idb.ts](../src/features/notes/sync/idb.ts)
- **redb is paused — never make it load-bearing** for a new feature. New models are Supabase-first; redb is kept only for the future offline/"lite" version and not-yet-migrated legacy modules. → [data-layers.md](./data-layers.md)
- **Vitest has no `@/` alias — VALUE imports from `lib/` in a test's graph must be relative.** `vitest.config.ts` defines no `resolve.alias`, so a runtime (value) import like `import { deriveLinkKey } from "@/lib/entity-links"` fails to resolve under `bun run test` ("Failed to resolve import @/lib/…"), even though `tsc` (which reads tsconfig `paths`) is happy. **Type-only** `@/` imports are fine — they're erased before resolution, which is why existing tests (`mention.test.ts`, `rollup.test.ts`) use `@/` for types and still pass. The rule: anything reachable from a `*.test.ts(x)` via a *value* import must use a **relative** path for `lib/*` (see `spine/activity.ts` → `../../lib/entity-links`, `spine/suggest.ts`). Components/hooks bundled only by rsbuild may use `@/` values (rsbuild resolves it); the trap is strictly the vitest graph. Standalone `bunx vitest` resolves `@/` even less than `bun run test` — always verify with the project script.
- **Corollary: a unit test must NOT import a component `.tsx` — extract the pure logic to a `.ts` and test that.** Every `src/components/ui/*` primitive imports `@/lib/utils`, so importing any `.tsx` that renders one (e.g. a settings section using `Badge`) drags `@/lib/utils` into the vitest graph → `Failed to resolve import "@/lib/utils" from ui/badge.tsx`, failing the whole suite even when you only wanted a pure exported helper. DF-19d hit this testing `keyScope` by importing `api-keys-section.tsx`; fixed by moving `keyScope` into a pure `api-keys.ts` (the `account.ts`/`billing.ts` pattern — pure logic in `.ts` is unit-tested, the `.tsx` component is live-verified). (2026-07-11.)
- **The local done-check is `bun run verify`** (typecheck + lint:tw + lint:css + unit tests) — it mirrors CI's gate. CI does **not** run the e2e / visual-snapshot / billing suites (those stay local/manual), so a green PR doesn't cover them.
- **Dead-code sweeps: "is it mounted?" is not "is it alive?" — trace the OUTPUT, not just the importers.** `useSlotBookingsSync` was mounted in `app-gate.tsx` (so import-graph tools call it live) yet its entire effect was writing a localStorage key with zero readers — and it PATCHed `slot_bookings.calendar_synced=true` server-side for rows that surfaced nowhere, actively corrupting the "unsynced" signal for any future re-implementation. When sweeping, follow each candidate's *sinks* (storage keys, tables, events) to a real consumer before calling it live. Also: `bun run verify` catches zero Rust breakage — any sweep touching `src-tauri` needs its own `cargo check` (CLEAN-1, 2026-07-03).
- **A code-graph / import-graph "isolated, prune-safe" verdict can miss a compile-only coupling into a load-bearing module — re-verify with `rg` before deleting.** Graphify (and the backend memo it fed) reported `graph_helix`/`embeddings` as "isolated, in no coupling hotspot, touches zero feature code." They were **runtime-dead** but **compile-coupled**: `graph_helix` was woven into the **live email engine** via `commands/email/graph_outbox.rs`, called from ~11 sites across `email.rs`/`sync.rs`/`realtime.rs`, and `queue_graph_upsert_for_envelope` wrote an `email_graph_outbox` redb row on *every* envelope sync (only the *flush* was gated behind `graph.is_enabled()`, false without `HELIX_SIDECAR_PATH`). Removing `helix-rs` therefore required excising that dead tendril from email — not the "zero feature code" the graph claimed. The graph counts *edges it saw*; a subsystem whose outputs nothing reads (dead) can still be *written to* from live code (coupled). When a graph says "safe to delete," still `rg` every symbol (types, redb tables, command fns) for writers, not just readers, before cutting (proposal C, 2026-07-11). → [docs/decisions.md](./decisions.md)
- **`src-tauri` has a `lite` Cargo feature (off by default) — the redb↔Supabase `sync` worker compiles only under `--features lite`.** `cargo check`/`build` in the **default** (cloud) config does NOT compile `src/sync/mod.rs` or the `AppState.sync_worker` field / `auth.rs` start-stop paths (all `#[cfg(feature = "lite")]`). If you edit `sync/` or anything gated for the future offline/"lite" build, a default `cargo check` won't catch breakage there — run `cargo check --features lite` too (proposal C, 2026-07-11). → [src-tauri/Cargo.toml](../src-tauri/Cargo.toml)
- **Visual-snapshot PNG baselines are NOT generated in CI** and are platform-suffixed (`*-visual-darwin.png`). Capture is a deliberate human `bun run e2e --update-snapshots` run on the canonical env. A visual diff means **stop and ask**, never auto-accept/regenerate.
- **macOS Liquid Glass app icon has been lost in merges twice.** It lives in-repo at `scripts/icons/source/Moduo.icon`; regenerate with `bun run icon:liquid` (needs full Xcode for `actool`). Don't let a merge drop it.
- **The desktop bundle's frontend must be built with `MODUO_TARGET=desktop`, into `dist/` — a stale `dist/` masks the bug.** `rsbuild.config.ts` routes the *web* target to `dist/web/` and the *desktop* target to `dist/` (frontendDist=`../dist`), AND aliases `@tauri-apps/api/core` to a throwing stub whenever `MODUO_TARGET=web`. So building the frontend with `build:web` (the old `beforeBuildCommand`) put `index.html` in `dist/web/` and left `dist/` empty → a clean `bun run build:desktop` embedded no assets → runtime **"asset not found: index.html"**; even if it had loaded, `invoke()` would throw `[tauri-stub]`. Fixed 2026-07-13 by pointing `beforeBuildCommand` at a new `build:desktop:web` = `MODUO_TARGET=desktop rsbuild build`. All three desktop entry points (`build:desktop`, `build:desktop:signed:{debug,release}`) funnel through `beforeBuildCommand`, so they're all covered. The trap hid because the main checkout usually has a stale `dist/index.html` from a prior `dev:desktop`/manual build; only a fresh tree (or `rm -rf dist` first) reproduces it. Verify desktop frontend builds by confirming `dist/index.html` exists AND the bundle contains `__TAURI_INTERNALS__` (real API), not `called in web build` (the stub). → [rsbuild.config.ts](../rsbuild.config.ts), [src-tauri/tauri.conf.json](../src-tauri/tauri.conf.json)

## Supabase / migrations

- **The repo CANNOT bootstrap a database — `supabase db reset` does not work and never has.** Prod has 73 applied migration versions against 42 repo files, and no file at all exists for the 26 applied before `create_tasks_module` (the whole profiles/workspaces/notes/CRM/billing foundation) or for three later hardening applies — so **22 of prod's 44 tables are created by no migration** — including `profiles`, `workspaces`, `workspace_members`, `workspace_invites`, `notes`, `calendar_events`, `dashboard_layouts`. A fresh reset doesn't just order things ambiguously: most migrations *fail outright*, because their policies and FKs reference tables that were never created. Treat "it's in a migration file" as saying nothing about whether a fresh DB can be built. Fixing it means capturing a `00000000000000_baseline.sql` from prod — see [OPS-2's inventory](./reviews/ops-2-schema-reconciliation.md) §4.
- **`REVOKE … FROM PUBLIC` does NOT revoke `anon` on Supabase.** Supabase's default privileges grant `anon` (and `authenticated`) EXECUTE on `public` functions *directly*, not via `PUBLIC`, so a revoke that names only `PUBLIC` (and even `authenticated`) leaves anon holding EXECUTE. This is why OPS-2 found **15 SECURITY DEFINER functions anon could call**, including six internal `*_op__guard*` helpers and the auth-less legacy `accept_workspace_invite`. **The surprise is where it went wrong:** each module's bulk op-grant *loop* already revokes anon correctly (`contacts_module.sql:550`, `calendar_module.sql:532`, `email_module.sql:538`), and contacts_module even comments the behaviour. What omitted anon were the **six hand-written per-guard REVOKE pairs a few hundred lines above the correct loop in the same file** (`email_module.sql:186-187,210-211`; `calendar_module.sql:147-148,180-181`; `contacts_module.sql:150-151,174-175`) — undetected since 2026-06-26 (~4.8 weeks for contacts). So the lesson is not "audit the loops": it is **one-off hand revokes drift from the loop pattern already present in the same migration** — if you are writing a bare `REVOKE` next to a file that has a grant loop, put it in the loop. Always assert the fix with `has_function_privilege('anon', …) = false`, never by reading the migration.
- **Before revoking EXECUTE on a helper, check whether an RLS policy calls it — and what role that policy targets.** `tasks_module_can_access_workspace`, `profile_plan_tier_text` and `workspaces_owned_count_for_user` are anon-callable and leak real values, but 22 policies invoke them and every one is defined for role `public` (which includes `anon`). Revoking would convert an anonymous query's clean empty result into `permission denied for function`. Scope the policies `TO authenticated` first, then revoke. → `select … from pg_policies where qual like '%fn_name%'`
- **A text hash is NOT a drift check — normalize before you compare function bodies.** Comparing `pg_proc.prosrc` against the repo's `CREATE FUNCTION` body flags 19 of 110 functions here, and **all 19 are formatting**: prod stores `('edit','admin')` / `SET x=now()` where the files say `('edit', 'admin')` / `SET x = now()`, because email, contacts-v2 and workspace-roles were applied from a compacted copy. Strip comments, collapse whitespace, and drop spaces around `( ) , ; =` on *both* sides — then real drift is zero and visible. `bun run db:reconcile` bakes this in; use it rather than hand-rolling the comparison. → [scripts/db-reconcile.ts](../scripts/db-reconcile.ts)
- **Applying a long-unapplied OLD migration can silently REGRESS an object that a NEWER, already-applied migration redefined.** Migrations are only safe in filename order; this repo routinely applies them *late* and *individually* via MCP `apply_migration`, so an old file's `CREATE OR REPLACE` runs **after** newer ones and wins. Before applying any back-dated migration, `grep -l "FUNCTION public\.<fn> *(" supabase/migrations/*.sql` for **every** object it touches and diff the bodies against the newest definition — if they differ, apply a corrected body, not the stale file. Live example: `20260704180000_email_snooze_followup.sql` re-asserts `spine_activity_targets_me`, which the *newer* `20260714120000` also re-asserts and which had been applied 2026-07-27 — so OPS-1's 2026-07-29 apply of the older file overwrote it. It was safe only because the two **executable** bodies are identical (they differ only in comments); that was luck, not design. Diff the executable SQL, not the file. → [supabase/migrations/20260704180000_email_snooze_followup.sql](../supabase/migrations/20260704180000_email_snooze_followup.sql)
- **Two migrations may not share a timestamp prefix — Supabase applies the directory in lexicographic filename order, so a collision leaves that pair's order UNDEFINED on a fresh bootstrap.** Two collisions had shipped unnoticed (`20260702160000` ×2, `20260712120000` ×2) because nothing in `bun run verify` reads `supabase/migrations/` — the SQL never executes locally, so a stamp typo is invisible until a `db reset` produces a schema that differs from prod. `src/lib/migration-order.test.ts` (OPS-1) is now that check; when it fails, re-stamp the *idempotent* file of the pair (the `ADD COLUMN IF NOT EXISTS` one, so a re-apply is a no-op) and pick its new stamp so the directory **replays prod's real apply order** — get that from `list_migrations`, not from the filenames. "Keep the stamp a prod-apply record names" is only a tie-break, and it did NOT discriminate in OPS-1's case because both files of each pair had one. Then **grep the docs for the old stamp** — a bare `migration \`<stamp>\`` reference silently re-points at the other file (decisions.md 2026-07-29). Note prod's `supabase_migrations.schema_migrations` versions are generated by MCP `apply_migration` *at apply time* and bear no relation to the filename stamp, so a rename cannot break prod **via MCP `apply_migration`** (how this repo deploys) — only the docs. It would matter to `supabase db push`, which refuses local files sorting *before* the last remote version without `--include-all`; both OPS-1 renames move earlier, so that path needs the flag.
- **The repo's own docs are NOT evidence of what prod has — probe the database, and check the catalog, not just `list_migrations`.** OPS-1's ledger entry listed `20260712120000_df9_task_notifications.sql` as unapplied when it had shipped 2026-07-13; conversely `20260704180000`'s predicate change sat undeployed for ~3 weeks while the docs implied otherwise (found by DF-21d's probe). Both directions of drift have now happened. `list_migrations` alone is also insufficient — it shows *names* someone typed at apply time, not objects; a partial apply, a hand-run `execute_sql`, or a differently-named apply all lie. Query `pg_proc` / `information_schema.columns` / `pg_trigger` for the specific objects before deciding what to apply — that is the whole point of OPS-2.
- **`DROP FUNCTION` + `CREATE` (or any change to a function's return columns) RESETS its grants → silently re-opens `EXECUTE` to `PUBLIC`/`anon`.** A fresh `CREATE FUNCTION` defaults `EXECUTE` to `PUBLIC`, so re-creating a previously-locked-down function (the only way to change its `RETURNS TABLE` shape — `CREATE OR REPLACE` can't) drops the earlier `REVOKE ... FROM anon` and re-grants it to everyone. DF-21b's `notifications_list` DROP+CREATE (to add `dismissed_at`) did exactly this, and its two new ops shipped PUBLIC-executable — a security-posture regression the internal `auth.uid()`/access guards *masked* (anon reads return nothing, anon writes no-op), so it passed the round-trip smoke test. **Every migration that DROP+CREATEs a function MUST re-apply its grants block** (mirror CT-5: `REVOKE ALL FROM PUBLIC, anon; GRANT EXECUTE TO authenticated`). And because the broken migration may already be applied to prod, the fix is a **corrective follow-up migration** (editing the original file only helps fresh DBs) — verify with `has_function_privilege('anon', 'public.fn(args)', 'EXECUTE') = false`. → [supabase/migrations/20260713120000_notification_dismiss.sql](../supabase/migrations/20260713120000_notification_dismiss.sql), [CT-5 grant loop](../supabase/migrations/20260626130000_spine_comments_notifications.sql)
- **A new migration is NOT applied by `bun run verify`.** `verify` only runs typecheck/lint/unit-tests; it never touches Postgres. A green PR with a new `supabase/migrations/*.sql` means the SQL *parsed in your head*, not that it deployed — server invariants (RLS, RPCs, FKs, generated columns) are unproven until the migration is applied to a Supabase instance and exercised by an authenticated round-trip (the manual-test layer). Apply the migration and regenerate `src/types/supabase.ts` before any code *depends* on the new tables/RPCs. Don't apply to the shared/prod project without authorization.
- **The Supabase JS client is untyped (`SupabaseClient`, no `Database` generic).** So `supabaseClient.from("a_table_that_doesnt_exist_yet")` and `.rpc("an_unmigrated_fn", …)` both **typecheck fine** — TS can't catch a table/RPC-name typo or an arg-shape mismatch against an unmigrated schema. New runtime methods for new tables pass `verify` even if the migration is wrong or unapplied; the only real check is the live round-trip. (Mappers take `r: any`, so column renames are silent too.)
- **`runtime.workspace.joinInvite(token)` returns the accepted *invite* row, NOT a workspace** — `{ id: <invite id>, workspace_id, role, email, status, … }`. Its return type is `Promise<any>` (untyped, see above), so `mapWorkspace(inviteRow)` typechecks and passes `verify` while producing a garbage `WorkspaceSummary`: `id` = the invite id, `name` = `undefined`, `role` derived from the invite. The joined workspace's real id is `invite.workspace_id`; resolve the actual summary from a refreshed workspace list (`refreshWorkspaces()` now returns the fresh list for exactly this) and select *that*. Never `selectWorkspace(inviteRow.id)` either — it selects a non-existent workspace (→ `selectedWorkspace` goes `null`, the switcher unmounts). Bit `joinWorkspace` pre-DF-24; it only hid because its one consumer used the return value as a truthiness check. → [workspace-provider.tsx](../src/providers/workspace-provider.tsx)
- **Direction-agnostic link dedupe must use a collation that matches JS.** `entity_links.pair_key` (the unordered `least/greatest(type:id)` key) compares with `COLLATE "C"` (byte order) so it provably matches the TS `deriveLinkKey` (JS `<=` code-unit order). Plain `least/greatest` on `text` uses the DB's *default* collation (a locale on standard Supabase), which can order non-ASCII tokens differently than JS → the server-side and client-side dedupe keys silently disagree. Keep `spine_pair_key()` (SQL) and `deriveLinkKey()` (TS) in lockstep. → [src/lib/entity-links.ts](../src/lib/entity-links.ts)
- **A plpgsql function returning a composite type returns an all-NULL *row*, not SQL NULL, after a `SELECT … INTO` that finds nothing.** `RETURN v_row;` when `v_row` is unset serializes (via PostgREST) as `{id:null,…}`, not `null` — callers expecting `null` get a truthy object. Guard with `IF v_row.id IS NULL THEN RETURN NULL; END IF;` (see `links_op_delete`, `contacts_op_unlink`).
- **Wiring a brand-new RPC into a live read path breaks that surface until the migration is deployed.** `verify` never applies migrations, and the prod apply is a separate step — so between merging code that calls `runtime.x.newRpc()` and deploying its migration, the call 404s and can break the feature for everyone (e.g. the notification bell). For a *new* RPC consumed on a hot read path, wrap the call in try/catch and **degrade gracefully** (fall back to the prior behavior / empty) so the app survives the gap; the new data simply appears once the migration lands. (See `workspace-provider.refreshNotifications` wrapping `spine.listNotifications`.) Mutations the user explicitly triggers can surface the error instead.
- **A plpgsql/SQL function with `RETURNS TABLE(...)` whose out-columns share names with a table in its body (e.g. `workspace_id`, `id`, `payload`) is an ambiguity trap.** It only works while *every* column reference in the body stays table-qualified (`ma.workspace_id`); a single later unqualified ref silently resolves to the out-param instead of the column. Keep refs qualified (or prefix out-params `o_`). (See `notifications_list`.)
- **Probing an `auth.uid()`-dependent trigger/op via `execute_sql` runs as the service role, where `auth.uid()` is NULL — so any generation keyed on the caller silently no-ops (often inside an `EXCEPTION WHEN OTHERS` guard) and your probe reads a FALSE NEGATIVE.** Applying the DF-9 trigger (2026-07-13) then closing a blocker in a bare probe generated `tasks.unblocked=0` — not because the trigger was broken, but because `module_activity_log` (attributes `actor_id=auth.uid()`) threw on the null actor and the trigger swallowed it. Set the JWT claim transaction-local **before** the write: `PERFORM set_config('request.jwt.claims', json_build_object('sub','<user-uuid>','role','authenticated')::text, true);` — then re-probe (it then read `=1`). Wrap the whole thing in a `DO $$ … RAISE EXCEPTION 'ROLLBACK_OK …' $$` so it rolls back with zero residue. → [docs/decisions.md](./decisions.md) DF-9 prod-apply

- **PostgREST's 1000-row cap is a HARD per-request ceiling — `.limit(5000)` does NOT lift it, and nothing tells you.** Probed live against the hosted project (SCALE-1, 2026-07-29) with 1,510 rows in scope: an unbounded select, `?limit=1201` and `?limit=5000` each returned exactly **1000** rows, `content-range: 0-999/*`, no error, no warning. `db-max-rows` bounds the *response*, not just the default. The repo had believed the opposite for months — `listTagLinks` carried an "explicit ceiling; PostgREST silently caps at 1000 otherwise; 5000" comment and was itself truncating at 1000. The only way past it is `.range()` paging: use [`readPaged`](../src/lib/paged-select.ts), never a bare `.limit()` above 1000. Corollary for any "did I get everything?" check: the *exact* total needs `select("id", { count: "exact", head: true })` (`content-range: 0-999/1510`), which `readPaged` fires only when the cap actually bit.
- **Paging (`.range()`) is only correct under a TOTAL order — `position` / `name` / `created_at` all tie, and a tie across a page boundary silently skips one row and duplicates another.** Every paged read appends a unique tiebreaker (`.order("id")`) after its real sort. This is invisible in testing: the loss is a handful of rows in workspaces big enough to page at all. → [runtime.web.ts](../src/lib/runtime.web.ts) `selectCapped`
- **Windowing the calendar events read by date deletes recurring events from the UI unless series rows bypass the window.** A series' stored `start_time` is its **first** occurrence — a weekly meeting set up in 2019 is a 2019 row, so a `[today-12mo, today+24mo]` filter drops it and every occurrence it would have generated this week. SCALE-1's filter is `or(recurrence_rule.not.is.null, and(start_time.lte.TO, end_time.gte.FROM))`: series always come through, and the second arm is an *overlap* test (not `start_time` alone) so multi-day events straddling the window edge survive. Same trap as the DF-2 deep-link teleport, one layer down. → [window.ts](../src/features/calendar/window.ts)
- **A read window is a lie unless something widens it on navigation.** The calendar's window grows via `ensureRange(range.startMs, range.endMs)` driven from the page's visible range; without that wiring, paging back to an old month renders a convincingly *empty* calendar instead of a loading one. Growth is one-way (`widenCalendarWindow` never shrinks) so walking back and forth never refetches.

## Supabase / Realtime (NO-6)

- **`channel.send()` on a Realtime channel that isn't JOINED does NOT drop — it silently REST-falls-back with a `console.warn`.** The notes broadcast relay assumed `send()` was a no-op while joining/torn-down; in `@supabase/realtime-js` it POSTs to the broadcast REST endpoint instead (plus a deprecation warning), so early keystrokes (before SUBSCRIBED) or a flush after teardown spam REST + the console. Gate the outbound path on a `pushable` boolean set true only on `status==='SUBSCRIBED'` and back to false on cleanup / CLOSED / CHANNEL_ERROR / TIMED_OUT; drop the buffer while not pushable (durability rides the outbox + pull, not broadcast). → [use-note-realtime.ts](../src/features/notes/hooks/use-note-realtime.ts)
- **`WorkspaceMember` carries NO display name or avatar — only `userId`/`role`/`isActive`.** ~~Any "who" UI can't resolve a name from the members list.~~ **UPDATED DF-24 (2026-07-11):** `mapMember` now surfaces `displayName`/`avatarUrl` from the `profiles(*)` join `listMembers` already does — the modal renders real names. The join was always fetched; the mapper just threw it away. Presence/comments elsewhere still use the current user's email local-part + `useMentionSearch` for a searchable people source. → [workspace-mappers.ts](../src/features/workspaces/workspace-mappers.ts)
- **`workspace_members` uses a DIFFERENT role/permission vocabulary than the app and than `workspace_invites` — and the untyped client can't catch it.** The members table's CHECK constraints only accept **role ∈ {owner,admin,member,viewer}** and **permissions_{notes,tasks} ∈ {read,write,none}** (verified live: `editor`/`view`/`edit`/`admin` all 400 the insert). But the app's `WorkspaceRole` is `{owner,admin,editor,viewer}` and `ModulePermission` is `{none,view,edit,admin}`, and `workspace_invites` happily stores the app vocabulary. ## Calendar / CalDAV + ICS (CAL-8)

- **A provider mapper that swallows parse errors and returns `[]` can MASS-TOMBSTONE the whole account.** The CAL-6 sync loop diffs "what the fetch returned" against "what we last mirrored" and deletes the difference. An ICS feed URL that expired and now serves an HTML login page under **HTTP 200** (common) would map to `[]` → the diff tombstones every event → the account is then written `status:'ok'`, so the user's whole external calendar silently vanishes for all workspace members. - **A CalDAV/ICS account's credentials live only in the CONNECTING machine's keychain — a second desktop must not flip the shared row to `error`.** Every desktop in the workspace runs the 15-min sync loop over all accounts, but only the machine that connected holds the CalDAV password / ICS feed URL. ## Boot-time read caching (DF-12)

- **`supabaseClient.auth.getUser()` is a network round-trip to `/auth/v1/user`, and ~16 runtime methods called it independently** (every user-scoped read/write resolves the user first). That's why one boot fired it ×8. It's now deduped through `getAuthedUser()` ([runtime.web.ts](../src/lib/runtime.web.ts)) over the shared [`request-cache`](../src/lib/request-cache.ts). Any NEW runtime method that needs the current user must call `getAuthedUser()`, **never** `supabaseClient.auth.getUser()` directly, or it reintroduces a per-call `/auth/v1/user` hit.
- **Caching an auth/identity read at Infinity TTL is a session-brick trap unless you cache ONLY success.** `getUser()` returns `{data:{user:null}, error}` (it does NOT throw) on BOTH a transient failure (offline / mid-refresh 401 / 5xx) AND a genuine sign-out. If you cache that `null` at a long TTL, one boot blip pins `null` for the whole session → every read returns empty and every write fails RLS (`owner_id=""`), recoverable only by a real sign-in. `getAuthedUser` avoids it by **throwing** inside the fetcher on error-or-null (so `request-cache` never retains it) and returning `null` from an outer catch — same graceful `User | null` at call sites, but failures self-heal on the next call. Mirror this for any future Infinity-TTL cache: retain only a positive result.
- **A shared read-cache must clear its in-flight repopulation on invalidate, or a sign-out races back the old user.** `request-cache` guards this with a module `epoch` bumped on `invalidate`/`clear`; a fetch only writes back if `epoch` is unchanged since it started. Without it, a `getUser` in flight when `SIGNED_OUT` clears the cache would resolve after and re-cache the signed-out user.
- **A boot read-cache keyed by a fixed string (not the userId) leaks across a fast account switch on a shared browser.** `getCloudPrefs` cached prefs under a single `"prefs"` key; within its TTL a `SIGNED_OUT`→`SIGNED_IN(B)` would serve A's cached prefs to B (B adopts A's theme/accent, re-stamped as B's). Key any user-scoped cache by `userId` (`prefs:${userId}`) so a different user is a cache miss. → [src/lib/prefs-sync.ts](../src/lib/prefs-sync.ts)
- **A pure read path must not issue a write.** `layout-repo.load()` used to fire-and-forget a `dashboard.save()` to reconcile a cache-wins load up to the cloud — a `POST` on every boot that resolved to the local cache. Removed for DF-12: the local cache is the device's truth and a cut-off edit rides up on the next `save`, so cross-device propagation is delayed at most one edit, never lost. When adding a "reconcile on load" convenience, route it through the explicit save lifecycle, not the read. → [src/features/dashboard/data/layout-repo.ts](../src/features/dashboard/data/layout-repo.ts)

- **The dashboard grid drag is a bespoke pointer engine, not a dnd-kit consumer** — don't reach for the CT-3 drag machinery here. ## Dashboard persistence + pager (DB-4)

- **framer-motion's JS `animate={{ x: "…%" }}` can FREEZE mid-slide — drive a page slide with a CSS transition on an inline transform instead.** The DB-4 pager first animated each page layer via framer `animate={{ x: `${(i-active)*100}%` }}`; in live-verify the active layer got **stuck at `translateX(-45%)`** (a non-target value) — framer's rAF-driven tween never committed the final frame (the headless preview throttled rAF, but any frame-starved context — a backgrounded tab mid-swipe — is at risk). The fix: a plain `<div style={{ transform: translateX(…) }}>` + `className="transition-transform duration-(--motion-base) ease-(--ease-out)"`. ## Tasks data

- **`tasks.due_date` is a `timestamptz`, not a `YYYY-MM-DD` date.** The Tasks UI writes it from local midnight via `new Date(`${v}T00:00:00`).toISOString()` (e.g. `"2026-06-25T15:00:00.000Z"` for a JST user). ## Desktop email store (IM-2a)

- **A redb key that embeds a mutable field is a row leak, not just an ugly key — and the "obvious" fix (make the key stable) can destroy the index.** `envelope_order_key` is `{account}::{folder}::{reverse_ts}::{uid}`; a message with no `Date:` header gets `now_iso()` on every fetch ([`sync.rs`](../src-tauri/src/commands/email/sync.rs) `fetch_envelopes_for_uids`), so every refetch wrote a **second** order row and orphaned the first — unbounded growth, invisible because nothing reads that table yet. Making the key stable is the wrong instinct: strip the timestamp and the "order index" is just a duplicate of the envelope key. The fix is to recover the **previous** row's key (re-mint it from the stored row's fields) and delete it in the same transaction as the new write. Two consequences to remember: the derivation is **re-minted, not stored**, so changing the key format strands every existing row; and a point delete no longer sweeps pre-existing orphans the way the old full-table scan incidentally did. Same shape lives on unfixed in `EMAIL_BODY_LRU`, whose key embeds `last_accessed_at` — which is *why* `remove_body_cache` still scans that whole table. → [storage.rs](../src-tauri/src/commands/email/storage.rs) `stored_order_key`
- **Prefix-scanning a `{a}::{b}::{c}` keyspace: only the *fully-qualified* prefix is safe — deriving a prefix by cutting at the first separator silently drops rows.** Email account ids are `{provider}:{email}` or `custom:{email}:{imap_host}`, and a custom account on an IPv6 literal host mints `custom:me@x.com:[::1]` — an id that **contains the separator**. A scan that found account blocks by cutting each key at the first `::` computed `custom:me@x.com:[::` and matched nothing, so that account's mail vanished from "All accounts" while still appearing when the account was selected: asymmetric and silent. Rule: scan a prefix you were *handed* (`Some(account_id)`), never one you *parsed out of a key*, and always keep the row's own fields as the inclusion test so the key can only ever narrow what you read, never decide what counts. → [storage.rs](../src-tauri/src/commands/email/storage.rs) `list_envelopes_in_store`
- **Batching a per-row write into a per-chunk transaction silently multiplies the blast radius of a swallowed error — check what advances a cursor afterwards.** The IDLE worker did `let _ = upsert_envelope(...)` per row and then set `cursor.last_seen_uid = latest_uid`; with a 50-row batched write, one failure went from costing 1 message to costing 50 — and because the delta sync starts *after* the cursor and never looks back, those UIDs were stranded forever. Any `let _ =` write that a cursor/watermark update follows needs its result threaded into that update. → [realtime.rs](../src-tauri/src/commands/email/realtime.rs)
- **`bun run verify` covers ZERO Rust, and a default `cargo check` skips the `lite` feature — a Rust-only block needs `cargo check` + `cargo check --features lite` + `cargo test --lib` as its own gate.** Also worth knowing when touching `src-tauri`: the crate is **not** `cargo fmt`-clean at baseline (~55 pre-existing hunks across untouched files) and CI runs no fmt check, so `cargo fmt` on a whole file buries the review diff — hand-apply rustfmt's output to your own hunks instead and leave the rest. (Restates the CLEAN-1 rule with the fmt trap; IM-2a, 2026-07-29.)

## Email history depth (IM-2b)

- **`Option<i64>` as a "floor" carries two incompatible meanings — reusing one helper for both makes `None` an absorbing state that silently disables everything downstream.** IM-2b's depth floor is `Option<i64>` where `None` means *unbounded* when gating the prune, but *nothing reached yet* when advancing the reached floor. Advancing with the prune helper (`(None, _) | (_, None) => None`) made `None` a fixed point: `history_floor_ms` could never become `Some`, so the prune gate was never armed (AC10 passed only by total disablement) and `depth_gap_reopens` always returned false, so **raising the depth backfilled nothing, ever**. Every pure-function test still passed. Two lessons: give each meaning its own named function (`deepest_floor` vs `advance_reached_floor`), and **test the state transition, not just the helpers** — the engine's use was a single line no test executed, which is exactly how it shipped past the first review. → [sync.rs](../src-tauri/src/commands/email/sync.rs)
- **A `uid_validity` change invalidates every UID-shaped thing you cached about a folder — including "I'm done".** Carrying `backfill_complete`/`oldest_synced_uid`/`history_floor_ms` across a mailbox recreation is a data-loss path, not just staleness: local UIDs from the old numbering all sit above the new mailbox's high-water mark, so a "these UIDs can't exist on the server" sweep deletes the whole synced history — while `complete: true` guarantees the backwards walk never re-populates it. Reset the lot when `cursor.uid_validity != server uid_validity`, and only run a high-water-mark sweep while the generation is *unchanged*. (Related: `envelope_key` has no `uid_validity` segment and `body_fetch` doesn't check it, so a surviving stale-generation row can render another message's body — the ratified never-delete-in-window rule accepts that; don't "fix" it by deleting.) → [sync.rs](../src-tauri/src/commands/email/sync.rs)
- **Record a *measured* floor, not the configured one, or lowering a setting retroactively authorizes deletion.** IM-2b records how deep the walk got so the prune can never evict already-promised mail. Recording the *configured* depth breaks that: a 12-month walk that reached 6 months and is then lowered to 3 finds nothing below its frontier, reports "complete", records 3 months — and the prune is then free to delete the 3-to-6-month mail it had already fetched. `min(configured_floor, oldest_stored_timestamp)`. → `completed_floor` in [sync.rs](../src-tauri/src/commands/email/sync.rs)
- **`UID SEARCH SINCE` matches the server's INTERNALDATE; a local timestamp filter matches the `Date:` header — they disagree on any migrated mailbox.** After a mailbox migration every INTERNALDATE is the migration day, so `SINCE <3 months ago>` returns the *entire* mailbox and the client discards nearly all of it: a "3 months" choice walks ten years of UIDs. It terminates, but "ask the server for the range, it's cheaper" inverts for that case. Also: `SINCE` is **date**-granular, so truncate the local floor to that date's midnight or every round re-fetches up to a day of mail it then throws away; and the window is computed in **UTC**, so a depth boundary is off by up to a day for a non-UTC user. → [sync.rs](../src-tauri/src/commands/email/sync.rs) `depth_window`
- **Syncing more mail is not the same as making more mail reachable — check the read surface before calling a depth feature done.** IM-2b backfills 12 months of envelopes into redb, and a user can see none of it: the list is capped at 500 rows, instant search filters only the rows already loaded, and the Rust search scans only body text cached for messages already opened. The spec's own out-of-scope note asserted "deeper sync improves local search" while putting the 500-row cap out of scope — those cannot both hold. Whenever a block's payload is "more data in the store", name the surface that exposes it in the same breath. → [specs/import.md](../specs/import.md) §Open questions

## Notion import (IM-1)

- **A real Notion export is a ZIP INSIDE A ZIP — a reader that only looks one level in imports ZERO notes, silently.** The download is `Export-<uuid>.zip` containing `Export-<uuid>-Part-1.zip` containing the files; large workspaces add `Part-2`, `Part-3`.
