# Gotchas / footguns

Things that have bitten us, so they don't bite again. **Read before debugging; append when something costs you more than a few minutes.** Each entry: the trap, why it happens, what to do instead.

---

## Repo / build

- **`preview_start` in a `.claude/worktrees/*` session has two failure stages — only the first is fixable.** (1) `Port 8081 is in use by another chat's dev server` → fixed for good 2026-07-02: `.claude/launch.json`'s "web" config uses `autoPort: true` + a port-flag-free command, and `rsbuild.config.ts` honors an assigned `PORT` env (default stays 8081). (2) `EPERM: uv_cwd` → **not fixable from the session**: the preview sandbox binds to whichever worktree owns the currently *active* dev server, so while another chat serves :8081 the sandbox can't even `cwd` into yours. Do not kill the other session's rsbuild (that trap already bit us — Session 10). Workaround: `bun install` in the worktree, run `MODUO_TARGET=web ./node_modules/.bin/rsbuild dev --host 127.0.0.1 --port <free>` via Bash background, drive with the Chrome MCP, kill by the **exact port-specific** pattern when done.
- **Never import a bare `{ runtime }`.** Always resolve via `getRuntime()`. The bare export was an always-null const footgun; grep `./runtime` when auditing lib exports. → [data-layers.md](./data-layers.md)
- **redb is paused — never make it load-bearing** for a new feature. New models are Supabase-first; redb is kept only for the future offline/"lite" version and not-yet-migrated legacy modules. → [data-layers.md](./data-layers.md)
- **Vitest has no `@/` alias — VALUE imports from `lib/` in a test's graph must be relative.** `vitest.config.ts` defines no `resolve.alias`, so a runtime (value) import like `import { deriveLinkKey } from "@/lib/entity-links"` fails to resolve under `bun run test` ("Failed to resolve import @/lib/…"), even though `tsc` (which reads tsconfig `paths`) is happy. **Type-only** `@/` imports are fine — they're erased before resolution, which is why existing tests (`mention.test.ts`, `rollup.test.ts`) use `@/` for types and still pass. The rule: anything reachable from a `*.test.ts(x)` via a *value* import must use a **relative** path for `lib/*` (see `spine/activity.ts` → `../../lib/entity-links`, `spine/suggest.ts`). Components/hooks bundled only by rsbuild may use `@/` values (rsbuild resolves it); the trap is strictly the vitest graph. Standalone `bunx vitest` resolves `@/` even less than `bun run test` — always verify with the project script.
- **The local done-check is `bun run verify`** (typecheck + lint:tw + lint:css + unit tests) — it mirrors CI's gate. CI does **not** run the e2e / visual-snapshot / billing suites (those stay local/manual), so a green PR doesn't cover them.
- **Visual-snapshot PNG baselines are NOT generated in CI** and are platform-suffixed (`*-visual-darwin.png`). Capture is a deliberate human `bun run e2e --update-snapshots` run on the canonical env. A visual diff means **stop and ask**, never auto-accept/regenerate.
- **macOS Liquid Glass app icon has been lost in merges twice.** It lives in-repo at `scripts/icons/source/Moduo.icon`; regenerate with `bun run icon:liquid` (needs full Xcode for `actool`). Don't let a merge drop it.

## Supabase / migrations

- **A new migration is NOT applied by `bun run verify`.** `verify` only runs typecheck/lint/unit-tests; it never touches Postgres. A green PR with a new `supabase/migrations/*.sql` means the SQL *parsed in your head*, not that it deployed — server invariants (RLS, RPCs, FKs, generated columns) are unproven until the migration is applied to a Supabase instance and exercised by an authenticated round-trip (the manual-test layer). Apply the migration and regenerate `src/types/supabase.ts` before any code *depends* on the new tables/RPCs. Don't apply to the shared/prod project without authorization.
- **The Supabase JS client is untyped (`SupabaseClient`, no `Database` generic).** So `supabaseClient.from("a_table_that_doesnt_exist_yet")` and `.rpc("an_unmigrated_fn", …)` both **typecheck fine** — TS can't catch a table/RPC-name typo or an arg-shape mismatch against an unmigrated schema. New runtime methods for new tables pass `verify` even if the migration is wrong or unapplied; the only real check is the live round-trip. (Mappers take `r: any`, so column renames are silent too.)
- **Direction-agnostic link dedupe must use a collation that matches JS.** `entity_links.pair_key` (the unordered `least/greatest(type:id)` key) compares with `COLLATE "C"` (byte order) so it provably matches the TS `deriveLinkKey` (JS `<=` code-unit order). Plain `least/greatest` on `text` uses the DB's *default* collation (a locale on standard Supabase), which can order non-ASCII tokens differently than JS → the server-side and client-side dedupe keys silently disagree. Keep `spine_pair_key()` (SQL) and `deriveLinkKey()` (TS) in lockstep. → [src/lib/entity-links.ts](../src/lib/entity-links.ts)
- **A plpgsql function returning a composite type returns an all-NULL *row*, not SQL NULL, after a `SELECT … INTO` that finds nothing.** `RETURN v_row;` when `v_row` is unset serializes (via PostgREST) as `{id:null,…}`, not `null` — callers expecting `null` get a truthy object. Guard with `IF v_row.id IS NULL THEN RETURN NULL; END IF;` (see `links_op_delete`, `contacts_op_unlink`).
- **Wiring a brand-new RPC into a live read path breaks that surface until the migration is deployed.** `verify` never applies migrations, and the prod apply is a separate step — so between merging code that calls `runtime.x.newRpc()` and deploying its migration, the call 404s and can break the feature for everyone (e.g. the notification bell). For a *new* RPC consumed on a hot read path, wrap the call in try/catch and **degrade gracefully** (fall back to the prior behavior / empty) so the app survives the gap; the new data simply appears once the migration lands. (See `workspace-provider.refreshNotifications` wrapping `spine.listNotifications`.) Mutations the user explicitly triggers can surface the error instead.
- **A plpgsql/SQL function with `RETURNS TABLE(...)` whose out-columns share names with a table in its body (e.g. `workspace_id`, `id`, `payload`) is an ambiguity trap.** It only works while *every* column reference in the body stays table-qualified (`ma.workspace_id`); a single later unqualified ref silently resolves to the out-param instead of the column. Keep refs qualified (or prefix out-params `o_`). (See `notifications_list`.)

## Git / branching

- **`maciej` is a hot branch — merge-commit into it, never fast-forward.** Before editing in a worktree, **check the worktree's base vs `maciej`** (`git rev-list --left-right --count HEAD...maciej`) — sessions have started on a weeks-stale `main` base and edited stale copies of `CLAUDE.md` / `DESIGN_SYSTEM.md` / `tokens.css`. Cut `t/<owner>/<kebab>` off `maciej`, not `main`. A `SessionStart` hook (`.claude/hooks/session-start.sh`) now runs this check automatically and warns on a stale base at session start — but only takes effect once it's merged into `maciej`. → [CONTRIBUTING.md](../CONTRIBUTING.md)
- **Parallel sessions running `/execute next` off the same base CLAIM THE SAME BLOCK.** `BUILD_ORDER.md` reflects *merged* state only; an open PR that hasn't merged into `maciej` is invisible to it, so a new session off `maciej` sees the block still `[ ]` and `/execute next` deterministically picks it again. On 2026-06-27 three sessions each built CT-4 and/or CT-5 this way → duplicate files + two migrations creating the same tables (PRs #31/#32/#33 had to be reconciled by hand). `/execute next` is a *read*, not a *claim*. **Avoid:** give each parallel session an **explicit** block (`/execute CT-6`, not bare `next`), and/or **merge each block into `maciej` before starting the next round** (the "merge barrier" BUILD_ORDER already prescribes). `/wrap` now auto-merges into the personal branch + runs a duplication guard precisely to keep the ledger advancing so this can't recur. → [specs/BUILD_ORDER.md](../specs/BUILD_ORDER.md)

## Storybook / live-verify

- **Storybook renders nothing in this worktree — `Failed to fetch dynamically imported module: /.storybook/preview.tsx`.** Every story (existing `components-tag-chip--default` included, not just new ones) fails to render at runtime with this error, so interactive/screenshot live-verify of any component is currently blocked here. The Storybook *bundler* still starts and compiles stories cleanly (`sb dev` reports "started" with no errors) — so a clean Storybook boot confirms stories *compile*, but not that they *render*. Likely the worktree/preview-binding issue (see [[feedback-live-verify-in-worktree]] in memory). Until it's fixed, verify components via typecheck + unit tests on the pure logic + the validator pass; visual-snapshot baselines remain a deliberate human capture.
- **The Supabase MCP in this environment is connected to the "Ringdove" org (projects `flowboard`, `lunavale-web`), NOT Moduo's project (`wtoonrvuqumihpkbvwvs`).** So migrations/RPCs can't be applied or round-trip-tested against the real Moduo DB from here, and there's no local Docker for a `supabase` stack. SQL can only be syntax-checked locally (e.g. `pgsql-parser`); applying + the AC round-trip needs the MCP reconnected to the Moduo Supabase account or someone with that access.

## Lexical / spine text surfaces

- **A new Lexical `DecoratorNode` must be added to the editor's `initialConfig.nodes` array or it throws on import/insert.** `EntityRefNode` is registered in [`LexicalNoteEditor.tsx`](../src/features/notes/editor/LexicalNoteEditor.tsx); any future editor (comments in CT-5, etc.) that renders entity-ref chips must register it too. Inline decorator chips also need `createDOM` to set `contentEditable="false"` (mirror `EmbedNode`) or the caret lands *inside* the chip. → [src/features/spine/editor/entity-ref-node.tsx](../src/features/spine/editor/entity-ref-node.tsx)
- **Keyboard handlers registered via `editor.registerCommand` capture a stale closure.** The handler is registered once (deps `[editor]`), so it sees first-render values of props/state. Route the action through a ref refreshed each render (`commitRef.current`) — the `@` MentionMenuPlugin does this for Enter; the legacy SlashCommandPlugin sidesteps it by fetching `getRuntime()` fresh inside each handler. A handler that reads `runtime`/`workspaceId` directly from the closure can use a null value that has since populated.
- **The `SlashCommand` union type is closed** ([`src/features/notes/types.ts`](../src/features/notes/types.ts)) — adding a slash command id/group (e.g. the `/ref` "Refs" group) needs the union widened there or `tsc` rejects the `COMMANDS` entry. (`lint:tw` *ignores* the notes editor, so new menu UI there can match the legacy hex chrome — but spine files under `src/features/spine/` are gated and must be tokens-only.)

## Spine reads / activity

- **`runtime.tasks.listActivity` filters by `module` — omit it for spine entities.** It used to hardcode `.eq("module","tasks")`, so reading a *contact*/*company* entity's trail returned `[]` (their ops log under `module='contacts'`, not 'tasks') — a contact's ActivitySection + verb-bearing last-touch were silently empty. The `module` filter is now **optional**: pass `module:'tasks'` to scope to Tasks (the Tasks UI does), **omit it** to read an entity's activity across all modules (what a contact/company hub wants). When you read activity for a new module's entity, don't assume a module pin. → [src/lib/runtime.web.ts](../src/lib/runtime.web.ts) `listActivity`
- **A contact's "last touch" does NOT reflect edits to its *linked* entities** (only the contact's own activity + when things were linked to it). A linked task edited yesterday won't bump last-touch — that needs a batched cross-entity activity read or a materialized view (deferred, decisions.md CO-2 (b) / contacts spec decision 4). Don't read the `lastTouchLine` as a real-time "anything related happened" signal at alpha. → [src/features/contacts/rollup.ts](../src/features/contacts/rollup.ts)

## Contacts

- **CSV import must sniff the delimiter — Excel/European exports are `;`-delimited, not `,`.** The first cut of `parseCsv` hardcoded a comma split, so a semicolon file collapsed each line into ONE field: the whole line became the contact `name` (e.g. a contact literally named `;noname@x.io;;;;;`, and even the header row imported as a contact). `parseCsv` now auto-detects `, ; \t |` from the header line (outside quotes) via `detectDelimiter`. When adding any delimited-text parsing, detect — don't assume comma. → [src/features/contacts/import.ts](../src/features/contacts/import.ts)
- **Contact delete is soft + has no Undo yet.** `contacts_op_delete` (migration `20260628120000`) soft-deletes the contact (`deleted_at`), drops its live `entity_links`, and tombstones the registry entry; the UI is a confirm dialog in the context strip. There is **no un-delete/Undo op** yet (the toast can't offer one), and **companies have no delete op** at all — both are the next gaps.

- **Radix `Select.Item` forbids an empty-string `value`** — it throws at runtime ("must have a value prop that is not an empty string"). Our "No status" option (status `''`) rides a `__none__` sentinel mapped on both `value`/`onValueChange` and the item value (contact-hub + contact-form-dialog). Any future optional Select needs the same sentinel.
- **`ALTER COLUMN … TYPE … USING (…)` cannot contain a subquery** ("cannot use subquery in transform expression"). The `emails text[]`→jsonb migration converts per-row via an IMMUTABLE helper function (`contacts__emails_to_jsonb`) the USING just *calls* — a function call is allowed, a subquery isn't. → [supabase/migrations/20260628140000_contacts_v2.sql](../supabase/migrations/20260628140000_contacts_v2.sql)
- **Contact `email`/`phone` are derived scalars, not independent fields (v2).** They mirror the primary of the `emails`/`phones` JSONB lists, recomputed by `contacts_op_set_details` via `contacts__primary_value`. Don't write the scalar without updating the list (and vice-versa) — go through the ops. The flat `email` + its `lower(email)` index remain the dedupe/suggest fast-path.

## Tasks data

- **`tasks.due_date` is a `timestamptz`, not a `YYYY-MM-DD` date.** The Tasks UI writes it from local midnight via `new Date(`${v}T00:00:00`).toISOString()` (e.g. `"2026-06-25T15:00:00.000Z"` for a JST user). So a raw lexical compare against a `YYYY-MM-DD` "today" string (`t.due_date < today`) is **off by a day for users east of UTC** — a follow-up due *today* can read as *overdue*. Normalize the stored instant back to a **local** calendar date first (`new Date(iso)` → local `YYYY-MM-DD`, mirroring `tasks/helpers.ts` `toLocalInputValue`) before any date comparison. Bit the CO-5 needs-attention overdue check. → [src/lib/runtime.web.ts](../src/lib/runtime.web.ts) `loadOverdueFollowups`

## Spine deep-linking

- **`moduo:entity:open` is dispatched but nothing listens for it yet.** Multiple spine surfaces fire `window.dispatchEvent(new CustomEvent("moduo:entity:open", { detail: { type, id } }))` to "open an entity's hub" — CT-4's [`entity-ref-node.tsx`](../src/features/spine/editor/entity-ref-node.tsx), CT-7's [`recently-linked-widget.tsx`](../src/features/dashboard/ui/widgets/recently-linked-widget.tsx). There is **no `addEventListener("moduo:entity:open", …)` anywhere** yet, so the click is currently inert (the event contract is correct; the routing host is the missing half). A test that only asserts "the event fires" passes while the feature is end-to-end dead — assert navigation, not dispatch. Wiring the host listener (app shell → route via `ROUTE_BY_TYPE` from [`notifications.ts`](../src/features/spine/notifications.ts) + a per-page entity-focus param) is a shared follow-up; grep `moduo:entity:open` to find every dispatcher when you wire it.

## UI / design

- **"The app looks huge on web" was browser zoom**, not fonts or density. Check the browser zoom level before chasing a density/type-scale bug.
- **dnd-kit drags aren't simulable with synchronous synthetic events.** Its rAF collision-detection loop drops same-tick pointer events (why earlier sessions called drag "unsimulable"). To live-verify a drag, dispatch pointer events with **per-frame delays** between move steps. → [build-log.md](./build-log.md)
- **Don't hardcode visual values.** If a needed color/size/radius/shadow/duration isn't a token, add it to `src/styles/tokens.css` — never inline it. Motion goes through the motion tokens so `prefers-reduced-motion` keeps working. → [DESIGN_SYSTEM.md](../DESIGN_SYSTEM.md)
