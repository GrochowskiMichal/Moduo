# Gotchas / footguns

Things that have bitten us, so they don't bite again. **Read before debugging; append when something costs you more than a few minutes.** Each entry: the trap, why it happens, what to do instead.

---

## Repo / build

- **TanStack Router: an object `search` in `navigate()` REPLACES the whole query string.** `navigate({ to: "/contacts", search: { action: "new" } })` silently wipes an existing `?type&id` selection. When adding one param on a route that carries others, use the functional updater: `search: (prev) => ({ ...prev, action: "new" })`. Bit FX-1 (the palette's New-contact wiped the open contact's selection); `/contacts` is the app's first search-param route, so every future `navigate` targeting it must think about this.

- **`preview_start` in a `.claude/worktrees/*` session has two failure stages — only the first is fixable.** (1) `Port 8081 is in use by another chat's dev server` → fixed for good 2026-07-02: `.claude/launch.json`'s "web" config uses `autoPort: true` + a port-flag-free command, and `rsbuild.config.ts` honors an assigned `PORT` env (default stays 8081). (2) `EPERM: uv_cwd` → **not fixable from the session**: the preview sandbox binds to whichever worktree owns the currently *active* dev server, so while another chat serves :8081 the sandbox can't even `cwd` into yours. Do not kill the other session's rsbuild (that trap already bit us — Session 10). Workaround: `bun install` in the worktree, run `MODUO_TARGET=web ./node_modules/.bin/rsbuild dev --host 127.0.0.1 --port <free>` via Bash background, drive with the Chrome MCP, kill by the **exact port-specific** pattern when done.
- **Never import a bare `{ runtime }`.** Always resolve via `getRuntime()`. The bare export was an always-null const footgun; grep `./runtime` when auditing lib exports. → [data-layers.md](./data-layers.md)
- **redb is paused — never make it load-bearing** for a new feature. New models are Supabase-first; redb is kept only for the future offline/"lite" version and not-yet-migrated legacy modules. → [data-layers.md](./data-layers.md)
- **Vitest has no `@/` alias — VALUE imports from `lib/` in a test's graph must be relative.** `vitest.config.ts` defines no `resolve.alias`, so a runtime (value) import like `import { deriveLinkKey } from "@/lib/entity-links"` fails to resolve under `bun run test` ("Failed to resolve import @/lib/…"), even though `tsc` (which reads tsconfig `paths`) is happy. **Type-only** `@/` imports are fine — they're erased before resolution, which is why existing tests (`mention.test.ts`, `rollup.test.ts`) use `@/` for types and still pass. The rule: anything reachable from a `*.test.ts(x)` via a *value* import must use a **relative** path for `lib/*` (see `spine/activity.ts` → `../../lib/entity-links`, `spine/suggest.ts`). Components/hooks bundled only by rsbuild may use `@/` values (rsbuild resolves it); the trap is strictly the vitest graph. Standalone `bunx vitest` resolves `@/` even less than `bun run test` — always verify with the project script.
- **The local done-check is `bun run verify`** (typecheck + lint:tw + lint:css + unit tests) — it mirrors CI's gate. CI does **not** run the e2e / visual-snapshot / billing suites (those stay local/manual), so a green PR doesn't cover them.
- **Dead-code sweeps: "is it mounted?" is not "is it alive?" — trace the OUTPUT, not just the importers.** `useSlotBookingsSync` was mounted in `app-gate.tsx` (so import-graph tools call it live) yet its entire effect was writing a localStorage key with zero readers — and it PATCHed `slot_bookings.calendar_synced=true` server-side for rows that surfaced nowhere, actively corrupting the "unsynced" signal for any future re-implementation. When sweeping, follow each candidate's *sinks* (storage keys, tables, events) to a real consumer before calling it live. Also: `bun run verify` catches zero Rust breakage — any sweep touching `src-tauri` needs its own `cargo check` (CLEAN-1, 2026-07-03).
- **Visual-snapshot PNG baselines are NOT generated in CI** and are platform-suffixed (`*-visual-darwin.png`). Capture is a deliberate human `bun run e2e --update-snapshots` run on the canonical env. A visual diff means **stop and ask**, never auto-accept/regenerate.
- **macOS Liquid Glass app icon has been lost in merges twice.** It lives in-repo at `scripts/icons/source/Moduo.icon`; regenerate with `bun run icon:liquid` (needs full Xcode for `actool`). Don't let a merge drop it.

## Supabase / migrations

- **A new migration is NOT applied by `bun run verify`.** `verify` only runs typecheck/lint/unit-tests; it never touches Postgres. A green PR with a new `supabase/migrations/*.sql` means the SQL *parsed in your head*, not that it deployed — server invariants (RLS, RPCs, FKs, generated columns) are unproven until the migration is applied to a Supabase instance and exercised by an authenticated round-trip (the manual-test layer). Apply the migration and regenerate `src/types/supabase.ts` before any code *depends* on the new tables/RPCs. Don't apply to the shared/prod project without authorization.
- **The Supabase JS client is untyped (`SupabaseClient`, no `Database` generic).** So `supabaseClient.from("a_table_that_doesnt_exist_yet")` and `.rpc("an_unmigrated_fn", …)` both **typecheck fine** — TS can't catch a table/RPC-name typo or an arg-shape mismatch against an unmigrated schema. New runtime methods for new tables pass `verify` even if the migration is wrong or unapplied; the only real check is the live round-trip. (Mappers take `r: any`, so column renames are silent too.)
- **Direction-agnostic link dedupe must use a collation that matches JS.** `entity_links.pair_key` (the unordered `least/greatest(type:id)` key) compares with `COLLATE "C"` (byte order) so it provably matches the TS `deriveLinkKey` (JS `<=` code-unit order). Plain `least/greatest` on `text` uses the DB's *default* collation (a locale on standard Supabase), which can order non-ASCII tokens differently than JS → the server-side and client-side dedupe keys silently disagree. Keep `spine_pair_key()` (SQL) and `deriveLinkKey()` (TS) in lockstep. → [src/lib/entity-links.ts](../src/lib/entity-links.ts)
- **A plpgsql function returning a composite type returns an all-NULL *row*, not SQL NULL, after a `SELECT … INTO` that finds nothing.** `RETURN v_row;` when `v_row` is unset serializes (via PostgREST) as `{id:null,…}`, not `null` — callers expecting `null` get a truthy object. Guard with `IF v_row.id IS NULL THEN RETURN NULL; END IF;` (see `links_op_delete`, `contacts_op_unlink`).
- **Wiring a brand-new RPC into a live read path breaks that surface until the migration is deployed.** `verify` never applies migrations, and the prod apply is a separate step — so between merging code that calls `runtime.x.newRpc()` and deploying its migration, the call 404s and can break the feature for everyone (e.g. the notification bell). For a *new* RPC consumed on a hot read path, wrap the call in try/catch and **degrade gracefully** (fall back to the prior behavior / empty) so the app survives the gap; the new data simply appears once the migration lands. (See `workspace-provider.refreshNotifications` wrapping `spine.listNotifications`.) Mutations the user explicitly triggers can surface the error instead.
- **A plpgsql/SQL function with `RETURNS TABLE(...)` whose out-columns share names with a table in its body (e.g. `workspace_id`, `id`, `payload`) is an ambiguity trap.** It only works while *every* column reference in the body stays table-qualified (`ma.workspace_id`); a single later unqualified ref silently resolves to the out-param instead of the column. Keep refs qualified (or prefix out-params `o_`). (See `notifications_list`.)

## Routes / app chrome

- **A new top-level route needs FIVE wirings, and the compiler catches none of them:** (1) `src/app/router/route-tree.tsx` (the route), (2) `app-chrome-constants.ts` (the nav tab) + the permission filter in `app-chrome.tsx`, (3) **`routeToFeatureLayout` in `src/features/layout/panel-events.ts`** — miss this and the top-bar panel toggles silently mutate ANOTHER feature's persisted panel state (the fallthrough returns `"notes"`) while the page's own `FeaturePanelsShell` ignores them, (4) the `module-N` shortcut count (`src/lib/shortcuts.ts` + the fixed `useShortcut` calls in app-chrome — the Nth tab past the list loses its ⌘N silently), (5) the command palette's `navActions` (`global-command-palette.tsx`). CAL-1 hit 3–5; a validator agent caught #3 pre-ship.
- **Setting `scrollbar-width` (e.g. Tailwind's `scrollbar-thin`) makes Chromium ignore all `::-webkit-scrollbar` rules for that element** — the native thin scrollbar renders, colored by `color-scheme`, i.e. WHITE on our dark surfaces. Pair it with `scrollbar-color: var(--border) transparent` (done app-wide in `.scrollbar-thin`, global.css). Editing the webkit block does nothing while scrollbar-width is set.

- **A "new" table may already exist in prod from the pre-migrations era — check `src/types/supabase.ts` BEFORE writing `CREATE TABLE IF NOT EXISTS`.** The legacy exploratory calendar created `calendar_events` straight from the dashboard (no migration file), owner-scoped with client-direct writes. A `CREATE TABLE IF NOT EXISTS` for the Wave-2 shape would have silently no-op'd and left every new column missing at runtime (untyped client = no compile error, per the gotcha above). CAL-2 extends it in place instead (ALTER + drop-all-policies loop via `pg_policies`, since dashboard-era policy names are unknown). Grep the generated types for the table name first, always.
- **Radix dismiss (Esc) runs on a document-level CAPTURE listener — it fires before your input's onKeyDown, and `onOpenChange(false)` can't tell Esc from click-away.** The quick-create popover initially committed the event on Esc because the dismiss path ran commit-on-close before the input's Esc handler could cancel. Handle `onEscapeKeyDown` on the Content with `event.preventDefault()` + your own cancel, and `onPointerDownOutside` for the click-away path; keep `onOpenChange` only as a discard fallback. → [src/features/calendar/ui/event-quick-create.tsx](../src/features/calendar/ui/event-quick-create.tsx)
- **`<input type="datetime-local">` fires change per keyboard segment edit** — committing in `onChange` writes garbage intermediates (year "0002") to the server, one RPC per keystroke. Draft-state + commit on blur/Enter, like the title-field pattern. → [event-detail-panel.tsx](../src/features/calendar/ui/event-detail-panel.tsx)
- **Custom pointer-drag engines need three exits, not one:** `pointerup` alone loses the gesture when the button releases outside the window/over an iframe (sticky ghost + a surprise commit on the next click). Also handle `pointercancel`, self-heal on `pointermove` with `e.buttons === 0`, and re-measure cached rects per move (wheel-scroll mid-drag shifts them). NOTE for synthetic testing: dispatch moves with `buttons: 1` or the self-heal cancels your test gesture. → [calendar-grid.tsx](../src/features/calendar/ui/calendar-grid.tsx)

## Git / branching

- **`maciej` is a hot branch — merge-commit into it, never fast-forward.** Before editing in a worktree, **check the worktree's base vs `maciej`** (`git rev-list --left-right --count HEAD...maciej`) — sessions have started on a weeks-stale `main` base and edited stale copies of `CLAUDE.md` / `DESIGN_SYSTEM.md` / `tokens.css`. Cut `t/<owner>/<kebab>` off `maciej`, not `main`. A `SessionStart` hook (`.claude/hooks/session-start.sh`) now runs this check automatically and warns on a stale base at session start — but only takes effect once it's merged into `maciej`. → [CONTRIBUTING.md](../CONTRIBUTING.md)
- **Parallel sessions running `/execute next` off the same base CLAIM THE SAME BLOCK.** `BUILD_ORDER.md` reflects *merged* state only; an open PR that hasn't merged into `maciej` is invisible to it, so a new session off `maciej` sees the block still `[ ]` and `/execute next` deterministically picks it again. On 2026-06-27 three sessions each built CT-4 and/or CT-5 this way → duplicate files + two migrations creating the same tables (PRs #31/#32/#33 had to be reconciled by hand). `/execute next` is a *read*, not a *claim*. **Avoid:** give each parallel session an **explicit** block (`/execute CT-6`, not bare `next`), and/or **merge each block into `maciej` before starting the next round** (the "merge barrier" BUILD_ORDER already prescribes). `/wrap` now auto-merges into the personal branch + runs a duplication guard precisely to keep the ledger advancing so this can't recur. → [specs/BUILD_ORDER.md](../specs/BUILD_ORDER.md)

## Storybook / live-verify

- **The preview-MCP browser can report `window.innerWidth === 0`** (persistently, not just pre-paint), so every viewport-driven component mounts in its narrow/sheet mode — `FeaturePanelsShell` rendered the NO-3 notes sidebar as a Sheet at a "1280px" viewport because the app measured 0 at mount. It is a preview-tool artifact, not an app bug: the same build in a real Chrome (claude-in-chrome MCP) laid out correctly. When a layout looks inexplicably mobile in the preview, check `window.innerWidth` via preview_eval BEFORE debugging breakpoints; fall back to the Chrome MCP for viewport-sensitive verification.
- **supabase-js is fetch-stubbable at runtime** — patching `window.fetch` in the page DOES intercept its REST/RPC calls (it resolves fetch late), so unapplied-migration surfaces can be live-verified end-to-end with an in-page fake backend: stub `/rest/v1/rpc/<op>` + the new-column SELECTs, then remount the page **via SPA navigation** (nav to another module and back) — a hard reload wipes the stubs, but an SPA remount re-runs the module load through them. (NO-3 was verified this way: capture → CRDT push → rename → trash/restore, all against stubs.)

The Storybook *bundler* still starts and compiles stories cleanly (`sb dev` reports "started" with no errors) — so a clean Storybook boot confirms stories *compile*, but not that they *render*. Likely the worktree/preview-binding issue (see [[feedback-live-verify-in-worktree]] in memory). Until it's fixed, verify components via typecheck + unit tests on the pure logic + the validator pass; visual-snapshot baselines remain a deliberate human capture.
- **The Supabase MCP in this environment is connected to the "Ringdove" org (projects `flowboard`, `lunavale-web`), NOT Moduo's project (`wtoonrvuqumihpkbvwvs`).** So migrations/RPCs can't be applied or round-trip-tested against the real Moduo DB from here, and there's no local Docker for a `supabase` stack. SQL can only be syntax-checked locally (e.g. `pgsql-parser`); applying + the AC round-trip needs the MCP reconnected to the Moduo Supabase account or someone with that access.

## Module contract / MCP connector

- **A new module's `<module>_module_permission` MUST include the `module_api_key_id()` branch, or every agent WRITE through its ops is dead on arrival.** The MCP connector runs as service_role: `auth.uid()` is NULL, so an auth.uid()-only permission function returns `'none'` and the op guard raises "no edit access" **even for a properly-scoped key** — while the connector's *reads* work fine (they query tables directly, never hitting the guard), which makes the breakage easy to miss in a read-only smoke test. This shipped broken in **three** modules (spine CT-1, contacts CO-1, calendar CAL-2 — the copy-paste source was the pre-connector shape) and was only caught by CAL-7's validator; all three were fixed in one migration ([`20260702170000_module_permissions_api_keys.sql`](../supabase/migrations/20260702170000_module_permissions_api_keys.sql), applied to prod). When writing a new module's permission fn, **copy `tasks_module_permission`** (the api-key branch reads `k.scopes ->> '<module>'`), not the others' old shape — and remember `verify` can't catch this (it's a server-side auth-context behavior; only a keyed round-trip proves it).
- **`tasks_op_reschedule` schedules-from-NULL as of `20260702170000`** — it used to quietly no-op when the task had nothing scheduled ("triage race" guard), which made any caller that *meant* "schedule this" report phantom success (bit the CAL-7 connector's `calendar_schedule_task`). If you relied on the no-op-when-unscheduled behavior, that's gone; the op now always sets the time and logs `{"from": null, …}`.

## Prefs sync

- **Adding a `user_preferences` sync domain needs SEVEN coordinated touchpoints, and the untyped Supabase client catches none of the column ones.** To add a domain (e.g. CAL-6b's "calendar"): (1) a migration adding `<domain> jsonb` + `<domain>_updated_at timestamptz` (the FOR-ALL own-row RLS already covers new columns); (2) the generated `src/types/supabase.ts` user_preferences Row/Insert/Update (hand-add — the client is untyped so a missing column here won't error, but keep it honest); (3) `UserPreferences` in [runtime.types.ts](../src/lib/runtime.types.ts); (4) `prefsRowToModel` + the `.select(...)` string in **both** `preferences.get` and `preferences.set` in [runtime.web.ts](../src/lib/runtime.web.ts) (tauri delegates); (5) `SyncDomain` union + `META_KEY` + the `domainValue` switch + the `pushDomain` patch in [prefs-sync.ts](../src/lib/prefs-sync.ts); (6) a `useDomainSync`-wired hook (copy `useFocusPrefs`); (7) call `pushLocalChange` on every syncable mutation. Miss the `.select` column in `set` and the write silently drops the domain on the returned row (typechecks fine — untyped client).

## Calendar / external mirror (CAL-6)

- **Microsoft Graph event `dateTime` is a NAIVE wall value + a separate `timeZone` field — never parse it raw.** `Date.parse("2026-07-02T09:00:00.0000000")` treats it as the machine's LOCAL zone → wrong instant. The desktop sync MUST request `Prefer: outlook.timezone="UTC"`, so the mapper appends `Z` for a naive value tagged UTC/absent; a naive value tagged with a **non-UTC Windows zone name** ("Pacific Standard Time" — `Intl` can't resolve these) is **dropped, not shifted** (a missing chip beats a wrong-slot one). Google is the opposite: its `dateTime` carries a real offset; only its all-day `date` (date-only) needs local-midnight normalization or it spills a day east of UTC. → [src/features/calendar/mirror.ts](../src/features/calendar/mirror.ts)
- **To live-verify the web mirror WITHOUT the desktop OAuth engine, seed via the RPCs from the browser.** `fetch` `${SUPABASE_URL}/rest/v1/rpc/calendar_op_account_upsert` then `…/calendar_op_mirror_events` with the injected session token + publishable key (recipe in [[project-test-account-hosted]]) — mirrored external events then render on web exactly as a real sync would. Remove with `calendar_op_account_remove` to test the cascade. The whole external-render/attribution/visibility/removal path is verifiable this way; only the desktop OAuth *round-trip* is truly manual.

## Storybook / live-verify (cont.)

- **Editing a CUSTOM HOOK's body during an HMR session throws a false "React has detected a change in the order of Hooks" error in the consuming component.** A custom hook's internal hooks count toward its *caller's* hook list, so rewriting e.g. `useBlockFocus` (removing an effect, adding a callback) while the page is hot-mounted makes the caller's (`CalendarPageView`) hook sequence differ across the hot-swap → React logs the scary reorder error. It is an **HMR artifact, not a real bug**: a full `location.reload()` mounts fresh with the new consistent order and the error is gone. **Always hard-reload before trusting (or reporting) a hook-order error seen right after editing a hook** — a soft SPA `navigate()` to the same URL does NOT clear it (no remount). Confirmed CAL-5, 2026-07-02.
- **Computer-tool `left_click` at a coordinate can miss a thin grid chip; the pointer engine never fires.** A ~28px task-block chip on the calendar was un-clickable via `mcp__claude-in-chrome__computer left_click` (high-DPI coord mapping landed just off the chip's x), so the custom pointer-drag engine's `onPointerDown` never ran and no popover opened — with **no error** to signal the miss. Verify chip-level interactions by dispatching a real `PointerEvent` sequence (`pointerdown` on the element at `rect.x + rect.width*0.6`, then `pointerup` on `window` with `buttons:0`) via `javascript_tool`, or click larger targets (toolbar buttons) by coordinate. The engine itself is fine — the tool's pixel click was the problem.

## Lexical / spine text surfaces

- **A portal rendered next to a Lexical editor can't win focus with `autoFocus` — Lexical's post-update focus restore steals it back.** The slash menu's stage-2 picker mounted a cmdk `CommandInput` with autoFocus, but the `editor.update()` that removed the slash token re-focused the contenteditable a beat later → every keystroke went into the NOTE BODY while the picker sat mouse-only (cmdk only handles keys when focus is inside it). Focus such surfaces in a `setTimeout(≈30ms)` AFTER the update settles, and own your dismissal: Escape via the portal's own `onKeyDown` (the editor's `KEY_ESCAPE_COMMAND` only fires while the EDITOR has focus) plus a document-level `pointerdown` outside-check. → [slash-menu-plugin.tsx](../src/features/notes/editor/plugins/slash-menu-plugin.tsx)
- **`@lexical/markdown`'s `ELEMENT_TRANSFORMERS` does NOT include `CHECK_LIST`** — spread the defaults and `- [x]` imports as a bullet item with LITERAL "[x]" text, and a byte-stable round-trip test still passes (export re-emits the literal). Add `CHECK_LIST` explicitly BEFORE the list transformers, and pin the STRUCTURE in tests (`"listType":"check"`, no literal marker), not just the bytes. Also: 0.40 ships no HR transformer (`---` needs a custom one), and ordered-list start lives on the LIST node's `start` field, not the items' `value`. → [markdown.ts](../src/features/notes/editor/markdown.ts)

## Lexical / spine text surfaces (cont.)

- **A new Lexical `DecoratorNode` must be added to the editor's `initialConfig.nodes` array or it throws on import/insert.** `EntityRefNode` is registered in [`LexicalNoteEditor.tsx`](../src/features/notes/editor/LexicalNoteEditor.tsx); any future editor (comments in CT-5, etc.) that renders entity-ref chips must register it too. Inline decorator chips also need `createDOM` to set `contentEditable="false"` (mirror `EmbedNode`) or the caret lands *inside* the chip. → [src/features/spine/editor/entity-ref-node.tsx](../src/features/spine/editor/entity-ref-node.tsx)
- **Keyboard handlers registered via `editor.registerCommand` capture a stale closure.** The handler is registered once (deps `[editor]`), so it sees first-render values of props/state. Route the action through a ref refreshed each render (`commitRef.current`) — the `@` MentionMenuPlugin does this for Enter; the legacy SlashCommandPlugin sidesteps it by fetching `getRuntime()` fresh inside each handler. A handler that reads `runtime`/`workspaceId` directly from the closure can use a null value that has since populated.
- **The `SlashCommand` union type is closed** ([`src/features/notes/types.ts`](../src/features/notes/types.ts)) — adding a slash command id/group (e.g. the `/ref` "Refs" group) needs the union widened there or `tsc` rejects the `COMMANDS` entry. (`lint:tw` *ignores* the notes editor, so new menu UI there can match the legacy hex chrome — but spine files under `src/features/spine/` are gated and must be tokens-only.)

## React effects

- **An effect that owns a debounce timer must NOT list an inline callback prop in its deps** — every parent re-render (a sync-status flip, any state change) re-runs the effect, and the cleanup clears the pending timer, so the debounced call can starve FOREVER under steady re-render pressure. The notes editor's first-line-title derivation never fired because `onTitleDerived` was an inline arrow: each CRDT flush toggled status → re-render → timer killed. Ride the callback in a ref (`ref.current = cb` each render) and keep the effect's deps to the stable subscription source. → [src/features/notes/ui/note-editor.tsx](../src/features/notes/ui/note-editor.tsx) `TitleDerivationPlugin`

## Drag-to-link (dnd-kit consumers)

- **`useDraggable`/`useDroppable` throw without a `<DndContext>` ancestor — gate a draggable row behind a flag + a wrapper component, never a conditional hook.** FX-9 makes contacts directory rows drag sources, but the directory must stay renderable without a DndContext (stories, other mounts). The pattern: a `DraggableRow` wrapper that calls `useDragPayload` is rendered ONLY when the page passes `draggable` (which guarantees a DndContext); the plain `DirectoryRow` is rendered otherwise. Don't call `useDraggable` conditionally inside one component (rules-of-hooks) — switch which component you render. Spread the drag `listeners` only (not `attributes`) on a row that already has click-to-select semantics, or you add an extra tab-stop + `role=button` on the row. Pair a `PointerSensor` `activationConstraint: { distance: 6 }` so a plain click still selects. → [src/features/contacts/ui/contact-directory.tsx](../src/features/contacts/ui/contact-directory.tsx)
- **`createLinkWithToast` (the generic CT-3 drop path) writes ONLY the spine edge — a denormalized FK is the consumer's job.** Dropping a person on a company writes the canonical `works-at` `entity_links` row, but the generic machinery knows nothing about `contacts.company_id`. The /contacts `onDragEnd` therefore layers a dual-write on top: after a `works-at` drop it also calls `updateContact({setCompany})` so the card header company chip reflects it (mirrors `setCompany` + the entry modal). Any future CT-3 consumer with a denormalized mirror of a link must do the same — don't assume the drop set your FK. → [src/routes/pages/contacts-page.tsx](../src/routes/pages/contacts-page.tsx) `onDragEnd`
- **`links_op_create` is idempotent (`ON CONFLICT DO NOTHING`, returns the existing row) — a re-drop is NOT an error, so "already linked" feedback needs a client guard.** `createLinkWithToast` can't tell "created" from "already existed"; dropping a duplicate would pop a confirmation toast with an **Undo** that deletes a link the user didn't just make. Guard in `onDragEnd` against the **drop-target's direct-link keys** before creating (for a company, use its OWN links — `useCompanyHub.directLinkKeys` — not the union roll-up, which includes member-inherited rows and would over-reject). → [src/routes/pages/contacts-page.tsx](../src/routes/pages/contacts-page.tsx)

## Spine reads / activity

- **`runtime.tasks.listActivity` filters by `module` — omit it for spine entities.** It used to hardcode `.eq("module","tasks")`, so reading a *contact*/*company* entity's trail returned `[]` (their ops log under `module='contacts'`, not 'tasks') — a contact's ActivitySection + verb-bearing last-touch were silently empty. The `module` filter is now **optional**: pass `module:'tasks'` to scope to Tasks (the Tasks UI does), **omit it** to read an entity's activity across all modules (what a contact/company hub wants). When you read activity for a new module's entity, don't assume a module pin. → [src/lib/runtime.web.ts](../src/lib/runtime.web.ts) `listActivity`
- **A contact's "last touch" does NOT reflect edits to its *linked* entities** (only the contact's own activity + when things were linked to it). A linked task edited yesterday won't bump last-touch — that needs a batched cross-entity activity read or a materialized view (deferred, decisions.md CO-2 (b) / contacts spec decision 4). Don't read the `lastTouchLine` as a real-time "anything related happened" signal at alpha. → [src/features/contacts/rollup.ts](../src/features/contacts/rollup.ts)

## Contacts

- **A relation-kind is only sensible for some endpoint-type pairs — constrain every write seam, not just the menu.** The "Ben Okafor · Attachment" bug was a contact↔contact link set to `attachment` via the unconstrained "Change relation" menu (it listed all 8 kinds). The fix is the pure matrix [`allowedKinds(a,b)`](../src/features/spine/kind-constraints.ts): `references`/`mentions` for any pair; `works-at` only contact↔company; `paid-by` only money↔party; `attachment` only when one end is attachable (file/email/receipt) — never person↔person. It gates the change-relation menu (`entity-hub.tsx`), and `coerceKindForPair` clamps the drag `resolveKind` and the suggestion-accept kind so a bad *derived* kind can't persist either. When adding a link write path, run the proposed kind through `coerceKindForPair(kind, aType, bType)`. → [src/features/spine/kind-constraints.ts](../src/features/spine/kind-constraints.ts)
- **A contact's last-touch prefers INTERACTIONS over record edits (FX-4) — changing the `RECORD_EDIT_OPS` set silently changes the surfaced verb.** `buildContactRollup` picks the most-recent stamp whose op is NOT in `RECORD_EDIT_OPS` (link creations + comments = interactions; `contacts.update`/`set_status`/`set_details`/`create`/`set_favorite` = record edits), falling back to the latest record edit only when there is no interaction. So a status change made *after* an older linked-task no longer wins "last touch". Two rollup tests encode this — if you add a new contacts op, decide whether it's an interaction before it starts (mis)winning last-touch. → [src/features/contacts/rollup.ts](../src/features/contacts/rollup.ts)

- **CSV import must sniff the delimiter — Excel/European exports are `;`-delimited, not `,`.** The first cut of `parseCsv` hardcoded a comma split, so a semicolon file collapsed each line into ONE field: the whole line became the contact `name` (e.g. a contact literally named `;noname@x.io;;;;;`, and even the header row imported as a contact). `parseCsv` now auto-detects `, ; \t |` from the header line (outside quotes) via `detectDelimiter`. When adding any delimited-text parsing, detect — don't assume comma. → [src/features/contacts/import.ts](../src/features/contacts/import.ts)
- **Contact delete is soft + has no Undo yet.** `contacts_op_delete` (migration `20260628120000`) soft-deletes the contact (`deleted_at`), drops its live `entity_links`, and tombstones the registry entry; the UI is a confirm dialog in the context strip. There is **no un-delete/Undo op** yet (the toast can't offer one), and **companies have no delete op** at all — both are the next gaps.

- **Radix `Select.Item` forbids an empty-string `value`** — it throws at runtime ("must have a value prop that is not an empty string"). Our "No status" option (status `''`) rides a `__none__` sentinel mapped on both `value`/`onValueChange` and the item value (contact-hub + contact-form-dialog). Any future optional Select needs the same sentinel.
- **`ALTER COLUMN … TYPE … USING (…)` cannot contain a subquery** ("cannot use subquery in transform expression"). The `emails text[]`→jsonb migration converts per-row via an IMMUTABLE helper function (`contacts__emails_to_jsonb`) the USING just *calls* — a function call is allowed, a subquery isn't. → [supabase/migrations/20260628140000_contacts_v2.sql](../supabase/migrations/20260628140000_contacts_v2.sql)
- **Contact `email`/`phone` are derived scalars, not independent fields (v2).** They mirror the primary of the `emails`/`phones` JSONB lists, recomputed by `contacts_op_set_details` via `contacts__primary_value`. Don't write the scalar without updating the list (and vice-versa) — go through the ops. The flat `email` + its `lower(email)` index remain the dedupe/suggest fast-path.

## Tasks data

- **`tasks.due_date` is a `timestamptz`, not a `YYYY-MM-DD` date.** The Tasks UI writes it from local midnight via `new Date(`${v}T00:00:00`).toISOString()` (e.g. `"2026-06-25T15:00:00.000Z"` for a JST user). So a raw lexical compare against a `YYYY-MM-DD` "today" string (`t.due_date < today`) is **off by a day for users east of UTC** — a follow-up due *today* can read as *overdue*. Normalize the stored instant back to a **local** calendar date first (`new Date(iso)` → local `YYYY-MM-DD`, mirroring `tasks/helpers.ts` `toLocalInputValue`) before any date comparison. Bit the CO-5 needs-attention overdue check. → [src/lib/runtime.web.ts](../src/lib/runtime.web.ts) `loadOverdueFollowups`

## Spine deep-linking

- **`moduo:entity:open` is dispatched but nothing listens for it yet.** Multiple spine surfaces fire `window.dispatchEvent(new CustomEvent("moduo:entity:open", { detail: { type, id } }))` to "open an entity's hub" — CT-4's [`entity-ref-node.tsx`](../src/features/spine/editor/entity-ref-node.tsx), CT-7's [`recently-linked-widget.tsx`](../src/features/dashboard/ui/widgets/recently-linked-widget.tsx). A test that only asserts "the event fires" passes while the feature is end-to-end dead — assert navigation, not dispatch. ## UI / design

- **A clickable container with `role="button"` + its own Enter/Space `onKeyDown` swallows the keyboard activation of every nested native button.** The keydown bubbles from the inner `<button>` (e.g. CompleteToggle) to the container, whose handler `preventDefault()`s and runs the container action — mouse clicks still work (the inner button stops click propagation), so the break is keyboard-only and easy to miss. Either check `e.target === e.currentTarget` in the container handler, or don't make the container a button at all (TL-1 bars dropped role/tabIndex — Board-card parity — and let the inner checkbox be the native tab stop). Also: `role="button"` with interactive descendants is invalid ARIA to begin with. → [src/features/tasks/ui/task-timeline-view.tsx](../src/features/tasks/ui/task-timeline-view.tsx)
- **`position: sticky` works inside absolutely-positioned elements** (the containing scroll ancestor is what matters), which is how the timeline pins lane labels (`sticky left-0`) and month labels (`sticky left-1` inside an `overflow-hidden` band) inside a 2-axis scroll canvas. But remember `mask-image` masks EVERYTHING on the element — borders, box-shadow focus rings, and any content — so a faded (masked) surface must never carry content or a focus ring you need visible. → [task-timeline-view.tsx](../src/features/tasks/ui/task-timeline-view.tsx)

- **"The app looks huge on web" was browser zoom**, not fonts or density. Check the browser zoom level before chasing a density/type-scale bug.
- **dnd-kit's `event.delta` is NOT pure pointer travel — it folds auto-scroll compensation in.** Computing a drop point as `activatorEvent.clientY + delta.y` drifts by exactly the amount any scrollable ancestor auto-scrolled mid-drag (bit CAL-3: drops landed hours late after the grid auto-scrolled). Track the raw pointer yourself (a document-level capture `pointermove` listener while dragging) and use that at drop time. Related: `pointerWithin` only for pointer-driven drop targets — any closest-center fallback resolves out-of-bounds releases to the nearest droppable and "drops" them. → [src/features/calendar/ui/calendar-page-view.tsx](../src/features/calendar/ui/calendar-page-view.tsx)
  - **…and a raw-pointer tracker is ALSO not enough if you resolve the target at pointermove time.** Anything that moves the canvas under a *stationary* pointer — dnd-kit autoScroll, a wheel scroll, a window-origin shift — changes what's under the cursor without firing `pointermove`, so a day/slot computed in the move handler goes stale by drop. Store raw **coordinates** in the tracker and resolve against a rect measured **in `onDragEnd`**; disable `autoScroll` when the surface derives its target from the pointer (TL-2's timeline axis). → [src/features/tasks/ui/task-timeline-view.tsx](../src/features/tasks/ui/task-timeline-view.tsx)
- **The preview browser throttles background-tab timers and never fires rAF** — multi-step synthetic gestures (chained `setTimeout`/`requestAnimationFrame` frames) stall mid-sequence and `preview_eval` times out while the page is fine. Taking a `preview_screenshot` forces progress; keep scripted gestures to few steps, never rAF-based, and treat an eval timeout as "throttled", not "hung" (check with a screenshot before debugging). Also: dnd-kit's PointerSensor listens on `document` — synthetic moves dispatched on `window` never reach it; dispatch on `document.body`.
- **dnd-kit drags aren't simulable with synchronous synthetic events.** Its rAF collision-detection loop drops same-tick pointer events (why earlier sessions called drag "unsimulable"). To live-verify a drag, dispatch pointer events with **per-frame delays** between move steps. → [build-log.md](./build-log.md)
- **Don't hardcode visual values.** If a needed color/size/radius/shadow/duration isn't a token, add it to `src/styles/tokens.css` — never inline it. Motion goes through the motion tokens so `prefers-reduced-motion` keeps working. → [DESIGN_SYSTEM.md](../DESIGN_SYSTEM.md)
