# Gotchas: UI, routes, Storybook, drag and the dashboard grid

Read before working in `src/components/`, `src/routes/`, `.storybook/`, dashboard. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Routes / app chrome

- **Signing out from inside the app sets off the app gate's own redirect to a plain `/auth`.** `AppGate` renders `<Navigate to="/auth" replace />` as soon as the session ends. Sign out first and then navigate somewhere carrying state (`/auth?deleted=1`), and the gate's redirect can win and drop that state. Navigate first, then sign out, and let the destination tolerate the moment it is still signed in, as `AuthPage` does for `deleted`. `finishAccountDeletion` in `src/features/settings/delete-account.ts` is the pattern and has a test for the order. A second trap on the same path: while a navigation loads, `useRouterState`'s `location` already names the destination but the old layout is still mounted, so any "this route isn't mine" redirect inside it fires on the way out. App chrome's guard did, and bounced `/auth?deleted=1` to the first tab. Such a guard waits while `state.status === "pending"` (`useUnknownRouteRedirect`; its test uses the real router, since mocks can't show this). (2026-10-08, PRIV-2b)
- **The top bar's right column has about 180 px at the 1024 px minimum window, and it never grows.** With all seven tabs labelled, Focus timer + Help + bell + avatar leave roughly 72 px for the timer. The nav's `1fr auto 1fr` grid keeps both side columns equal (no growth to fit content), so anything wider squeezes the avatar (`UserMenu`'s trigger can shrink) and then overlaps the tabs. Before adding anything to the top bar, measure it at 1024 px with the longest label it can show (canvas `measureText` works); the Focus timer shortens its wordy states below `xl` for this reason. → [src/components/app/focus-session-chip.tsx](../../src/components/app/focus-session-chip.tsx) (2026-10-10, call 96)
- **A new top-level route needs FIVE wirings, and the compiler catches none of them:** (1) `src/app/router/route-tree.tsx` (the route), (2) `app-chrome-constants.ts` (the nav tab) + the permission filter in `app-chrome.tsx`, (3) **`routeToFeatureLayout` in `src/features/layout/panel-events.ts`** — miss this and the top-bar panel toggles silently mutate ANOTHER feature's persisted panel state (the fallthrough returns `"notes"`) while the page's own `FeaturePanelsShell` ignores them, (4) the `module-N` shortcut count (`src/lib/shortcuts.ts` + the fixed `useShortcut` calls in app-chrome — the Nth tab past the list loses its ⌘N silently), (5) the command palette's `navActions` (`global-command-palette.tsx`). CAL-1 hit 3–5; a validator agent caught #3 pre-ship.
- **HIDING a route (nav tab removed but route kept) has a SIXTH wiring the add-a-route gotcha doesn't list: the app-chrome redirect guard.** `app-chrome.tsx` runs `if (!isSettingsRoute && !modulesNavItems.some(t => t.href === pathname)) navigate({to: modulesNavItems[0].href, replace:true})` — it bounces ANY pathname not in the visible nav to the first tab. So dropping a tab from `baseModulesNavItems` silently makes that route **unreachable even by direct URL** (it redirects to Home), even though the route + its `routeToFeatureLayout` entry are intact. DF-4 hit this hiding Mindmap: `/mindmap` bounced to `/` until the guard was taught to exempt it. Fix pattern: keep an explicit `hiddenReachableRoutes` allowlist (in `app-chrome-constants.ts`) and skip the bounce for those paths. Live-caught (path came back `/` after navigating to `/mindmap`), not test-caught — no test covers the guard.
- **The default-landing-view boot redirect (DF-19f) is a ONE-SHOT in `homeRoute.beforeLoad` gated on a synchronous localStorage auth sniff — not a component effect.** `consumeLandingRedirect(pathname, searchStr)` ([preferences.ts](../../src/lib/preferences.ts)) redirects `/` → the chosen module via `throw redirect()` (flash-free, before render). Three subtleties that a naive version gets wrong: (1) it must NOT consume the one-shot for a signed-out visitor (they hit `/`, get bounced to `/auth`, and the shot must survive to fire on the post-login return) — so it sniffs `sb-*-auth-token` in localStorage (supabase-js's default storage key; the client sets no custom `storageKey`) and returns null without consuming when absent; (2) ANY query string at `/` (e.g. a `?section=` deep link, or an OAuth `?code=` callback) means "explicit intent" → skip the redirect without consuming; (3) it only ever touches `/` (a non-home path is already a deep link). Known benign edge: a stale/expired-but-present token burns the shot once (lands Home instead of the chosen view that launch). "Last used" is fed by a `router.subscribe("onResolved")` in [router/index.tsx](../../src/app/router/index.tsx) that stores the current landable route. → [src/app/router/route-tree.tsx](../../src/app/router/route-tree.tsx)
- **The app motion override (`data-motion`, DF-19f) layers over the OS `prefers-reduced-motion` in tokens.css, but token-independent keyframe loops in global.css need explicit gating.** The motion *tokens* (`--motion-*`) are zeroed by `:root[data-motion="reduced"]` and kept-under-OS-reduce by `@media (prefers-reduced-motion: reduce) { :root:not([data-motion="full"]) { … } }`, so any transition/animation whose duration is a token honours the override for free. But a decorative loop with a **hardcoded** duration (`.auth-hero-float` 22s, `.track-pulse` 1.8s, `.mail-flag-wave__cloth` 1.4s) that disables itself only under `@media (prefers-reduced-motion: reduce)` will ignore `data-motion="reduced"` on a normal-OS machine AND still be killed by `data-motion="full"` under OS-reduce. Each such block needs a `:root[data-motion="reduced"] <sel> { animation:none }` companion + `:root:not([data-motion="full"])` on the media-query body (done for the four in global.css). New hardcoded-duration decorative animation → repeat the pattern (or drive its duration off a motion token). → [src/global.css](../../src/global.css), [src/styles/tokens.css](../../src/styles/tokens.css)
- **Setting `scrollbar-width` (e.g. Tailwind's `scrollbar-thin`) makes Chromium ignore all `::-webkit-scrollbar` rules for that element** — the native thin scrollbar renders, colored by `color-scheme`, i.e. WHITE on our dark surfaces. Pair it with `scrollbar-color` (the global default in global.css does: `var(--scroll-thumb) transparent` on `*`, DS-1). Editing the webkit block does nothing while scrollbar-width is set; it only reaches pre-18.2 WKWebView.
- **Since DS-1 every element gets a styled `::-webkit-scrollbar`, so `[scrollbar-width:none]` alone no longer hides a bar on old WebKit (Tauri on pre-18.2 macOS) — it draws the 10px custom bar instead.** Hide with `.no-scrollbar`, which covers both paths; `src/global-css.test.ts` fails on the bare utility. Styled WebKit bars are also classic (they take layout width, never overlay), which is why pane scrollers carry `.pane-scroll`. → [src/global.css](../../src/global.css)
- **`.pane-scroll` (`scrollbar-gutter: stable`) goes on the element that scrolls, never on a wrapper whose child scrolls.** A stable gutter is reserved for `overflow: hidden` too, and for an `overflow: auto` box that never overflows because nothing caps its height, so on `FeaturePanelsShell`'s `<main>`/rail wrappers (their children scroll) or on a panel that just grows, it draws a dead strip. Deliberate exclusions in DS-1: the calendar hours grid (`calendar-grid.tsx`) — its day header and all-day row sit outside the scroller on the same grid columns, so a gutter on the scroller alone would shift its columns off the header whenever the grid doesn't overflow (fixing it means giving the header rows the same gutter); the calendar rail (its mini month is a fixed 7 × 32px grid, and 11px less width overflows it at the default rail width of a ~1280px window); the notes Outline panel (its `<nav>` has no height cap, so it grows instead of scrolling); and Radix `ScrollArea` (it draws its own overlay bar). → [src/global.css](../../src/global.css)

- **A "new" table may already exist in prod from the pre-migrations era — check `src/types/supabase.ts` BEFORE writing `CREATE TABLE IF NOT EXISTS`.** The legacy exploratory calendar created `calendar_events` straight from the dashboard (no migration file), owner-scoped with client-direct writes. A `CREATE TABLE IF NOT EXISTS` for the Wave-2 shape would have silently no-op'd and left every new column missing at runtime (untyped client = no compile error, per the gotcha above). CAL-2 extends it in place instead (ALTER + drop-all-policies loop via `pg_policies`, since dashboard-era policy names are unknown). Grep the generated types for the table name first, always.
- **Radix dismiss (Esc) runs on a document-level CAPTURE listener — it fires before your input's onKeyDown, and `onOpenChange(false)` can't tell Esc from click-away.** The quick-create popover initially committed the event on Esc because the dismiss path ran commit-on-close before the input's Esc handler could cancel. Handle `onEscapeKeyDown` on the Content with `event.preventDefault()` + your own cancel, and `onPointerDownOutside` for the click-away path; keep `onOpenChange` only as a discard fallback. → [src/features/calendar/ui/event-quick-create.tsx](../../src/features/calendar/ui/event-quick-create.tsx)
- **A Radix menu item that opens something which takes focus (a popover, an inline editor) must wait for the menu to close.** The closing menu returns focus to where it was (the list) in a 0 ms timer after it unmounts; a popover opened in `onSelect` reads that as focus outside and dismisses itself, and an editor that commits on blur commits and closes. The Tasks row menu's Schedule… / Set due date… / Move to bucket… / Rename all silently did nothing for months. Fix: `onSelect` only records the action; the content's `onCloseAutoFocus` calls `event.preventDefault()` and runs it. Related: Radix Popover now defers outside-pointer dismissal to the `click`, and a trigger whose `onClick` stops propagation never registers as an outside interaction, so Radix refocuses the trigger after a click-to-close; pass `onCloseAutoFocus={(e) => e.preventDefault()}` when your own close handler places focus. Regression test: [task-row-menu.test.tsx](../../src/features/tasks/ui/task-row-menu.test.tsx). → [task-row.tsx](../../src/features/tasks/ui/task-row.tsx)
- **`<input type="datetime-local">` fires change per keyboard segment edit** — committing in `onChange` writes garbage intermediates (year "0002") to the server, one RPC per keystroke. Draft-state + commit on blur/Enter, like the title-field pattern. → [event-detail-panel.tsx](../../src/features/calendar/ui/event-detail-panel.tsx)
- **Custom pointer-drag engines need three exits, not one:** `pointerup` alone loses the gesture when the button releases outside the window/over an iframe (sticky ghost + a surprise commit on the next click). Also handle `pointercancel`, self-heal on `pointermove` with `e.buttons === 0`, and re-measure cached rects per move (wheel-scroll mid-drag shifts them). NOTE for synthetic testing: dispatch moves with `buttons: 1` or the self-heal cancels your test gesture. → [calendar-grid.tsx](../../src/features/calendar/ui/calendar-grid.tsx)
- **SettingsModal (anything inside AppChrome) mounts → unmounts → remounts SEVERAL times during boot** (workspace-loading churn; three mounts observed live in one cold load, DF-3 2026-07-10 — and a workspace switch remounts AppChrome the same way via `WorkspaceGate`'s `loading → null`). Consequences: (1) a `window` CustomEvent dispatched during boot (e.g. the `/settings?section=…` redirect page's `dispatchOpenSettings`) is heard by a listener that unmounts moments later — the event is effectively lost; (2) a one-shot "pending" buffer consumed on mount is wiped the same way. Component state in AppChrome's subtree does NOT survive boot. Fix pattern (validator-hardened): a module-level **sticky** buffer that ONLY the deep-link path arms (`dispatchOpenSettings(detail, {sticky:true})`), every modal mount inside a 30s TTL re-applies, and a **user close disarms** (`clearPendingOpenSettings` from `onOpenChange(false)`/the ⌘, toggle) — buffering EVERY dispatch re-opens a modal the user explicitly closed on the next remount. Any future boot-time event → AppChrome-subtree consumer needs the same treatment (or the remount churn itself fixed — CC-13 boot-storm neighborhood). → [settings-events.ts](../../src/features/settings/settings-events.ts)
- **supabase-js reports PostgREST/REST failures via the result's `error` field — it does NOT throw.** A `catch` around `await supabaseClient.from(...).select(...)` only sees network-level rejections; destructuring just `{ data }` silently coerces a 500/expired-JWT-401/RLS error to "no rows", which reads as "no subscription"/"empty" downstream. If the distinction between *absent* and *failed* matters (it did in the SubscriptionGate — a paying user would have been paywalled on a transient error), check `error` and route it explicitly (`if (error) throw …`). Bit DF-3's gate fail-open (2026-07-10). → [app-gate.tsx](../../src/routes/layouts/app-gate.tsx)
- **`window.location.origin` inside the Tauri webview is `tauri://localhost` (macOS/Linux) or `http://tauri.localhost` (Windows) — never send it to an external service as a return/redirect URL.** Stripe rejects non-http(s) return_urls (and even if accepted, the link would dead-end in a normal browser). On desktop omit the URL and let the server-side fallback (`APP_URL`) win, or use the hosted web origin (`PUBLIC_WEB_ORIGIN`). Also: platform forks for "open this URL" should detect the desktop **shell** (`"__TAURI_INTERNALS__" in window`), not `getRuntime()?.capabilities` — the runtime singleton is null before init, and the web fallback (`window.location.href = url`) would navigate the whole Tauri webview to the external site with no way back. Both bit DF-3's Manage-billing button (validator, 2026-07-10). → [use-entitlement.ts](../../src/hooks/use-entitlement.ts) `openStripeUrl`/`isDesktopShell`
- **A command palette that mixes server-filtered results with cmdk items MUST run `shouldFilter={false}`.** cmdk's default filter scores every `CommandItem`'s `value` against the input — so a search result whose `value` is an id-based key (`entity:task:<uuid>`, needed for a stable/unique key) scores 0 against "water" and cmdk **hides it**, even though the server already matched it. DF-10's palette turns cmdk filtering off and filters the *static* nav/create actions itself (label-substring); entity results come pre-filtered from `searchEntities`'s `ilike`. Setting the result `value` to the label instead would re-enable cmdk filtering but collides on duplicate labels (cmdk uses `value` for selection/highlight) — the mention-picker hit this first and also runs `shouldFilter={false}`. Also: the shared **`CommandDialog` does NOT forward arbitrary props to its inner `Command`** — it spreads `...props` onto the Radix `Dialog`, not cmdk. DF-10 added an explicit `commandProps` pass-through (spread onto `Command`, className cn-merged) to reach `shouldFilter`. → [src/components/app/global-command-palette.tsx](../../src/components/app/global-command-palette.tsx), [src/components/ui/command.tsx](../../src/components/ui/command.tsx)
- **Live-verify caveat: in the preview pane a Radix Dialog can look "stuck open" after `setOpen(false)`.** The palette (a Radix `Dialog`) closed correctly on select in code, but `document.querySelector('[cmdk-input]')` still returned it in back-to-back `javascript_tool` reads — the pane's rAF/chained-timer throttle (already noted under Storybook/live-verify) defers Radix's close transition/state flush. A `computer{screenshot}` **forces progress** and the dialog then reads closed. Don't diagnose a close-on-select "regression" from DOM polling alone in the preview pane — force a repaint first, or verify in real Chrome. (DF-10, 2026-07-11.)

- **A page overrides a GLOBAL keyboard shortcut by claiming the key in the CAPTURE phase, not by registering "later".** `useGlobalShortcuts` (app-chrome) is a **bubble**-phase `window` keydown listener mounted once at boot; a page-level bubble listener mounted later STILL fires after it (same target+phase → registration order, and AppChrome always mounts first), so it can't win by ordering. To let a page's plain key beat a global one — DF-16's email `?` triage legend vs the app-wide `?` shortcuts sheet — register the page's listener in **capture** (`window.addEventListener('keydown', fn, true)`; the capture flag MUST match on `removeEventListener`) and `preventDefault()` what it handles; the global bubble handler reads `event.defaultPrevented` and bails. Guard the capture listener on modifiers (`metaKey||ctrlKey||altKey`) + typing targets so it only claims its own plain keys and every global ⌘-combo still passes through. → [src/features/email/ui/email-page-view.tsx](../../src/features/email/ui/email-page-view.tsx), [src/lib/shortcuts.ts](../../src/lib/shortcuts.ts)
- **A `?` / Shift+/ key matcher must accept BOTH `key==='?'` and `shiftKey && key==='/'`.** Most layouts resolve Shift+/ to `event.key==='?'`, but some keyboard layouts — and synthetic key events (the live-verify automation's `shift+/` did exactly this) — deliver `key==='/'` with `shiftKey` set. Matching only `'?'` silently misses the keypress. Caught in DF-16 live-verify (the sheet opened from the bus + button but not the synthetic `?` key until the matcher was widened). → [src/lib/shortcuts.ts](../../src/lib/shortcuts.ts) `help`
- **React bubbles `keydown` OUT of portals into ancestor `onKeyDown` handlers — a list's key handler also hears keys typed in its rows' popovers and context menus.** React propagates synthetic events along the React tree, not the DOM, so a Radix popover/menu rendered inside a row (portaled to `<body>`) still bubbles to the list container. The Tasks List did exactly this: Space or ⌘⌫ in a row's schedule popover date field completed or deleted the selected task, and arrows moved the cursor underneath. Guard the handler with `event.currentTarget.contains(event.target)` (the portal content isn't a DOM descendant), and bail on modified keys unless the list binds them: a list that `preventDefault()`s ⌘K hides it from `useGlobalShortcuts`, which skips default-prevented events. → [src/features/tasks/ui/list-keys.ts](../../src/features/tasks/ui/list-keys.ts) `listKeyActionFor`
- **Rendering `WorkspaceSwitcher` at 1 workspace re-exposes delete-the-last — `softDeleteWorkspace` has NO last-one guard.** DF-16 dropped the old `≤1 → return null` (so a single-workspace user finally sees their identity + ⌘⇧W works), which surfaced the per-row trash affordance for the only workspace; deleting it lands a **zero-workspace broken state** (the provider just calls `runtime.workspace.softDelete` + refresh). The UI gate is `workspaces.length > 1` on the trigger, folded into `isDeleteOpen`, AND on both confirm paths (Enter + the Del button) so a background 2→1 `refreshWorkspaces` (a teammate removing you) with an open delete panel can't slip through. The robust fix — a last-one guard in `softDeleteWorkspace`/`leaveWorkspace` themselves — **landed in DF-24**: both provider ops now `throw` when `workspacesRef.current.length <= 1` (read via a ref so their callback identity doesn't churn), so no caller (UI, a future MCP tool, a bulk op) can strand the user at zero. The UI gates (switcher `canDeleteWorkspaces`, the modal's `canLeave`) still hold as the first line; the provider guard is defense-in-depth. → [src/components/workspace-switcher.tsx](../../src/components/workspace-switcher.tsx), [src/providers/workspace-provider.tsx](../../src/providers/workspace-provider.tsx)

## Storybook / live-verify

- **After a big `git merge`/branch-switch mid-session, RESTART the rsbuild dev server before live-verifying — a hot-reload leaves it building against stale module content.** DF-21a merged 11 commits + reverted/deleted files while `dev:web` was running; rsbuild's incremental build got wedged on the *old* `notification-center.tsx` (errored on imports the current file no longer has, though `bun run typecheck` was green against disk). Compounding: `read_console_messages` returns an **accumulated buffer** — old `*.hot-update.js` link errors keep re-appearing after a reload and read as "live" when they're stale (the tell: they cite a hot-update chunk hash from the *previous* server process). Fix: `preview_stop` → `preview_start` for a clean build, then trust a fresh screenshot (the app rendering + the feature working) over the console buffer. `preview_logs {level:'error'}` on the CURRENT serverId is the authoritative build-status source, not the browser console.
- **The preview-MCP browser can report `window.innerWidth === 0`** (persistently, not just pre-paint), so every viewport-driven component mounts in its narrow/sheet mode — `FeaturePanelsShell` rendered the NO-3 notes sidebar as a Sheet at a "1280px" viewport because the app measured 0 at mount. It is a preview-tool artifact, not an app bug: the same build in a real Chrome (claude-in-chrome MCP) laid out correctly. When a layout looks inexplicably mobile in the preview, check `window.innerWidth` via preview_eval BEFORE debugging breakpoints; fall back to the Chrome MCP for viewport-sensitive verification.
- **`getComputedStyle()` LIES about a transitioned property right after you flip a token/theme attribute — it can report the pre-change value indefinitely, so a token fix reads as "didn't work".** Verifying the light+mono accent fix (2026-07-27), flipping `data-theme` and reading the primary button's `backgroundColor` kept returning the OLD white — after a 700ms settle, with `--motion-fade` only `.1s`. The button was in fact painted correctly; every *other* signal agreed (the element's own computed `--primary` was the new near-black, and a bare `<div class="bg-primary">` probe in the same subtree resolved near-black). The culprit is the `transition-[…background-color…]` on `Button`: when the underlying **custom property** changes, the running transition's computed value can go stale. Two ways to get the truth: set `el.style.transition='none'` + force a reflow (`void el.offsetHeight`) and re-read, or — best — take a **screenshot** and look. Rule: when a computed-style read contradicts the element's own resolved custom property, trust the custom property and the screenshot, not `backgroundColor`/`color`. Don't "fix" working CSS because of this.
- **A *scoped* `data-accent` wrapper silently defeats theme-compound accent rules.** `preWorkspace()` (route-tree.tsx) puts `data-accent="mono"` on a `display:contents` div so out-of-gate pages stay monochrome. That wrapper carries **only** `data-accent`, so a rule keyed on `[data-theme="light"][data-accent="mono"]` (both attrs on `<html>`) never matches it — and the wrapper's own plain `[data-accent="mono"]` (0,1,0), being a *closer* ancestor, wins for the whole subtree. Any theme-dependent accent rule therefore needs BOTH forms: `[data-theme="light"][data-accent="mono"]` **and** the descendant `[data-theme="light"] [data-accent="mono"]`. Same trap for any future scoped-accent surface. Related: a custom property declared with `var()` resolves on the element that declares it and inherits already computed, so a token derived from `--primary` and declared only on `:root` ignores a scoped `data-accent`. Since DS-1 the derived tokens (the state layer and `--selected-*`) are re-declared on `:where(:root, [data-theme], [data-shade], [data-accent])` (tokens.css §5b, zero specificity), so they re-resolve in any wrapper that carries one of those attributes. A wrapper that sets `--primary` some other way (a class, an inline style) still leaves them on the outer value; add the attribute instead. → [tokens.css](../../src/styles/tokens.css), [route-tree.tsx](../../src/app/router/route-tree.tsx)
- **A `TooltipTrigger asChild` overwrites its child's `data-state` with the tooltip's (`"closed"`/`"delayed-open"`), so `data-[state=on|open|active]:` styles on a wrapped Radix item silently never match.** This is why the icon-only view switcher showed no current segment: every SegmentedControl item in icon-only mode sits in a tooltip, and `data-[state=on]:bg-…` never applied (the plain-text switcher, which has no tooltip, looked fine). Key a wrapped control's state on its ARIA attribute instead, since Radix keeps those: `aria-checked:` (toggle/radio items), `aria-selected:` (tabs), `aria-expanded:` (menu triggers). The same trap applies to any IconButton (always tooltip-wrapped) styled with `data-[state=open]:`. `segmented-control.test.tsx` reproduces it in jsdom. (DS-2, 2026-10-08.) → [src/components/ui/segmented-control.tsx](../../src/components/ui/segmented-control.tsx)
- **A translucent state fill REPLACES an opaque rest fill, it doesn't stack on it.** `hover:bg-state-hover` on a control that rests on `bg-muted` or `bg-card` swaps the opaque grey for 5% foreground over the page, which is usually DARKER than the rest. A filled control hovers one step up the ladder instead (`bg-state-active` → `bg-state-active-hover`), or uses an opaque hover. When checking a transitioned fill in the browser, disable transitions first (`*{transition:none!important}`): getComputedStyle keeps returning the pre-change colour (see the Storybook/live-verify entry). (DS-2.) → [src/styles/tokens.css](../../src/styles/tokens.css) §5b
- **In Tailwind v4, `aria-*:` and `data-*:` variants are emitted after `hover:`, so with equal specificity the current/open state wins over hover.** For example, the settings nav's `hover:bg-state-hover data-[state=active]:bg-state-active` keeps the current item on the active step while it is hovered. A state set by a JS conditional (`active ? … : "hover:…"`) needs no ordering at all. (DS-2.)
- **A full-strength hover edge outshines the translucent selection ring.** `SELECTED_OPTION` draws the selected option with a 32% `ring-state-selected` on a transparent border, so an unselected neighbour that hovers to `hover:border-foreground` (100%) reads STRONGER than the one you picked: the booking page's days, times and video options did exactly that after DS-2. When an option moves onto the selection recipe, drop its hover edge below the ring (`hover:border-foreground/30`, as task cards do). (DS-2 review, 2026-10-08.) → [src/components/ui/selection.ts](../../src/components/ui/selection.ts)
- **jsdom can't test how a custom property resolves.** `getComputedStyle` there returns the raw declared text (`color-mix(…var(--primary)…)`, no `var()` substitution) on the element that declares it and an empty string on its children (no inheritance). Token scoping tests read the stylesheet structure and compile the utilities with Tailwind's `compile()` instead (`src/styles/tokens.test.ts`); the resolution itself is checked in a real browser. (DS-1, 2026-10-08.)
- **supabase-js is fetch-stubbable at runtime** — patching `window.fetch` in the page DOES intercept its REST/RPC calls (it resolves fetch late), so unapplied-migration surfaces can be live-verified end-to-end with an in-page fake backend: stub `/rest/v1/rpc/<op>` + the new-column SELECTs, then remount the page **via SPA navigation** (nav to another module and back) — a hard reload wipes the stubs, but an SPA remount re-runs the module load through them. (NO-3 was verified this way: capture → CRDT push → rename → trash/restore, all against stubs.)

- **Chrome-MCP screenshots with `save_to_disk: true` return an ID but no retrievable file path** (nothing lands in ~/Downloads, the scratchpad, or Application Support — checked during DF-14), and `zoom` + `save_to_disk` can outright fail via CDP. Treat the session transcript as the canonical home for before/after visual evidence (screenshots embed inline there); don't promise separate image files from a live-verify run. For a before/after pair, `git stash` → capture → `git stash pop` works fine with the dev server's HMR.
- **Storybook rendered nothing — `Failed to fetch dynamically imported module: /.storybook/preview.tsx`. ## React effects

- **`act(() => api.fn())` turns into an un-awaited async `act` the day `fn` starts returning a promise, and it breaks the NEXT test, not this one.** React sees the thenable, warns "You called act(async () => ...) without await", and leaves its act scope open; the following test's `renderHook` then never commits (`result.current` is `null` → "Cannot read properties of null"), so the failure points at an innocent test. TV-T1 hit it when `createTask` began returning the saved task's promise. Write test callbacks that call an API for its side effect with a block body: `act(() => { api.fn(); })`, or `await act(async () => …)` when you want the result. To find the culprit, run the failing test alone (it passes) and pair it with each earlier test by `--testNamePattern`. → [use-tasks-module.test.tsx](../../src/features/tasks/hooks/use-tasks-module.test.tsx)
- **`useSyncExternalStore`'s `getSnapshot` must return the SAME value until the store changes — never an inline `() => []` / `() => ({})` / `() => new Set()` fallback.** A fresh array on every read looks like a change, so React re-renders, reads again, and dies with **React #185 "Maximum update depth exceeded"** (dev also logs "The result of getSnapshot should be cached"). Chat shipped this to prod (2026-10-06): the typing store fell back to `() => []` while the realtime link was still `null`, so the page crashed on every load. - **An effect that owns a debounce timer must NOT list an inline callback prop in its deps** — every parent re-render (a sync-status flip, any state change) re-runs the effect, and the cleanup clears the pending timer, so the debounced call can starve FOREVER under steady re-render pressure. - **A `useCallback` that BOTH sets a piece of state AND lists that state in its deps, fired from its own effect, is a self-cascade — it re-fetches on boot.** `WorkspaceProvider.refreshWorkspaces` depended on `selectedWorkspaceId` (to preserve the current selection) and *set* it; its boot effect listed `[refreshWorkspaces, …]`, so the `null → resolved` selection change recreated the callback → re-ran the effect → a second `workspace.list()`. - **A `reqRef` request counter drops stale replies, not replies that land after unmount — bump it in the cleanup of the effect that runs the loader.** The calendar loader guarded every late `set*` with `reqRef.current === req`, but nothing bumped the counter on unmount, so its un-awaited busy-overlay RPC could still `setBusy` after a test's jsdom was torn down. - **A `reqRef` guard stops a stale reply from landing, but not what the previous workspace already wrote — tag that state with the workspace it was fetched for and filter on read.** The calendar's busy overlay lands after `loading` settles (it must never hold the calendar up), so on a w1 → w2 switch w1's busy blocks sat next to w2's events until w2's reply came.
