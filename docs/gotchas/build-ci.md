# Gotchas: Build, CI and desktop release pipeline

Read before working in `.github/`, `scripts/`, `package.json`, `rsbuild.config.ts`. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Repo / build

- **Landing: a prod-landing PR merged from Maciej's account doesn't deploy.** Vercel builds only commits whose git author is on Mike's Vercel team, and `gh pr merge` writes a merge commit authored by En5hi (seen on #306, 1c45ca6c). The PR's own Vercel check can also fail on the Hobby plan's daily build limit, which isn't a build failure. Prefer Mike merging with "Create a merge commit"; if you merge it yourself, tell Maciej that Mike has to redeploy that commit. Reproduce the build locally instead of retrying: `MODUO_BUILD_TARGET=landing VERCEL_GIT_COMMIT_REF=prod-landing node scripts/vercel-build.mjs`.
- **Desktop CI: Apple's notarization queue, not the compile, is what makes the Mac build slow.** A cached universal compile takes about 4 minutes and a cold one about 8; runs that sat for 40–75 minutes were all waiting on `notarytool --wait`, and the old workflow waited twice (Tauri notarized the `.app`, then a second step notarized the `.dmg`). The build now makes one submission (the `.dmg`, which covers the `.app` inside), waits up to 20 minutes, and hands anything slower to the `notarize-mac` job, which waits on the same submission id. If that job times out, use **Re-run failed jobs**: it never rebuilds or resubmits. Don't pass `APPLE_ID`/`APPLE_PASSWORD` to `tauri build`; that turns the `.app` notarization back on. See `_desktop-release.yml` and `scripts/ci-macos-notarize.sh`.
- **Desktop CI: don't pass `APPLE_CERTIFICATE` to `tauri build` when the workflow already imported the cert.** Tauri imports a second copy into its own temporary keychain, and in run 37636171897 `codesign` hung on "replacing existing signature" for 1.5 hours, until the run was cancelled. Import once (keychain with partition list, no auto-lock) and give Tauri only `APPLE_SIGNING_IDENTITY`. The import step test-signs a throwaway binary with a 90-second cap, so this fails fast if it ever happens again.
- **Desktop CI: `HTTP status code: 401. Invalid credentials` from notarization means the Apple app-specific password is wrong or revoked.** Apple revokes app-specific passwords when the Apple ID password changes. Generate a new one at appleid.apple.com and update the `APPLE_ID_PASSWORD` secret, or add an App Store Connect API key (`APPLE_API_KEY_ID`, `APPLE_API_ISSUER`, `APPLE_API_KEY_P8`), which the script prefers and which isn't tied to the Apple ID password. The login check runs first and fails within seconds.
- **Desktop CI: in a `shell: bash` step on Windows, `${{ github.workspace }}` loses its backslashes.** `D:\a\Moduo\Moduo` turned into `D:aModuoModuo` and `tauri build --config` failed. Use `"$GITHUB_WORKSPACE"` quoted, or `$RUNNER_TEMP`.
- **Desktop CI: `export X="$(cmd)"` hides a failing `cmd`.** `export` returns 0, so an updater-key script that failed would have left the key empty. Assign first (`KEY="$(cmd)"`), then export.
- **Desktop CI: `Swatinem/rust-cache` doesn't save the cache when the job fails, unless you set `cache-on-failure: true`.** After the toolchain change every desktop run failed at signing, so nothing was saved and Windows kept compiling cold (about 17 minutes instead of about 5).
- **Desktop CI: "The job was not started because recent account payments have failed or your spending limit needs to be increased" is a GitHub billing block.** It stops every job, `checks` included, within seconds, and it can't be fixed in the repo. Fix it under the account's Billing & plans settings, then re-run.
- **Tauri rejects the updater private key when anything follows its `=` padding.** The key from `tauri signer generate` is one base64 line. A trailing character after `==` (a second pasted value) fails the Windows build with `Invalid symbol 61, offset …` after the installer is already built, and the signature is discarded. CI runs `scripts/ci-normalize-updater-key.sh` before `tauri build`. The public half of that same key has to be the `pubkey` in `tauri.conf.json`, or the app will not trust the update.
- **Entire.io repo Analytics follow GitHub's default branch, which is `develop`.** Home and Sessions show every branch; Overview/Analytics/Commits do not. Work that stays on `mike`/`maciej`/`t/*` looks like "empty analytics" even when capture is healthy. Land bigger chunks on `develop` (`/s3` step 5b). Do not retarget GitHub's default without an explicit ask. → [docs/entire.md](../entire.md)
- **Closed domain vocabularies live in `supabase/functions/_shared/contracts/` (`@contracts/*`), not in ad-hoc feature unions.** Add/remove a status/role/tier in `vocabularies.ts` + tests + any Postgres CHECK together. Leave polymorphic entity types, IMAP folders, Stripe event names, and opaque prefs as open strings. Runtime mappers parse those closed fields with Zod (`rows.ts`); a bad list row is skipped, a bad mutation payload throws. Hosted Edge Functions do not pick up those parsers until they are redeployed.
- **Edge Functions that `import { z } from "zod"` must deploy with `--import-map supabase/functions/deno.json`.** Without it the hosted bundler fails (`Relative import path "zod" not prefixed`). Keep `--no-verify-jwt` for functions that do their own auth (JWT / Stripe signature / `moduo_sk_` / public token).

- **Biome 2.5.6 is the JS/TS linter+formatter and part of `bun run verify`** (`bun run lint:js` = `biome check .`). It FAILS on error-level diagnostics only — warnings (currently ~210: a11y, `useExhaustiveDependencies`, `noArrayIndexKey`) are a burn-down budget, not blockers. Run `bun run format:fix` (= `biome check --write .`) to auto-apply format + import organization + safe fixes. Never hand-fix formatting — let the tool own it.
- **`storybook-static/` is TRACKED in git** — a committed Storybook build export with minified vendor bundles. It polluted every repo-wide tool's scan (Biome initially reported 24k "errors", 13k of them from these bundles). Excluded in `biome.json`; consider un-tracking it + gitignoring when someone owns that decision (it predates Biome). Also: Biome's CSS parser **loses to Tailwind v4 at-rules** → `!**/*.css` excluded (stylelint owns CSS).
- **Linter-drain loops (`while ((match = regex.exec(s)))` / `while ((next = iterator.next()))`) trip `suspicious/noAssignInExpressions`** — DON'T "fix" by moving the assignment to loop end when the body uses `continue`/`break` (the continue skips the re-read = infinite loop). Suppress with a scoped `// biome-ignore lint/suspicious/noAssignInExpressions: <idiom> idiom` (see `ics-mirror.ts`, `check-arbitrary-tw.ts`).
- **Iterating callbacks must not implicitly `return` values** (`lint/suspicious/useIterableCallbackReturn`): inside `.forEach`/`.map`/`.flatMap` use a braced body `arr.forEach((x) => { doAsync(x); })`, or explicit `void doAsync(x)` — members with implicit returns are gate-blocking errors.

- **React Compiler v1.0 is enabled (`reactCompiler: true` in `rsbuild.config.ts`).** It validates the Rules of React at build time and auto-memoizes components. Violations surface as **warnings** (not errors) in the terminal during `rsbuild dev`/`rsbuild build`. Existing `useMemo`/`useCallback` calls become no-ops under the compiler — leave them in place during initial adoption (removing them is a separate cleanup). The compiler is incompatible with Legend State's `use$` hook (use `useValue`/`observer` instead) — but Legend State is not yet installed. If you add a new library that uses unusual React patterns, check for compiler warnings in the dev terminal. → [specs/toolchain-upgrade-react-compiler.md](../../specs/toolchain-upgrade-react-compiler.md)

- **Compiler-forbidden idioms (fixed TC-2; don't reintroduce):** (1) `const xRef = useRef(x); xRef.current = x` at render scope → write inside `useEffect(() => { xRef.current = x })` instead (reading inside event handlers/effects stays fine). (2) `useState(() => factoryThatCapturesRefs())` / `useMemo(() => new StatefulEngine())` → the SWC refs-analysis treats closure-captured refs in initializers as render-time access; construct in a mount effect (see `use-email-compose.ts` hold pattern). Two **deliberate leaves**: `use-notes-module.ts` engine `useMemo` (lifetime restructure not worth it) and `tasks-plan-view.tsx:142` one-shot deep-link ref reads (`inboundPending` — arrival-flush semantics intentionally depend on render-time visibility). Files whose ONLY failures are try/finally / throw-in-catch / dynamic-import / PruneHoistedContexts / computed-destructuring are **SWC port TODOs — do NOT rewrite valid code**; they self-resolve as `@rsbuild/plugin-react` ships new SWC. Probe your file list any time with `reactCompiler: { panicThreshold: "all_errors" }` (temporarily — it FAILS the build).

- **Route-level code splitting lives in `src/app/router/route-tree.tsx`** — `/notes` `/email` `/mindmap` `/p/$token` load via `lazyRouteComponent(() => import(page), "NamedExport")`. Adding a new heavy route (editors, XYFlow, markdown extremes) → same pattern; adding a heavy dep inside an EAGER route pulls it back into the 675 KB gzip entry — check chunk output after. 13 async chunks currently.

- **TanStack Router: an object `search` in `navigate()` REPLACES the whole query string.** `navigate({ to: "/contacts", search: { action: "new" } })` silently wipes an existing `?type&id` selection. When adding one param on a route that carries others, use the functional updater: `search: (prev) => ({ ...prev, action: "new" })`. Bit FX-1 (the palette's New-contact wiped the open contact's selection); `/contacts` is the app's first search-param route, so every future `navigate` targeting it must think about this.

- **`preview_start` in a `.claude/worktrees/*` session has two failure stages — only the first is fixable.** (1) `Port 8081 is in use by another chat's dev server` → fixed for good 2026-07-02: `.claude/launch.json`'s "web" config uses `autoPort: true` + a port-flag-free command, and `rsbuild.config.ts` honors an assigned `PORT` env (default stays 8081). (2) `EPERM: uv_cwd` → **not fixable from the session**: the preview sandbox binds to whichever worktree owns the currently *active* dev server, so while another chat serves :8081 the sandbox can't even `cwd` into yours. Do not kill the other session's rsbuild (that trap already bit us — Session 10). Workaround: `bun install` in the worktree, run `MODUO_TARGET=web ./node_modules/.bin/rsbuild dev --host 127.0.0.1 --port <free>` via Bash background, drive with the Chrome MCP, kill by the **exact port-specific** pattern when done.
- **Never import a bare `{ runtime }`.** Always resolve via `getRuntime()`. The bare export was an always-null const footgun; grep `./runtime` when auditing lib exports. → [data-layers.md](../data-layers.md)
- **A "reset local cache" that clears `moduo.appearance` also nukes the device-local display prefs (density / text-size / tab style) that deliberately never sync to cloud** — so on reload they snap back to defaults while theme/accent/font re-adopt from cloud. They ride *inside* the same `moduo.appearance` localStorage blob (appearance.ts: "per-device fields never leave localStorage"), so a key-prefix clear can't spare them. DF-19g's reset owns this by **disclosing it in the confirm copy** ("device-only display settings reset to defaults"), not by silently dropping them — the designer treats density as a first-class customization axis. Any future cache-wipe that touches `moduo.appearance` must either preserve the device subset or say so. → [advanced-section.tsx](../../src/features/settings/sections/advanced-section.tsx)
- **Deleting the Notes IndexedDB is only safe once the outbox is empty — and the guard must count BOTH outboxes across ALL workspaces.** The per-note y-indexeddb doc DBs (`moduo:notes-v2:doc:*`) hold local CRDT state; `deleteDocOutboxEntries` runs only *after* a successful `pushUpdates` (engine-v2), so an empty `docOutbox`+`metaOutbox` provably means every local edit reached the cloud and the doc DBs can be dropped losslessly. DF-19g's reset gates on `countPendingOutbox()` (idb.ts) which counts globally because the delete is global; the blocked-dialog path removes the reset button entirely (not just disables it) so there's no code path from pending>0 to a delete. Caveat it can't cover: an edit stranded in the engine's in-memory `memOutbox` (a transient IDB-write failure) is invisible to a durable-store count. Also `indexedDB.databases()` is unsupported on Firefox/older Safari → there only the named `moduo-notes-v2` is deleted, per-note doc DBs survive (harmless: outbox empty, cloud is truth). → [advanced-section.tsx](../../src/features/settings/sections/advanced-section.tsx), [idb.ts](../../src/features/notes/sync/idb.ts)
- **redb is paused — never make it load-bearing** for a new feature. New models are Supabase-first; redb is kept only for the future offline/"lite" version and not-yet-migrated legacy modules. → [data-layers.md](../data-layers.md)
- **~~Vitest has no `@/` alias~~ — FIXED 2026-08-14 (DF-18). `rstest.config.ts` now mirrors tsconfig's `@/* → ./src/*`,** so value imports of `@/lib/*` and component `.tsx` files resolve under `bun run test` (that's what made `src/components/ui/*.test.tsx` render tests possible at all). The old rule — "anything reachable from a `*.test.ts(x)` must import `lib/*` relatively" — **no longer applies to new code**. Two things it leaves behind: (a) existing code shaped by the old trap still uses relative paths (`spine/activity.ts`, `spine/suggest.ts`, the self-contained `dashboard/engine/`, `keyScope` in a pure `api-keys.ts`, the hand-rolled `<button>` in `lib/undo-toast.tsx`) — correct, just no longer required, and unwinding them is optional cleanup, not a fix; (b) the alias is scoped to the test graph — **always verify with `bun run test`.** Storybook's own vite config is separate and still lacks the alias (see §Live-verify).
- **A unit test MAY now import a component `.tsx`** (see above) — `src/components/ui/eyebrow.test.tsx` / `detail-title.test.tsx` render real primitives via `@testing-library/react`. Extracting pure logic into a `.ts` is still the better default for *logic*; it is no longer a workaround for a resolver limitation. (Superseded 2026-08-14; was DF-19d, 2026-07-11.)
- **Testing time-based code under Rstest: `rs.useFakeTimers()` fakes `Date` too, so model a throttled or suspended timer with `rs.setSystemTime(Date.now() + ms)` and then `rs.advanceTimersByTime(1000)`.** `setSystemTime` moves the wall clock *and* shifts every pending timer by the same amount, so exactly one tick fires after the jump — a hidden tab whose timer ran once a minute, or a machine waking from sleep. Second trap: an `async` helper that `await`s a value that's already synchronous still yields a microtask, and synchronous `advanceTimersByTime` doesn't run microtasks between timers, so the caller strands half-way and later timer-driven calls see it as still running (TV-F1's periodic flushes silently skipped until `runSink` only awaited real promises). Await only when it's a promise; use `advanceTimersByTimeAsync` when the code under test really is async. → [src/features/focus/engine.test.ts](../../src/features/focus/engine.test.ts)
- **The local done-check is `bun run verify`** (typecheck + lint:tw + lint:css + unit tests) — it mirrors CI's gate. CI does **not** run the e2e / visual-snapshot / billing suites (those stay local/manual), so a green PR doesn't cover them.
- **A unit test that mounts code calling `supabaseClient` directly is talking to prod: `runtime.web.ts` falls back to the prod URL and publishable key when no env is set.** `use-calendar-module.ts` fetches its busy overlay with `supabaseClient.rpc("calendar_busy_blocks")`, outside the runtime its test fakes, so every run of that test made a live call. When the reply arrived after the jsdom environment was torn down, `setBusy` threw `window is not defined`, the worker died, and `bun run test` exited 1 with every test passing (once in seven full runs on 2026-10-08; never with the file run alone, because the worker exits before the reply lands). Stub the client in the test (`rs.spyOn(supabaseClient, "rpc")`), or better, route the call through the runtime. → [use-calendar-module.window.test.tsx](../../src/features/calendar/hooks/use-calendar-module.window.test.tsx)
- **After a big `bun.lock` change, reinstall from scratch: `rm -rf node_modules && bun install --frozen-lockfile`.** An install over the old tree can skip nested packages the new lock adds. After the 2026-10-07 toolchain bump that left `stylelint/node_modules/globby` without its own `unicorn-magic` 0.4, so `bun run lint:css` crashed with `ERR_PACKAGE_PATH_NOT_EXPORTED` (`./node` of `unicorn-magic`) though CI, which installs fresh, passed. A crash inside `node_modules` right after pulling a lockfile change is the install, not the code.
- **Dead-code sweeps: "is it mounted?" is not "is it alive?" — trace the OUTPUT, not just the importers.** `useSlotBookingsSync` was mounted in `app-gate.tsx` (so import-graph tools call it live) yet its entire effect was writing a localStorage key with zero readers — and it PATCHed `slot_bookings.calendar_synced=true` server-side for rows that surfaced nowhere, actively corrupting the "unsynced" signal for any future re-implementation. When sweeping, follow each candidate's *sinks* (storage keys, tables, events) to a real consumer before calling it live. Also: `bun run verify` catches zero Rust breakage — any sweep touching `src-tauri` needs its own `cargo check` (CLEAN-1, 2026-07-03).
- **A code-graph / import-graph "isolated, prune-safe" verdict can miss a compile-only coupling into a load-bearing module — re-verify with `rg` before deleting.** Graphify (and the backend memo it fed) reported `graph_helix`/`embeddings` as "isolated, in no coupling hotspot, touches zero feature code." They were **runtime-dead** but **compile-coupled**: `graph_helix` was woven into the **live email engine** via `commands/email/graph_outbox.rs`, called from ~11 sites across `email.rs`/`sync.rs`/`realtime.rs`, and `queue_graph_upsert_for_envelope` wrote an `email_graph_outbox` redb row on *every* envelope sync (only the *flush* was gated behind `graph.is_enabled()`, false without `HELIX_SIDECAR_PATH`). Removing `helix-rs` therefore required excising that dead tendril from email — not the "zero feature code" the graph claimed. The graph counts *edges it saw*; a subsystem whose outputs nothing reads (dead) can still be *written to* from live code (coupled). When a graph says "safe to delete," still `rg` every symbol (types, redb tables, command fns) for writers, not just readers, before cutting (proposal C, 2026-07-11). → [docs/decisions.md](../decisions.md)
- **`src-tauri` has a `lite` Cargo feature (off by default) — the redb↔Supabase `sync` worker compiles only under `--features lite`.** `cargo check`/`build` in the **default** (cloud) config does NOT compile `src/sync/mod.rs` or the `AppState.sync_worker` field / `auth.rs` start-stop paths (all `#[cfg(feature = "lite")]`). If you edit `sync/` or anything gated for the future offline/"lite" build, a default `cargo check` won't catch breakage there — run `cargo check --features lite` too (proposal C, 2026-07-11). → [src-tauri/Cargo.toml](../../src-tauri/Cargo.toml)
- **Visual-snapshot PNG baselines are NOT generated in CI** and are platform-suffixed (`*-visual-darwin.png`). Capture is a deliberate human `bun run e2e --update-snapshots` run on the canonical env. A visual diff means **stop and ask**, never auto-accept/regenerate.
- **macOS Liquid Glass app icon has been lost in merges twice.** It lives in-repo at `scripts/icons/source/Moduo.icon`; regenerate with `bun run icon:liquid` (needs full Xcode for `actool`). Don't let a merge drop it.
- **The desktop bundle's frontend must be built with `MODUO_TARGET=desktop`, into `dist/` — a stale `dist/` masks the bug.** `rsbuild.config.ts` routes the *web* target to `dist/web/` and the *desktop* target to `dist/` (frontendDist=`../dist`), AND aliases `@tauri-apps/api/core` to a throwing stub whenever `MODUO_TARGET=web`. So building the frontend with `build:web` (the old `beforeBuildCommand`) put `index.html` in `dist/web/` and left `dist/` empty → a clean `bun run build:desktop` embedded no assets → runtime **"asset not found: index.html"**; even if it had loaded, `invoke()` would throw `[tauri-stub]`. Fixed 2026-07-13 by pointing `beforeBuildCommand` at a new `build:desktop:web` = `MODUO_TARGET=desktop rsbuild build`. All three desktop entry points (`build:desktop`, `build:desktop:signed:{debug,release}`) funnel through `beforeBuildCommand`, so they're all covered. The trap hid because the main checkout usually has a stale `dist/index.html` from a prior `dev:desktop`/manual build; only a fresh tree (or `rm -rf dist` first) reproduces it. Verify desktop frontend builds by confirming `dist/index.html` exists AND the bundle contains `__TAURI_INTERNALS__` (real API), not `called in web build` (the stub). → [rsbuild.config.ts](../../rsbuild.config.ts), [src-tauri/tauri.conf.json](../../src-tauri/tauri.conf.json)
- **A `PUBLIC_*` var that `rsbuild.config.ts` defines reaches the bundle as `""` when it's unset, not `undefined` — so `import.meta.env.X ?? fallback` never falls back.** Every var in its `source.define` block is read with `readLocalEnvValue` (which returns `""` when the var is missing) and defined as `JSON.stringify(value)`. `lib/analytics.ts` used `PUBLIC_POSTHOG_HOST ?? "https://app.posthog.com"`, so a build with the key but no host would have sent events to the app's own origin, not to PostHog. Use `(import.meta.env.X ?? "").trim() || fallback`. Tests can't see this on their own: Rstest compiles `import.meta.env` to `process.env`, where an unset var is `undefined`, so a test only catches it by stubbing the var as `""` (`rs.stubEnv`), as `analytics.test.ts` does. → [analytics.ts](../../src/lib/analytics.ts)
- **`performance.prefetch: { type: "async-chunks" }` prefetches EVERY dynamic import, including code that must not download until a user agrees.** Rsbuild writes a `<link rel="prefetch">` for each async chunk into `index.html`, so after the first paint the browser downloads all of them, posthog-js included, even though `lib/analytics.ts` only `import()`s it after consent. The code never ran, but "not downloaded until you say yes" was false. Fix: name the chunk (`import(/* webpackChunkName: "posthog" */ "posthog-js")`) and add it to `prefetch.exclude`, keeping Rsbuild's default `/\.(?:webmanifest|pdf|txt)$/i` because setting `exclude` replaces it. Check with `MODUO_TARGET=web rsbuild build` and grep `dist/web/index.html`. Dev-mode lazy compilation also loads a tiny `…posthog-js…lazy-compilation-proxy.js` stub at start; that's dev-only, not the library. → [rsbuild.config.ts](../../rsbuild.config.ts)
- **A green Vercel check on `staging-app` doesn't mean app.staging.moduo.app serves that commit.** On 2026-10-08 the check on `staging-app`'s head (bf3b7d57) read "Deployment has completed", and its own deployment URL served the new files, yet app.staging.moduo.app still served an older bundle (`index.99737fd876.js` against the head's `index.6fb4a206d9.js`). The `staging-app` builds are listed as Preview deployments, and the staging domain didn't follow them. To prove a change is deployable, read the deployment URL from `gh api repos/GrochowskiMichal/Moduo/deployments/<id>/statuses` (the `environment_url` of the deployment whose `sha` is the head) and curl that. To prove it's live, curl the real domain and compare the `static/js/index.*.js` name. app.moduo.app changes only when someone runs "Promote to production → app". (2026-10-08, TX-2)
