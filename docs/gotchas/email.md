# Gotchas: Email engine and import

Read before working in `src/features/email/`, email commands in `src-tauri/`, or the transactional email kit `supabase/functions/_shared/email/`. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Email engine (EM-1)

- **lettre's `MessageId` / `in_reply_to` / `references` headers emit the value VERBATIM — they do NOT add angle brackets.** lettre's *own* default Message-ID is `format!("<{}@{}>", …)` (already bracketed), so `.message_id(Some(id))` expects the bracketed form and passes it through. Stripping brackets (the instinct that "lettre re-wraps") emits `Message-ID: id@host` — RFC-invalid, and it breaks threading + the Sent-copy match the follow-up tracker relies on. Pass `<id@domain>`; and skip blank ids (an empty string → a malformed `<>` token). Confirmed by unit test on `message.formatted()` bytes (the only way to assert lettre header shape). → [src-tauri/src/commands/email/smtp.rs](../../src-tauri/src/commands/email/smtp.rs)
- **Never construct a lettre recipient header via the tuple `header::To(mboxes)` — the field is `pub(crate)`.** From outside lettre, use `header::To::from(mboxes)` (the `From<Mailboxes>` impl); `Mailboxes::new()` + `.push()` builds the list. Also: `MultiPart::mixed()` returns a *builder* — its first `.singlepart`/`.multipart` finalizes to a `MultiPart` that further parts chain onto (don't reassign a `MultiPart` to a `MultiPartBuilder` binding). `.singlepart`/`.multipart` return `Result` (missing From/Date), so `?` them. → [src-tauri/src/commands/email/smtp.rs](../../src-tauri/src/commands/email/smtp.rs)
- **The email secret keychain scope is `email_{user_id}_{account_id}` — NEVER migrate/wipe a legacy secret without an authenticated session.** Legacy secrets were stored un-scoped in redb (`secret::{account_id}`). The lazy migration writes them into the *current user's* keychain scope and wipes redb; if the session is momentarily absent, `session_user_id` is `None` and migrating under a fallback scope would strand the secret once a real user id returns (the account would falsely flip to `reauth_required`, orphaning a keychain item). `resolve_secret(user_id: Option<&str>, …)` returns the legacy secret **read-only** (no keychain write, no wipe) when there's no session; migration waits for a real user id. Same "never drop a secret" rule as the locked-keychain case (`get_secret` maps a locked keychain to `Ok(None)`). → [src-tauri/src/commands/email/secrets.rs](../../src-tauri/src/commands/email/secrets.rs)
- **The email accounts list is an unlocked read-modify-write** (`read_accounts` → mutate one row → `write_accounts` the whole vec). Two concurrent sends, or a send racing the IDLE worker's `patch_account_sync_state`, can interleave and clobber a `status`/`last_sync_at`/`last_error` update. **Pre-existing** (the legacy `email_send_saved` + `patch_account_sync_state` do the same); `email_send_message` inherits it. Benign at single-user desktop scale; the real fix is a per-account patch under the store write-guard — a tracked follow-up, not an EM-1 blocker. → [src-tauri/src/commands/email/storage.rs](../../src-tauri/src/commands/email/storage.rs)

## Email engine (EM-2/4/5)

- **OAuth token refresh MUST be an async pre-step — not inside `ensure_account_config`.** `reqwest::blocking` panics when called from a tokio async-worker thread ("Cannot start a runtime from within a runtime"), and `ensure_account_config` is sync yet runs on the async command thread (send_commands.rs) as well as inside `spawn_blocking` — so it can neither block-refresh nor `.await`. The refresh (`email::oauth::ensure_fresh_access`, async reqwest) is therefore called at the **top of each async command** (`email_send_message`, `email_sync_now`, `email_list_envelopes` force-sync, `email_apply_message_op`, `email_list_folders`) BEFORE any config build / `spawn_blocking`; it re-saves the keychain secret, and `ensure_account_config` just reads the now-fresh token. The IDLE worker (a plain bg thread) does NOT refresh — it reads the stored token best-effort and drops if stale (foreground syncs refresh). Don't move the refresh into the sync config path. → [src-tauri/src/commands/email/oauth.rs](../../src-tauri/src/commands/email/oauth.rs)
- **`References` is NOT in the IMAP ENVELOPE — parse it from the fetched HEADER.FIELDS block.** The ENVELOPE carries `message_id` + `in_reply_to`, so the pre-EM-4 fetch read those from `item.envelope()` and never touched the `BODY.PEEK[HEADER.FIELDS …]` bytes. References (needed for root-keyed threading) only lives in the header — add `REFERENCES` to the fetch and read `item.header()` (the section bytes) via `parse_references` (case-insensitive, unfolds continuation lines, keeps `<…>` brackets so tokens match the ENVELOPE `message_id`). Thread keying then prefers `references[0]` (the root) so an A←B←C chain with B missing stays one thread. → [src-tauri/src/commands/email/sync.rs](../../src-tauri/src/commands/email/sync.rs), [parsing.rs](../../src-tauri/src/commands/email/parsing.rs)
- **Any "does this account have a secret?" check must be credential-kind-agnostic.** `email_accounts_list` flips a row to `reauth_required` when it has no secret — it used `get_password(...).is_some()`, which returns `None` for an OAuth account (an oauth secret has no password), so an OAuth Gmail account would be **falsely flagged reauth on every list**. Use `secrets::account_has_secret` (true for Password OR Oauth). Same trap for any future code that gates on "is there a credential." → [src-tauri/src/commands/email/account_commands.rs](../../src-tauri/src/commands/email/account_commands.rs)
- **Triage (archive/move/delete) undo is a JS-held window, NOT an IMAP reversal.** Reversing an archive/delete means un-expunging + restoring the pre-move UID — which we've lost. So `useEmailModule.triage()` copies the undo-send pattern: it hides the thread locally and only fires `email_apply_message_op` after `TRIAGE_UNDO_MS` (or immediately on unmount); Undo before then is a pure local restore, no server op ever ran. Consequence: the mail stays on the server for the 8s window after the user archives (already hidden from their view). Don't try to build a reverse-move undo. Star/read flags, being cheap + exactly reversible, apply immediately instead. → [src/features/email/hooks/use-email-module.ts](../../src/features/email/hooks/use-email-module.ts)
- **A triage op targets a UID, but "archiving a thread" must fan out to every message of the thread in the folder.** `email_apply_message_op` acts on one `(account, folder, uid)`; the hook maps a thread → all its envelopes in that folder and applies the op to each. A single-UID archive would leave the thread's other inbox messages behind. → [src/features/email/hooks/use-email-module.ts](../../src/features/email/hooks/use-email-module.ts)

## Email engine (EM-6/7/8)

- **`20260704180000`'s comment says it patches *both* follow-up ops to reset the one-shot guard; it patches only one — and that comment is now the text sitting in prod.** `email_op_follow_up` nulls `follow_up_notified_at` (re-arm), but `email_op_clear_follow_up` (`20260704170000`) leaves it alone. Harmless today: `email_op_follow_up_due` short-circuits on `follow_up_cleared_at IS NOT NULL`, and every re-arm path goes through `email_op_follow_up`, which nulls both. It becomes a live bug the moment anything clears a follow-up *without* setting `follow_up_cleared_at`, or the due-check stops reading that column. Don't "fix" it by re-applying the old migration file (see §Supabase / migrations on back-dated applies) — write a forward migration.
- **`spine_activity_targets_me` did NOT notify you about your OWN action — a self-set reminder needs the actor-agnostic `notify_user_ids` branch.** The original predicate is `actor≠me AND payload.mentioned_user_ids @> [me]` — deliberately excluding self (you don't get pinged for @mentioning yourself). But a snooze-due / follow-up-due reminder is a self-notification: YOU are the actor and the target. EM-6 added a second, actor-agnostic disjunct `payload.notify_user_ids @> [me]` (written only by `email_op_snooze_due`/`_follow_up_due`, targeting `owner_id`). Any future "remind ME about my own thing" activity must set `notify_user_ids`, not `mentioned_user_ids`, or the actor≠me guard silently swallows it. It's owner-only so other workspace members (who can read the ref) aren't spammed. → [supabase/migrations/20260704180000_email_snooze_followup.sql](../../supabase/migrations/20260704180000_email_snooze_followup.sql)
- **✅ RESOLVED — the branch is live in prod now; keep this entry for the *lesson*, not as a live warning.** DF-21d's `20260714120000` was **applied 2026-07-27** (post-apply live probe green), which is what actually restored the two-branch `spine_activity_targets_me`; OPS-1 then applied `20260704180000` on 2026-07-29 and *confirmed* the deployed definition against `pg_proc` (its own re-assert was a no-op). Read the rest of this bullet as the post-mortem it is. — **The `notify_user_ids` predicate branch above was AUTHORED (EM-6, `20260704180000`) but for ~3 weeks was NEVER APPLIED to prod — a 2026-07-14 (DF-21d) rolled-back probe found the DEPLOYED `spine_activity_targets_me` was still the CT-5 mention-only shape.** So for that period, EVERY notify-branch notification was silently dark in prod: DF-9's `tasks.unblocked` AND email snooze-due/follow-up-due (despite DF-9's "verified live" note, which was a rolled-back in-txn probe that re-CREATE'd the branch, not a test of the deployed predicate — a probe-vs-deployed trap: `apply_migration` and a same-txn `CREATE OR REPLACE … RAISE ROLLBACK` prove the *logic*, not that the function is live). **Lesson:** after a migration that changes a shared predicate/function, VERIFY THE DEPLOYED DEFINITION separately (`pg_get_functiondef('public.fn(args)'::regprocedure)`) — a green build + a rolled-back logic probe do NOT prove it's deployed; a migration file existing in the repo does not mean it was applied. DF-21d's `20260714120000` re-asserts the two-branch predicate (idempotent, backward-compatible) to make itself self-sufficient AND resurrect the other types; **it is applied to prod** (confirmed by OPS-1's 2026-07-29 catalog probe), so the one-time surfacing of previously-dark `tasks.unblocked`/email-due rows has already happened (it was bounded anyway: `notifications_list LIMIT 50`, badge caps at 99, Mark-all-read clears). → [supabase/migrations/20260714120000_comments_notify_owner_participants.sql](../../supabase/migrations/20260714120000_comments_notify_owner_participants.sql)
- **Tasks are written CLIENT-DIRECT — there is no `tasks_op_create` SECURITY DEFINER fn to `PERFORM` from another module's SQL op.** `runtime.tasks.upsertTask` does `supabaseClient.from("tasks").upsert(taskModelToRow(...))` straight to the table (client-direct writes, RLS-guarded). So an "atomic convert-to-task" email op **cannot** create the task in SQL without re-implementing `taskModelToRow` (position, status defaults, bucket resolution) — which drifts silently against the untyped client. EM-8 convert is therefore client-orchestrated (`upsertTask` → `spine.createLink`), matching calendar/notes. If you need a cross-module task-create, do it client-side through `upsertTask`, not a SQL `PERFORM`. → [src/features/email/ui/email-page-view.tsx](../../src/features/email/ui/email-page-view.tsx) `runConvert`
- **Convert-undo (and any undo that removes a link it "created") must guard against `_op_link` idempotency.** `email_op_link`/`links_op_create` return the PRE-EXISTING row on a duplicate (`ON CONFLICT DO NOTHING` → re-select). So capturing `link.id` after linking doesn't tell you the link is new — if a thread↔contact link already existed, undo would delete a link the user made earlier. EM-8's `runConvert` pre-checks `spine.listLinks` for the thread and only marks the contact link (+ the ref, via `refCreated`) for undo when THIS convert actually created it. Same class as the FX-9 "already linked" drag guard. → [src/features/email/ui/email-page-view.tsx](../../src/features/email/ui/email-page-view.tsx)
- **The IMAP ENVELOPE carries `cc` but the sync didn't store it — reply-all silently dropped everyone CC'd.** `StoredEnvelope` captured `to` (from `envelope.to`) but not `envelope.cc`, and `EmailEnvelope` (TS) had no `cc`, so `buildComposeDraft` reply-all could only re-add the To-line. EM-7 added `StoredEnvelope.cc` (+ the DTO field + TS `EmailEnvelope.cc`, all `#[serde(default)]` for old redb rows) so reply-all unions original To+Cc minus every self-address. Anytime you rebuild recipients from an envelope, remember Cc is a separate field. → [src-tauri/src/commands/email/model.rs](../../src-tauri/src/commands/email/model.rs), [src/features/email/compose.ts](../../src/features/email/compose.ts)
- **Snooze restore is a TS desktop orchestrator, not a Rust scheduler — the IMAP move is Rust, the scheduling + cloud writes are TS.** A "Rust 60s scheduler that writes the due activity row" (the original plan note) can't work: Rust has no Supabase session/JWT to write `module_activity`. So [`use-email-snooze-restore.ts`](../../src/features/email/hooks/use-email-snooze-restore.ts) runs the 60s loop (mount + focus catch-up) where the runtime lives, calling Rust `email_snooze_restore` for the IMAP move-back and the cloud `snoozeDue`/`followUpDue`/`clearFollowUp` ops for state+notifications — mirroring `useCalendarSync`. It only progresses while /email is mounted (app-level mount for true background is a follow-up). **Order matters:** reply-clears run BEFORE the follow-up-due notify so a replied-to thread never fires a spurious "no reply" reminder. → [src/features/email/hooks/use-email-snooze-restore.ts](../../src/features/email/hooks/use-email-snooze-restore.ts)

## Email engine (EM-9/10)

- **A redb "sidecar" table must be pruned/removed where its PARENT is, not on its own schedule.** EM-9's `EMAIL_BODY_TEXT` (the 8KB lowercase body-text search index) is keyed identically to the body cache (`account::folder::uid`) precisely so the eviction path co-removes it: it's written in `persist_body_cache` and deleted in `remove_body_cache` (which the LRU prune calls), so it can never outlive its body or leak into search after the body is gone. Any future per-body sidecar (attachments index, embeddings, etc.) must hook the SAME `remove_body_cache` seam — a separate prune loop would drift. → [src-tauri/src/commands/email/storage.rs](../../src-tauri/src/commands/email/storage.rs)
- **IMAP has no cross-folder SEARCH — "search the entire mailbox" on a standard server means iterating folders.** `UID SEARCH` only searches the *selected* mailbox, so a single SEARCH against INBOX is NOT a full-mailbox search (it misses Archive/Sent/all labels). Gmail is the exception (`X-GM-RAW` in All Mail sees everything). EM-9's `email_search_server` therefore LISTs the account's selectable folders and unions per-folder searches for non-Gmail; per-folder failures isolate (one bad folder ≠ whole-search failure), results cap newest-first. Don't ship an INBOX-only SEARCH behind an "entire mailbox" label (validator MAJOR). → [src-tauri/src/commands/email/search.rs](../../src-tauri/src/commands/email/search.rs) `run_server_search`
- **A deploy-gated prefs domain must NOT be added to the SHARED `preferences.get`/`set` `.select()` unconditionally — it breaks appearance/focus/calendar until the migration deploys.** The prefs read is one row with all domains; a `.select("…, email, email_updated_at")` against a DB without the column 400s the WHOLE query (the hot theme/font read at app boot). EM-10's fix: a module-level `emailPrefsColumnAvailable` flag + `isMissingEmailColumn` (42703) guard — the full select/upsert is tried, and the first missing-column error flips the flag off and retries with the base columns; the other domains are never dropped, email degrades to local-only, and it auto-heals once the column exists. Use this pattern for any prefs domain whose migration can't be applied in the same session. → [src/lib/runtime.web.ts](../../src/lib/runtime.web.ts) `preferences.get`/`set`
- **The typed Supabase client's `.select()` needs a string LITERAL, not a `string` variable.** A dynamic `const cols = cond ? A : B` passed to `.select(cols)` trips the client's template-literal type parser (`ParserError<"Unexpected input…">`) because it can't statically parse a union/`string`. Cast the dynamic column set to a literal type (`.select(cols as typeof PREFS_COLS_FULL)`) — the client is effectively untyped at runtime anyway, and the cast just satisfies the parser. Bit the EM-10 deploy-gap guard (which needs a runtime-chosen column set). → [src/lib/runtime.web.ts](../../src/lib/runtime.web.ts)
- **Smart-inbox classifier ordering is load-bearing — Auto-Submitted/no-reply must be checked BEFORE List-Unsubscribe.** A GitHub/CI notification carries BOTH `List-Unsubscribe` (so you can mute the repo) AND `Auto-Submitted: auto-generated` — if List-Unsubscribe is tested first it misfiles to Newsletters. The pinned order (override → known-contact → auto-submitted/no-reply → list-unsubscribe → bulk-precedence → personal) is encoded in `classify.ts` and pinned by a test; a dogfood tuning pass is sanctioned (brief §5) but keep the test in lockstep if you retune. → [src/features/email/classify.ts](../../src/features/email/classify.ts)

## Email MCP + widget (EM-11)

- **The `email_thread` entity id is `email_refs.id` (uuid), NOT the text `thread_key`.** `email_op_ref_upsert` registers `entities_op_upsert('email_thread', r.id)`, and `email_op_link(p_thread_id uuid)` + the app's `linkThread({threadId: ref.id})` both key on that uuid. The `thread_key` is an RFC-822 References-root id (text) — passing it to `email_op_link` raises `invalid input syntax for type uuid` (or worse, silently forks a second divergent entity). The MCP connector's `email_link` looked up `thread_key` first (validator BLOCKER); it now passes `ref.id`. **The connector is Deno + NOT in `bun run verify`, so a wrong RPC arg only surfaces at deploy / MCP-1's keyed round-trip** — cross-check every connector RPC arg against the migration signature + the app's runtime mapping by hand. → [supabase/functions/moduo-mcp/modules/email.ts](../../supabase/functions/moduo-mcp/modules/email.ts)
- **`moduo:entity:open` silently swallows an id-less open — but `email` is a legitimate id-less "open my inbox" gesture.** `entityOpenTarget` used to `if (!id) return null` at the top, and the app-chrome host listener bailed on `!detail.id` — so the EM-11 widget's per-account unread rows (which have no thread id) were dead clicks. Email has no URL thread-selection yet, so it routes to `/email` regardless of id: the email cases now sit BEFORE the id guard in `entityOpenTarget`, and the listener only requires `type`. Any future module page that wants an id-less "just open the page" deep-link needs the same carve-out (the id guard is for *selection*, not navigation). → [src/lib/entity-open.ts](../../src/lib/entity-open.ts), [src/components/app/app-chrome.tsx](../../src/components/app/app-chrome.tsx)
- **Pushing per-account UNREAD to `email_accounts.unread_count` is NOT an AC14 tissue-privacy regression — accounts are owner-scoped, refs are workspace-visible.** EM-11's desktop→cloud unread push writes owner-RLS `email_accounts` (only you ever see your accounts/counts), distinct from the workspace-visible `email_refs` tissue. Keep that line: account metadata (unread, status, signature) is owner-private; only deliberately-actioned *threads* become workspace tissue. The push is `!isDesktop`-guarded + debounced + deduped-by-count so optimistic triage doesn't spam Supabase. → [src/features/email/hooks/use-email-module.ts](../../src/features/email/hooks/use-email-module.ts)

## Email reader hardening (DF-6)

- **The reader iframe's no-script guarantee is now TWO cooperating layers, not the sandbox alone.** `sandbox="allow-scripts"` (needed for the auto-height reporter) means email HTML could execute if BOTH the DOM strip (`<script>`/on\* removal) and the CSP `script-src 'nonce-…'` were weakened. Never add `allow-same-origin`, never add `'unsafe-inline'` to script-src, and keep the nonce random per document. The height reporter's `targetOrigin` is `"*"` on purpose — pinning the desktop's `tauri://localhost` custom-scheme origin is unreliable in WKWebView matching and a silent mismatch would kill auto-height (payload is one integer, the app is never framed). → [src/features/email/utils/email-html.ts](../../src/features/email/utils/email-html.ts)
- **`user_preferences` domain sync is whole-object LWW — adding a field to a prefs domain means an OLD client can wipe it.** A pre-DF-6 build's `sanitizeEmailPrefs` drops `imageAllowedSenders`; any pref write from that build pushes the whole `email` domain without it, and the newer client adopts the cloud copy → the allow-list silently resets. Bounded at single-user alpha (rebuild-and-replace desktop distribution), but when adding prefs fields, consider field-level merge in `reconcileDomain` or a domain version bump. → [src/features/email/prefs.ts](../../src/features/email/prefs.ts) · [src/lib/prefs-sync.ts](../../src/lib/prefs-sync.ts)
- **`countRemoteRefs`/`buildEmailReaderDoc`: srcset remote-detection splits on whitespace AND commas** — it over-detects a remote-looking token inside a data: URI (fails safe: over-blocks). Inline-style stripping is DECLARATION-level (`split(";")` filter) — a remote `url()` drops its whole declaration; don't "improve" it back to regex surgery inside `url(…)`, parens/commas in URLs mangle survivors. → [src/features/email/utils/email-html.ts](../../src/features/email/utils/email-html.ts)
- **Live-verifying iframe/srcdoc behavior from a worktree: the preview harness can't spawn servers here** (sandbox `getcwd` EPERM) and Storybook fails on a pre-existing `@/lib/utils` vite-alias gap. The working recipe: generate the real srcdoc via a bun script (jsdom `DOMParser` shim), inline it into a self-contained harness page (escape `</` when embedding HTML in a `<script>` string!), and drive headless Chromium via the repo's Playwright with `executablePath` pointed at the newest `~/Library/Caches/ms-playwright/chromium_headless_shell-*` (the cached build may be newer than the lib expects). Run the script from inside `node_modules/` so bare imports resolve. → [docs/testing/df-6-email-pack.md](../testing/df-6-email-pack.md)

## Email history depth (IM-2b)

- **`Option<i64>` as a "floor" carries two incompatible meanings — reusing one helper for both makes `None` an absorbing state that silently disables everything downstream.** IM-2b's depth floor is `Option<i64>` where `None` means *unbounded* when gating the prune, but *nothing reached yet* when advancing the reached floor. Advancing with the prune helper (`(None, _) | (_, None) => None`) made `None` a fixed point: `history_floor_ms` could never become `Some`, so the prune gate was never armed (AC10 passed only by total disablement) and `depth_gap_reopens` always returned false, so **raising the depth backfilled nothing, ever**. Every pure-function test still passed. Two lessons: give each meaning its own named function (`deepest_floor` vs `advance_reached_floor`), and **test the state transition, not just the helpers** — the engine's use was a single line no test executed, which is exactly how it shipped past the first review. → [sync.rs](../../src-tauri/src/commands/email/sync.rs)
- **A `uid_validity` change invalidates every UID-shaped thing you cached about a folder — including "I'm done".** Carrying `backfill_complete`/`oldest_synced_uid`/`history_floor_ms` across a mailbox recreation is a data-loss path, not just staleness: local UIDs from the old numbering all sit above the new mailbox's high-water mark, so a "these UIDs can't exist on the server" sweep deletes the whole synced history — while `complete: true` guarantees the backwards walk never re-populates it. Reset the lot when `cursor.uid_validity != server uid_validity`, and only run a high-water-mark sweep while the generation is *unchanged*. (Related: `envelope_key` has no `uid_validity` segment and `body_fetch` doesn't check it, so a surviving stale-generation row can render another message's body — the ratified never-delete-in-window rule accepts that; don't "fix" it by deleting.) → [sync.rs](../../src-tauri/src/commands/email/sync.rs)
- **Record a *measured* floor, not the configured one, or lowering a setting retroactively authorizes deletion.** IM-2b records how deep the walk got so the prune can never evict already-promised mail. Recording the *configured* depth breaks that: a 12-month walk that reached 6 months and is then lowered to 3 finds nothing below its frontier, reports "complete", records 3 months — and the prune is then free to delete the 3-to-6-month mail it had already fetched. `min(configured_floor, oldest_stored_timestamp)`. → `completed_floor` in [sync.rs](../../src-tauri/src/commands/email/sync.rs)
- **`UID SEARCH SINCE` matches the server's INTERNALDATE; a local timestamp filter matches the `Date:` header — they disagree on any migrated mailbox.** After a mailbox migration every INTERNALDATE is the migration day, so `SINCE <3 months ago>` returns the *entire* mailbox and the client discards nearly all of it: a "3 months" choice walks ten years of UIDs. It terminates, but "ask the server for the range, it's cheaper" inverts for that case. Also: `SINCE` is **date**-granular, so truncate the local floor to that date's midnight or every round re-fetches up to a day of mail it then throws away; and the window is computed in **UTC**, so a depth boundary is off by up to a day for a non-UTC user. → [sync.rs](../../src-tauri/src/commands/email/sync.rs) `depth_window`
- **Syncing more mail is not the same as making more mail reachable — check the read surface before calling a depth feature done.** IM-2b backfills 12 months of envelopes into redb, and a user can see none of it: the list is capped at 500 rows, instant search filters only the rows already loaded, and the Rust search scans only body text cached for messages already opened. The spec's own out-of-scope note asserted "deeper sync improves local search" while putting the 500-row cap out of scope — those cannot both hold. Whenever a block's payload is "more data in the store", name the surface that exposes it in the same breath. → [specs/import.md](../../specs/import.md) §Open questions

## Email depth picker (IM-2c-a)

- **A new connect-time option has to be threaded through EVERY connect path — the OAuth one has its own input type and will silently swallow the default.** The depth picker sits in the same dialog as "Sign in with Google", but `email_gmail_oauth_start` takes `EmailGmailOAuthStartInput` (not `EmailAccountConnectInput`) and built its account with `EmailHistoryDepth::default()`. Picking "Everything" then connecting with Google gave you 12 months, with no error and no hint. Same trap in the *existing-account* branch of `connectAndSave`, which updates eight fields and would have skipped the new one. When you add a field to a connect flow, grep for every `StoredEmailAccount {` literal — there are three. → [oauth.rs](../../src-tauri/src/commands/email/oauth.rs) · [account_commands.rs](../../src-tauri/src/commands/email/account_commands.rs)
- **An `aria-label` on a `combobox` trigger REPLACES the selected value for screen readers.** A `SelectTrigger` labelled `aria-label="Mail history to sync"` never announces "12 months" — the accessible name wins over the content. Use a visible `<label htmlFor>` (or `aria-labelledby`) instead; the trigger's own text is the value. → [email-history-depth-select.tsx](../../src/features/email/ui/email-history-depth-select.tsx)
- **A consequence line that only renders while an edit is "dirty" is invisible in practice.** The picker showed "Nothing already synced is deleted" by comparing the draft against the stored value — but the draft is cleared the moment the write lands, so the reassurance flashed for one round-trip and vanished. If a message explains what a committed action *did*, keep it after the commit, and reserve its space so committing doesn't reflow the row. → [email-history-depth-select.tsx](../../src/features/email/ui/email-history-depth-select.tsx)
- **Don't promise "in the background" for work that only advances inside a sync round.** Raising the depth re-opens the backfill, but the engine has no background driver — an IDLE account can sit parked ~29 minutes, so the only reliable trigger is the Refresh button. The setting now kicks a sync itself, and the copy says "fills in as you use Mail". Match the words to the engine, not to the intent. → [history-depth.ts](../../src/features/email/history-depth.ts)

## Transactional email kit (TX-1)

- **Outlook.com's dark mode flags text and backgrounds with different attributes.** It adds `[data-ogsc]` to elements whose text colour it rewrote and `[data-ogsb]` to those whose background it rewrote. Put every `color` override under `[data-ogsc]` and every `background-color` override under `[data-ogsb]` (`darkColorRules` / `darkBackgroundRules` in `supabase/functions/_shared/email/render.ts`). Scoping both under `[data-ogsc]` turned a button label near-black on a background Outlook had left dark. (2026-10-08)
- **An email's "auto" look follows the viewer's OS, including inside a Storybook iframe.** In a dark Browser pane the light preview rendered dark. Previews force the look with `renderEmail(doc, { colorScheme: "light" | "dark" })`; real sends always use `"auto"`. (2026-10-08)
- **Email images must have the exact pixel shape their `width`/`height` attributes promise.** Outlook desktop sizes images from the attributes, not CSS, so a lockup exported at another ratio is squashed. The contract with the brand pipeline is the header comment of `supabase/functions/_shared/email/assets.ts` (lockup 192 × 44 @2x, mark 26 × 26 @2x). (2026-10-08)
- **Ink artwork on a transparent PNG vanishes in phone mail apps that darken emails themselves** (Gmail, Outlook on iOS/Android) without honouring `prefers-color-scheme`, so the dark-variant swap never fires. Maciej decided against a halo (brand decision 74a in `.design/brand/DECISIONS.md`, on `t/maciej/brand-1-asset-pipeline` until it merges; brand rule 25 bans outlines and glows): the kit swaps to the Paper files where dark mode is detectable (the media query, Outlook's `[data-ogsc]`), and Gmail's app keeping the Ink logo is an accepted limit. (2026-10-08)
- **A missing file under app.moduo.app answers 200 with the app's HTML, not 404.** Vercel's SPA catch-all rewrites unknown paths to `index.html`, so an email image URL that "works" by status code can still be a broken image. Check `content-type: image/png` (and the pixel size) before relying on an email asset. (2026-10-08)

## Sign-in codes on Resend (TX-2)

- **Supabase gives an HTTP auth hook five seconds in total, its own retries included, and any non-2xx answer becomes an error for the caller.** Auth retries on 429/503 with a non-empty `retry-after` and on network errors, each with a new `webhook-id`, until the shared 5 s deadline. A 200 needs `Content-Type: application/json`. Answering late is worse than failing: Auth rolls back the request, so a code that already went out never works. `auth-email-hook` answers within 4.5 s, retries Resend only when the retry still fits, and writes its log after answering (`EdgeRuntime.waitUntil`). (2026-10-08)
- **For `email_change`, Supabase's token names are reversed.** With Secure Email Change on, `token` (with `token_hash_new`) goes to the current address `user.email`, and `token_new` (with `token_hash`) goes to `user.new_email`; with it off, the one code goes to the new address. (2026-10-08)
- **The Send Email Hook replaces every auth email, the dashboard's "Send invitation" included.** A hook that sends a bare code for `invite` locks invitees out while sign-ups are off: their code request is refused until the address is confirmed, and only the invite link confirms it. The hook keeps the `/auth/v1/verify?type=invite` link (`auth-variants.ts`). That link lives as long as a code (the OTP expiry), so 600 s makes invite links last 10 minutes. (2026-10-08)
- **Switching the hook on before its secret is set breaks every sign-in.** The function then rejects every request (`signature_rejected`) and the screen says "We couldn't send your code". Create the hook switched off, set `SEND_EMAIL_HOOK_SECRET`, then switch it on (docs/email-runbook.md); the rollback is the same switch. (2026-10-08)
- **Auth runs the Send Email Hook inside the transaction that creates the user, so nothing on another connection can see that user yet.** For a dashboard invite (and every first sign-in once sign-ups are on), `auth.users` holds the new row uncommitted while the hook runs; a log insert over PostgREST that references it through a foreign key fails. `email_outbox.to_user_id` therefore has no foreign key, and the daily purge removes rows of deleted accounts (after an hour's grace). When such a send fails, Auth rolls the user back, so the hook logs that failure with `to_user_id` null: otherwise the purge would delete exactly the evidence of a new user's failed code. The same goes for anything else the hook might write about the user. (2026-10-08)
- **Supabase Auth joins several webhook signatures with ", ", not a space.** During a secret rotation the header reads `v1,<sig>, v1,<sig>`; splitting on spaces leaves a trailing comma that never matches, and every sign-in fails. `webhook.ts` drops the separator comma. (2026-10-08)

## Outbox worker (TX-3)

- **A retention clock that runs from `created_at` deletes email that hasn't gone out yet.** TX-2's purge deleted every outbox row older than 30 days, which was right while the table only logged sent codes. Once it queues, a reminder or a "founder access ending" email can be queued months ahead and would be deleted before its day. `email_outbox__purge()` keeps `queued`/`sending` rows and counts 30 days from `coalesce(sent_at, last_attempt_at, created_at)`. Any new retention rule on a queue table: decide what the clock means for rows that haven't happened yet. (2026-10-09)
- **Resend's `email.delivered` webhook carries two times, and `data.created_at` is the wrong one.** `data.created_at` is when the email was created (sent); the event's top-level `created_at` is when it was delivered. `delivered_at` comes from the event's time. (2026-10-09)
- **A queued email must render from its payload alone, and a copy change can still fail a row that is mid-retry.** Resend keeps an `Idempotency-Key` for 24 hours and refuses the same key with a different body (409 `invalid_idempotent_request`, not worth retrying). A template that reads the clock would change the body between attempts; one that doesn't still changes if a deploy edits its copy while a row waits for its next attempt, and that row ends `failed`. Keep every time a template prints in the payload (the ops alert's `detected_at`), and expect a failed row or two when copy changes during an outage. (2026-10-09)
- **Two template kinds break any loop over `EMAIL_TEMPLATES[kind](EMAIL_FIXTURES[kind])`.** With one kind it type-checks; with two, TypeScript calls the union of template functions with the intersection of their data types and fails. Loop through the generic `templateDoc(kind, data)` (or `renderTemplate`) in `templates/index.ts`. (2026-10-09)
