# Gotchas: Spine, MCP contract, contacts and tasks data

Read before working in `src/features/spine/`, `moduo-mcp`, contacts, tasks. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Module contract / MCP connector

- **A connector tool that returns another module's data has to respect that module's key scope too.** Tools are listed per module, but the spine's are cross-cutting: `links_search_entities` returned note and contact titles to a key with Links View and Notes None, and `calendar_day` returned task titles to a key without Tasks. Filter by the entity type's module (`keyCanSeeEntityType`, `MCP_ENTITY_TYPE_MODULES` in `@contracts/mcp-key-scopes`) as well as by the creator's per-item access, and check any entity a write points at (`assertReach` in `moduo-mcp/share.ts`). A tool whose RPC is guarded by another module's scope goes in `MCP_TOOL_NEEDS`, so it's hidden instead of failing. → [supabase/functions/moduo-mcp/share.ts](../../supabase/functions/moduo-mcp/share.ts)
- **Live-verifying an Edge Function: the in-app preview browser can't reach the `…functions/v1/*` subdomain — its fetches fail with `Failed to fetch` (no request ever reaches the function, confirmed via `get_logs`).** Auth (`/auth/v1/token`) + REST (`/rest/v1/*`) work from the preview browser, but the functions host is blocked by its network sandbox. Verify an edge function **server-side with `curl`** instead (Bash reaches the internet; no browser CORS either): `curl -X POST …/functions/v1/<fn> -H "apikey: <publishable>" -H "Authorization: Bearer <jwt>"`. For a **destructive** function (e.g. `delete-account`) that must not touch the reusable hosted test account: create a **disposable fixture user via service-role SQL** — `insert into auth.users(instance_id,id,aud,role,email,encrypted_password,email_confirmed_at,created_at,updated_at,raw_app_meta_data,raw_user_meta_data,confirmation_token,recovery_token,email_change_token_new,email_change) values('00000000-0000-0000-0000-000000000000', gen_random_uuid(), 'authenticated','authenticated','fx@…', crypt('pw',gen_salt('bf')), now(),now(),now(),'{"provider":"email","providers":["email"]}'::jsonb,'{}'::jsonb,'','','','')` (the empty-string token columns are required; `raw_app_meta_data.provider=email` + `email_confirmed_at` let a password-grant succeed) + a `profiles` row + a workspace it owns — mint its JWT via password grant, exercise both paths against the fixture (DF-19h: made it sole-own a shared ws → 409 blocked; then solo → 200 + cascade), then it self-cleans (the clean delete removes it). Never call a destructive edge fn with the real test account's JWT. (DF-19h, 2026-07-12.)
- **`workspace_members.role` CHECK accepts only `{owner,admin,member,viewer}` — NOT `editor`** (the app/invites vocabulary uses `editor`; DF-24 bridges it). A raw `insert … role='editor'` into `workspace_members` fails the `workspace_members_role_check`; use `member`. (Re-bit while seeding a fixture member for DF-19h delete testing — see [[the DF-24 vocabulary-mismatch gotcha above]].)
- **A new module's `<module>_module_permission` MUST include the `module_api_key_id()` branch, or every agent WRITE through its ops is dead on arrival.** The MCP connector runs as service_role: `auth.uid()` is NULL, so an auth.uid()-only permission function returns `'none'` and the op guard raises "no edit access" **even for a properly-scoped key** — while the connector's *reads* work fine (they query tables directly, never hitting the guard), which makes the breakage easy to miss in a read-only smoke test. This shipped broken in **three** modules (spine CT-1, contacts CO-1, calendar CAL-2 — the copy-paste source was the pre-connector shape) and was only caught by CAL-7's validator; all three were fixed in one migration ([`20260702170000_module_permissions_api_keys.sql`](../../supabase/migrations/20260702170000_module_permissions_api_keys.sql), applied to prod). When writing a new module's permission fn, **copy `tasks_module_permission`** (the api-key branch reads `k.scopes ->> '<module>'`), not the others' old shape — and remember `verify` can't catch this (it's a server-side auth-context behavior; only a keyed round-trip proves it).
- **`tasks_op_reschedule` schedules-from-NULL as of `20260702170000`** — it used to quietly no-op when the task had nothing scheduled ("triage race" guard), which made any caller that *meant* "schedule this" report phantom success (bit the CAL-7 connector's `calendar_schedule_task`). If you relied on the no-op-when-unscheduled behavior, that's gone; the op now always sets the time and logs `{"from": null, …}`.

## Spine reads / activity

- **Notification MUTES are applied ONCE, in the workspace-provider — never re-filter per consumer (DF-19f).** The provider derives its exposed `notifications` from `rawNotifications.filter((i) => isNotificationEnabled(i.op, notificationPrefs))` (`isNotificationEnabled` from [`src/lib/preferences.ts`](../../src/lib/preferences.ts), keyed on the row's `op`; taxonomy `mention | assigned | dueFollowUp | unblocked`), so every consumer — the bell (`notification-center.tsx`), the dashboard Activity widget — inherits AC10 for free by reading `notifications` + `unreadCountWorkspace`. **Do NOT build a second notification-prefs classifier/hook** (DF-21a tried, got a validator BLOCKER: a parallel 6-key taxonomy + a `moduo.notifications` localStorage mirror that nothing wrote → permanent no-op). A new notification TYPE (e.g. DF-21e overdue) EXTENDS `preferences.ts`'s `NotificationType` union + `OP_TO_NOTIFICATION_TYPE`, and the provider filter picks it up automatically. → [src/lib/preferences.ts](../../src/lib/preferences.ts), [src/providers/workspace-provider.tsx](../../src/providers/workspace-provider.tsx)
- **`runtime.tasks.listActivity` filters by `module` — omit it for spine entities.** It used to hardcode `.eq("module","tasks")`, so reading a *contact*/*company* entity's trail returned `[]` (their ops log under `module='contacts'`, not 'tasks') — a contact's ActivitySection + verb-bearing last-touch were silently empty. The `module` filter is now **optional**: pass `module:'tasks'` to scope to Tasks (the Tasks UI does), **omit it** to read an entity's activity across all modules (what a contact/company hub wants). When you read activity for a new module's entity, don't assume a module pin. → [src/lib/runtime.web.ts](../../src/lib/runtime.web.ts) `listActivity`
- **A contact's "last touch" does NOT reflect edits to its *linked* entities** (only the contact's own activity + when things were linked to it). A linked task edited yesterday won't bump last-touch — that needs a batched cross-entity activity read or a materialized view (deferred, decisions.md CO-2 (b) / contacts spec decision 4). Don't read the `lastTouchLine` as a real-time "anything related happened" signal at alpha. → [src/features/contacts/rollup.ts](../../src/features/contacts/rollup.ts)
- **A hub row's snippet (DF-7) can be legitimately absent even when the row looks live — a spine link can outlive its target's module row.** Row snippets come from a live batched module read (`enrichHubRows`: `tasks.list`/`notesV2.listMeta`/`calendar.listModule`), all of which filter `deleted_at IS NULL`. If a task/note/event is **soft-deleted but its `entity_links` row + `entities` registry entry weren't cleaned up** (a real state in the test workspace — a deleted "Water plants" task whose registry `deleted_at` was still null), the hub still renders the row (label from the un-tombstoned registry) but with **no snippet** — the module read returned no live meta, so the projector correctly degrades. This is NOT a projector bug; it's the graceful path. When debugging a "missing snippet", first check whether the target's module row is soft-deleted (and whether the registry entity should have been tombstoned) before suspecting the meta plumbing. Diagnose by dumping `enrichHubRows`' `wantTask` set vs the built `snippetMeta` keys — an id in `wantTask` but absent from the map means `*.list` didn't return it (deleted/filtered), not a lookup miss. → [src/features/contacts/hooks/enrich-hub-rows.ts](../../src/features/contacts/hooks/enrich-hub-rows.ts)
- **Task notifications (`tasks.assigned` / `tasks.unblocked`, DF-9) are generated by a TABLE TRIGGER on `public.tasks`, not by an intent op — because Tasks are written client-direct (no `tasks_op_create/assign`).** Every OTHER notification (comment @mention, email snooze/follow-up-due) comes from a `*_op_*` RPC calling `module_activity_log`; task ones come from `tasks_notify_spine()` (`20260712120000_df9_task_notifications.sql`). So when you hunt "where does this task notification come from", it's the trigger, not an RPC. Three traps for anyone editing it: **(1)** the trigger MUST be `SECURITY DEFINER` — `module_activity_log` is revoked from `authenticated`, so a plain (invoker) trigger fired by a client-direct upsert gets "permission denied for function module_activity_log". `auth.uid()` still resolves to the real caller inside it (GUC, not role-based). **(2)** Don't add a `spine_activity_targets_me` branch for these — assigned reuses `mentioned_user_ids` (the actor≠me branch, so self-owned tasks stay silent) and unblocked reuses `notify_user_ids` (actor-agnostic). **(3)** unblocked's `notify_user_ids` is deliberate, NOT a bug: "fixing" it to `mentioned_user_ids` (actor≠me) would make it never fire in a single-user workspace (you always close your own blockers) — killing the feature for the alpha's dominant case. "Assignee" == `owner_id` (no assignee column exists yet); the trigger fires when owner is set to a member ≠ the actor. → [supabase/migrations/20260712120000_df9_task_notifications.sql](../../supabase/migrations/20260712120000_df9_task_notifications.sql)

## Contacts

- **A relation-kind is only sensible for some endpoint-type pairs — constrain every write seam, not just the menu.** The "Ben Okafor · Attachment" bug was a contact↔contact link set to `attachment` via the unconstrained "Change relation" menu (it listed all 8 kinds). The fix is the pure matrix [`allowedKinds(a,b)`](../../src/features/spine/kind-constraints.ts): `references`/`mentions` for any pair; `works-at` only contact↔company; `paid-by` only money↔party; `attachment` only when one end is attachable (file/email/receipt) — never person↔person. It gates the change-relation menu (`entity-hub.tsx`), and `coerceKindForPair` clamps the drag `resolveKind` and the suggestion-accept kind so a bad *derived* kind can't persist either. When adding a link write path, run the proposed kind through `coerceKindForPair(kind, aType, bType)`. → [src/features/spine/kind-constraints.ts](../../src/features/spine/kind-constraints.ts)
- **A contact's last-touch prefers INTERACTIONS over record edits (FX-4) — changing the `RECORD_EDIT_OPS` set silently changes the surfaced verb.** `buildContactRollup` picks the most-recent stamp whose op is NOT in `RECORD_EDIT_OPS` (link creations + comments = interactions; `contacts.update`/`set_status`/`set_details`/`create`/`set_favorite` = record edits), falling back to the latest record edit only when there is no interaction. So a status change made *after* an older linked-task no longer wins "last touch". Two rollup tests encode this — if you add a new contacts op, decide whether it's an interaction before it starts (mis)winning last-touch. → [src/features/contacts/rollup.ts](../../src/features/contacts/rollup.ts)

- **CSV import must sniff the delimiter — Excel/European exports are `;`-delimited, not `,`.** The first cut of `parseCsv` hardcoded a comma split, so a semicolon file collapsed each line into ONE field: the whole line became the contact `name` (e.g. a contact literally named `;noname@x.io;;;;;`, and even the header row imported as a contact). `parseCsv` now auto-detects `, ; \t |` from the header line (outside quotes) via `detectDelimiter`. When adding any delimited-text parsing, detect — don't assume comma. → [src/features/contacts/import.ts](../../src/features/contacts/import.ts)
- **Contact delete is soft + has no Undo yet.** `contacts_op_delete` (migration `20260628120000`) soft-deletes the contact (`deleted_at`), drops its live `entity_links`, and tombstones the registry entry; the UI is a confirm dialog in the context strip. There is **no un-delete/Undo op** yet (the toast can't offer one), and **companies have no delete op** at all — both are the next gaps.

- **Radix `Select.Item` forbids an empty-string `value`** — it throws at runtime ("must have a value prop that is not an empty string"). Our "No status" option (status `''`) rides a `__none__` sentinel mapped on both `value`/`onValueChange` and the item value (contact-hub + contact-form-dialog). Any future optional Select needs the same sentinel.
- **`ALTER COLUMN … TYPE … USING (…)` cannot contain a subquery** ("cannot use subquery in transform expression"). The `emails text[]`→jsonb migration converts per-row via an IMMUTABLE helper function (`contacts__emails_to_jsonb`) the USING just *calls* — a function call is allowed, a subquery isn't. → [supabase/migrations/20260628140000_contacts_v2.sql](../../supabase/migrations/20260628140000_contacts_v2.sql)
- **Contact `email`/`phone` are derived scalars, not independent fields (v2).** They mirror the primary of the `emails`/`phones` JSONB lists, recomputed by `contacts_op_set_details` via `contacts__primary_value`. Don't write the scalar without updating the list (and vice-versa) — go through the ops. The flat `email` + its `lower(email)` index remain the dedupe/suggest fast-path.

## Tasks data

- **`tasks.due_date` is a `timestamptz`, not a `YYYY-MM-DD` date.** The Tasks UI writes it from local midnight via `new Date(`${v}T00:00:00`).toISOString()` (e.g. `"2026-06-25T15:00:00.000Z"` for a JST user). So a raw lexical compare against a `YYYY-MM-DD` "today" string (`t.due_date < today`) is **off by a day for users east of UTC** — a follow-up due *today* can read as *overdue*. Normalize the stored instant back to a **local** calendar date first (`new Date(iso)` → local `YYYY-MM-DD`, mirroring `tasks/helpers.ts` `toLocalInputValue`) before any date comparison. Bit the CO-5 needs-attention overdue check. → [src/lib/runtime.web.ts](../../src/lib/runtime.web.ts) `loadOverdueFollowups`
- **An app-level accrual store that flushes through a *mounted-only* module sink loses time if it flushes against the not-yet-loaded bundle.** DF-11 lifted the Focus timer into a module store that keeps ticking while `/tasks` is unmounted; it flushes tracked seconds through `useTasksModule.addTimeSpent`, registered as a sink while /tasks is mounted. On **remount**, `useTasksModule` starts at `EMPTY_BUNDLE` and `load()` is async — so the store's drain-on-register fires *before* the bundle has the task, `addTimeSpent`'s `bundle.tasks.find` misses, and the write is silently dropped. If the store zeroes its accrued counter on flush unconditionally, **the exact seconds accrued while away are lost** (the DF-11 validator BLOCKER — it's the headline feature's own data). Fix pattern: the sink must **report whether it persisted** (`addTimeSpent` returns `boolean`, `false` when the task isn't in the bundle), the store **retains** accrued on a `false`, and a **`!api.loading` re-drain** (via `flushFocusSession()`) banks it once the bundle loads. `apiRef.current` is refreshed in the render body before effects, so the post-load drain hits the loaded-bundle `addTimeSpent`. Generalizes: any "persist-later through a mounted consumer" seam needs the consumer to confirm consumption, never fire-and-forget-then-clear. → [src/features/tasks/focus-session-store.ts](../../src/features/tasks/focus-session-store.ts) `flush`/`registerFocusFlushSink`, [use-tasks-module.ts](../../src/features/tasks/hooks/use-tasks-module.ts) `addTimeSpent`

## Spine deep-linking

- **`moduo:entity:open` is now HOSTED (FX-1) — but a "deep link" that only routes to the module page is a dead-end, not a fix.** The host listener lives in [`app-chrome.tsx`](../../src/components/app/app-chrome.tsx) and routes via `entityOpenTarget` ([`entity-open.ts`](../../src/lib/entity-open.ts)). Historically only contact/company/note carried URL selection (`search`); task/event/email routed to a bare `/tasks`/`/calendar`/`/email` and landed **unselected** — the app's #1 trust-killer (CC-1). DF-1 fixed tasks (`?id=` selection); DF-2 does calendar/email. When you add a dispatcher, assert the entity is **selected on arrival**, not just that navigation happened — a test that stops at "the route changed" passes while the click still dead-ends. Grep `moduo:entity:open` for every dispatcher; **note `notification-center.tsx` is a SECOND spine surface** (not just widget rows / ref chips) and must dispatch the event, not `navigate({to})` (it dropped the id until DF-1).
- **A page that mirrors its selection into the URL can't tell its own echo from an inbound deep link.** When `/tasks` writes `?id=<selected>` on every selection (so refresh restores it), that same `?id` looks identical to a fresh external open when the component remounts (refresh, back/forward) — naively re-applying it re-runs "take me there" side effects (force plan mode, clear filters), which regressed Execute-mode refresh. DF-1's fix: the app-chrome listener stamps a **one-shot intent marker** (`markEntityOpenIntent`/`takeEntityOpenIntent` in `entity-open.ts`); only a *marked* arrival gets the full treatment, a mirrored echo restores quietly. Any DF-2 module doing URL-mirrored selection needs the same discriminator. → [src/lib/entity-open.ts](../../src/lib/entity-open.ts) · [src/features/tasks/ui/tasks-plan-view.tsx](../../src/features/tasks/ui/tasks-plan-view.tsx)
- **Mirroring a j/k cursor into the URL will trip WebKit's `history.replaceState` throttle.** WKWebView/Safari (the Tauri desktop runtime) hard-caps `replaceState` at ~100 calls / 30s and throws `SecurityError` past it — an undebounced URL mirror wired to a key-repeat cursor reaches that in ~4s of holding `j`. Tasks selection is state **trailing-debounced (250ms) into the URL**, NOT URL-derived like notes (whose selection is click-rate). The URL is correct only at rest. Don't copy the notes URL-as-source-of-truth pattern onto a keyboard-cursor list. → [src/features/tasks/ui/tasks-plan-view.tsx](../../src/features/tasks/ui/tasks-plan-view.tsx)
- **A deep-link "reveal" must be an explicit one-shot signal, not inferred from "selected but not visible".** Inferring reveal (expand the collapsed group / parent that holds the selection) from selection-invisibility conflates a real deep link with routine fallbacks — completing/archiving/moving a task into a deliberately-collapsed group would pop that group open on every such action, and entering "All" would break the one-open-by-default rule. DF-1 threads a `{id, seq}` `revealRequest` from the apply effect to the List view; it expands a collapsed group **only** for that request, once. Ordinary selection fallbacks never touch collapse state. → [src/features/tasks/ui/tasks-plan-view.tsx](../../src/features/tasks/ui/tasks-plan-view.tsx) · [task-list-view.tsx](../../src/features/tasks/ui/task-list-view.tsx)
- **`EntityOpenTarget.search` is now `Record<string,string>` + an explicit `intentId` (DF-2) — not every param is called `id`.** The route map carries calendar's `?event=` and email's `?thread=`, so the old app-chrome `markEntityOpenIntent(target.search.id)` (which assumed an `id` key) became `markEntityOpenIntent(target.intentId)`. When you add a new deep-link type, set BOTH `search` (the page's validated shape) and `intentId` (the id to mark) — a `search` with no `intentId` won't stamp the "take me there" intent. → [src/lib/entity-open.ts](../../src/lib/entity-open.ts)
- **Not every URL-selection needs DF-1's URL-mirror machinery — Calendar/Email deep links are consume-once COMMANDS (DF-2).** Tasks mirror a j/k cursor into the URL bidirectionally (debounced, dual-ref echo discrimination) because selection is the primary interaction. Calendar's day-anchor already persists per-device (view state) and email selection is transient, so their deep links read `?event=`/`?thread=` once (a `processedRef` gate, `!module.loading` before ruling stale), apply, then **clear the param with `replace`**. Don't hand-copy the tasks mirror onto a page whose selection isn't a URL-worthy cursor — you'd add churn and an echo-discrimination problem that page doesn't have. → [src/features/calendar/ui/calendar-page-view.tsx](../../src/features/calendar/ui/calendar-page-view.tsx) · [src/features/email/ui/email-page-view.tsx](../../src/features/email/ui/email-page-view.tsx)
- **A deep link that "selects + scrolls a row" must first switch to the view that RENDERS that row.** The email desktop thread row carries `data-thread-id` **only in the inbox view** — the snoozed/follow-up sub-views render `EmailDestinationList` and search renders its own results, neither with the attribute. So the DF-2 apply forces `setView("inbox")` + `search.clear()` + unified account scope before `revealBySelector`, or the scroll silently no-ops from a sub-view (the reader still opens, but the list doesn't move). Also the unified-scope reset is load-bearing: a single-account scope drops the selection via the `selectedThread`-not-in-scope auto-clear effect. → [src/features/email/ui/email-page-view.tsx](../../src/features/email/ui/email-page-view.tsx)
- **A recurring event's `entity` id points at the SERIES ROW (its `startsAt` = the first occurrence) — deep-linking naively teleports months back.** DF-2's calendar apply expands the nearest occurrence ≥ today via `expandEventOccurrences(event, todayMs, +1yr)[0]` (falling back to `startsAt` for one-offs / ended series). Bonus: using the same expander the chips use means the highlight key `${id}:${occ.startMs}` matches a real chip. Note `expandEventOccurrences`' `MAX_OCCURRENCES=100` cap truncates the TAIL, but the FIRST result in a `[today, +1yr]` window is always the nearest upcoming — so the cap is harmless here. → [src/features/calendar/ui/calendar-page-view.tsx](../../src/features/calendar/ui/calendar-page-view.tsx)
- **`email_refs` is op-only-write: a direct REST DELETE is RLS-swallowed (200 + zero rows), so `email_op_ref_remove` is the ONLY way to remove a ref.** ✅ **It is deployed as of 2026-07-29 (OPS-1)** — what follows describes the era before that, kept because it explains the leftover row. Before that apply you could not clean up a seeded email tissue ref at all, which is why a DF-2 live-verify probe ref still lingers in the "Claude Test S2" workspace — it is now removable via `email_op_ref_remove` (deliberately left in place by OPS-1; deleting prod data is the designer’s call). Seeded email refs are cleanable again — but note `email_op_ref_remove` has **no inverse**: there is no `email_op_ref_restore` (unlike notes/contacts/calendar), and it also soft-deletes every `entity_links` row touching the thread, tombstones the registry entry and writes a permanent `email.ref_remove` activity row. Undoing one means hand-written SQL across three tables. → [supabase/migrations/20260704190000_email_ref_remove.sql](../../supabase/migrations/20260704190000_email_ref_remove.sql)
