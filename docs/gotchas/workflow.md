# Gotchas: Git, branching and Claude Code

Read before working in git, branches, skills, hooks. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Git / branching

- **`bun run verify` is red on develop: `lint:js` (Biome) reports 57 errors (found 2026-10-07).** CI never ran Biome, so nothing caught it; every session's done gate now fails on files it didn't touch. Most errors are `--write`-fixable (unused imports, import order, useless fragments); the rest are `noArrayIndexKey` and a11y rules in `workspace-switcher.tsx`, `tag-input.tsx`, stories and `src/tw`. Block LINT-1 fixes them and then adds `lint:js` to `checks.yml`. Until then, `/s2` judges `lint:js` only on the files its block changed (`bunx biome check <files>`), and says so in its report.

- **`maciej` is a hot branch — merge-commit into it, never fast-forward.** Before editing in a worktree, **check the worktree's base vs `maciej`** (`git rev-list --left-right --count HEAD...maciej`) — sessions have started on a weeks-stale `main` base and edited stale copies of `CLAUDE.md` / `DESIGN_SYSTEM.md` / `tokens.css`. Cut `t/<owner>/<kebab>` off `maciej`, not `main`. A `SessionStart` hook (`.claude/hooks/session-start.sh`) now runs this check automatically and warns on a stale base at session start — but only takes effect once it's merged into `maciej`. → [CONTRIBUTING.md](../../CONTRIBUTING.md)
- **Parallel sessions running `/execute next` off the same base CLAIM THE SAME BLOCK.** `BUILD_ORDER.md` reflects *merged* state only; an open PR that hasn't merged into `maciej` is invisible to it, so a new session off `maciej` sees the block still `[ ]` and `/execute next` deterministically picks it again. On 2026-06-27 three sessions each built CT-4 and/or CT-5 this way → duplicate files + two migrations creating the same tables (PRs #31/#32/#33 had to be reconciled by hand). `/execute next` is a *read*, not a *claim*. **Avoid:** give each parallel session an **explicit** block (`/execute CT-6`, not bare `next`), and/or **merge each block into `maciej` before starting the next round** (the "merge barrier" BUILD_ORDER already prescribes). `/wrap` now auto-merges into the personal branch + runs a duplication guard precisely to keep the ledger advancing so this can't recur. → [specs/BUILD_ORDER.md](../../specs/BUILD_ORDER.md)
- **`gh` can be signed in to the WRONG account, and git then reports the repo as nonexistent — not as an auth failure.** `gh auth status` lists every logged-in account but only one is *active*; if the active one lacks access to `GrochowskiMichal/moduohyb`, both `git fetch` and `gh api` fail with **`remote: Repository not found` / HTTP 404**, which reads exactly like a bad remote URL or a deleted repo. (This machine holds two accounts — `rdstudio-dev` and `En5hi`; only `En5hi` can see this repo, and the active one silently reverts.) **The damage is specifically to staleness guards:** a session that concludes "no network" falls back to the *local* `origin/maciej` ref, which can be many commits and several merged blocks behind — DOC-1 planned its whole reconcile against a ref that was 4 commits stale and had to redo ~10 claims at wrap when the real `maciej` turned out to have shipped DF-18. **Before trusting any "the remote is unreachable" conclusion, run `gh auth status` and check *which* account is active**; fix with `gh auth switch --hostname github.com --user En5hi`. Verify the remote really is live with `git ls-remote --heads origin maciej` — it prints the true head SHA, so it doubles as the freshness check. (2026-08-14.)

## Claude Code / skills

- **Edit `AGENTS.md`, never `CLAUDE.md`.** CLAUDE.md is a one-line pointer (since 2026-07-14): OpenCode gives `AGENTS.md` precedence and ignores CLAUDE.md entirely once it exists, and Claude Code just follows the pointer — so an edit to CLAUDE.md changes *nothing* in either tool. Same for skills: `.claude/skills/` is the **one home both tools discover** — don't copy skills into `.opencode/skills/` (they'd drift); `.opencode/` holds only the thin `/s1-3` command wrappers and the `validator` subagent. → [AGENTS.md](../../AGENTS.md)
- **Global skills are shared with Junction.** `~/.agents/skills/*` and `~/.claude/skills/impeccable/` are loaded by *every* project. Do **not** edit them for Moduo work — Moduo-specific skills/commands live **repo-local** in `.claude/skills/` and `.claude/commands/`. → `.claude/skills/`
- **A reserved built-in slash command silently shadows a same-named project skill — the built-in wins and the skill is unreachable.** Our workflow skills were named `plan`/`execute`/`wrap`; `/plan` is a reserved built-in (enter plan mode), so typing `/plan` hit the gated built-in ("isn't available in this environment") and NEVER ran the project skill — invocable only via the Skill tool, not the slash command. **Renamed 2026-07-08 to the stage-numbered `/s1` (plan) · `/s2` (execute) · `/s3` (wrap)** (bare numbers = terse + collision-proof; the command name comes from the **directory** name, `name:` frontmatter is display-only). When adding a project skill, avoid the reserved list (`/plan`, `/review`, `/simplify`, `/verify`, `/loop`, `/run`, `/init`, `/compact`, `/ultraplan`, `/ultrareview`, … — all single words); a hyphenated or numbered name is safe. No restart/cache-clear needed — Claude Code watches skill dirs live (a fresh session or `/reload-skills` picks up the rename). → `.claude/skills/s1|s2|s3/`

## Subframe MCP / CLI

- **The Subframe MCP's OAuth token expires after about 1–2 hours and isn't always refreshed mid-session.** A 401 `invalid_token` after a long idle is an expired token, not a broken setup: log in again (`claude mcp login subframe`). (Found 2026-10-01, under OpenCode; carried over from the unmerged `t/maciej/api-key-scopes`.)
- **`design_component` jobs are rate-limited, about one per 5–8 minutes per account.** Fire five or more at once and every call is rejected for minutes. Run them one after another with backoff. Read tools (`list_*`, `get_*`, `wait_for_jobs`) aren't limited.
- **Bulk design-system import (`npx @subframe/cli import --manifest …`) is gated per team.** "Design system import is not enabled for this team" is an access gate, not a bug (request access at https://tally.so/r/3jv511). Incremental `design_component` imports give the same quality (the same agent, per Subframe's own skill doc); bulk only saves orchestration. A manifest is at `.subframe/import-design-system.json`, generated 2026-10-01: regenerate it against today's components before you use it.
