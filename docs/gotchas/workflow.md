# Gotchas: Git, branching and Claude Code

Read before working in git, branches, skills, hooks. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Git / branching

- **`gh`'s active account can flip to `rdstudio-dev` mid-session** (another session switches it), and then `git push` answers 403 and `gh pr create` says "Head sha can't be blank". Run `gh auth switch --user En5hi` right before each push or PR.
- **The main checkout's `.env.local` can point at the cloud project.** A worktree has no `.env.local`; copying the main one into it gave a dev server on the cloud database while the tests (which read `supabase status`) used the local stack. Write the worktree's own file with the four keys `scripts/local/env.ts` sets (`PUBLIC_`/`MODUO_SUPABASE_URL` = `http://127.0.0.1:54321`, `…_PUBLISHABLE_KEY` from `supabase status -o json`), and check the served bundle names `127.0.0.1:54321` before signing in. (2026-10-13, TV-D13)
- **`bun run env:local` (and `supabase status`) stop nothing.** Its "Stopped services: [supabase_imgproxy_moduo supabase_edge_runtime_moduo supabase_pooler_moduo]" lists services the local stack already runs without; it reads as if the command stopped them (TV-D12's note says so). Writing a worktree's `.env.local` with `bun scripts/local/env.ts local` is safe while other sessions use the stack. (2026-10-14, TV-U18)
- **The local stack runs in OrbStack, but the shell's Docker context can be Docker Desktop, where `supabase status` finds nothing.** `docker ps` showed no `supabase_*_moduo` container while the stack was up and healthy (`docker --context orbstack ps` lists them), so `bun run env:local` couldn't read the key. Run it as `DOCKER_HOST=unix://$HOME/.orbstack/run/docker.sock bun run env:local`. And with parallel lanes on the one shared stack, don't `local:reset` to try a migration (it wipes what the others applied): apply your file with `psql … -f supabase/migrations/<yours>.sql` and run `bun run db:test <name>`. (2026-10-15, MOD-141)
- **Making the repo public published every pushed Entire checkpoint.** Entire's pre-push hook had uploaded full agent transcripts as `refs/entire/*`; on 2026-10-07 the repo went public with 79 of them on GitHub (secret values were redacted by Entire, the conversations were not). They were deleted from the remote and kept locally, and pushing is now off. A gitleaks scan of all history the same day also found a committed desktop login session file (`src-tauri/.moduo_keychain_*`, now untracked and ignored) and the Modal key in old `opencode.json` history (revoked). Before changing repo visibility again, run `gitleaks git` over all refs and check `git ls-remote origin` for anything that isn't code.

- **A linter upgrade can turn `bun run verify` red on files nobody touched.** On 2026-10-07 Biome 2.5.15 started linting the scripts and styles inside `apps/landing/index.html` (41 errors) and the vitest→rstest switch left 16 files with unsorted imports, so verify failed for every session while CI, which didn't run Biome, stayed green. LINT-1 fixed it: safe import fixes in `src/`, Biome linting switched off for `apps/landing/**` (a hand-written, separately deployed page in classic script with intentional CSS fallbacks; `landing-v4` would have added 15 more errors), and `bun run lint:js` in `checks.yml`, so CI now catches it. After any toolchain bump (including the `.bun-lint-version` canary pin), run `bun run lint:js`, not just typecheck and tests.

- **`maciej` is a hot branch — merge-commit into it, never fast-forward.** Before editing in a worktree, **check the worktree's base vs `maciej`** (`git rev-list --left-right --count HEAD...maciej`) — sessions have started on a weeks-stale `main` base and edited stale copies of `CLAUDE.md` / `DESIGN_SYSTEM.md` / `tokens.css`. Cut `t/<owner>/<kebab>` off `maciej`, not `main`. A `SessionStart` hook (`.claude/hooks/session-start.sh`) now runs this check automatically and warns on a stale base at session start — but only takes effect once it's merged into `maciej`. → [CONTRIBUTING.md](../../CONTRIBUTING.md)
- **Parallel sessions running `/execute next` off the same base CLAIM THE SAME BLOCK.** `BUILD_ORDER.md` reflects *merged* state only; an open PR that hasn't merged into `maciej` is invisible to it, so a new session off `maciej` sees the block still `[ ]` and `/execute next` deterministically picks it again. On 2026-06-27 three sessions each built CT-4 and/or CT-5 this way → duplicate files + two migrations creating the same tables (PRs #31/#32/#33 had to be reconciled by hand). `/execute next` is a *read*, not a *claim*. **Avoid:** give each parallel session an **explicit** block (`/execute CT-6`, not bare `next`), and/or **merge each block into `maciej` before starting the next round** (the "merge barrier" BUILD_ORDER already prescribes). `/wrap` now auto-merges into the personal branch + runs a duplication guard precisely to keep the ledger advancing so this can't recur. → [specs/BUILD_ORDER.md](../../specs/BUILD_ORDER.md)
- **`gh` can be signed in to the WRONG account, and git then reports the repo as nonexistent — not as an auth failure.** `gh auth status` lists every logged-in account but only one is *active*; if the active one lacks access to `GrochowskiMichal/moduohyb`, both `git fetch` and `gh api` fail with **`remote: Repository not found` / HTTP 404**, which reads exactly like a bad remote URL or a deleted repo. (This machine holds two accounts — `rdstudio-dev` and `En5hi`; only `En5hi` can see this repo, and the active one silently reverts.) **The damage is specifically to staleness guards:** a session that concludes "no network" falls back to the *local* `origin/maciej` ref, which can be many commits and several merged blocks behind — DOC-1 planned its whole reconcile against a ref that was 4 commits stale and had to redo ~10 claims at wrap when the real `maciej` turned out to have shipped DF-18. **Before trusting any "the remote is unreachable" conclusion, run `gh auth status` and check *which* account is active**; fix with `gh auth switch --hostname github.com --user En5hi`. Verify the remote really is live with `git ls-remote --heads origin maciej` — it prints the true head SHA, so it doubles as the freshness check. (2026-08-14.)

## Claude Code / skills

- **`Write(path)` permission rules do nothing; only `Edit(path)` is matched for file tools.** Claude Code warns once at start ("is not matched by file permission checks") and then ignores the rule, so a `Write(**/*.test.*)` deny lets Write through. One `Edit(<glob>)` rule covers Edit, Write and NotebookEdit (checked live 2026-10-26, HV-18). And srt's `denyWrite` globs (`**/*.test.*`) apply on macOS only; on Linux srt skips write patterns, so the frozen-tests sandbox layer holds only on the Mac.
- **A hook added to `.claude/settings.json` doesn't run in the session that added it**: Claude Code reads the hooks when the session starts. REL-3's session pushed `v1.2.0` with `guard-release.sh` not yet loaded, so the marker wasn't consumed and had to be removed by hand. Test a new hook with its test script, and expect it to work only from the next session. (2026-10-19, REL-3)

- **`/plugin` and `claude plugin …` commands rewrite `.claude/settings.json`.** They reorder its keys, and on 2026-10-08 `claude plugin install ts7-lsp@moduo-local --scope project` also deleted the `moduo-local` entry from the project's `extraKnownMarketplaces` because the same marketplace was declared in user settings; committed, that would have broken the plugin on every other machine. After any plugin command, run `git diff .claude/settings.json` and revert only the hunks you didn't mean to change (`git checkout -p .claude/settings.json`). Add project plugins by editing the JSON, not through `/plugin`.
- **The TypeScript language server answers navigation but reports no type errors after an edit.** TypeScript 7's `tsc --lsp` (the `ts7-lsp` project plugin) only publishes diagnostics for `tsconfig.json`, never for `.ts`/`.tsx` files, so a clean LSP result after an edit proves nothing. Use it for go-to-definition, references and hover; run `bun run typecheck` for errors. Rust is different: `rust-analyzer-lsp` does report diagnostics.
- **Edit `AGENTS.md`, never `CLAUDE.md`.** CLAUDE.md is a one-line pointer (since 2026-07-14): OpenCode gives `AGENTS.md` precedence and ignores CLAUDE.md entirely once it exists, and Claude Code just follows the pointer — so an edit to CLAUDE.md changes *nothing* in either tool. Same for skills: `.claude/skills/` is the **one home both tools discover** — don't copy skills into `.opencode/skills/` (they'd drift); `.opencode/` holds only the thin `/s1-3` command wrappers and the `validator` subagent. → [AGENTS.md](../../AGENTS.md)
- **Install a third-party skill as plain files, not with its `npx skills add` installer.** The installer writes the real files into `.agents/skills/`, symlinks them into `.claude/skills/` and adds a `skills-lock.json`; committing the symlinks alone gives every other clone dangling links (Subframe nearly shipped that in `942a66b`). Copy the skill folder from upstream into `.claude/skills/<name>/`, keep its `LICENSE`, record the upstream commit in [docs/agent-setup.md](../agent-setup.md), and check `git diff --cached --raw` shows no mode `120000`. (2026-10-17, libraries-dev) → `.claude/skills/`
- **Global skills are shared with Junction.** `~/.agents/skills/*` and `~/.claude/skills/impeccable/` are loaded by *every* project. Do **not** edit them for Moduo work — Moduo-specific skills/commands live **repo-local** in `.claude/skills/` and `.claude/commands/`. → `.claude/skills/`
- **A reserved built-in slash command silently shadows a same-named project skill — the built-in wins and the skill is unreachable.** Our workflow skills were named `plan`/`execute`/`wrap`; `/plan` is a reserved built-in (enter plan mode), so typing `/plan` hit the gated built-in ("isn't available in this environment") and NEVER ran the project skill — invocable only via the Skill tool, not the slash command. **Renamed 2026-07-08 to the stage-numbered `/s1` (plan) · `/s2` (execute) · `/s3` (wrap)** (bare numbers = terse + collision-proof; the command name comes from the **directory** name, `name:` frontmatter is display-only). When adding a project skill, avoid the reserved list (`/plan`, `/review`, `/simplify`, `/verify`, `/loop`, `/run`, `/init`, `/compact`, `/ultraplan`, `/ultrareview`, … — all single words); a hyphenated or numbered name is safe. No restart/cache-clear needed — Claude Code watches skill dirs live (a fresh session or `/reload-skills` picks up the rename). → `.claude/skills/s1|s2|s3/`
- **A worktree-isolated agent's Bash guard refuses heredocs, `psql -F'|'`, arguments built from shell variables, and loops or pipelines it can't parse; `cd <worktree> && <plain command>` is fine.** SQL is the usual casualty: write it to a file with the Write tool and run `psql -X -f <absolute path>`, and spell every path out in full instead of building it in a variable. (CV-0 spikes 4 and 5)

- **`bun run verify` fails `test:scripts` ("stop: no agent name → the key name") in a shell where `MODUO_AGENT_NAME` is set,** because the presence-hook test inherits it. Not a regression: run it as `env -u MODUO_AGENT_NAME bun run verify`. (DB-PERF-1, 2026-10-22)

- **Run one `/product-lab` at a time per Mac.** Every run re-seeds the lab people (`lab*@moduo.local`) with fresh workspaces and soft-deletes their previous ones, so two runs at once (two worktrees) delete each other's data mid-capture. It never touches `dev@` or another spec's people. Its preview server takes `LAB_PORT` (default 4317) if two lanes need the build at once. (2026-10-23)
- **Playwright's WebKit tabs only to text fields**, as Safari does until someone turns on keyboard navigation, so a Tab walk in WebKit skips every button and link. The lab's focus walk always runs in Chromium for that reason; keyboard journeys should use the app's shortcuts, not Tab. (2026-10-23)

- **A lane can't get its own Claude config folder without a fresh login.** With `CLAUDE_CONFIG_DIR` set to a new folder, `claude -p` answers "Not logged in": on macOS the login sits in the Keychain under a name derived from the config folder (`Claude Code-credentials-<hash>`), and the new folder's `.claude.json` also loses the workspace trust, so project allow rules are ignored. Lanes keep the shared `~/.claude` and run with `~/.claude.json` write-denied instead (`.claude/sandbox/lane.srt.json`). Isolating fully would need a `claude setup-token` token in `CLAUDE_CODE_OAUTH_TOKEN`. Also: srt takes the command string with `-c`; a single positional string is treated as the program name. (2026-10-24, HV-1 live lane run)

- **srt's `allowLocalBinding` opens every localhost port, so `127.0.0.1:<port>` entries in `allowedDomains` restrict nothing.** On macOS, local binding adds `(allow network-outbound (remote ip "localhost:*"))`; a sandboxed `nc 127.0.0.1 54322` reached the shared stack's Postgres with only the model API allowlisted. Without local binding rstest dies on its port probe (`listen EPERM ::1:3000`). The A/B rig closes the stack's ports with `scripts/harness-ab/srt-offline.mjs`; HV-1's lane profile still allows all of localhost. macOS also refuses `sandbox-exec` inside another sandbox (`sandbox_apply: Operation not permitted`), so an outer deny layer around srt doesn't work. (2026-10-26, HV-20)

## Subframe MCP / CLI

- **The Subframe MCP's OAuth token expires after about 1–2 hours and isn't always refreshed mid-session.** A 401 `invalid_token` after a long idle is an expired token, not a broken setup: log in again (`claude mcp login subframe`). (Found 2026-10-01, under OpenCode; carried over from the unmerged `t/maciej/api-key-scopes`.)
- **`design_component` jobs are rate-limited, about one per 5–8 minutes per account.** Fire five or more at once and every call is rejected for minutes. Run them one after another with backoff. Read tools (`list_*`, `get_*`, `wait_for_jobs`) aren't limited.
- **Bulk design-system import (`npx @subframe/cli import --manifest …`) is gated per team.** "Design system import is not enabled for this team" is an access gate, not a bug (request access at https://tally.so/r/3jv511). Incremental `design_component` imports give the same quality (the same agent, per Subframe's own skill doc); bulk only saves orchestration. A manifest is at `.subframe/import-design-system.json`, generated 2026-10-01: regenerate it against today's components before you use it.
- **`bun run verify` fails `moduo-report.test.ts` on a Mac where `MODUO_AGENT_NAME` is exported.** The hook's shell test (`tools/claude-plugins/moduo-agent/hooks/moduo-report.test.sh`) checks the "no agent name → key name" fallback and inherits your real agent name. CI has no such variable and passes. Locally, run `env -u MODUO_AGENT_NAME -u MODUO_MCP_KEY bun run verify` until the test clears those variables itself. (2026-10-22, MOD-517)
