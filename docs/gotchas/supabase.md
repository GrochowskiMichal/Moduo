# Gotchas: Supabase, migrations, Realtime, caching

Read before working in `supabase/`, `src/lib/runtime*`. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Supabase / migrations

- **The local stack is one database for every session on the Mac; a reset wipes the others' work.** On 2026-10-16, five builder lanes and a migration lane ran against it at once. A `local:reset` (or `supabase db reset` / `stop --no-backup`) from any one of them would have erased the others' applied migrations and test rows mid-run. `stack.sh` now refuses reset and down without `MODUO_SHARED_STACK_OK=1`, and the project settings deny the raw commands (AGENTS.md rule 13). Apply your migration on top with `psql … -1 -f`. When a test fails because the shared DB lacks someone else's migrations (e.g. `chat_privacy.test.sql` before Chat v2's are loaded), report it; don't reset to "fix" it. → [scripts/local/stack.sh](../../scripts/local/stack.sh)

- **A `db push` from a scratch folder needs two things the repo's `config.toml` doesn't give it:** copy `supabase/templates/` next to it (the auth email templates are config paths, or the CLI refuses to load the config) and set `[db.migrations] enabled = true` in the scratch copy only (the repo keeps it off, so a push there silently says "up to date"). Always read the dry run's file list before the real push. (Chat v2 release, 2026-10-16)
- **Another session may apply a migration to prod between your snapshot and your push** (MOD-155 landed at 17:22 the day of the Chat release, under a different version than its file). Re-read prod's history count and newest version right before pushing, and grep your release files for every function the newcomer redefines. (Chat v2 release, 2026-10-16)
- **Never `supabase db push` from the repo folder: the repo's migration versions and prod's history don't match.** Most older files were renamed after applying, applied in the SQL editor, or came from another branch, so the CLI sees dozens of "unapplied" files. Push a release from a scratch folder that holds only the new files, plus an empty placeholder per version prod already has (decision 2026-10-14). Dry-run first with `--include-all`.
- **`supabase db push` writes `config.toml`'s Vault secrets to the target before migrating** unless you pass `--skip-vault`. Against prod, always pass it.
- **Removing a workspace member leaves `share.bypass` on for the rest of that transaction.** `share_member_removed` sets it with `set_config(..., true)` and never puts it back. In the app every removal is its own request, so nothing else runs under it; a SQL test that removes someone and then goes on runs every later write as system work (no assignment notices, for one), and its checks pass or fail for the wrong reason. Reset it right after (`PERFORM set_config('share.bypass', '', true)`). → [teams_routing.test.sql](../../supabase/tests/teams_routing.test.sql) (2026-10-13, TV-D13)
- **`updated_at` is the clock, `now()` is the transaction's start.** The tasks module's stamp trigger (`tasks_stamp_updated_at`) writes `clock_timestamp()`, so a row stamped in the same transaction as a `DEFAULT now()` row reads as *later* than it. "Changed since X was written" then says yes for X's own write. Stamp the marker with `clock_timestamp()` after the write it records (`import_rows.logged_at`), and in a SQL test move `updated_at` back with `SET LOCAL session_replication_role = replica` (the trigger re-stamps any plain UPDATE). → [import.test.sql](../../supabase/tests/import.test.sql) (2026-10-13, TV-D16)
- **Inside one SQL test every row carries the same `now()`.** The whole run is one transaction, so `created_at DESC` ties and "the newest notice" is whichever row the id breaks the tie towards; the grouped-notice lookups in `tasks_notify_spine` (`ORDER BY created_at DESC, id DESC`) behave the same way there. Pick a row by what it holds (its task ids, its recipient), never by order. → [teams_routing.test.sql](../../supabase/tests/teams_routing.test.sql) (2026-10-13, TV-D13)
- **Storage upsert needs SELECT + INSERT + UPDATE, and new buckets on current hosted Postgres must set `type`.** The JS client's `upload(..., { upsert: true })` is an insert that also updates, and it reads the object back — a policy set with only INSERT fails with a vague RLS error. `storage.buckets.type` (`STANDARD` / `ANALYTICS` / `VECTOR`) is `NOT NULL` on the hosted project; an insert that omits it fails. Profile pictures and workspace logos share the public `avatars` bucket (`profiles/{uid}/…`, `workspaces/{workspace id}/…`). → [20261001140000_avatars_bucket_workspace_mark.sql](../../supabase/migrations/20261001140000_avatars_bucket_workspace_mark.sql)

- **API-key migration is strict, not dual-read.** Browser code uses `PUBLIC_SUPABASE_PUBLISHABLE_KEY`; Edge Functions use the platform-provided `SUPABASE_SECRET_KEYS` JSON object and require its `default` value to start with `sb_secret_`. Do not add a fallback to legacy key variables: the point of this migration is to make old dependencies fail at deploy/config time, not survive silently. Create the new default secret key, verify that `SUPABASE_SECRET_KEYS.default` is injected into a canary function, then deploy the strict functions. Functions using user JWTs, Stripe signatures, workspace API keys, or public capability tokens still perform their own in-code authorization with `verify_jwt=false`.

- **The repo CANNOT bootstrap a database — `supabase db reset` does not work and never has.** At OPS-2 time prod had 73 applied migration versions while the repo holds 43 files, and no file at all exists for the 26 applied before `create_tasks_module` (the whole profiles/workspaces/notes/CRM/billing foundation) or for three later hardening applies — so **22 of prod's 44 tables are created by no migration** — including `profiles`, `workspaces`, `workspace_members`, `workspace_invites`, `notes`, `calendar_events`, `dashboard_layouts`. A fresh reset doesn't just order things ambiguously: most migrations *fail outright*, because their policies and FKs reference tables that were never created. Treat "it's in a migration file" as saying nothing about whether a fresh DB can be built. Fixing it means capturing a `00000000000000_baseline.sql` from prod — see [OPS-2's inventory](../reviews/ops-2-schema-reconciliation.md) §4.
- **The local stack's function grants are broader than prod's, so a probe there can pass for the wrong reason.** After `bun run local:reset` loads the snapshot, Postgres default privileges have granted `anon` and `authenticated` EXECUTE on every function, including service-only helpers like `perm_actor_id`. A SECURITY INVOKER trigger or policy that calls one works locally and fails on prod with `42501 permission denied for function …`, the same SQLSTATE a deliberate refusal uses (found 2026-10-10, before it shipped). Before probing grants, replay prod's: `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;` then the snapshot's `REVOKE/GRANT ALL ON FUNCTION "public".…` lines (`grep -E '^(REVOKE|GRANT) ALL ON FUNCTION "public"' ~/.cache/moduo/supabase-snapshot/public.sql`). Make triggers that call `perm_actor_id()` SECURITY DEFINER, and have probes assert the refusal's message, not just `42501`. → [supabase/probes/write-checks.probe.sql](../../supabase/probes/write-checks.probe.sql)
- **The local stack has no Realtime: the prod snapshot carries no publication membership.** `pg_dump --schema public` leaves out `ALTER PUBLICATION … ADD TABLE`, and `stack.sh` replays only migrations newer than the snapshot, so after `bun run local:up`/`local:reset` the `supabase_realtime` publication is empty: every subscription joins, says SUBSCRIBED and never gets an event, with no error (found 2026-10-10, TV-D5). Check `select tablename from pg_publication_tables where pubname = 'supabase_realtime'` (prod has 9: the 3 chat tables and the 6 from TV-D5) and re-apply the idempotent publication blocks of `20261006150000_chat_module.sql` and `20261008223000_tasks_realtime_publication.sql` with `psql -v ON_ERROR_STOP=1 -f`. Never `supabase migration up` against the local stack: it has no migration history and would replay every file. A permanent fix belongs in `scripts/local/stack.sh` bootstrap. Bit again 2026-10-20: the shared stack's publication held only the chat tables, so tasks-10k's "a project added or renamed" case waited for a project that never arrived live (it showed after a reload, which looks like a stale selector but isn't). Every table the migrations publish (grep `supabase_realtime` in `supabase/migrations/`) was re-added with an add-only `DO` block, no migration replay.
- **`REVOKE … FROM PUBLIC` does NOT revoke `anon` on Supabase.** Supabase's default privileges grant `anon` (and `authenticated`) EXECUTE on `public` functions *directly*, not via `PUBLIC`, so a revoke that names only `PUBLIC` (and even `authenticated`) leaves anon holding EXECUTE. This is why OPS-2 found **15 SECURITY DEFINER functions anon could call**, including six internal `*_op__guard*` helpers and the auth-less legacy `accept_workspace_invite`. **The surprise is where it went wrong:** each module's bulk op-grant *loop* already revokes anon correctly (`contacts_module.sql:550`, `calendar_module.sql:532`, `email_module.sql:538`), and contacts_module even comments the behaviour. What omitted anon were the **six hand-written per-guard REVOKE pairs a few hundred lines above the correct loop in the same file** (`email_module.sql:186-187,210-211`; `calendar_module.sql:147-148,180-181`; `contacts_module.sql:150-151,174-175`) — undetected since 2026-06-26 (~4.8 weeks for contacts). So the lesson is not "audit the loops": it is **one-off hand revokes drift from the loop pattern already present in the same migration** — if you are writing a bare `REVOKE` next to a file that has a grant loop, put it in the loop. Always assert the fix with `has_function_privilege('anon', …) = false`, never by reading the migration.
- **Internal SECURITY DEFINER helpers need `authenticated` revoked too, and they don't always look internal.** OPS-2 swept for what *anon* could call; nobody swept `authenticated`. `20260703120000_notes_module.sql` revoked `notes__purge_ids`, `notes__subtree_ids` and `notes_op__guard_note` from PUBLIC and anon only, the lines right below a `notes_op__guard` revoke that did name authenticated. So any signed-in user could hard-delete another workspace's trashed notes over `/rest/v1/rpc/notes__purge_ids`: the helper has no guard because its callers guard. Then `20261006210000_perm_sharing.sql` paired most of its functions with a REVOKE + GRANT but skipped `share_grant_workspace`, which isn't `__`-named, so it shipped executable by PUBLIC: an anonymous caller could share any item with a whole workspace at any level. Rules: a function only other definer functions call gets `REVOKE ALL … FROM PUBLIC, anon, authenticated` plus `GRANT EXECUTE … TO service_role`, inside the grant loop; name it `*__*` so the convention flags it; assert `has_function_privilege` for **both** client roles; and after any migration that adds definer functions, run `bun run db:reconcile` query 4 (client-callable `*__*` helpers, plus every definer function anon can run outside `ANON_DEFINER_ALLOWED`). The revoke never breaks the callers: a definer function runs as its owner, so caller grants don't apply inside it. That is how every notes op always reached the long-revoked `notes_op__guard`. → [20261007223443](../../supabase/migrations/20261007223443_revoke_notes_internal_helpers.sql), [20261008002050](../../supabase/migrations/20261008002050_revoke_sharing_helper_grants.sql)
- **RLS does not gate `TRUNCATE` — a table with RLS on but `GRANT ALL … TO anon` is still wipeable by anon.** The legacy `public.waitlist` (and `founders_interest`) shipped with RLS + anon holding SELECT/UPDATE/DELETE/TRUNCATE; PostgREST doesn't expose TRUNCATE, but any other path with the anon role does. Both are closed now (`20261001160000` and `20261007000830`). For server-only tables, `REVOKE ALL … FROM PUBLIC, anon, authenticated` and verify with `has_table_privilege('anon', 'public.x', 'TRUNCATE')`. Edge Functions here deploy fine from the CLI with `supabase functions deploy <fn> --project-ref wtoonrvuqumihpkbvwvs --no-verify-jwt --import-map supabase/functions/deno.json --use-api`.
- **Before revoking EXECUTE on a helper, check whether an RLS policy calls it — and what role that policy targets.** A policy for role `public` (which includes `anon`) that calls a helper anon can't run turns an anonymous query's clean empty result into `permission denied for function`. Scope the policy `TO authenticated` first, then revoke: TV-SEC1 did this for `tasks_module_can_access_workspace`, `profile_plan_tier_text` and `workspaces_owned_count_for_user` (signed-in callers and server code only). → `select … from pg_policies where qual like '%fn_name%'`
- **A text hash is NOT a drift check — normalize before you compare function bodies.** Comparing `pg_proc.prosrc` against the repo's `CREATE FUNCTION` body flags 19 of 110 functions here, and **all 19 are formatting**: prod stores `('edit','admin')` / `SET x=now()` where the files say `('edit', 'admin')` / `SET x = now()`, because email, contacts-v2 and workspace-roles were applied from a compacted copy. Strip comments, collapse whitespace, and drop spaces around `( ) , ; =` on *both* sides — then real drift is zero and visible. `bun run db:reconcile` bakes this in; use it rather than hand-rolling the comparison. → [scripts/db-reconcile.ts](../../scripts/db-reconcile.ts)
- **Applying a long-unapplied OLD migration can silently REGRESS an object that a NEWER, already-applied migration redefined.** Migrations are only safe in filename order; this repo routinely applies them *late* and *individually* via MCP `apply_migration`, so an old file's `CREATE OR REPLACE` runs **after** newer ones and wins. Before applying any back-dated migration, `grep -l "FUNCTION public\.<fn> *(" supabase/migrations/*.sql` for **every** object it touches and diff the bodies against the newest definition — if they differ, apply a corrected body, not the stale file. Live example: `20260704180000_email_snooze_followup.sql` re-asserts `spine_activity_targets_me`, which the *newer* `20260714120000` also re-asserts and which had been applied 2026-07-27 — so OPS-1's 2026-07-29 apply of the older file overwrote it. It was safe only because the two **executable** bodies are identical (they differ only in comments); that was luck, not design. Diff the executable SQL, not the file. When your file builds on a body from a migration that may not be applied yet, make it refuse to run before that one: a `DO` block that checks `pg_proc.prosrc` and raises (`20261008124500` checks that `contacts_op_create` already stamps `perm_actor_id()`). → [supabase/migrations/20260704180000_email_snooze_followup.sql](../../supabase/migrations/20260704180000_email_snooze_followup.sql)
- **Two migrations may not share a timestamp prefix — Supabase applies the directory in lexicographic filename order, so a collision leaves that pair's order UNDEFINED on a fresh bootstrap.** Two collisions had shipped unnoticed (`20260702160000` ×2, `20260712120000` ×2) because nothing in `bun run verify` reads `supabase/migrations/` — the SQL never executes locally, so a stamp typo is invisible until a `db reset` produces a schema that differs from prod. `src/lib/migration-order.test.ts` (OPS-1) is now that check, but it only sees one branch: parallel blocks pick stamps on their own branches (TV-D3 and TV-D5 collided twice on 2026-10-08: `20261008223000`, then `20261008224500`, each picked after a rename), so before picking one, and again right before merging, list the migrations in open PRs (`gh pr view <n> --json files`), and once a migration is on prod, stamp the file after everything prod applied before it; when it fails, re-stamp the *idempotent* file of the pair (the `ADD COLUMN IF NOT EXISTS` one, so a re-apply is a no-op) and pick its new stamp so the directory **replays prod's real apply order** — get that from `list_migrations`, not from the filenames. "Keep the stamp a prod-apply record names" is only a tie-break, and it did NOT discriminate in OPS-1's case because both files of each pair had one. Then **grep the docs for the old stamp** — a bare `migration \`<stamp>\`` reference silently re-points at the other file (decisions.md 2026-07-29). Note prod's `supabase_migrations.schema_migrations` versions are generated by MCP `apply_migration` *at apply time* and bear no relation to the filename stamp, so a rename cannot break prod **via MCP `apply_migration`** (how this repo deploys) — only the docs. It would matter to `supabase db push`, which refuses local files sorting *before* the last remote version without `--include-all`; both OPS-1 renames move earlier, so that path needs the flag.
- **Corollary — a `gotchas.md` entry can itself go stale, and this one did.** The ⚠️ bullet in §Email engine (EM-6/7/8) asserted `20260704180000`'s `notify_user_ids` branch "was NEVER APPLIED to prod". True when written (2026-07-14); false from 2026-07-27, when DF-21d's `20260714120000` landed — but it sat here unchanged, in the file every session is told to read first, until DOC-1 caught it (2026-08-14). **The rule this yields: a durable footgun doc records the *lesson*, never the *status*.** If an entry needs to name current deployment state, write the lesson here and put the state in [`specs/BUILD_ORDER.md`](../../specs/BUILD_ORDER.md) — a resolvable claim parked in a permanent doc is a landmine, because nothing prompts anyone to revisit it when it resolves. Same trap in the other direction: ~25 completed-block notes in BUILD_ORDER/decisions.md say "migration deploy-ready but unapplied", which is accurate *history* but reads as a present-tense TODO; both files now carry a banner saying so rather than 25 hand-edits. (DOC-1, 2026-08-14.)
- **The repo's own docs are NOT evidence of what prod has — probe the database, and check the catalog, not just `list_migrations`.** OPS-1's ledger entry listed `20260712120000_df9_task_notifications.sql` as unapplied when it had shipped 2026-07-13; conversely `20260704180000`'s predicate change sat undeployed for ~3 weeks while the docs implied otherwise (found by DF-21d's probe). Both directions of drift have now happened. `list_migrations` alone is also insufficient — it shows *names* someone typed at apply time, not objects; a partial apply, a hand-run `execute_sql`, or a differently-named apply all lie. Query `pg_proc` / `information_schema.columns` / `pg_trigger` for the specific objects before deciding what to apply — that is the whole point of OPS-2.
- **`DROP FUNCTION` + `CREATE` (or any change to a function's return columns) RESETS its grants → silently re-opens `EXECUTE` to `PUBLIC`/`anon`.** A fresh `CREATE FUNCTION` defaults `EXECUTE` to `PUBLIC`, so re-creating a previously-locked-down function (the only way to change its `RETURNS TABLE` shape — `CREATE OR REPLACE` can't) drops the earlier `REVOKE ... FROM anon` and re-grants it to everyone. DF-21b's `notifications_list` DROP+CREATE (to add `dismissed_at`) did exactly this, and its two new ops shipped PUBLIC-executable — a security-posture regression the internal `auth.uid()`/access guards *masked* (anon reads return nothing, anon writes no-op), so it passed the round-trip smoke test. **Every migration that DROP+CREATEs a function MUST re-apply its grants block** (mirror CT-5: `REVOKE ALL FROM PUBLIC, anon; GRANT EXECUTE TO authenticated`). And because the broken migration may already be applied to prod, the fix is a **corrective follow-up migration** (editing the original file only helps fresh DBs) — verify with `has_function_privilege('anon', 'public.fn(args)', 'EXECUTE') = false`. → [supabase/migrations/20260713120000_notification_dismiss.sql](../../supabase/migrations/20260713120000_notification_dismiss.sql), [CT-5 grant loop](../../supabase/migrations/20260626130000_spine_comments_notifications.sql)
- **A new migration is NOT applied by `bun run verify`.** `verify` only runs typecheck/lint/unit-tests; it never touches Postgres. A green PR with a new `supabase/migrations/*.sql` means the SQL *parsed in your head*, not that it deployed — server invariants (RLS, RPCs, FKs, generated columns) are unproven until the migration is applied to a Supabase instance and exercised by an authenticated round-trip (the manual-test layer). Apply the migration and regenerate `src/types/supabase.ts` before any code *depends* on the new tables/RPCs. Don't apply to the shared/prod project without authorization.
- **The app's Supabase client is typed since 2026-10-20 (`SupabaseClient<Database>`, `lib/runtime.db.ts`); before that it was untyped and a wrong `p_*` name surfaced only as PGRST202, which the "not deployed yet" fallbacks swallowed.** Three things to know: (1) `bun run db:types` generates from **prod**, not the local stack, because the shared local stack can lag prod (on 2026-10-20 it was missing half of chat v2) or carry another session's unmerged migration; `db:types:local` is for a migration still in development, but only on a stack that is up to date with prod; otherwise call the not-yet-shipped RPC through `untypedDb` with a "type it after db:types" comment (as `notes_op_move`'s `p_follow_parent` and `prefs_op_set` do), and keep its deploy-gap guard until it ships. (2) The generator types every RPC argument as non-null; `scripts/db-types.ts` adds `| null` to each, because Postgres accepts NULL for any argument and the runtime passes `null` on purpose. Don't "fix" call sites to `undefined`: that drops the argument and changes which default applies. (3) A table or RPC picked by a runtime string (sync feeds, per-kind templates) goes through `untypedDb(db)`; keep the names in a const map next to it. Throw with `runRpc`/`runQuery` (or `new DbError(error)`), which keep the PostgREST code. Mappers still take `r: any`, so a column rename is still silent there. (4) With the fallbacks gone, a local stack missing recent migrations makes reads throw (the Tasks bundle, sync feeds, templates) instead of reading empty: bring the local stack up to date (apply the missing repo migrations with `psql … -1 -f`) before `dev:web` against it.
- **`runtime.workspace.joinInvite(token)` returns the accepted *invite* row, NOT a workspace** — `{ id: <invite id>, workspace_id, role, email, status, … }`. Its return type is `Promise<any>` (untyped, see above), so `mapWorkspace(inviteRow)` typechecks and passes `verify` while producing a garbage `WorkspaceSummary`: `id` = the invite id, `name` = `undefined`, `role` derived from the invite. The joined workspace's real id is `invite.workspace_id`; resolve the actual summary from a refreshed workspace list (`refreshWorkspaces()` now returns the fresh list for exactly this) and select *that*. Never `selectWorkspace(inviteRow.id)` either — it selects a non-existent workspace (→ `selectedWorkspace` goes `null`, the switcher unmounts). Bit `joinWorkspace` pre-DF-24; it only hid because its one consumer used the return value as a truthiness check. → [workspace-provider.tsx](../../src/providers/workspace-provider.tsx)
- **Direction-agnostic link dedupe must use a collation that matches JS.** `entity_links.pair_key` (the unordered `least/greatest(type:id)` key) compares with `COLLATE "C"` (byte order) so it provably matches the TS `deriveLinkKey` (JS `<=` code-unit order). Plain `least/greatest` on `text` uses the DB's *default* collation (a locale on standard Supabase), which can order non-ASCII tokens differently than JS → the server-side and client-side dedupe keys silently disagree. Keep `spine_pair_key()` (SQL) and `deriveLinkKey()` (TS) in lockstep. → [src/lib/entity-links.ts](../../src/lib/entity-links.ts)
- **A plpgsql function returning a composite type returns an all-NULL *row*, not SQL NULL, after a `SELECT … INTO` that finds nothing.** `RETURN v_row;` when `v_row` is unset serializes (via PostgREST) as `{id:null,…}`, not `null` — callers expecting `null` get a truthy object. Guard with `IF v_row.id IS NULL THEN RETURN NULL; END IF;` (see `links_op_delete`, `contacts_op_unlink`).
- **Wiring a brand-new RPC into a live read path breaks that surface until the migration is deployed.** `verify` never applies migrations, and the prod apply is a separate step — so between merging code that calls `runtime.x.newRpc()` and deploying its migration, the call 404s and can break the feature for everyone (e.g. the notification bell). For a *new* RPC consumed on a hot read path, wrap the call in try/catch and **degrade gracefully** (fall back to the prior behavior / empty) so the app survives the gap; the new data simply appears once the migration lands. (See `workspace-provider.refreshNotifications` wrapping `spine.listNotifications`.) Mutations the user explicitly triggers can surface the error instead.
- **A plpgsql/SQL function with `RETURNS TABLE(...)` whose out-columns share names with a table in its body (e.g. `workspace_id`, `id`, `payload`) is an ambiguity trap.** It only works while *every* column reference in the body stays table-qualified (`ma.workspace_id`); a single later unqualified ref silently resolves to the out-param instead of the column. Keep refs qualified (or prefix out-params `o_`). (See `notifications_list`.)
- **Probing an `auth.uid()`-dependent trigger/op via `execute_sql` runs as the service role, where `auth.uid()` is NULL — so any generation keyed on the caller silently no-ops (often inside an `EXCEPTION WHEN OTHERS` guard) and your probe reads a FALSE NEGATIVE.** Applying the DF-9 trigger (2026-07-13) then closing a blocker in a bare probe generated `tasks.unblocked=0` — not because the trigger was broken, but because `module_activity_log` (attributes `actor_id=auth.uid()`) threw on the null actor and the trigger swallowed it. Set the JWT claim transaction-local **before** the write: `PERFORM set_config('request.jwt.claims', json_build_object('sub','<user-uuid>','role','authenticated')::text, true);` — then re-probe (it then read `=1`). Wrap the whole thing in a `DO $$ … RAISE EXCEPTION 'ROLLBACK_OK …' $$` so it rolls back with zero residue. → [docs/decisions.md](../decisions.md) DF-9 prod-apply
- **Deleting `supabase/functions/<name>/` does not undeploy the function.** The deployed copy keeps answering, with its secrets, until someone runs `supabase functions delete <name> --project-ref wtoonrvuqumihpkbvwvs` or deletes it in the dashboard, and any branch that still has the folder can deploy it again. Check from outside with a plain GET to `/functions/v1/<name>`: the gateway answers `404 {"code":"NOT_FOUND"}` once it's gone, while a live function answers itself (`founders-apply` returned `405`). Log the undeploy in decisions.md and land the removal on every branch people deploy from. **Now a check:** `bun run functions:reconcile` lists every deployed function that has no folder here and exits 1 on one; it only reads, so the delete stays a human step. → [scripts/functions-reconcile.ts](../../scripts/functions-reconcile.ts) · [docs/decisions.md](../decisions.md) 2026-10-07
- **A per-IP rate limit in an Edge Function reads `cf-connecting-ip`, through [`_shared/client-ip.ts`](../../supabase/functions/_shared/client-ip.ts), not the leftmost `x-forwarded-for`.** Probed on 2026-10-08 with a throwaway echo function: a plain request arrived with `cf-connecting-ip: <client>` and `x-forwarded-for: <client>,<client>, <internal hop>`. A request that sent its own `X-Forwarded-For` arrived with exactly the same values (the gateway rebuilt the header and dropped the forged entries), a forged `X-Real-IP` never arrived, and a request carrying its own `CF-Connecting-IP` was refused by Cloudflare (`error code: 1000`) before reaching the function. So the old leftmost-XFF code in `waitlist-join` wasn't spoofable that day, but only because of undocumented gateway behaviour that has differed before: a [2025 report](https://github.com/orgs/supabase/discussions/34647) shows `spoofed,<client>`. `cf-connecting-ip` is the header Cloudflare itself guarantees. The edge logs can't settle this: they record `cf_connecting_ip` and `x_real_ip` but not `x_forwarded_for`, and they show the gateway's view, not the function's. The project host has only A records, so every caller arrives over IPv4 today; the helper keys IPv6 callers by /64 for the day that changes. - **supabase-js signs a tab in from any `#access_token=…` URL unless `detectSessionInUrl` is `false`, and that is a login CSRF.** With the default implicit flow, auth-js's `_initialize` reads `access_token`, `refresh_token`, `expires_in` and `token_type` from the fragment of whatever app URL loaded, checks the token against `/auth/v1/user` and saves it over the current session. ## The shared store and delta reads (TV-D11a)

- **A delta read by `updated_at` loses rows unless it pages by key and starts early.** Offset pages shift when a row in an earlier page is saved mid-read (it moves to the end), so the row that slid past the page edge is never read, and its stamp is older than the new cursor; a transaction stamped at T1 can also commit after you read T2. The store reads `updated_at >= cursor − 5 min`, ordered by (`updated_at`, `id`) and paged with `or=(updated_at.gt."T",and(updated_at.eq."T",id.gt.X))` (timestamps double-quoted inside `or=`), and dedupes by newest stamp. The hard-delete tables (`task_queue`, `tag_links`, `task_relations`) delta too since TV-D11b: their rows carry `updated_at` and a delete leaves a row in `sync_tombstones`, so a delta reads both streams and starts the next read at the earlier cut (`deltaCursor`); a database without that migration answers whole. → [runtime.web.tasks.ts](../../apps/app/src/lib/runtime.web.tasks.ts) `readByKey` / `syncReadTable` / `readTombstonedChanges`, [kernel/delta.ts](../../apps/app/src/lib/sync/kernel/delta.ts) `readDelta` / `keysetAfter` / `deltaCursor`
- **A row RLS stops returning never shows up in a delta, and Realtime sends nothing for it.** A project made private, or a member removed, leaves its rows on the device forever unless something compares ids. The store checks every live id of its tables after the first delta of a session and then every 10 minutes (`checkAccess`, `tasks.syncIds`), and purges what's gone, from the device copy too. → [store.ts](../../apps/app/src/lib/sync/store.ts)
- **postgrest-js retries a failed GET three times (1 + 2 + 4 s) before it answers with the error.** A lost connection therefore reads as "slow" for 7 s, then fails; an offline cold start waits that long per read. Reads that must fail fast (the store's) call `.retry(false)` and retry themselves. → [runtime.web.tasks.ts](../../apps/app/src/lib/runtime.web.tasks.ts) `syncReadTable`
- **supabase-js never throws on a lost connection: the error object's message is `TypeError: Failed to fetch` (Chromium), `Load failed` (Safari) or `NetworkError when attempting to fetch resource.` (Firefox).** `isNetworkError` matches those words (and `navigator.onLine === false`) to tell "keep it for later" from "the server said no". → [network.ts](../../apps/app/src/lib/sync/network.ts)
- **An op's answer can be older than the row the store already holds (a teammate's Realtime row landed first).** Answers apply unless the copy is strictly newer; Realtime rows only when strictly newer (an equal stamp is your own echo). Test fixtures whose answers carry an older `updated_at` than the loaded rows don't apply: give loaded rows an older stamp. → [kernel/landing.ts](../../apps/app/src/lib/sync/kernel/landing.ts) `lands` / `LandedRows.applyRows`
- **A null session is not a sign-out.** auth-js's `getSession()` answers `{ session: null, error }` when an expired access token can't refresh (offline), and `INITIAL_SESSION` emits null too, while the session stays in storage and comes back online. Wiping anything per person on "session is null" deleted offline captures; wipe only on the `SIGNED_OUT` event (and account deletion). → [auth-provider.tsx](../../apps/app/src/providers/auth-provider.tsx), `wipeSyncCopies` / `attachSyncUser`
- **A delete must leave a mark, or a read already on its way brings the row back.** A delta in flight still holds the old version of anything changed in its lookback window; a whole read of the queue started before a removal still has the row. The store keeps the deleted row's stamp (an older version never lands, a restore does) and when each id went (a read that began earlier skips it). → [kernel/landing.ts](../../apps/app/src/lib/sync/kernel/landing.ts) `LandedRows` (`applyRows`, `forget`, `replaceSlice`)
- **A write debounce starves under a steady stream of changes.** The device copy's write was debounced (each change put it off another 800 ms); with teammates saving all the time it was never written. Throttle instead: the first change schedules the write, later ones ride along. → [store.ts](../../apps/app/src/lib/sync/store.ts) `schedulePersist`
- **An IndexedDB database can exist without its object store** (someone opened it without an upgrade handler, e.g. a test probe), and `open(name, 1)` then fires no upgrade: every transaction on the store throws, so every write fails quietly for good. Open without a version, check `objectStoreNames`, and reopen one version up to create the store. Tasks', Chat's and Notes' databases all open through the kernel's `idbOpener`. → [kernel/idb.ts](../../apps/app/src/lib/sync/kernel/idb.ts) `idbOpener`
- **A grant or a revoke moves no stamp, so delta sync never sees it.** Sharing a project with you (a `resource_grants` row, unpublished) makes its old tasks, statuses and sections visible with their old `updated_at`; taking it away hides them with no event. The store reads small sharing-dependent tables whole (projects, areas, teams), runs the access check when the projects you see change, and reads by id what the check finds new. → [store.ts](../../apps/app/src/lib/sync/store.ts) `checkAccess`
- **Nothing makes a person's Inbox but a read that asks for it.** The old `tasks.list` called `ensureWebInbox` on every open; with the store reading tables directly, a new member's first open had no Inbox and capture had nowhere to land. The store calls `seedInbox` once a session when it sees none of your own. → [store.ts](../../apps/app/src/lib/sync/store.ts) `ensureInbox`

- **A Realtime channel that names a table outside the publication (or one that doesn't exist) still says SUBSCRIBED, then delivers nothing for any of its tables.** Probed on the local stack (2026-10-11, TV-D11b): `tasks` + an unpublished `task_completions` on one channel got no `tasks` events; `tasks` + a published table did. A build ahead of its database would lose every live update. Put a newly published table on a channel of its own. → [realtime.ts](../../apps/app/src/features/tasks/realtime.ts) `LIVE_SIDE_TABLES`
- **RLS costs about 0.2 ms per task row (`can_access` in plpgsql), and a filter that isn't leakproof runs after it.** At 10,000 tasks a whole read or an id check takes about 2 s on the local stack, and `title ILIKE '%x%'` under RLS checks access on every row first (2 s for 20 matches). Indexable leakproof conditions (`workspace_id =`, `updated_at >=`) are applied first, so deltas stay cheap. A search that filters text must test the text first and the access per match: SECURITY DEFINER, as `tasks_search` does. → [20261011120000_tasks_sync_feed_search.sql](../../supabase/migrations/20261011120000_tasks_sync_feed_search.sql)
- **An AFTER DELETE trigger that writes a row pointing at the deleted row's parent breaks the parent's cascade.** Deleting a workspace (or an account, whose erasure deletes owned workspaces) cascades to `task_queue`, `tag_links`, `resource_grants`…; a trigger there that inserts a tombstone or a feed row referencing that workspace (or that person) fails the whole delete with a foreign key error (23503). TV-D11b's validator caught it before apply. Such a trigger returns early when the parent is gone (`NOT EXISTS (SELECT 1 FROM public.workspaces WHERE id = OLD.workspace_id)`), and `sync_feed.test.sql` deletes a workspace and an account to prove it. → [20261011120000_tasks_sync_feed_search.sql](../../supabase/migrations/20261011120000_tasks_sync_feed_search.sql)
- **Since TV-D11b the grant feed (`access_changes`) tells the store when a share changes, but the store's first read of a session only takes the feed's cursor.** What changed while the app was closed is the session's first access check's job (it runs after the first delta); don't "replay" the feed's lookback from before the session (it re-ran a whole check for old changes). → [store.ts](../../apps/app/src/lib/sync/store.ts) `readAccessFeed`
- **`store.sendStatus` doesn't touch the queue: after a check-off the copy can still show the row the server dropped (finishing leaves every queue), until the tombstone arrives.** TV-H1's Home Undo first checked "is it still in my line-up?" against the copy, found the stale row and skipped putting the task back in Focus. The module hides this with `queueFollowStatus`; outside it, decide queue placement from a queue op's answer (`opQueueAdd` answers with my whole line-up on the server), never from the copy, and filter queue rows to open tasks before counting them. → [check-off.ts](../../apps/app/src/features/tasks/check-off.ts) `restoreFocusPlace`

## Boot-time read caching (DF-12)

- **`supabaseClient.auth.getUser()` is a network round-trip to `/auth/v1/user`, and ~16 runtime methods called it independently** (every user-scoped read/write resolves the user first). That's why one boot fired it ×8. It's now deduped through `getAuthedUser()` ([runtime.web.shared.ts](../../apps/app/src/lib/runtime.web.shared.ts)) over the shared [`request-cache`](../../apps/app/src/lib/request-cache.ts). Any NEW runtime method that needs the current user must call `getAuthedUser()`, **never** `supabaseClient.auth.getUser()` directly, or it reintroduces a per-call `/auth/v1/user` hit.
- **Caching an auth/identity read at Infinity TTL is a session-brick trap unless you cache ONLY success.** `getUser()` returns `{data:{user:null}, error}` (it does NOT throw) on BOTH a transient failure (offline / mid-refresh 401 / 5xx) AND a genuine sign-out. If you cache that `null` at a long TTL, one boot blip pins `null` for the whole session → every read returns empty and every write fails RLS (`owner_id=""`), recoverable only by a real sign-in. `getAuthedUser` avoids it by **throwing** inside the fetcher on error-or-null (so `request-cache` never retains it) and returning `null` from an outer catch — same graceful `User | null` at call sites, but failures self-heal on the next call. Mirror this for any future Infinity-TTL cache: retain only a positive result.
- **A shared read-cache must clear its in-flight repopulation on invalidate, or a sign-out races back the old user.** `request-cache` guards this with a module `epoch` bumped on `invalidate`/`clear`; a fetch only writes back if `epoch` is unchanged since it started. Without it, a `getUser` in flight when `SIGNED_OUT` clears the cache would resolve after and re-cache the signed-out user.
- **A boot read-cache keyed by a fixed string (not the userId) leaks across a fast account switch on a shared browser.** `getCloudPrefs` cached prefs under a single `"prefs"` key; within its TTL a `SIGNED_OUT`→`SIGNED_IN(B)` would serve A's cached prefs to B (B adopts A's theme/accent, re-stamped as B's). Key any user-scoped cache by `userId` (`prefs:${userId}`) so a different user is a cache miss. → [src/lib/prefs-sync.ts](../../apps/app/src/lib/prefs-sync.ts)
- **A pure read path must not issue a write.** `layout-repo.load()` used to fire-and-forget a `dashboard.save()` to reconcile a cache-wins load up to the cloud — a `POST` on every boot that resolved to the local cache. Removed for DF-12: the local cache is the device's truth and a cut-off edit rides up on the next `save`, so cross-device propagation is delayed at most one edit, never lost. ## Edge Functions calling PostHog (PRIV-3)

- **PostHog has two hosts, and deleting a person takes a JSON body its API reference doesn't show.** Events go to the ingestion host `eu.i.posthog.com`; the private API (persons, deletion) is `https://eu.posthog.com`, with a personal API key (`phx_…`, scope `person:write`), never the public project key (`phc_…`). `POST /api/projects/<id>/persons/bulk_delete/` reads `distinct_ids` / `delete_events` from the **JSON body**, although the reference lists them as query parameters; it answers **202** with a summary, and an unknown distinct id is still a 202 (`persons_found: 0`). The person goes at once; the events are only **queued** for PostHog's weekly run (Sundays 05:00 UTC), and only events PostHog already has go, which is why `analytics-forget` waits ~10 s before deleting (in the function, not the app, so the request leaves while the person is still signed in). An event sent after the deletion creates the person again, so `app_signed_out` is tracked only when the person signs out (never on a SIGNED_OUT auth-js fires itself), the Danger zone records a "no" before signing out, and analytics starts only once the profile read confirms the account (a cached session outlives an account deleted elsewhere by up to an hour). Treat only a timeout, 408, 429 or 5xx as worth retrying; any other 4xx, or a success that isn't JSON (a wrong host's web page), is a refusal. Otherwise one broken setting fails every account deletion. To deploy a function with large shared files, `supabase functions deploy <fn> --project-ref wtoonrvuqumihpkbvwvs --no-verify-jwt --use-api` from the repo root uploads exactly the files it imports (no Docker); the connector's `deploy_edge_function` needs every file's contents pasted in. → [posthog-erasure.ts](../../supabase/functions/_shared/posthog-erasure.ts), [analytics-forget.ts](../../supabase/functions/_shared/analytics-forget.ts)
