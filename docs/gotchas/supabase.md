# Gotchas: Supabase, migrations, Realtime, caching

Read before working in `supabase/`, `src/lib/runtime*`. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Supabase / migrations

- **Storage upsert needs SELECT + INSERT + UPDATE, and new buckets on current hosted Postgres must set `type`.** The JS client's `upload(..., { upsert: true })` is an insert that also updates, and it reads the object back — a policy set with only INSERT fails with a vague RLS error. `storage.buckets.type` (`STANDARD` / `ANALYTICS` / `VECTOR`) is `NOT NULL` on the hosted project; an insert that omits it fails. Profile pictures and workspace logos share the public `avatars` bucket (`profiles/{uid}/…`, `workspaces/{workspace id}/…`). → [20261001140000_avatars_bucket_workspace_mark.sql](../../supabase/migrations/20261001140000_avatars_bucket_workspace_mark.sql)

- **API-key migration is strict, not dual-read.** Browser code uses `PUBLIC_SUPABASE_PUBLISHABLE_KEY`; Edge Functions use the platform-provided `SUPABASE_SECRET_KEYS` JSON object and require its `default` value to start with `sb_secret_`. Do not add a fallback to legacy key variables: the point of this migration is to make old dependencies fail at deploy/config time, not survive silently. Create the new default secret key, verify that `SUPABASE_SECRET_KEYS.default` is injected into a canary function, then deploy the strict functions. Functions using user JWTs, Stripe signatures, workspace API keys, or public capability tokens still perform their own in-code authorization with `verify_jwt=false`.

- **The repo CANNOT bootstrap a database — `supabase db reset` does not work and never has.** At OPS-2 time prod had 73 applied migration versions while the repo holds 43 files, and no file at all exists for the 26 applied before `create_tasks_module` (the whole profiles/workspaces/notes/CRM/billing foundation) or for three later hardening applies — so **22 of prod's 44 tables are created by no migration** — including `profiles`, `workspaces`, `workspace_members`, `workspace_invites`, `notes`, `calendar_events`, `dashboard_layouts`. A fresh reset doesn't just order things ambiguously: most migrations *fail outright*, because their policies and FKs reference tables that were never created. Treat "it's in a migration file" as saying nothing about whether a fresh DB can be built. Fixing it means capturing a `00000000000000_baseline.sql` from prod — see [OPS-2's inventory](../reviews/ops-2-schema-reconciliation.md) §4.
- **`REVOKE … FROM PUBLIC` does NOT revoke `anon` on Supabase.** Supabase's default privileges grant `anon` (and `authenticated`) EXECUTE on `public` functions *directly*, not via `PUBLIC`, so a revoke that names only `PUBLIC` (and even `authenticated`) leaves anon holding EXECUTE. This is why OPS-2 found **15 SECURITY DEFINER functions anon could call**, including six internal `*_op__guard*` helpers and the auth-less legacy `accept_workspace_invite`. **The surprise is where it went wrong:** each module's bulk op-grant *loop* already revokes anon correctly (`contacts_module.sql:550`, `calendar_module.sql:532`, `email_module.sql:538`), and contacts_module even comments the behaviour. What omitted anon were the **six hand-written per-guard REVOKE pairs a few hundred lines above the correct loop in the same file** (`email_module.sql:186-187,210-211`; `calendar_module.sql:147-148,180-181`; `contacts_module.sql:150-151,174-175`) — undetected since 2026-06-26 (~4.8 weeks for contacts). So the lesson is not "audit the loops": it is **one-off hand revokes drift from the loop pattern already present in the same migration** — if you are writing a bare `REVOKE` next to a file that has a grant loop, put it in the loop. Always assert the fix with `has_function_privilege('anon', …) = false`, never by reading the migration.
- **RLS does not gate `TRUNCATE` — a table with RLS on but `GRANT ALL … TO anon` is still wipeable by anon.** The legacy `public.waitlist` (and `founders_interest`) shipped with RLS + anon holding SELECT/UPDATE/DELETE/TRUNCATE; PostgREST doesn't expose TRUNCATE, but any other path with the anon role does. Both are closed now (`20261001160000` and `20261007000830`). For server-only tables, `REVOKE ALL … FROM PUBLIC, anon, authenticated` and verify with `has_table_privilege('anon', 'public.x', 'TRUNCATE')`. Edge Functions here deploy fine from the CLI with `supabase functions deploy <fn> --project-ref wtoonrvuqumihpkbvwvs --no-verify-jwt --import-map supabase/functions/deno.json --use-api`.
- **Before revoking EXECUTE on a helper, check whether an RLS policy calls it — and what role that policy targets.** `tasks_module_can_access_workspace`, `profile_plan_tier_text` and `workspaces_owned_count_for_user` are anon-callable and leak real values, but 22 policies invoke them and every one is defined for role `public` (which includes `anon`). Revoking would convert an anonymous query's clean empty result into `permission denied for function`. Scope the policies `TO authenticated` first, then revoke. → `select … from pg_policies where qual like '%fn_name%'`
- **A text hash is NOT a drift check — normalize before you compare function bodies.** Comparing `pg_proc.prosrc` against the repo's `CREATE FUNCTION` body flags 19 of 110 functions here, and **all 19 are formatting**: prod stores `('edit','admin')` / `SET x=now()` where the files say `('edit', 'admin')` / `SET x = now()`, because email, contacts-v2 and workspace-roles were applied from a compacted copy. Strip comments, collapse whitespace, and drop spaces around `( ) , ; =` on *both* sides — then real drift is zero and visible. `bun run db:reconcile` bakes this in; use it rather than hand-rolling the comparison. → [scripts/db-reconcile.ts](../../scripts/db-reconcile.ts)
- **Applying a long-unapplied OLD migration can silently REGRESS an object that a NEWER, already-applied migration redefined.** Migrations are only safe in filename order; this repo routinely applies them *late* and *individually* via MCP `apply_migration`, so an old file's `CREATE OR REPLACE` runs **after** newer ones and wins. Before applying any back-dated migration, `grep -l "FUNCTION public\.<fn> *(" supabase/migrations/*.sql` for **every** object it touches and diff the bodies against the newest definition — if they differ, apply a corrected body, not the stale file. Live example: `20260704180000_email_snooze_followup.sql` re-asserts `spine_activity_targets_me`, which the *newer* `20260714120000` also re-asserts and which had been applied 2026-07-27 — so OPS-1's 2026-07-29 apply of the older file overwrote it. It was safe only because the two **executable** bodies are identical (they differ only in comments); that was luck, not design. Diff the executable SQL, not the file. → [supabase/migrations/20260704180000_email_snooze_followup.sql](../../supabase/migrations/20260704180000_email_snooze_followup.sql)
- **Two migrations may not share a timestamp prefix — Supabase applies the directory in lexicographic filename order, so a collision leaves that pair's order UNDEFINED on a fresh bootstrap.** Two collisions had shipped unnoticed (`20260702160000` ×2, `20260712120000` ×2) because nothing in `bun run verify` reads `supabase/migrations/` — the SQL never executes locally, so a stamp typo is invisible until a `db reset` produces a schema that differs from prod. `src/lib/migration-order.test.ts` (OPS-1) is now that check; when it fails, re-stamp the *idempotent* file of the pair (the `ADD COLUMN IF NOT EXISTS` one, so a re-apply is a no-op) and pick its new stamp so the directory **replays prod's real apply order** — get that from `list_migrations`, not from the filenames. "Keep the stamp a prod-apply record names" is only a tie-break, and it did NOT discriminate in OPS-1's case because both files of each pair had one. Then **grep the docs for the old stamp** — a bare `migration \`<stamp>\`` reference silently re-points at the other file (decisions.md 2026-07-29). Note prod's `supabase_migrations.schema_migrations` versions are generated by MCP `apply_migration` *at apply time* and bear no relation to the filename stamp, so a rename cannot break prod **via MCP `apply_migration`** (how this repo deploys) — only the docs. It would matter to `supabase db push`, which refuses local files sorting *before* the last remote version without `--include-all`; both OPS-1 renames move earlier, so that path needs the flag.
- **Corollary — a `gotchas.md` entry can itself go stale, and this one did.** The ⚠️ bullet in §Email engine (EM-6/7/8) asserted `20260704180000`'s `notify_user_ids` branch "was NEVER APPLIED to prod". True when written (2026-07-14); false from 2026-07-27, when DF-21d's `20260714120000` landed — but it sat here unchanged, in the file every session is told to read first, until DOC-1 caught it (2026-08-14). **The rule this yields: a durable footgun doc records the *lesson*, never the *status*.** If an entry needs to name current deployment state, write the lesson here and put the state in [`specs/BUILD_ORDER.md`](../../specs/BUILD_ORDER.md) — a resolvable claim parked in a permanent doc is a landmine, because nothing prompts anyone to revisit it when it resolves. Same trap in the other direction: ~25 completed-block notes in BUILD_ORDER/decisions.md say "migration deploy-ready but unapplied", which is accurate *history* but reads as a present-tense TODO; both files now carry a banner saying so rather than 25 hand-edits. (DOC-1, 2026-08-14.)
- **The repo's own docs are NOT evidence of what prod has — probe the database, and check the catalog, not just `list_migrations`.** OPS-1's ledger entry listed `20260712120000_df9_task_notifications.sql` as unapplied when it had shipped 2026-07-13; conversely `20260704180000`'s predicate change sat undeployed for ~3 weeks while the docs implied otherwise (found by DF-21d's probe). Both directions of drift have now happened. `list_migrations` alone is also insufficient — it shows *names* someone typed at apply time, not objects; a partial apply, a hand-run `execute_sql`, or a differently-named apply all lie. Query `pg_proc` / `information_schema.columns` / `pg_trigger` for the specific objects before deciding what to apply — that is the whole point of OPS-2.
- **`DROP FUNCTION` + `CREATE` (or any change to a function's return columns) RESETS its grants → silently re-opens `EXECUTE` to `PUBLIC`/`anon`.** A fresh `CREATE FUNCTION` defaults `EXECUTE` to `PUBLIC`, so re-creating a previously-locked-down function (the only way to change its `RETURNS TABLE` shape — `CREATE OR REPLACE` can't) drops the earlier `REVOKE ... FROM anon` and re-grants it to everyone. DF-21b's `notifications_list` DROP+CREATE (to add `dismissed_at`) did exactly this, and its two new ops shipped PUBLIC-executable — a security-posture regression the internal `auth.uid()`/access guards *masked* (anon reads return nothing, anon writes no-op), so it passed the round-trip smoke test. **Every migration that DROP+CREATEs a function MUST re-apply its grants block** (mirror CT-5: `REVOKE ALL FROM PUBLIC, anon; GRANT EXECUTE TO authenticated`). And because the broken migration may already be applied to prod, the fix is a **corrective follow-up migration** (editing the original file only helps fresh DBs) — verify with `has_function_privilege('anon', 'public.fn(args)', 'EXECUTE') = false`. → [supabase/migrations/20260713120000_notification_dismiss.sql](../../supabase/migrations/20260713120000_notification_dismiss.sql), [CT-5 grant loop](../../supabase/migrations/20260626130000_spine_comments_notifications.sql)
- **A new migration is NOT applied by `bun run verify`.** `verify` only runs typecheck/lint/unit-tests; it never touches Postgres. A green PR with a new `supabase/migrations/*.sql` means the SQL *parsed in your head*, not that it deployed — server invariants (RLS, RPCs, FKs, generated columns) are unproven until the migration is applied to a Supabase instance and exercised by an authenticated round-trip (the manual-test layer). Apply the migration and regenerate `src/types/supabase.ts` before any code *depends* on the new tables/RPCs. Don't apply to the shared/prod project without authorization.
- **The Supabase JS client is untyped (`SupabaseClient`, no `Database` generic).** So `supabaseClient.from("a_table_that_doesnt_exist_yet")` and `.rpc("an_unmigrated_fn", …)` both **typecheck fine** — TS can't catch a table/RPC-name typo or an arg-shape mismatch against an unmigrated schema. New runtime methods for new tables pass `verify` even if the migration is wrong or unapplied; the only real check is the live round-trip. (Mappers take `r: any`, so column renames are silent too.)
- **`runtime.workspace.joinInvite(token)` returns the accepted *invite* row, NOT a workspace** — `{ id: <invite id>, workspace_id, role, email, status, … }`. Its return type is `Promise<any>` (untyped, see above), so `mapWorkspace(inviteRow)` typechecks and passes `verify` while producing a garbage `WorkspaceSummary`: `id` = the invite id, `name` = `undefined`, `role` derived from the invite. The joined workspace's real id is `invite.workspace_id`; resolve the actual summary from a refreshed workspace list (`refreshWorkspaces()` now returns the fresh list for exactly this) and select *that*. Never `selectWorkspace(inviteRow.id)` either — it selects a non-existent workspace (→ `selectedWorkspace` goes `null`, the switcher unmounts). Bit `joinWorkspace` pre-DF-24; it only hid because its one consumer used the return value as a truthiness check. → [workspace-provider.tsx](../../src/providers/workspace-provider.tsx)
- **Direction-agnostic link dedupe must use a collation that matches JS.** `entity_links.pair_key` (the unordered `least/greatest(type:id)` key) compares with `COLLATE "C"` (byte order) so it provably matches the TS `deriveLinkKey` (JS `<=` code-unit order). Plain `least/greatest` on `text` uses the DB's *default* collation (a locale on standard Supabase), which can order non-ASCII tokens differently than JS → the server-side and client-side dedupe keys silently disagree. Keep `spine_pair_key()` (SQL) and `deriveLinkKey()` (TS) in lockstep. → [src/lib/entity-links.ts](../../src/lib/entity-links.ts)
- **A plpgsql function returning a composite type returns an all-NULL *row*, not SQL NULL, after a `SELECT … INTO` that finds nothing.** `RETURN v_row;` when `v_row` is unset serializes (via PostgREST) as `{id:null,…}`, not `null` — callers expecting `null` get a truthy object. Guard with `IF v_row.id IS NULL THEN RETURN NULL; END IF;` (see `links_op_delete`, `contacts_op_unlink`).
- **Wiring a brand-new RPC into a live read path breaks that surface until the migration is deployed.** `verify` never applies migrations, and the prod apply is a separate step — so between merging code that calls `runtime.x.newRpc()` and deploying its migration, the call 404s and can break the feature for everyone (e.g. the notification bell). For a *new* RPC consumed on a hot read path, wrap the call in try/catch and **degrade gracefully** (fall back to the prior behavior / empty) so the app survives the gap; the new data simply appears once the migration lands. (See `workspace-provider.refreshNotifications` wrapping `spine.listNotifications`.) Mutations the user explicitly triggers can surface the error instead.
- **A plpgsql/SQL function with `RETURNS TABLE(...)` whose out-columns share names with a table in its body (e.g. `workspace_id`, `id`, `payload`) is an ambiguity trap.** It only works while *every* column reference in the body stays table-qualified (`ma.workspace_id`); a single later unqualified ref silently resolves to the out-param instead of the column. Keep refs qualified (or prefix out-params `o_`). (See `notifications_list`.)
- **Probing an `auth.uid()`-dependent trigger/op via `execute_sql` runs as the service role, where `auth.uid()` is NULL — so any generation keyed on the caller silently no-ops (often inside an `EXCEPTION WHEN OTHERS` guard) and your probe reads a FALSE NEGATIVE.** Applying the DF-9 trigger (2026-07-13) then closing a blocker in a bare probe generated `tasks.unblocked=0` — not because the trigger was broken, but because `module_activity_log` (attributes `actor_id=auth.uid()`) threw on the null actor and the trigger swallowed it. Set the JWT claim transaction-local **before** the write: `PERFORM set_config('request.jwt.claims', json_build_object('sub','<user-uuid>','role','authenticated')::text, true);` — then re-probe (it then read `=1`). Wrap the whole thing in a `DO $$ … RAISE EXCEPTION 'ROLLBACK_OK …' $$` so it rolls back with zero residue. → [docs/decisions.md](../decisions.md) DF-9 prod-apply
- **Deleting `supabase/functions/<name>/` does not undeploy the function.** The deployed copy keeps answering, with its secrets, until someone runs `supabase functions delete <name> --project-ref wtoonrvuqumihpkbvwvs` or deletes it in the dashboard, and any branch that still has the folder can deploy it again. Check from outside with a plain GET to `/functions/v1/<name>`: the gateway answers `404 {"code":"NOT_FOUND"}` once it's gone, while a live function answers itself (`founders-apply` returned `405`). Log the undeploy in decisions.md and land the removal on every branch people deploy from. **Now a check:** `bun run functions:reconcile` lists every deployed function that has no folder here and exits 1 on one; it only reads, so the delete stays a human step. → [scripts/functions-reconcile.ts](../../scripts/functions-reconcile.ts) · [docs/decisions.md](../decisions.md) 2026-10-07
- **A per-IP rate limit in an Edge Function reads `cf-connecting-ip`, through [`_shared/client-ip.ts`](../../supabase/functions/_shared/client-ip.ts), not the leftmost `x-forwarded-for`.** Probed on 2026-10-08 with a throwaway echo function: a plain request arrived with `cf-connecting-ip: <client>` and `x-forwarded-for: <client>,<client>, <internal hop>`. A request that sent its own `X-Forwarded-For` arrived with exactly the same values (the gateway rebuilt the header and dropped the forged entries), a forged `X-Real-IP` never arrived, and a request carrying its own `CF-Connecting-IP` was refused by Cloudflare (`error code: 1000`) before reaching the function. So the old leftmost-XFF code in `waitlist-join` wasn't spoofable that day, but only because of undocumented gateway behaviour that has differed before: a [2025 report](https://github.com/orgs/supabase/discussions/34647) shows `spoofed,<client>`. `cf-connecting-ip` is the header Cloudflare itself guarantees. The edge logs can't settle this: they record `cf_connecting_ip` and `x_real_ip` but not `x_forwarded_for`, and they show the gateway's view, not the function's. The project host has only A records, so every caller arrives over IPv4 today; the helper keys IPv6 callers by /64 for the day that changes. To re-probe: put an echo function in a scratch folder, `supabase functions deploy <probe> --workdir <scratch> --project-ref wtoonrvuqumihpkbvwvs --no-verify-jwt --use-api`, have it answer only requests with a random query token, compare a plain request with forged ones, then `supabase functions delete <probe>` and check for the gateway's 404 (above). (2026-10-08)
- **A hosted check that only hits the 400 path says nothing about the write.** `founders-apply` upserted `name` and `applied_at`, two columns `founders_interest` never had, so any valid request failed with PostgREST's unknown-column error (PGRST204) and a 500. Nobody noticed for five months: ZE-11's hosted check passed because it only posted an invalid email, and the untyped client (above) means tsc can't catch it either. When a function writes a table, compare the payload's keys with the table's columns (`src/types/supabase.ts` or `information_schema.columns`).

- **PostgREST's 1000-row cap is a HARD per-request ceiling — `.limit(5000)` does NOT lift it, and nothing tells you.** Probed live against the hosted project (SCALE-1, 2026-07-29) with 1,510 rows in scope: an unbounded select, `?limit=1201` and `?limit=5000` each returned exactly **1000** rows, `content-range: 0-999/*`, no error, no warning. `db-max-rows` bounds the *response*, not just the default. The repo had believed the opposite for months — `listTagLinks` carried an "explicit ceiling; PostgREST silently caps at 1000 otherwise; 5000" comment and was itself truncating at 1000. The only way past it is `.range()` paging: use [`readPaged`](../../src/lib/paged-select.ts), never a bare `.limit()` above 1000. Corollary for any "did I get everything?" check: the *exact* total needs `select("id", { count: "exact", head: true })` (`content-range: 0-999/1510`), which `readPaged` fires only when the cap actually bit.
- **Paging (`.range()`) is only correct under a TOTAL order — `position` / `name` / `created_at` all tie, and a tie across a page boundary silently skips one row and duplicates another.** Every paged read appends a unique tiebreaker (`.order("id")`) after its real sort. This is invisible in testing: the loss is a handful of rows in workspaces big enough to page at all. → [runtime.web.ts](../../src/lib/runtime.web.ts) `selectCapped`
- **Windowing the calendar events read by date deletes recurring events from the UI unless series rows bypass the window.** A series' stored `start_time` is its **first** occurrence — a weekly meeting set up in 2019 is a 2019 row, so a `[today-12mo, today+24mo]` filter drops it and every occurrence it would have generated this week. SCALE-1's filter is `or(recurrence_rule.not.is.null, and(start_time.lte.TO, end_time.gte.FROM))`: series always come through, and the second arm is an *overlap* test (not `start_time` alone) so multi-day events straddling the window edge survive. Same trap as the DF-2 deep-link teleport, one layer down. → [window.ts](../../src/features/calendar/window.ts)
- **A read window is a lie unless something widens it on navigation.** The calendar's window grows via `ensureRange(range.startMs, range.endMs)` driven from the page's visible range; without that wiring, paging back to an old month renders a convincingly *empty* calendar instead of a loading one. Growth is one-way (`widenCalendarWindow` never shrinks) so walking back and forth never refetches.

- **An owner-only RLS policy does NOT protect data the MCP connector or an Edge Function reads — they use the service role, which bypasses RLS.** PERM-0 made `calendar_events` / `email_refs` owner-only, but `moduo-mcp`'s calendar/email/links tools and `booking-public` read those tables with the secret key, so each needed its own `owner_id` filter (`ctx.key.createdBy` / `link.owner_user_id`). When you tighten a policy, grep `supabase/functions/**` for every `.from("<table>")` and `rpc` that returns its rows; SECURITY DEFINER SQL functions (e.g. `links_suggest`) bypass RLS the same way. → `supabase/migrations/20261006180000_perm0_privacy.sql`
- **You CAN execute a migration's SQL before touching the hosted project: a throwaway local Postgres + a stub schema.** Homebrew's `postgresql@17` is on this machine. `initdb --no-locale` (LANG/LC_ALL=C, or initdb fails on locale) and start with `-k /tmp` (the scratchpad path is longer than the 103-byte Unix-socket limit). Stub only what the migration touches: roles `anon`/`authenticated`/`service_role`, an `auth.uid()` that reads `request.jwt.claims`, the tables/columns, and the helper functions copied from their newest migrations. Then run behavior probes with `set_config('request.jwt.claims', …)` + `SET ROLE authenticated`. It proved PERM-0's RLS/grant/key-cap behavior end to end, which `bun run verify` never does. Don't add a blanket `GRANT EXECUTE ON ALL FUNCTIONS` in the probe script — it silently undoes the migration's revokes and fakes a failure.

- **A plpgsql trigger that a backfill fires resolves its function calls at RUN time — every function it calls must already exist when the backfill UPDATE runs, even in a branch that won't execute.** PERM-1's member resolver called `perm_can_grant` inside an `IF TG_OP = 'INSERT' AND …` guard; the backfill was an UPDATE, but the planner still needs the function to exist to plan the expression, and the migration failed. Define helpers before any statement that fires a trigger using them. **And the corollary that broke production (2026-10-06, 20:37–21:15 UTC):** in a generic trigger shared by several tables, a field read like `NEW.body` / `NEW.parent_id` must sit in its OWN `IF` nested under a `TG_TABLE_NAME` check. `IF v_module = 'chat' AND NEW.body …` or `ELSIF TG_TABLE_NAME = 'notes' AND NEW.parent_id …` errors with `record "new" has no field "body"` on every other table — PL/pgSQL resolves every `NEW.x` named in an expression before evaluating it, so `AND` does not short-circuit the lookup. The sharing migration did exactly this and every task edit, bucket create and note save failed until a hotfix (`20261006230000_perm_sharing_write_hotfix.sql`). Test a generic trigger with a write on EVERY table it's attached to, not just one.
- **`supabase db query` can apply a whole migration file to the hosted project in one transaction — but it needs `--linked --project-ref <ref>` together** (`--project-ref` alone errors "only applies when targeting the linked project", and plain `--linked` errors when the repo isn't `supabase link`ed). Wrap the file in `BEGIN; … COMMIT;` and insert the `supabase_migrations.schema_migrations` row yourself in the same transaction so history matches the filename. Used for PERM-1 (59 KB — too big to paste into an MCP call comfortably).
- **A share check that `SELECT`s the row being inserted fails the INSERT's `WITH CHECK`.** `can_access` reads the row, which isn't visible yet mid-INSERT. Bucket inserts must pass on `owner_id = auth.uid()` (the row isn't readable yet); task inserts must pass on the parent bucket, which already exists. Don't `UPDATE` the same note inside its `AFTER INSERT` grant trigger — the grant's own flag trigger already writes `workspace_shared`, and a second update hits "tuple already modified". Owner archive of a removed member's private notes has to `set_config('share.bypass','1', true)` first, or `perm_enforce_write` blocks the rewrite. A calendar busy overlay must not `await` its RPC before `setLoading(false)` — an unmigrated `calendar_busy_blocks` hangs the whole calendar.
- **`auth.admin.deleteUser` erases only what foreign keys cascade, and many user columns here have no FK.** It takes `profiles`, owned workspaces (and their rows) and memberships. It does not reach Stripe, Storage objects, or any `user_id` / `owner_id` / `owner_user_id` column without an FK. Among those without one: `user_integrations`, `exposed_slot_links`, `booking_link_hosts`, `calendar_accounts`, `contacts` and `contact_private_notes` (prod's FKs to `profiles` are in the Relationships of `src/types/supabase.ts`; FKs to `auth.users` only show in the live query in [docs/testing/t-maciej-delete-account-erasure.md](../testing/t-maciej-delete-account-erasure.md)). Rows like those in workspaces the user owns go with the workspace; elsewhere they survive. So: a new table keyed by a user gets an FK with `ON DELETE CASCADE`, or a line in [`_shared/account-erasure.ts`](../../supabase/functions/_shared/account-erasure.ts); a new place that stores user files or an external record goes in that module too. And never delete a user from the Supabase dashboard: that is the bare `deleteUser`, minus the erasure. (2026-10-07)
- **A trigger on `workspace_members` DELETE is also an account-deletion trigger.** FK cascades run ordinary DELETEs, so user triggers fire on them. Deleting an account cascades its memberships, which fires PERM's `share_member_removed` (built for removing a member). It hands the person's private buckets in other people's workspaces to those owners, and their private notes too unless the `notes.created_by` SET NULL cascade happens to run first (the order of cascade triggers is not something to rely on). Any trigger written for "member removed" has to make sense for "account deleted" too, or check for it. (2026-10-07)
- **Deleting a Stripe customer doesn't erase our `stripe.*` mirror of it.** The open-source Sync Engine's `customer.deleted` handler upserts only `id, object, deleted` into `stripe.customers` ([source, og branch](https://github.com/stripe/sync-engine/blob/og/packages/sync-engine/src/stripeSync.ts)), so the mirrored email, name and address stay, and `stripe.invoices` / `stripe.charges` rows keep their billing details. ## Supabase / Realtime (NO-6)

- **Realtime `postgres_changes` applies the subscriber's RLS to INSERT/UPDATE but NOT to DELETE** — a DELETE event carries the old primary key to every subscriber of the table/filter. That's why chat deletes are soft (`deleted_at`) and reactions/thread counts are denormalized onto the message row: every live change is an UPDATE on one RLS-filtered table. Don't add a child table you hard-delete from if its existence/ids are sensitive. → `supabase/migrations/20261006150000_chat_module.sql`
- **Private Realtime channels (`config: { private: true }`) are authorized by RLS on `realtime.messages`** (`realtime.topic()`), not by your app tables. Chat's `chat:<workspace id>` typing/presence channel is allowed by `chat_realtime_topic_allowed()`; a new private topic family needs its own policy pair (select + insert) or the join silently fails and presence stays empty.

- **`channel.send()` on a Realtime channel that isn't JOINED does NOT drop — it silently REST-falls-back with a `console.warn`.** The notes broadcast relay assumed `send()` was a no-op while joining/torn-down; in `@supabase/realtime-js` it POSTs to the broadcast REST endpoint instead (plus a deprecation warning), so early keystrokes (before SUBSCRIBED) or a flush after teardown spam REST + the console. - **`WorkspaceMember` carries NO display name or avatar — only `userId`/`role`/`isActive`.** ~~Any "who" UI can't resolve a name from the members list.~~ **UPDATED DF-24 (2026-07-11):** `mapMember` now surfaces `displayName`/`avatarUrl` from the `profiles(*)` join `listMembers` already does — the modal renders real names. The join was always fetched; the mapper just threw it away. Presence/comments elsewhere still use the current user's email local-part + `useMentionSearch` for a searchable people source. → [workspace-mappers.ts](../../src/features/workspaces/workspace-mappers.ts)
- **`workspace_members` uses a DIFFERENT role/permission vocabulary than the app and than `workspace_invites` — and the untyped client can't catch it.** The members table's CHECK constraints only accept **role ∈ {owner,admin,member,viewer}** and **permissions_{notes,tasks} ∈ {read,write,none}** (verified live: `editor`/`view`/`edit`/`admin` all 400 the insert). But the app's `WorkspaceRole` is `{owner,admin,editor,viewer}` and `ModulePermission` is `{none,view,edit,admin}`, and `workspace_invites` happily stores the app vocabulary. So `joinInvite` copying `invite.role`/`invite.permissions_*` straight into the `workspace_members` insert made **every** real redemption 400 on a CHECK — the invite loop was silently data-broken (nobody had ever completed a join, so it never showed). **Any write to `workspace_members` must go through the bridges** `toMemberRole`/`toMemberPerm` ([workspace-mappers.ts](../../src/features/workspaces/workspace-mappers.ts)); reads normalize back via `normalizeMemberRole` (`member`→`editor`). "owner"` but `workspaces` has **no `role` column**, so every workspace read as owner/edit — the caller's real role/perms live in the nested `workspace_members(*)` row and must be derived from it (DF-24 passes `currentUserId` in). `verify` catches none of this — only a live authed insert does. → [runtime.web.ts](../../src/lib/runtime.web.ts) `joinInvite`/`updateMemberPermissions`, [workspace-mappers.ts](../../src/features/workspaces/workspace-mappers.ts) `mapWorkspace`
- **Managing ANOTHER member's `workspace_members` row (role change, remove, transfer ownership) can't be a client-direct write — the base RLS is own-row.** A direct `.from("workspace_members").update(...).eq("id", <someone-else>)` silently affects 0 rows (RLS filters it out) — which reads as a no-op success, not an error. `updateMemberPermissions` shipped this way and role changes for other members quietly did nothing. Rule: owner manages everyone incl. admins; an admin manages only editors/viewers (never a peer admin, never grants admin); the owner is never removed/role-changed (hands off via transfer). ## Prefs sync

- **Adding a `user_preferences` sync domain needs EIGHT coordinated touchpoints, and the untyped Supabase client catches none of the column ones.** To add a domain (e.g. CAL-6b's "calendar", DF-19f's "preferences"): (1) a migration adding `<domain> jsonb` + `<domain>_updated_at timestamptz` (the FOR-ALL own-row RLS already covers new columns); (2) the generated `src/types/supabase.ts` user_preferences Row/Insert/Update (hand-add — the client is untyped so a missing column here won't error, but keep it honest); (3) `UserPreferences` in [runtime.types.ts](../../src/lib/runtime.types.ts); (4) `prefsRowToModel` (adds the field) + `preferences.get`/`.set` in [runtime.web.ts](../../src/lib/runtime.web.ts) (tauri delegates) — the select-column list + missing-column attribution now live in [prefs-columns.ts](../../src/lib/prefs-columns.ts) (see the deploy-gap gotcha below), so a NON-base domain adds itself to `OPTIONAL_PREFS_COLS` + `optionalPrefsAvailable` there; (5) `SyncDomain` union + `META_KEY` + the `domainValue` switch + the `pushDomain` patch in [prefs-sync.ts](../../src/lib/prefs-sync.ts); (6) a `useDomainSync`-wired hook (copy `useFocusPrefs`); (7) call `pushLocalChange` on every syncable mutation; **(8) mount that hook APP-WIDE, not only in its Settings pane** (see next bullet). Miss the `.select` column in `set` and the write silently drops the domain on the returned row (typechecks fine — untyped client).
- **A synced prefs domain reconciles with the cloud ONLY while a component calling its `useDomainSync` hook is mounted — so a domain read only from its Settings section silently never syncs cross-device until that pane is opened.** appearance rides the always-mounted `Toaster` (it reads `useAppearance` for the toast theme, [sonner.tsx](../../src/components/ui/sonner.tsx)); focus rides the Execute-view timer. DF-19f's `usePreferences` lives only in the Preferences section, so its landing-view/motion/sound/reopen would have first-painted from the localStorage mirror but NEVER pulled a change made on another device until you opened Settings → Preferences. Fixed by mounting a null `<PreferencesSync/>` (just calls `usePreferences()`) app-wide in [main.tsx](../../src/main.tsx), next to `<Toaster/>`. The hook no-ops until signed in. Any new domain needs an always-mounted consumer for boot reconcile — the Settings section alone is not enough. → [src/lib/preferences.ts](../../src/lib/preferences.ts)
- **The `user_preferences` deploy-gap guard now spans TWO optional columns (email = EM-10, preferences = DF-19f) via a retry-drop loop keyed by the column NAME in the PostgREST message.** [prefs-columns.ts](../../src/lib/prefs-columns.ts) builds the `.select()` list from the base cols + whichever optional domains are still believed present, and `missingOptionalPrefsDomain(err)` attributes a `42703` to a specific domain by matching `\b<name>\b.*does not exist` in the message (the bare code is ambiguous with >1 optional column; a `\b` before the name avoids a false match inside the table name `user_preferences`). `runtime.web`'s `get`/`set` retry up to 3× dropping the named domain each time (rebuilding the upsert row so the dropped domain isn't written). Adding a third optional column = extend `OPTIONAL_PREFS_COLS` + `optionalPrefsAvailable` + the name checks; the attribution is unit-tested in [prefs-columns.test.ts](../../src/lib/prefs-columns.test.ts) (runtime.web itself is too heavy to import into vitest).
- **To make a NON-settings component react to a prefs change, read the store with `usePreferencesValue()` — NOT `usePreferences()`.** `usePreferences()` wires `useDomainSync` (auth listeners + cross-device reconcile + push); calling it from a *second* consumer (e.g. the workspace-provider notification filter, the dashboard widget) spins a **duplicate reconcile/push loop** that races the single app-wide `<PreferencesSync/>` in main.tsx. `usePreferencesValue()` (DF-19f-notif) is just `useSyncExternalStore(subscribe, getSnapshot)` over the same module store — reactive, no sync engine — so a local toggle propagates to every consumer, but only the one `<PreferencesSync/>` owns the cloud round-trip. - **The optional `user_preferences` domain columns are `NOT NULL` (DEFAULT `'{}'` / `now()`), so you can't `NULL` a domain to "reset" it — and an empty `{}` object IS the "never synced" sentinel.** `reconcileDomain` treats a 0-key jsonb object as absent (`hasCloud = !!raw && Object.keys(raw).length > 0 && !!updatedAt`) → local seeds it. When cleaning up a test account's prefs domain (e.g. after a live-verify wrote one), `UPDATE user_preferences SET <domain> = '{}'::jsonb` restores the pre-sync state; `SET <domain> = null` throws `23502`. `<domain>_updated_at` is also NOT NULL — leave it, the empty object already means "unsynced" regardless of the timestamp. → [src/lib/prefs-sync.ts](../../src/lib/prefs-sync.ts) `reconcileDomain`

## Boot-time read caching (DF-12)

- **`supabaseClient.auth.getUser()` is a network round-trip to `/auth/v1/user`, and ~16 runtime methods called it independently** (every user-scoped read/write resolves the user first). That's why one boot fired it ×8. It's now deduped through `getAuthedUser()` ([runtime.web.ts](../../src/lib/runtime.web.ts)) over the shared [`request-cache`](../../src/lib/request-cache.ts). Any NEW runtime method that needs the current user must call `getAuthedUser()`, **never** `supabaseClient.auth.getUser()` directly, or it reintroduces a per-call `/auth/v1/user` hit.
- **Caching an auth/identity read at Infinity TTL is a session-brick trap unless you cache ONLY success.** `getUser()` returns `{data:{user:null}, error}` (it does NOT throw) on BOTH a transient failure (offline / mid-refresh 401 / 5xx) AND a genuine sign-out. If you cache that `null` at a long TTL, one boot blip pins `null` for the whole session → every read returns empty and every write fails RLS (`owner_id=""`), recoverable only by a real sign-in. `getAuthedUser` avoids it by **throwing** inside the fetcher on error-or-null (so `request-cache` never retains it) and returning `null` from an outer catch — same graceful `User | null` at call sites, but failures self-heal on the next call. Mirror this for any future Infinity-TTL cache: retain only a positive result.
- **A shared read-cache must clear its in-flight repopulation on invalidate, or a sign-out races back the old user.** `request-cache` guards this with a module `epoch` bumped on `invalidate`/`clear`; a fetch only writes back if `epoch` is unchanged since it started. Without it, a `getUser` in flight when `SIGNED_OUT` clears the cache would resolve after and re-cache the signed-out user.
- **A boot read-cache keyed by a fixed string (not the userId) leaks across a fast account switch on a shared browser.** `getCloudPrefs` cached prefs under a single `"prefs"` key; within its TTL a `SIGNED_OUT`→`SIGNED_IN(B)` would serve A's cached prefs to B (B adopts A's theme/accent, re-stamped as B's). Key any user-scoped cache by `userId` (`prefs:${userId}`) so a different user is a cache miss. → [src/lib/prefs-sync.ts](../../src/lib/prefs-sync.ts)
- **A pure read path must not issue a write.** `layout-repo.load()` used to fire-and-forget a `dashboard.save()` to reconcile a cache-wins load up to the cloud — a `POST` on every boot that resolved to the local cache. Removed for DF-12: the local cache is the device's truth and a cut-off edit rides up on the next `save`, so cross-device propagation is delayed at most one edit, never lost. When adding a "reconcile on load" convenience, route it through the explicit save lifecycle, not the read. → [src/features/dashboard/data/layout-repo.ts](../../src/features/dashboard/data/layout-repo.ts)

## Edge Functions calling PostHog (PRIV-3)

- **PostHog has two hosts, and deleting a person takes a JSON body its API reference doesn't show.** Events go to the ingestion host `eu.i.posthog.com`; the private API (persons, deletion) is `https://eu.posthog.com`, with a personal API key (`phx_…`, scope `person:write`), never the public project key (`phc_…`). `POST /api/projects/<id>/persons/bulk_delete/` reads `distinct_ids` / `delete_events` from the **JSON body**, although the reference lists them as query parameters; it answers **202** with a summary, and an unknown distinct id is still a 202 (`persons_found: 0`). The person goes at once; the events are only **queued** for PostHog's weekly run (Sundays 05:00 UTC), and only events PostHog already has go, which is why `analytics-forget` waits ~10 s before deleting (in the function, not the app, so the request leaves while the person is still signed in). An event sent after the deletion creates the person again, so `app_signed_out` is tracked only when the person signs out (never on a SIGNED_OUT auth-js fires itself), the Danger zone records a "no" before signing out, and analytics starts only once the profile read confirms the account (a cached session outlives an account deleted elsewhere by up to an hour). Treat only a timeout, 408, 429 or 5xx as worth retrying; any other 4xx, or a success that isn't JSON (a wrong host's web page), is a refusal. Otherwise one broken setting fails every account deletion. → [posthog-erasure.ts](../../supabase/functions/_shared/posthog-erasure.ts), [analytics-forget.ts](../../supabase/functions/_shared/analytics-forget.ts)
