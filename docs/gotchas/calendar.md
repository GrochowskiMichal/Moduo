# Gotchas: Calendar mirror, booking links, CalDAV

Read before working in `src/features/calendar/`, booking functions. Index of all areas: [docs/gotchas.md](../gotchas.md). Each entry: the trap, why it happens, what to do instead. A trap that bites twice should become a hook, a lint rule or a test.

## Calendar / external mirror (CAL-6)

- **Microsoft Graph event `dateTime` is a NAIVE wall value + a separate `timeZone` field — never parse it raw.** `Date.parse("2026-07-02T09:00:00.0000000")` treats it as the machine's LOCAL zone → wrong instant. The desktop sync MUST request `Prefer: outlook.timezone="UTC"`, so the mapper appends `Z` for a naive value tagged UTC/absent; a naive value tagged with a **non-UTC Windows zone name** ("Pacific Standard Time" — `Intl` can't resolve these) is **dropped, not shifted** (a missing chip beats a wrong-slot one). Google is the opposite: its `dateTime` carries a real offset; only its all-day `date` (date-only) needs local-midnight normalization or it spills a day east of UTC. → [src/features/calendar/mirror.ts](../../src/features/calendar/mirror.ts)
- **To live-verify the web mirror WITHOUT the desktop OAuth engine, seed via the RPCs from the browser.** `fetch` `${SUPABASE_URL}/rest/v1/rpc/calendar_op_account_upsert` then `…/calendar_op_mirror_events` with the injected session token + publishable key (recipe in [[project-test-account-hosted]]) — mirrored external events then render on web exactly as a real sync would. Remove with `calendar_op_account_remove` to test the cascade. The whole external-render/attribution/visibility/removal path is verifiable this way; only the desktop OAuth *round-trip* is truly manual.

## Calendar / booking links

- **`exposed_slot_links.schedule_type` must include `weekly`.** The legacy check only allowed `working_hours` and `custom`. Saving a link then fails the check and the dialog shows “Could not save the link.”
- **`user_integrations.provider` only allows `zoom`, `google_meet`, and `google_calendar`.** A new provider that skips this check inserts nothing and the connect callback returns `save_failed` on a blank page. Extend `user_integrations_provider_check` in the same change.
- **A second Google account needs `account_key`.** `user_integrations` used to be unique on `(user_id, provider)`, so connecting another Google login replaced the token. The key is the Google email (`''` for Zoom and Meet). `calendar-google-web` is the web sync/create path (`verify_jwt=false`, user JWT checked inside). Web `fetchExternalEvents` must throw for providers it cannot read — returning `[]` tombstones the mirror.
- **Booking links are `https://moduo.app/book/…` and `https://staging.moduo.app/book/…`.** Those hosts are landing deployments. `scripts/vercel-build.mjs` puts the marketing page at `index.html` and the app shell at `app.html`, and `vercel.json` rewrites `/book` to `/app.html` only when the host is `moduo.app`, `www.moduo.app` or `staging.moduo.app`. `moduo.app` redirects to `www.moduo.app` (308), so production links land on the www host — without its rule `/book` there serves the marketing page. The app hosts keep serving `/book` from their own `index.html`.
- **`*_op_*` helpers like `entities_op_tombstone` call `spine_op__guard`, which needs a signed-in member — they fail inside a migration** ("You don't have edit access to links in this workspace"). A data fix in a migration updates `public.entities` directly. Also: run a migration file with `supabase db query --linked -f`, and only insert its `schema_migrations` row after it succeeded (the file runs as one transaction and rolls back on error).
- **`exposed_slot_links` carries legacy CHECK constraints that are not in the repo's migrations** (`video_provider`, `location_type`, `schedule_type`). A new value saves fine locally and fails on the hosted DB with "violates check constraint". Before adding a value, read them: `select conname, pg_get_constraintdef(oid) from pg_constraint where conrelid='public.exposed_slot_links'::regclass and contype='c'`. `guest_choice` was added by `20261002090000_booking_link_video_choice.sql`.
- **Zoom on booking links needs a Zoom Marketplace "General app" (user-managed OAuth) and two secrets.** Set `ZOOM_CLIENT_ID` / `ZOOM_CLIENT_SECRET` on the Supabase project; the app's OAuth redirect URL and allow list must contain `https://<project>.supabase.co/functions/v1/booking-zoom-connect`; scopes `meeting:write:meeting`, `meeting:delete:meeting`, `user:read:user`. Without them `booking-zoom-connect` reports `configured:false` and the link editor greys Zoom out. Deploy `booking-zoom-connect` with `--no-verify-jwt` (Zoom's callback has no JWT). Zoom rotates the refresh token on every refresh — `zoomAccess` saves the new one; skipping that save logs the host out after an hour. The desktop `integration_connect_zoom` loopback flow is not used for booking.
- **A public booking only works after the migration and two edge functions are deployed with `verify_jwt=false`.** `booking-public` and `booking-google-connect` have no guest JWT (the Google callback is a browser redirect). They need `MODUO_TOKEN_ENCRYPTION_SECRET` (same value as the desktop app). `GOOGLE_CALENDAR_CLIENT_ID` / `GOOGLE_CALENDAR_CLIENT_SECRET` are the **Desktop** OAuth client (no redirect field; desktop Connect copies the keychain token). `GOOGLE_CALENDAR_WEB_CLIENT_ID` / `GOOGLE_CALENDAR_WEB_CLIENT_SECRET` are a separate **Web application** client whose Authorized redirect URI is this function's URL. A refresh token only works with the client that issued it, so booking refresh tries the desktop client first, then the web client. Google's own invite email is `sendUpdates=all`. The short Moduo email needs `RESEND_API_KEY`; if it is missing the booking still succeeds and the Meet link is on the confirmation page.

- **An OAuth callback can't tell who consented, so it must not decide whose account the tokens land on.** The connect callbacks of `booking-google-connect` and `booking-zoom-connect` are JWT-less browser redirects; a signed `state` only proves who *started*. So the callback saves nothing: it checks the state and 302s to `<https app host>/calendar?connect=<provider>&connect_code&connect_state#` (`_shared/oauth-connect.ts`), and the signed-in app posts `{ action: "finish", code, state }` with its own JWT (`src/features/calendar/connect-return.ts`). The function exchanges the code only when that JWT's user is `state.uid`, else 403 `wrong_account`. Until 2026-10-08 the app took a session from any `#access_token=…` URL fragment (closed by #281, `detectSessionInUrl: false`), so the session in a tab wasn't proof on its own; these stay as defense in depth: the 302 ends in an empty `#` (a redirect without a fragment inherits the request's), and the app finishes silently only when `sessionStorage` holds the state this tab started (`rememberConnectStart`), otherwise it shows a confirm toast naming the signed-in email. A desktop Zoom connect always gets that confirm, since it finishes in the system browser, which must be signed in to the same account (signed out → `/auth` drops the params; connect again). Return hosts are https only, never the dev server (`start` takes the origin from the request); a connect started on localhost finishes on app.moduo.app. PKCE (verifier = HMAC of the state, no storage) means a code only finishes with its own state. Return params are prefixed because supabase-js reads `code`/`error` from the URL as a sign-in callback. **Deploy the web app before the functions**: new functions with an old app strand every connect on `/calendar` (nothing calls `finish`). A function-origin cookie set on a GET step wouldn't bind the browser (that GET URL is as forwardable as the consent link), and `*.supabase.co` can't serve an HTML confirm page.
- **Never build a link we email from the request.** booking-public is public and unauthenticated; it took the Cancel link's host from `body.origin`, so a forged request made our sender mail a link to any domain. The Origin header is just as forgeable outside a browser. Get every emailed host from `supabase/functions/_shared/app-origin.ts` (`bookingOrigin`, `appOrigin`); a client hint may only choose between the hosts listed there. A new public host needs adding there and, for `/book`, to `vercel.json`. Any public endpoint that sends mail also needs a rate limit (`booking_rate_check`, `waitlist_join`). → [supabase/functions/_shared/app-origin.ts](../../supabase/functions/_shared/app-origin.ts)

## Calendar / CalDAV + ICS (CAL-8)

- **A provider mapper that swallows parse errors and returns `[]` can MASS-TOMBSTONE the whole account.** The CAL-6 sync loop diffs "what the fetch returned" against "what we last mirrored" and deletes the difference. An ICS feed URL that expired and now serves an HTML login page under **HTTP 200** (common) would map to `[]` → the diff tombstones every event → the account is then written `status:'ok'`, so the user's whole external calendar silently vanishes for all workspace members. Fix (CAL-8): `mapIcsEvents` **throws** when non-empty input parses to zero VCALENDARs (a valid-but-empty calendar still returns `[]`); the per-account catch flips `error` and keeps the last mirror. Any future provider mapper on the delete-diff path needs the same "empty vs unparseable" distinction. → [src/features/calendar/ics-mirror.ts](../../src/features/calendar/ics-mirror.ts), [src/features/calendar/hooks/use-calendar-sync.ts](../../src/features/calendar/hooks/use-calendar-sync.ts)
- **Expanded-occurrence mirror ids must key on the ORIGINAL recurrence slot, never the moved/instant start.** Keying `uid::<movedStartIso>` churns the id when an occurrence is rescheduled (tombstone+recreate instead of update), collides when an override is moved onto another occurrence's slot, and — because a local-midnight all-day `toISOString()` embeds the machine zone — churns **every all-day id** on an OS-timezone change. Key on the recurrence-id wall fields (`uid::YYYY-MM-DDThh:mm:ss`) instead: stable, collision-free, tz-independent. Also: the monotonic-window `break` in the expansion loop drops an override moved *backward* into the window from a base slot past the break — handle overrides in a separate post-loop pass. → [src/features/calendar/ics-mirror.ts](../../src/features/calendar/ics-mirror.ts)
- **ical.js `TimezoneService` is a global singleton — `register` is first-wins and state leaks across resources.** Registering a VTIMEZONE whose TZID is already present is skipped, so a second CalDAV resource that defines the *same non-IANA TZID name* with *different rules* converts with the first resource's zone. Reset (`ICAL.TimezoneService.reset()`) around **each** resource, not once per batch. Also cache the per-zone `Intl.DateTimeFormat` (a recurring expansion converts start+end per occurrence — the repo's cached-formatter posture). → [src/features/calendar/ics-mirror.ts](../../src/features/calendar/ics-mirror.ts)
- **A manual HTTP redirect loop that re-sends `Authorization` must gate on the host.** reqwest strips `Authorization` on cross-host redirects *by design* (open-redirect / MITM would otherwise capture the password). CAL-8's CalDAV client follows redirects manually (iCloud legitimately hops `caldav.icloud.com` → `pXX-caldav.icloud.com`), so it must re-implement that guard: forward Basic auth only to the same host or the same registrable domain (`same_registrable_domain`, last-two-labels). → [src-tauri/src/commands/caldav.rs](../../src-tauri/src/commands/caldav.rs)
- **A CalDAV/ICS account's credentials live only in the CONNECTING machine's keychain — a second desktop must not flip the shared row to `error`.** Every desktop in the workspace runs the 15-min sync loop over all accounts, but only the machine that connected holds the CalDAV password / ICS feed URL. A second machine's fetch throws `*_missing_credentials`/`missing_descriptor`; treating that as a sync failure flips `status:'error'` (rail shows Reconnect), the owning machine flips it back next cycle → **Reconnect flaps every ≤15 min for everyone**. The loop now skips the status write for local-credential-absence errors. Same per-machine limitation as the OAuth engine, but the OAuth path never had a second writer. → [src/features/calendar/hooks/use-calendar-sync.ts](../../src/features/calendar/hooks/use-calendar-sync.ts)
- **Keychain cleanup on account removal can't live in the (web) runtime — it's a desktop-side step the UI must run BEFORE `removeAccount`.** `runtime.calendar.removeAccount` is a Supabase RPC with no OS-keychain access (the keychain is a Tauri `invoke`), so a CalDAV/ICS account's stored secret is cleaned up by `cleanupCredentialsForRemoval` at each UI remove seam (Settings + the calendar rail), called *before* the row is deleted so the "is this the account's last calendar?" check can still see it. Consequence: any NEW remove path (bulk remove, an MCP tool, a workspace-delete cascade) that calls `removeAccount` directly will orphan the keychain secret. It's harmless (an unused secret, overwritten on the next connect), but if you add a remove path, run the cleanup first. Same reason a fast concurrent remove of two sibling CalDAV calendars can leave the shared secret orphaned — both snapshots still see the other row. → [src/features/calendar/caldav-connect.ts](../../src/features/calendar/caldav-connect.ts)
- **A connect flow that saves a credential before creating its account row must roll the credential back on total failure.** CAL-8b's CalDAV connect saves the (server, username) password to the keychain, then upserts one account row per chosen calendar. If EVERY upsert fails (RLS, a pre-migration `p_sync_token` 404, a network blip), the password would sit in the keychain forever with no row pointing at it and no cleanup path. `connectCaldavCalendars` deletes the just-saved credential when zero rows landed (a partial success keeps it — those rows are real and a retry is idempotent on `external_id`). → [src/features/calendar/caldav-connect.ts](../../src/features/calendar/caldav-connect.ts)
- **Adding an optional param to an existing `_op_` RPC: send it only when non-null, or a pre-migration client 404s.** PostgREST resolves RPCs by the exact named-arg set, so calling `calendar_op_account_upsert` with `p_sync_token` against a database still on the 7-arg signature raises PGRST202 and breaks the call for *everyone* until the migration deploys. Guard `if (syncToken != null)` (both null and undefined omit it); post-migration `coalesce(p_sync_token, sync_token)` makes always-sending-null a no-op anyway, so nothing is lost. The old signature is DROPped (not overloaded) so the two don't become an ambiguous pair for default-arg calls. → [src/lib/runtime.web.ts](../../src/lib/runtime.web.ts), [supabase/migrations/20260703130000_calendar_account_sync_token.sql](../../supabase/migrations/20260703130000_calendar_account_sync_token.sql)
