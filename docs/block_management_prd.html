Block management — Notes editor (Notion parity)

Product requirements document for the NotesBlockControlsPlugin layer on top of the existing Lexical/Yjs editor. Covers every user-facing behavior, interaction constraint, edge case, and acceptance criterion for v1.

v1.0 — draft In scope: text, lists, toggles, code, tables Stack: Lexical · Yjs · React Lexical DraggableBlockPlugin baseline
01

Goal & scope

Users should be able to freely reorder, convert, duplicate, and delete editor blocks using pointer and keyboard interactions that feel identical to Notion's desktop experience. The implementation stays entirely within the existing Lexical + Yjs stack so collaboration and persistence require zero schema changes.

"Deep parity" for v1 means: every text-like block type (paragraphs, headings, lists, todos, quotes, code, toggles, dividers, tables) is draggable and has a contextual action menu. It does not mean Notion databases, embeds, synced blocks, AI, columns, or full Notion mobile drag.

02

User stories

  • As a writer, I can drag any block to reorder it without losing focus or undo history.
  • As a writer, I can click the six-dot handle to open an action menu for the hovered block.
  • As a writer, I can click + to insert a new block below the current one and immediately open the block picker.
  • As a writer, I can convert a paragraph into a heading, list, quote, or code block without retyping content.
  • As a writer, I can select multiple contiguous blocks and drag or delete them as a group.
  • As a writer using a keyboard, I can move any block up or down via a shortcut without using a mouse.
  • As a collaborator, block reorders made by one user are immediately reflected for all other connected users.
  • As a reader with a read-only note, I see no gutter controls at all.

Block resolution rules

When the user's pointer enters a block region, the system must resolve which node to treat as the draggable unit:

  • For top-level paragraphs, headings, quotes, code blocks, dividers, and tables: the hovered DOM node itself.
  • For list items (bullet/number/todo): walk up from the cursor until the nearest list item ancestor. Never resolve to the whole list wrapper.
  • For a block inside an open toggle: resolve to that child block, not the toggle shell — unless the cursor is on the toggle label line itself.
  • For a collapsed toggle: always resolve to the toggle shell regardless of cursor position.
  • If resolution is ambiguous (e.g. cursor exactly on the border between two items), prefer the block whose vertical midpoint is closest to the cursor.
04

Gutter controls

A fixed-width gutter (32 px) sits to the left of the editor content area. Controls appear on hover of any block and contain exactly two affordances: a + insert button and a ⋮⋮ six-dot drag handle.

Visibility rules

  • Controls are hidden by default and appear when the cursor enters a block's bounding box.
  • Controls remain visible while the cursor is anywhere inside the gutter or inside the hovered block.
  • Controls disappear when the cursor exits both the gutter and the block, with a 120 ms fade-out delay to prevent flickering on fast cursor movement.
  • Controls are never shown in read-only mode.
  • Controls are never shown during an active drag operation (they reappear after drop).
  • On mobile (touch-only) devices, controls are replaced by a long-press gesture that opens the block menu directly.

Plus (+) button

Scenario — normal insert
User hovers over a paragraph. The + button appears in the gutter aligned to the block's top line. User clicks +. A new empty paragraph is inserted immediately below the hovered block, focus moves to it, and the slash/block picker opens automatically as if the user had typed /. The hovered block is not modified.
Scenario — insert after last block
User hovers over the last block in the note. Clicking + inserts a new paragraph at the end of the document and opens the picker. Behavior is identical to inserting below any other block.
Scenario — insert adjacent to a list
User hovers over a bullet list item. Clicking + inserts a new paragraph after the entire list group (i.e. below the last item in the same list), not between list items. This avoids accidentally fragmenting a list. Focus and picker open as normal.
Do
Insert a clean paragraph node after the block's parent list if the hovered block is a list item.
Don't
Insert the new block between two list items, which would split the list.
  • Tooltip text: "Click to add a block below" (shown after 400 ms hover).
  • Keyboard: Alt+Enter (Windows/Linux) / Opt+Enter (macOS) when a block is focused inserts below and opens picker — same behavior as clicking +.

Six-dot drag handle

  • Visual: six dots in a 2×3 grid, 14 px high, color --color-text-tertiary at rest, --color-text-secondary on hover.
  • Tooltip (400 ms delay): "Drag to move · Click for options"
  • Click (no drag): opens the block action menu anchored to the handle position.
  • Pointer-down + move ≥ 4 px: initiates drag. Menu does not open if drag was initiated.
  • Cursor changes to grab on hover, grabbing while dragging.
05

Drag & drop behavior

Drag initiation

  • Drag starts only from the six-dot handle, never from block content itself.
  • Threshold: pointer must move ≥ 4 px before drag state is committed (prevents accidental drags on click).
  • On drag start: the dragged block (or block group) gets a semi-transparent drag preview rendered via a cloned DOM node. The original block collapses to a placeholder with a dashed border and 40% opacity.
  • All other editor controls (toolbar, slash picker, gutter) are hidden for the duration of the drag.
  • Text selection is cleared on drag start.

Drop target & indicator

  • A 2 px horizontal blue line (--color-border-info) shows the insertion point between blocks as the dragged item moves.
  • The drop line appears only between valid sibling targets. It never appears inside a code block, inside a table cell, or as a child of an incompatible parent.
  • When the drag enters an invalid zone, the drop line disappears and the cursor shows no-drop.
  • Drop line position snaps to block boundaries; it does not float freely between arbitrary pixel rows.
The drop line must never appear inside a collapsed toggle's hidden children area, since that region is not rendered and drops there would silently fail.

Valid drop zones

Dragged blockValid drop targetsInvalid targets
Top-level paragraph / heading / quote / dividerBetween any top-level blocks; between open toggle childrenInside table; inside code block; inside collapsed toggle
List item (bullet / number / todo)Between sibling list items of same type; top-level position (converts to paragraph on drop); between items of different list type (converts type)Inside table; inside code block; inside a toggle that is collapsed
Toggle subtreeBetween top-level blocks onlyInside another toggle; inside table; inside code block
Table (whole)Between top-level blocks onlyInside toggle; inside code block; nested inside another table

Drop execution

  • On valid drop: Lexical editor update runs synchronously; the block is removed from source position and inserted at target position in one atomic transaction so Yjs sees a single patch.
  • On invalid drop or on Escape: the dragged block snaps back to its original position with a 150 ms ease-in animation. No document mutation occurs.
  • After a successful drop, focus moves to the dropped block and an undo entry is recorded as "Moved block".
  • If the user drops a list item outside its list, the item is converted to a paragraph at the top-level position. This conversion is part of the same undo entry.
  • Dropping a block onto itself (same position) is a no-op with no undo entry.
Scenario — reorder headings
Document has: H2 "Section A", paragraph, H2 "Section B", paragraph. User drags the handle of "Section B" and drops it above "Section A". Result: H2 "Section B" is now first, followed by its original paragraph, then "Section A" and its paragraph. Only the H2 block itself moves; adjacent paragraphs are unaffected.
Scenario — drag list item out of list
A bullet list has three items. User drags item 2 out of the list and drops it between two top-level headings. Item 2 is removed from the list (items 1 and 3 remain as a valid list), and a new paragraph block containing item 2's text is inserted between the two headings. Undo reverses both the conversion and the position change.
Scenario — drag table to invalid zone
User begins dragging a table. They move it over a code block. The drop line disappears and the cursor shows no-drop. User releases. The table snaps back to its original position. No editor state change.

Touch / mobile drag fallback

  • Touch devices do not support pointer drag in v1.
  • Long-press (500 ms hold) on any block opens the block menu with "Move up" and "Move down" actions instead.
  • A visual ripple or haptic (where available) confirms long-press recognition.
  • The gutter + button is accessible via tap on touch devices.
06

Block action menu

The menu is a floating panel anchored to the six-dot handle. It is triggered by clicking the handle (not dragging) or by a keyboard shortcut.

Menu structure

SectionActionsNotes
Turn intoText · Heading 1 · Heading 2 · Heading 3 · Bulleted list · Numbered list · To-do · Quote · Code · ToggleOnly shows types the current block can convert to (see registry). Active type is highlighted.
ActionsDuplicate · Copy block text · DeleteAlways shown.
MoveMove up · Move downMove up disabled if block is first; move down disabled if block is last. For list items, moves within the list.
InsertInsert block above · Insert block belowBoth open the slash picker in the newly created empty paragraph.

Menu behavior

  • Menu opens with a 120 ms ease-out scale animation from the handle anchor point.
  • Clicking anywhere outside the menu or pressing Escape closes it with no action taken.
  • The menu closes immediately after any action is selected.
  • Menu width: 220 px fixed. If anchored position would clip the viewport edge, the panel flips to the opposite side.
  • Keyboard navigation: ArrowUp / ArrowDown to move between items; Enter or Space to select; Escape to close and return focus to the block.
  • Keyboard shortcut to open menu while a block is focused: Ctrl+/ (Windows/Linux) / Cmd+/ (macOS).

Turn into — conversion rules

  • All inline formatting (bold, italic, code spans, links) is preserved during conversion unless the target type does not support inline formatting (code block: content becomes plain text).
  • Converting a paragraph to a toggle: the paragraph text becomes the toggle label; a new empty child paragraph is created inside the toggle.
  • Converting a toggle to a paragraph: the toggle label becomes a paragraph; child blocks are moved to top-level immediately after the new paragraph, in their original order.
  • Converting a list item to a non-list type removes it from the list. If it was the only item, the empty list wrapper is also removed. If it was the first or last item, the list is trimmed. If it was a middle item, the list is split into two separate lists.
  • Converting a paragraph to a list type: the paragraph becomes the first item in a new list. If the block immediately above or below is an existing list of the same type, the new item is merged into that list instead of creating an isolated single-item list.
  • Converting a code block: all formatting is stripped; the result is one or more paragraphs split at newlines.
  • Converting a heading with no text: the heading becomes an empty paragraph with no error.
Scenario — turn list item into heading
A bullet list has 4 items. User opens the menu on item 3 and selects "Heading 2". Item 3 is removed from the bullet list; the list is split — items 1 & 2 form one bullet list, items 4 forms another (or a single-item list). The new H2 block is inserted between the two lists. Undo restores the original 4-item list.

Delete action

  • Deletes the block immediately with no confirmation dialog.
  • If the deleted block is the only block in the document, it is replaced by an empty paragraph instead of leaving an empty editor. The undo entry still exists so the user can recover the content.
  • After deletion, focus moves to the block immediately above; if none exists, to the block below; if none exists (document is now empty), to the new empty paragraph.
  • Deleting a toggle with open children also deletes all children. Undo restores the toggle and its children.
  • Deleting a list item follows the same list-splitting rules as conversion (above).

Duplicate action

  • Inserts an identical copy of the block (including all formatting, children for toggles, and checked state for todos) immediately below the source block.
  • For tables: the full table structure and all cell content is duplicated.
  • For toggles: children are duplicated but the open/closed state of the duplicate starts closed.
  • After duplication, focus and selection move to the duplicated block.
  • Undo removes the duplicate.

Copy block text action

  • Copies the block's plain text content (no formatting) to the system clipboard.
  • For toggles: copies the toggle label text only, not child content.
  • For tables: copies a tab-separated representation (rows separated by newline, cells by tab).
  • A transient toast "Copied" appears for 1.5 s near the menu anchor. No editor state changes.
07

Multi-block selection

Selection mechanics

  • Multi-block selection is created by clicking a block's gutter region and then Shift-clicking another block's gutter, selecting all blocks between them (inclusive).
  • Alternatively, clicking and dragging in the gutter (not on the handle itself) draws a lasso selection over the blocks it passes through.
  • Selected blocks get a blue left border accent and a subtle background tint (--color-background-info at 30% opacity).
  • A floating mini-toolbar appears above the selection with: "Delete selected", "Duplicate selected", "Move up", "Move down".
  • Pressing Escape clears multi-selection.

Valid multi-select groups

  • All selected blocks must share the same parent. Selecting blocks across two different toggle containers is not allowed and the selection snaps to the parent of the first selected block.
  • A group may span mixed types (e.g. paragraph + heading + list item) as long as they share a parent.
  • A collapsed toggle counts as a single selectable unit; its children cannot be individually selected while collapsed.
  • Tables and code blocks may be part of a multi-selection group but cannot be selected partially (i.e. selecting some rows of a table is not supported in this layer).

Dragging a multi-select group

  • Initiating drag on any handle within a multi-block selection drags the entire group.
  • The drag preview shows a stacked representation: the first block's text, then "and N more" label.
  • Drop rules follow the strictest constraint in the group. If any block in the group has an invalid target, the entire drop is rejected.
  • On successful drop: blocks are inserted at the target in their original relative order, as a single undo entry.
Dragging a multi-selection that spans different list groups is rejected entirely. The user must move items one at a time in that case.
Scenario — delete multiple blocks
User Shift-clicks three paragraphs. The mini-toolbar appears. User clicks "Delete selected". All three paragraphs are deleted in one operation. If these were the only blocks in the document, a single empty paragraph is left. Undo restores all three in their original positions.
Scenario — cross-parent selection rejected
User clicks the gutter of a paragraph at top level, then Shift-clicks a block inside an open toggle. The selection is clamped: only top-level blocks between the first click and the toggle's shell are selected. The block inside the toggle is not included. A brief tooltip reads "Can't select across containers".
08

Edge cases & constraints

Empty document protection

  • The document must always contain at least one block node. Any action (delete, drag, convert) that would result in a completely empty document must instead leave an empty paragraph.
  • This check runs inside the Lexical editor update callback, not as a post-hoc patch.

Code block interior

Do
Show the drag handle on the code block's outer shell. Allow the whole code block to be dragged as a unit.
Don't
Show the slash picker, block menu, or gutter controls while the cursor is inside code text. Code blocks manage their own internal cursor.
  • Detecting "inside code text": check if the active Lexical selection anchor is a descendant of a CodeNode. If so, suppress all block control events.

Collapsed toggles

  • A collapsed toggle is treated as a single indivisible block for all drag and menu purposes.
  • Dropping another block between the toggle shell and its hidden children is impossible — the children are not in the rendered DOM.
  • Opening a toggle that is being dragged cancels the drag.

Tables

  • Tables can only be moved as a whole. There is no row or column drag in this feature scope.
  • The drag handle for a table appears on the table's top-left corner region, not on individual rows.
  • The "Turn into" submenu is absent from the table block menu (only Delete, Duplicate, Move, Insert available).

Undo / redo

  • Every block action (move, convert, duplicate, delete, insert) must produce exactly one undo entry.
  • Multi-block operations produce a single undo entry covering the entire group operation.
  • Undoing a block move restores the block to its exact prior position, including within lists and toggles.
  • Undoing a "turn into" restores the original type, including re-merging list items back into their original list if they were split.
  • Rapid sequential operations (e.g. moving a block up 5 times quickly) produce 5 separate undo entries, not one merged entry.

Collaborative editing

Scenario — concurrent move conflict
User A drags block X from position 2 to position 4. Simultaneously, User B deletes block X. Yjs CRDT resolves this: User A's move will either succeed (if deletion hasn't propagated) or result in a no-op once the deletion is applied. The editor must not crash or produce duplicate nodes. The resulting state may differ from what either user intended; no explicit conflict UI is shown in v1.
  • All mutations go through Lexical editor updates — Yjs automatically handles CRDT merging of the resulting document state.
  • No additional collaboration conflict UI is required for v1.

Drag during IME / composition

  • If an IME composition session is active (user typing CJK/Korean/etc. characters), the drag handle is non-interactive until composition ends.
  • Drag initiation clears any pending composition.

Very long documents

  • Gutter controls must not cause layout thrash on documents with 500+ blocks. Controls are positioned absolutely relative to the editor container, not rerendered per-scroll.
  • Drag-over detection uses a throttled pointer-move handler (max once per 16 ms / ~60 fps).
  • Block resolution on hover uses a cached block-to-DOM map invalidated only on Lexical editor updates, not on every pointer move.

Selection state preservation

  • After a successful block move, the cursor/caret returns to the same relative character offset within the moved block.
  • After delete: cursor moves to the block above (or below if none).
  • After duplicate: cursor moves to the start of the duplicate.
  • After convert: cursor stays at the same character offset within the converted block.
  • None of these actions should collapse a range selection to a caret unintentionally.
09

Persistence & data model

The block management layer makes no changes to the persistence layer for v1. All mutations happen through Lexical editor state; Yjs serialises the resulting document automatically.

  • No new Supabase tables, columns, or migrations required.
  • No Tauri IPC changes required.
  • Block order is fully encoded in the Lexical document tree, which Yjs treats as a Y.XmlFragment. Reorders are represented as Yjs move operations on the underlying XML nodes.
  • A full page reload should restore the exact block order as it was before reload, including any reorders made before the previous session ended.
  • The read-only flag checked to suppress gutter controls must come from the existing note access-level mechanism, not a new property.
Collaboration integrity check: after any drag-and-drop involving two simultaneous connected clients, reload both clients and confirm the resulting document is identical in both (same block order, no duplicates, no missing blocks).

Accessibility & keyboard

ARIA roles

  • The drag handle button has role="button", aria-label="Block options", and tabIndex={0}.
  • The + button has aria-label="Insert block below".
  • The block action menu uses role="menu" with role="menuitem" children.
  • During drag, the drag region has aria-grabbed="true" and drop targets have aria-dropeffect="move".

All keyboard shortcuts apply to the block that currently has caret focus (or the selection group). Shortcuts should not conflict with browser defaults or existing editor shortcuts — audit against the existing Lexical keymap before shipping.

Reduced motion

  • When prefers-reduced-motion: reduce is set: all drag animations, block placeholder transitions, menu open/close animations, and drop line fade-ins are replaced with instant state changes (no transitions).
  • The snap-back animation on invalid drop is also suppressed under reduced motion.

Focus management

  • Opening the block menu via keyboard must trap focus inside the menu panel until it closes.
  • Closing the menu returns focus to the block's editable area (not the handle button), so the user can immediately continue typing.
  • The + button is reachable by Tab when a block is focused (it should be adjacent in the tab order to the block it belongs to).

Out of scope for v1

  • Notion databases, relations, rollups, or filtered views.
  • Synced blocks or block references.
  • AI-generated blocks or AI block actions.
  • Column / side-by-side layouts.
  • Embedded media (video, audio, file embeds) — these may be draggable if they exist as opaque block nodes, but no media-specific behavior is specified.
  • Row or column drag within tables.
  • Pixel-perfect Notion mobile drag (touch drag is replaced by the long-press menu fallback).
  • Block comments or inline comments anchored to specific blocks.
  • Version history or block-level history diffing.
  • Supabase schema changes or Tauri IPC changes.
  • Drag across different notes (copy/paste is out of scope; this is single-document block management only).
  • Nested list dragging beyond the rules defined in the block registry (e.g. dragging sub-bullets independently of their parent).
  • Block-level permissions or per-block access control.
