- **2026-10-09 · Local-first cadence: build and test on the local stack; release to staging and prod in trains, not per block (PROPOSED, needs Mike's OK on the CI part).** Harness v2 is sound, but it treats every block like a release. The slowness comes from three automatic costs: each block is followed by PR → personal, then PR → `develop` with a wait for `static-checks`, then a back-merge; every `develop` push redeploys `staging-app` on Vercel (we hit the Hobby daily limit on 2026-10-08) and any `src-tauri/` change rebuilds the staging .dmg; and with no local database, every migration has to be applied to **prod** to be tested at all. Prod web and the prod .dmg/.exe were already manual (`promote-to-prod.yml`, `desktop-release-prod.yml` and `windows-portable.yml` are `workflow_dispatch` only). The prod build itself was never the problem; prod *data* was the test bed.
  **1. Local is the default.** `bun run local:up` runs Supabase, Edge Functions, Mailpit and Stripe webhooks on the Mac ([docs/local-dev.md](../local-dev.md)). Migrations are written and tested with `bun run local:reset`; a new migration is **not** applied to prod at the end of its block any more, but on release day. This replaces the 2026-10-08 practice of applying each verified migration to prod in-session.
  **2. Blocks land on the personal branch only.** `/s3` stops at the task → personal merge. Step 6b (personal → `develop`) runs only for a **sync**, triggered by the first of: **≥ 5 landed blocks**, **one finished spec/module**, **one week since the last sync**, or **Mike needs the code to build on**. A one-line fix stays on the personal branch.
  **3. Prod ships as a release train**, triggered by the first of: **≥ 2 syncs on `develop`**, **2 weeks**, or **a fix a real user is blocked by** (that one goes alone, same day). A train is: apply the pending migrations to prod in timestamp order (prod is checked against `bun run local:reset` first); deploy changed Edge Functions; run `promote-to-prod` (app); run `desktop-release-prod` (.dmg) and `windows-portable` (.exe) **only when `src-tauri/` or the bundle config changed since the last train** (web-only changes reach desktop users through the web origin); then Maciej's Tier 3 checklist. Weight overrides count: anything touching billing, auth, account deletion, RLS or `moduo-mcp` is its own small train, never bundled into a large one.
  **4. CI changes (agents can't edit `.github/workflows`, so Mike or Maciej applies):** (a) `checks.yml`: on `push` to `t/**` run only the gitleaks step; full verify runs on PRs and on `maciej`/`mike`/`develop`. (b) `desktop-release.yml`: drop the `push: develop, paths: src-tauri/**` trigger and keep the nightly cron + manual dispatch. (c) Optional: `sync-staging-app.yml` stays, since `develop` now moves weekly, not hourly.
  **5. Open:** a committed `00000000000000_baseline.sql` (so `supabase db reset` works without the prod snapshot) and committing the `stripe-webhook`/`stripe-setup`/`stripe-worker` source, which is only on prod today. → [docs/local-dev.md](../local-dev.md) · `scripts/local/stack.sh` · `.claude/skills/s3/SKILL.md` (step 6b wording still to change)

- **2026-10-08 · Every `/s2` and `/s3` report opens with a Status line and keeps "to finish this block" apart from findings; one block per session; unlanded work is always pushed.** After one night of parallel sessions Maciej had 24 open, and for most he couldn't tell how much was done, what came next, or whether a suggested change was needed for the block or just a finding. Four patterns caused it: the usage limit stopped 8 sessions mid-wrap and four of them held work only in their worktree; sessions rolled into the next block under the old title (the DS-1 session built DS-2); findings became chips and then new sessions (fewer than 10 became 24); and "Next" mixed the block's remaining steps with the next block. The report shape is now **Status** (Landed · Built, not landed · Blocked · Not started) → Changed → Test this → **To finish this block** → **❓ Needs you** → ⚠ Broke → **🔎 Found, not needed for this block** → **Session** (safe to archive, or why not). A finding becomes a chip or session only when it's in the current focus area or an unfixed security hole; an unfixed hole stays a local commit because the repo is public. → `.claude/skills/s2/SKILL.md` · `.claude/skills/s3/SKILL.md` · [AGENTS.md](../../AGENTS.md)

- **2026-10-08 · `main` and `develop` change only through a pull request whose `static-checks` job passed, and a weekly cloud routine gardens the knowledge files.** A GitHub ruleset ("Protect main and develop", no bypass) requires a PR (no approval count, since there are two of us), the `static-checks` status from `checks.yml`, and blocks force-pushes and deletion. That makes the `main`/`develop` part of `guard-git.sh` server-side, so it holds for every client, not only Claude Code; the hook alone still covers `prod-app`, `staging-app`, `refs/entire/*` and bare force-pushes elsewhere. Personal and task branches stay unprotected. The routine "Moduo knowledge gardener (weekly)" runs Mondays 07:07 Warsaw on Sonnet 5.5 in Anthropic's cloud: it re-syncs the decisions and gotchas indexes and counts, moves `[x]` lines to `BUILD_LOG.md`, lists possibly superseded decisions, duplicate gotchas and hook candidates, and opens one PR into `mike` for a human. It never merges. It can push only once the Claude GitHub App is installed on the repo. → [docs/agent-setup.md](../agent-setup.md) · [.github/AGENTS.md](../../.github/AGENTS.md)

- **2026-08-14 · DOC-1 (doc reconcile) — the doc set now declares an explicit authority hierarchy, and stale *status* claims are neutralized by banner, not by rewriting history.** Two calls made during the block. **(a) Authority is stated in-file, everywhere.** [`specs/BUILD_ORDER.md`](../../specs/BUILD_ORDER.md) is the **status of record**; [`ROADMAP.md`](../ROADMAP.md) is the **direction/why** doc (its header now says the ledger wins on any status disagreement); [`onboarding/HANDOFF.md`](../onboarding/HANDOFF.md) is a **narrative snapshot** carrying a "last reconciled" date, because it demonstrably drifts (it spent a month listing ~14 shipped blocks as "ready" or "blocked"); [`docs/reviews/whole-app-critique-2026-07-plan.md`](../reviews/whole-app-critique-2026-07-plan.md) is the DF wave's **spec**, its checkboxes an explicitly-labelled mirror of the ledger. *Driver:* every doc in this set had a plausible claim to being "the plan", so a fresh session could pick the wrong one — and one did. **(b) ~25 historical "migration deploy-ready but unapplied" block notes were left in place and neutralized with ONE banner each in BUILD_ORDER + this file**, instead of being edited individually. *Driver:* those clauses are accurate as *history* (they record why a block's acceptance criteria were unverified at ship time) and rewriting them would destroy the audit trail that OPS-1/OPS-2 depended on; the danger is only that a reader mistakes them for present state, which a banner fixes at a fraction of the diff and cannot itself go stale the way 25 hand-edits would. Only claims that read as **live instructions** (a ⚠️ "NEVER APPLIED to prod", a "DEPLOY-GATED: apply only AFTER…", a "still pending prod apply") were edited at the source. → [`specs/BUILD_ORDER.md`](../../specs/BUILD_ORDER.md) DOC-1
