- **2026-10-23 · MCPO-1: an app's OAuth token is refused everywhere but the connector, and passwords can't be set through Supabase Auth.** **(a)** Layers as planned: PostgREST pre-request `refuse_app_tokens` (403 `app_token` for tables, RPC, GraphQL), restrictive `app_tokens_refused` policies on `storage.objects`, `realtime.messages` and every table in the `supabase_realtime` publication (a test fails when a later migration publishes a table without one), and `_shared/app-token.ts` checked first in every Edge Function that takes a person's token. **(b) No Custom Access Token hook.** It runs on every sign-in (a bug there locks everyone out), (a)'s published-table policies already cover what `role = anon` was for, and setting `aud` for OAuth tokens doesn't make Supabase Auth refuse them (tried on GoTrue v2.197). **(c) No passwords through Auth (Mike's call).** The validator showed an app's token can `PUT /auth/v1/user {password}` and then sign in as an ordinary session with no `client_id`; GoTrue has no setting that keeps OAuth tokens off `/user`. A `BEFORE UPDATE OF encrypted_password` trigger on `auth.users` refuses every password write made by `supabase_auth_admin` (so `/user`, recovery and the admin API), and Settings → Account no longer has the change-password form. Moduo signs in by emailed code (TX-4 already strips passwords from new accounts); the 7 existing accounts' passwords keep working until cleared, and operator SQL (`seed.sql`) can still set one. Rejected: routing password changes through an Edge Function with a one-time ticket (keeps a feature nobody needs); `secure_password_change` (GoTrue skips the email nonce for a fresh session). **(d) The admin API is Auth too:** local e2e and perf seeders now set test passwords in SQL (`setLocalPassword` in `e2e/tests/support/local-stack.ts`). **(e) MFA stays off:** GoTrue's MFA-verified token drops `client_id`, so enabling MFA reopens the escalation. Accepted: the app can read the person's profile and other grants. → [specs/mcp-oauth.md](../../specs/mcp-oauth.md)
- **2026-10-22 · Apps connect by URL and sign-in; the token is exchanged for a scoped key; the connector moves onto Supabase's MCP foundation; no server-side code mode.** Mike's call after researching Cloudflare Code Mode, Anthropic's programmatic tool calling and Supabase's "MCP server for your app" kit; Maciej OK'd the new `/oauth/consent` route. **(a) Sign-in.** Supabase Auth's OAuth 2.1 server (Free plan, no charge; prod already signs with ES256) with dynamic client registration; the consent screen at `/oauth/consent` reuses the API key card and creates a **connection**: a `workspace_api_keys` row with `oauth_client_id` instead of a secret, one per (person, app), one workspace each, counted in the 20 cap. **(b) Exchange, not RLS.** The connector verifies the app's token, loads the connection for `(sub, client_id)` and then runs exactly as for a pasted key (service role + `x-moduo-key-id`). Rejected: running OAuth calls as the person under RLS (Supabase's template default). It breaks every Tasks read (`share_visible_ids` is service-role-only since `20261022130000`) and all nine chat agent RPCs, writes agent changes as the person (`module_activity_log` and `perm_actor_id()` put the person first), and RLS never applies module scopes, so the token would carry the person's whole access. **(c) Lockout.** Because the token is a real user token, it's refused everywhere else: a PostgREST pre-request guard on `client_id`, restrictive Storage and Realtime policies, an access-token hook setting `role` to `anon` for OAuth-issued tokens, and a shared Edge Function helper. Proved by tests before anything is switched on in prod (MCPO-1). **(d) Foundation.** `@modelcontextprotocol/server` 2.x (stateless, per-request server registering only the key's tools; protocol up to 2025-11-25) and `@supabase/server` for verification and protected-resource discovery. Our tool handlers, `parseToolArgs`, scopes and trail are kept: they're the product, the template has none of them. **(e) Code mode.** Cloudflare's server-side Code Mode solves a 2,500-endpoint API (1.17M tokens → ~1k); ours is 110 tools, ~16k tokens for a full-scope key, and Claude Code already defers our tools with tool search. Anthropic's programmatic tool calling doesn't apply to MCP-connector tools, and the MCP spec (2026-07-28 client best practices) makes both tool search and code mode the client's job. So no `code`/`execute` tool and no Worker in front; instead output schemas for the main reads and annotations on every tool (MCPO-6). Revisit when agents run long bulk call chains, the tool list passes ~30k tokens, or an important client lacks tool search; start read-only then. → [specs/mcp-oauth.md](../../specs/mcp-oauth.md)

- **2026-10-15 · Connector gaps from dogfooding (MOD-92, 93, 94, 111, 112, 113): `tasks_list` answers a short row by default, agents read comments (with Links: View), a task handle works in the link tools, tags the connector makes get the app's colour, and a tool's listing and its parser can't drift apart.** All agent's choices, confirmed for building, revisitable; no migration. **(a) `tasks_list` summary row (MOD-113).** Default `fields: "summary"`: `handle`, `id`, `title`, `status` (the category word, the vocabulary the `category` filter speaks) plus `status_name` only when the project's name for it isn't just the category written out ("In review", not "In progress"), `priority`, `assignee` (a name; none = Unassigned), `project` (only when the list spans projects), `section` (a name), `tags`, `due` (`YYYY-MM-DD`, `+ HH:MM` when timed), and `blocked` / `drifted` / `queued_by_me` / `subtasks` / `parent` (a handle) only when true. Names come only from projects the person can see (a task shared on its own doesn't name its project, as `tasks_time_report`). `fields: "full"` answers the old `shapeTask` shape; full pages default to 25, summary pages stay at 100 so a caller that pages without a `limit` still reads "short page = last". Why: 66 full rows were 57,000 characters (a 280-character description excerpt, both people as objects, every legacy field), past what an agent's client shows in one go. Rejected: dropping `id` (every tool now takes a handle, but `id` is what existing callers key on); an `include_description` switch (one `fields` switch reads simpler); minifying every tool's JSON in `index.ts` (would cut another ~20% everywhere, but changes every tool's output: a follow-up if pages are still too long). `tasks_search` and `tasks_queue` still answer the full shape. Callers that read `bucket_id`, `section_id`, `due_on` or `assignee.id` from a list now ask for `fields: "full"`. **(b) Comments (MOD-94) are Links'.** `comments_list(entity_type, entity_id, limit)` on the Links module (Links: View) reads an item's comments, newest last (the latest N, default 50, max 200, with the `total`), behind `assertReach`, so it needs View on the item's module too and shows only what the key's person can open, the app's rule (`comments__item_seen` and `perm_can_see_entity` are the same check). `tasks_get` carries the latest 20 (with `earlier_comments` counting the rest) only for a key with Links: View; without it there is no `comments` field at all. Each: `id`, `author` (a person's name, an app as `"<key name> (app)"`, as the app shows it), `at`, `edited`, `body`; reactions stay out. Why Links: the key card says Links covers "links, comments and search", and the default key is Tasks: View with Links: None, so a Tasks read of comments would have widened every existing key on deploy. Rejected: a Tasks-only `tasks_comments_list` (first build, the validator's catch); comments in `tasks_activity` (its description now points at `comments_list`). **(c) Handles in the link tools (MOD-112).** `assertReach` (`moduo-mcp/share.ts`) resolves a task handle with the resolver the Tasks tools use (moved to `moduo-mcp/task-ref.ts`, since `tasks-helpers.ts` imports `share.ts`) and answers the uuid; `links_list`, `links_suggest`, `links_create`, `comments_add`, `contacts_link`, `email_link` and `notes_link` pass that to their ops. A hidden task's handle reads like a missing one. **(d) Tag colours (MOD-93).** The palette and `pickTagColor` moved into `@contracts/vocabularies` (`src/components/tag-colors.ts` re-exports them), so the app and the connector share one rule. After a connector call that adds tags by name (`tasks_create` with `tags`, `tasks_update` with `tags_add`, `templates_apply`) the connector gives every live colourless tag in the workspace the hue the app would have picked, oldest first, which also colours the ones made before (nobody ever chooses "no colour": a recolour always names a hue). Colouring is editing a tag, so it runs only when `perm_can_tag` says the key's person may (the check the tags policy makes for the app), at most 50 tags a call, only while a tag is still colourless (a hue someone picks meanwhile wins), and best effort after the op succeeded. `tags.color` keeps no CHECK (read laxly, like the role below). Rejected for now: picking the colour in SQL (a `tags` insert trigger would cover every server path atomically, but needs a migration and a release train and puts the rule in two languages); it becomes the right home if another server path starts making tags. **(e) Listing vs parser (MOD-92).** `projects_create`/`projects_update` listed `description` but `TOOL_ARG_SCHEMAS` lacked it, so the parser stripped it before the handler ran. `moduo-mcp/tool-schemas.test.ts` now requires every tool's `inputSchema` and its Zod schema to name the same fields and the same required ones, and the Tasks connector tests call through `parseToolArgs` as `index.ts` does. **(f) Onboarding roles (MOD-111)** live in `vocabularies.ts` (`TASKS_ROLES`, `parse`/`normalize`/`is`); they're stored only in the preferences JSON, so there's no CHECK to mirror. **Deploy:** `moduo-mcp` only (no migration); the app changes are code moves. → [docs/moduo-mcp-connector.md](../moduo-mcp-connector.md)
- **2026-10-09 · API keys can expire, and Settings flags expired and unused keys; there is deliberately no per-key rate limit.** Prompted by a todo ("last-used, expiry and per-key rate limit") that was half stale: `last_used_at` already existed (stamped at most once a minute by `authenticate()`), the leak was already bounded (View-on-Tasks default, never above the creator, workspace-pinned, 20-key cap, instant revoke, no email send or body read), and a key is 192 bits of randomness, so guessing isn't a threat. **(a)** `workspace_api_keys.expires_at` (null = never; a CHECK keeps it after `created_at`); `workspace_api_keys_create` takes `p_expires_in_days` (null or 1–730; omitted = never, so an older app build behaves as before). Existing keys never expire. **(b)** The picker offers Never / 30 days / 90 days / 1 year and starts at **90 days** (the designer's call, 2026-10-09). **(c)** `moduo-mcp` refuses an expired key with the same 401 as a revoked one ([`_shared/api-key-expiry.ts`](../../supabase/functions/_shared/api-key-expiry.ts); an unreadable value fails closed). Enforced in the connector only, like the creator check: the SQL resolvers (`module_api_key_id()` and the scope functions) are reached solely through it, and it sets the key header only after verifying the secret, expiry included. **(d)** An expired key stays listed, marked "Expired", with its Edit-access button off; revoking clears it. **(e)** Rows say "Expires in N days" in the last week, and "Unused for N days" / "Never used in N days" from 60 days (`STALE_KEY_DAYS`). **(f) No rate limit:** it would add a DB round trip to every call to cap the damage of a leaked Edit key, while View is the default and every write is attributed. Revisit if abuse shows up; a Postgres fixed-window counter like `booking_rate_check` is the pattern. **Not built, worth having:** last caller IP / user agent on the key, to tell a stolen key's use from your own. **Deploy order: migration `20261009210000` first, then the app, then the connector.** The key list falls back to the old columns on 42703, but creating a key with an expiry fails until the migration is applied, and a `moduo-mcp` redeployed before it answers every key with a 401 (its select names `expires_at`). Expiry is checked in the connector **and** in the SQL resolvers (`module_api_key_creator`, `module_api_key_effective_scopes`, `module_api_key_scope`, migration `20261010090000`, added after the review pointed out that only revocation was enforced in depth), and `workspace_api_keys_set_scopes` refuses an expired key. Expired keys don't count toward the 20-key cap. → [supabase/migrations/20261009210000_api_key_expiry.sql](../../supabase/migrations/20261009210000_api_key_expiry.sql)
