- **2026-10-08 · API keys get None / View / Edit per module, inside the permission model: a key never gets more than its creator, and only its creator can widen it.** Delivers what the landing's "Bring any AI" section promises (ported from the unmerged `t/maciej/api-key-scopes`, 2026-10-02). **(a) Modules:** Tasks, Notes, Calendar, Email, Contacts, Chat, Links. Links is the spine (search, links, comments across the others). One closed vocabulary (`MCP_KEY_MODULES` / `MCP_KEY_SCOPES` in `@contracts/vocabularies`) held by a CHECK on `workspace_api_keys.scopes`. Admin stays non-grantable. **(b) The cap:** every call is capped by the creator's current access (PERM-0's `module_api_key_effective_scopes`; roles and exceptions apply through the write triggers, sharing through `share_visible_ids`). Setting scopes now refuses a level above what the creator can do today (`module_api_key_cap`), so the stored map is honest when it's set. It can read lower later if the creator's role shrinks; the key's row then says it's limited. **(c) Who may change a key:** anyone with `ws.api_keys` can narrow or revoke any key; **only the key's creator can widen it**, because a key acts as that person, and nobody else should be able to hand someone's agent more of their access. Errors no longer say "owners and admins", since custom roles can hold `ws.api_keys`. **(d) Rows a key creates belong to its creator** (`perm_actor_id()`, as PERM-0 ruled for owner columns): the keyed round-trip found six ops still stamping `auth.uid()` (NULL under a key), so link, comment and contact-link writes failed for every key, and agent-made contacts and notes were invisible to everyone (`20261008123000`). **(e) A key's comment reads as the app** ("Claude (app)"), never as the person: comments gain `author_kind` / `author_label`, like chat messages (`CONTENT_AUTHOR_KINDS`). **(f)** Removing an email thread checks that the *actor* can change links, so a key can't do what its creator couldn't (`20261008122000`). Migrations `20261008120000…123000` (renumbered from `20261002…`: `20261002120000` collided with `waitlist_updates_opt_in` on `prod-landing`; the first three bodies were already on prod from 2026-10-01/02). → [docs/moduo-mcp-connector.md](../moduo-mcp-connector.md) §Scoped API keys · [docs/testing/t-maciej-api-key-module-scopes.md](../testing/t-maciej-api-key-module-scopes.md)

- **2026-10-07 · PRIV-2 planned: what a deleted account leaves in other people's workspaces, its Stripe copy, and a privacy@ admin command** (Maciej's calls in /s1; spec [specs/privacy-account-erasure.md](../../specs/privacy-account-erasure.md), DoR-ready). **(a) Private = no other current member can see it** (by `can_access`), and it is hard-deleted with every trace (grants, tags, activity, entities and their links and comments). **(b) Shared items stay** for the people they were shared with, including items shared only with specific teammates; the new owner is the workspace owner if they could already see the item, otherwise the teammate with the most access (ties: earliest grant, then earliest to join), so nobody gains access to anything new. - **2026-10-07 · Account deletion now erases what the FK cascade can't reach: Stripe, Storage, booking links, integration tokens, waitlist.** **Deployed 2026-10-07 as `delete-account` v15**, after the read-only live check (designer's OK; results in the entry above); unauthenticated probes answer 401 / 405. The end-to-end delete on a throwaway account is still to do. Prompted by the privacy policy ("When you delete it, we delete this data, including your billing record at Stripe"); before this, `delete-account` only called `auth.admin.deleteUser`. Order, in [`_shared/account-erasure.ts`](../../supabase/functions/_shared/account-erasure.ts): the sole-owner **409 guard (unchanged)** → **Stripe**: every customer for the user (`profiles.stripe_customer_id` plus a `metadata['supabase_user_id']` search); live subscriptions are cancelled (no proration, comment "Moduo account deleted"), then the customer is deleted. A stored customer that Stripe tags with *another* user is never touched (the column was client-writable until 2026-10-06) → **Storage**: everything listed under `avatars/profiles/{uid}/` and `avatars/workspaces/{id}/` for every owned workspace, soft-deleted ones included → **booking**: `slot_bookings` and `slot_conflict_windows` for the user's slot ids (never a slot id another host's link shares), their co-host seats, their links (soft-deleted too), then one more bookings sweep for a guest who booked mid-delete → `user_integrations` → `contact_private_notes` (private by construction; ones in other people's workspaces have no FK) → `waitlist` (exact) + `founders_interest` (case-insensitive: it isn't normalized), only when the account's email is confirmed → `auth.admin.deleteUser` **last**. **Why explicit deletes, not FKs:** correct whatever prod's unverified FKs are, no migration, and with the auth delete last any failure leaves a retryable account (every step is idempotent). **Fail closed, two exceptions:** a failed step returns 500 with a step message ("wasn't deleted" for the guard and Stripe, which also says the plan may already be cancelled; "only partly deleted, try again" after). Exceptions, logged as warnings: a Stripe search *refused for good* (400/403; a 429 or 5xx still fails the step), so a key without search can't block every deletion; and no Stripe key when the profile has no customer (with one, it refuses). Google/Zoom grants are not revoked at the provider, same as the existing Disconnect; our encrypted copies are deleted. `bun run typecheck` now covers the module and its test. **Not covered yet (PRIV-2, decide next):** (1) the `stripe.*` Sync Engine mirror keeps the deleted customer's email/name, invoices and charges (the open-source engine's `customer.deleted` only updates `id/object/deleted`; confirm on prod's dashboard integration), Stripe itself keeps invoices/charges (its Redaction Jobs API is preview; tax-record retention is a legal call), and founder coupons + promotion codes carry the email in their name/metadata; (2) **private items in other people's workspaces outlive the account**: owner-only calendar and email accounts, private contacts, calendars. Private buckets there (and, depending on cascade order, private notes) are handed to that workspace's owner by the PERM `share_member_removed` trigger, which the membership cascade fires (read from the code; not live-probed); (3) a deleted co-host seat leaves the other owner's collective link paused (flagged off today; PERM-8b should handle a co-host vanishing); (4) a user deleted in the Supabase dashboard skips all of this. → [docs/testing/t-maciej-delete-account-erasure.md](../testing/t-maciej-delete-account-erasure.md) · [docs/gotchas.md](../gotchas.md) §Supabase

- **2026-10-06 · PERM-3…8 + PERM-2b: one `resource_grants` table; access = role ceiling ∩ grant.** Levels free/busy < view < edit < full. - **2026-07-11 · Workspace role hierarchy + transfer-ownership (follow-up to DF-24) landed** (`bun run verify` 1041 green; skeptical-senior validator on the authz logic; **all 12 authz paths round-trip-verified against prod**, rolled back clean). **Designer decision:** the `owner` tier must mean something — **only the owner manages admins**; an **admin** manages only members *below* admin (editor/viewer) and can neither remove/demote/promote another admin nor grant the admin role. Plus a **transfer-ownership** op the account-deletion effort needs (an owner must hand off before deleting). Ratified/built: **(a) Three SECURITY DEFINER ops** (migration `20260711180000_workspace_roles_transfer.sql`, **applied to prod + verified**): `workspace_op_remove_member` (now also raises `only the workspace owner can remove an admin`), `workspace_op_set_member_role(member,role,perm_notes,perm_tasks)` (role+perms in one authz-checked write — validates `p_role ∈ {admin,member,viewer}`, blocks changing the owner/self, and for a non-owner caller blocks both *managing an admin target* and *granting admin*), and `workspace_op_transfer_ownership(member)` (owner-only; sets `workspaces.owner_id`, promotes the target to `owner`, demotes the caller to `admin`). All determine owner via the authoritative `workspaces.owner_id`, not a role string. **(b) `updateMemberPermissions` now routes through `workspace_op_set_member_role`** — the old direct client `UPDATE workspace_members … WHERE id=other` was RLS-blocked (own-row write RLS), so changing another member's role silently failed before; the RPC both fixes that AND adds the hierarchy. **(c) The client mirror of the rules is a pure, tested module** [`member-permissions.ts`](../../src/features/workspaces/member-permissions.ts) (`canManageMember`/`assignableRolesFor`/`canTransferOwnership`, 6 tests) — the modal filters role options (admins never see "Admin"), gates the ⋯ menu (an admin sees none on a peer admin), and shows an owner-only "Make owner" item behind a confirm dialog. Keep this module and the SQL ops in lockstep. **(d) Transfer demotes the old owner to admin** (not stranded) — exactly the hand-off account-deletion will call before deleting the owner's account; the demote is an **UPSERT** (a `trg_workspaces_add_owner_member` trigger backfills owner memberships today, but the upsert survives that trigger ever changing). **(e) Validator-driven:** the modal's **Invite + pending-invites + MCP-keys sections are now OWNER-ONLY** (was owner||admin), because their RLS (`paid_plan_required_to_invite`, `workspace_api_keys_can_manage`) is owner-only — an admin was seeing forms the server rejects. Admins manage *existing members below them* via the per-row menu; workspace-level controls (invite/keys/billing) stay the owner's. If we later want admins to invite (as non-admin roles), that needs an admin branch in the invite INSERT policy. All three ops also got a **soft-deleted-workspace guard** (defense-in-depth). **Accepted non-fix:** transfer does NOT re-check the target's plan tier — the `free_users_max_one_workspace` limit is a *creation-time* gate, and you should be able to hand a workspace to any member (incl. a free-tier teammate); making the target own 2 workspaces via transfer is a deliberate, minor entitlement bypass. → [supabase/migrations/20260711180000_workspace_roles_transfer.sql](../../supabase/migrations/20260711180000_workspace_roles_transfer.sql) · [docs/gotchas.md](../gotchas.md) §Supabase
