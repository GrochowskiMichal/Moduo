- **2026-10-08 · PRIV-3: switching app analytics off, or deleting the account, deletes what PostHog holds for the person.** Both go through [`_shared/posthog-erasure.ts`](../../supabase/functions/_shared/posthog-erasure.ts): `POST https://eu.posthog.com/api/projects/<id>/persons/bulk_delete/` with the user id as distinct id and `delete_events` + `delete_recordings`. PostHog deletes the person at once and queues the events for its Sunday run. **Account deletion:** a `posthog` step runs **first** in `deleteAccount` (before Stripe), so an outage (network, 429, 5xx) fails the step with everything else untouched ("Couldn't delete your usage analytics, so your account wasn't deleted"), and a retry finishes. A permanent refusal (400/401/403/404, a wrong key, scope or project) is a **warning**, not a block: a broken key must never stop every account deletion. The warning carries the user id, so the data can still be deleted by hand. No secrets means the warning `posthog_not_configured`. `ErasureDeps.posthog` is required, so every caller (the PRIV-2c admin command too) decides it rather than skipping it by omission. **Switching off:** a new `analytics-forget` Edge Function (verify_jwt false, JWT checked in code) erases the caller's own person, never anyone else's. The app calls it the moment consent goes yes → no, while the person is still signed in; the function waits ~10 s before deleting, so PostHog's in-flight batch lands first ([`_shared/analytics-forget.ts`](../../supabase/functions/_shared/analytics-forget.ts)). A marker (`moduo:analytics-forget:<user id>`, one per switch-off, so an older answer can't clear a newer one) keeps the request until the function answers 200, and each later session of that person sends it again. A missing or refused PostHog setup answers **503**, not 200, so a switch-off made before the setup was fixed still happens afterwards. A yes again drops a request the server hasn't confirmed. A first "no" sends nothing. Consent is per device but the PostHog person is per account: switching off on one device erases what every device sent, and a device that still says yes keeps sending. **Deleting the account** also stops this device's analytics before it signs out (`forgetAnalyticsAccount`), since sign-out tracks `app_signed_out` and would recreate the erased person. Another device that still says yes can send a few events until its session ends; they carry an id that no longer links to anyone. **Accepted risk:** `analytics-forget` has no per-user throttle, so a signed-in user could loop it and use up PostHog's private-API rate limit, which would make account deletions fail (and retry) while it lasts. Alpha users are known; if abuse shows up or before public sign-up, add an atomic per-user ledger like the waitlist's (`20261001160000_waitlist_secure_join.sql`). **Setup (Mike, PostHog):** a personal API key with `person:write` on the Moduo project, plus the project id, as Edge Function secrets `POSTHOG_PERSONAL_API_KEY` / `POSTHOG_PROJECT_ID` (optional `POSTHOG_API_HOST`). Steps: [docs/testing/priv-3-posthog-erasure.md](../testing/priv-3-posthog-erasure.md). → [supabase/functions/analytics-forget](../../supabase/functions/analytics-forget/index.ts), [src/lib/analytics.ts](../../src/lib/analytics.ts)

- **2026-10-07 · PRIV-2 planned: what a deleted account leaves in other people's workspaces, its Stripe copy, and a privacy@ admin command** (Maciej's calls in /s1; spec [specs/privacy-account-erasure.md](../../specs/privacy-account-erasure.md), DoR-ready). **(a) Private = no other current member can see it** (by `can_access`), and it is hard-deleted with every trace (grants, tags, activity, entities and their links and comments). **(b) Shared items stay** for the people they were shared with, including items shared only with specific teammates; the new owner is the workspace owner if they could already see the item, otherwise the teammate with the most access (ties: earliest grant, then earliest to join), so nobody gains access to anything new. Same rule picks a new manager for channels the user managed alone. **(c)** Their tasks in other people's workspaces are unassigned (also on plain member removal, which fixes frozen tasks); their messages, comments and activity stay without a name; nobody is notified. **(d) Billing:** our copy of the Stripe customer profile and saved cards is wiped right away (Stripe sync 1.0.32 keeps a deleted customer's full profile otherwise); invoices and payment records stay at Stripe and in our copy for the legal period, usually 5 years, and the privacy policy says so. **(e) privacy@ requests** use an admin command (no UI) with a preview step; a sole owner of a shared workspace stops the command until a new owner is named per workspace. **(f) Copy:** the landing card "Delete your account and everything goes with it" stays as is (the privacy policy carries the details); the Danger zone adds "Things you shared with others stay with them, without your name." and the sign-in page confirms "Your account and your data were deleted." **(g)** Founder coupons and Stripe Redaction Jobs are out of scope. → [specs/privacy-account-erasure.md](../../specs/privacy-account-erasure.md)

- **2026-10-07 · App analytics (PostHog) is opt-in per person: the app asks after sign-in until you answer, it's off until you say yes, it shares the landing's PostHog project as `surface: "app"`, and the privacy policy describes it** (Maciej's calls: a one-time prompt after sign-in, "the more data we get the better, but ethically"; one project, because PostHog's free plan has one). `src/lib/analytics.ts` does nothing unless the build has `PUBLIC_POSTHOG_KEY` (no live build does), the browser isn't sending Do Not Track, and the signed-in person said yes. They can say it in the one-time question ([analytics-consent-prompt.tsx](../../src/components/app/analytics-consent-prompt.tsx)): a card in the toast stack, two buttons of equal weight ("Don't share" / "Share"), a privacy-policy link, shown after a 2-second settle and again on each launch until answered. Or in Settings → Preferences → Privacy, which is also where they change it later. The answer is kept per account on each device as `moduo:consent:<user id>` = `granted`/`denied`, the app's version of the landing's `moduo:consent`. Until then posthog-js isn't downloaded: its chunk is named `posthog` and kept out of the async-chunk prefetch in `rsbuild.config.ts`. Once loaded, it starts with `opt_out_capturing_by_default` + `opt_out_persistence_by_default`, is opted in only for that person, and sign-out or withdrawal opts it out and clears its storage (new events stop at once; ones captured just before can still go out with PostHog's current batch or its retries, which posthog-js can't drop). Defaults: EU host, identity = user id only (never email; each person gets their own device id), no autocapture / pageviews / replay / heatmaps / surveys / remote config, URLs cut to the route root, query- and referrer-derived values dropped. What gets sent: the explicit `track()` events plus `$identify`, with PostHog's device and browser details and our `surface: "app"`, `platform` (web/desktop), `environment` (production, staging, preview or development) and `app_version`. PostHog records the IP address unless the project's "Discard client IP data" setting is on. **One project, two surfaces:** filter or break down by `surface` (`app` here, `landing` on the website). The app's PostHog storage is named `ph_moduo_app…`, so it never touches the landing's on the shared moduo.app/book origin, and the landing's session replay can't reach the app (client-side off, no remote config). **Privacy policy:** live on moduo.app/privacy since 2026-10-07 (GrochowskiMichal/Moduo#232, merged into `prod-landing`): §04 gains "In the Moduo app"; §05, §07, §08, §09 and §11 follow. **Set the key only on a build that contains this change.** It's on `maciej`; `prod-app` still has the old wrapper, which sends the email without asking. Change the policy in the same breath as anything the app sends. **Deleting a person's PostHog data** on account deletion and on switching off is PRIV-3 (entry above, 2026-10-08); until its secrets are set it only logs a warning, and the live policy promises deletion on request, which stays true. → [src/lib/analytics.ts](../../src/lib/analytics.ts)

- **2026-10-07 · Account deletion now erases what the FK cascade can't reach: Stripe, Storage, booking links, integration tokens, waitlist.** **Deployed 2026-10-07 as `delete-account` v15**, after the read-only live check (designer's OK; results in the entry above); unauthenticated probes answer 401 / 405. The end-to-end delete on a throwaway account is still to do. Prompted by the privacy policy ("When you delete it, we delete this data, including your billing record at Stripe"); before this, `delete-account` only called `auth.admin.deleteUser`. Order, in [`_shared/account-erasure.ts`](../../supabase/functions/_shared/account-erasure.ts): the sole-owner **409 guard (unchanged)** → **Stripe**: every customer for the user (`profiles.stripe_customer_id` plus a `metadata['supabase_user_id']` search); live subscriptions are cancelled (no proration, comment "Moduo account deleted"), then the customer is deleted. A stored customer that Stripe tags with *another* user is never touched (the column was client-writable until 2026-10-06) → **Storage**: everything listed under `avatars/profiles/{uid}/` and `avatars/workspaces/{id}/` for every owned workspace, soft-deleted ones included → **booking**: `slot_bookings` and `slot_conflict_windows` for the user's slot ids (never a slot id another host's link shares), their co-host seats, their links (soft-deleted too), then one more bookings sweep for a guest who booked mid-delete → `user_integrations` → `contact_private_notes` (private by construction; ones in other people's workspaces have no FK) → `waitlist` (exact) + `founders_interest` (case-insensitive: it isn't normalized), only when the account's email is confirmed → `auth.admin.deleteUser` **last**. **Why explicit deletes, not FKs:** correct whatever prod's unverified FKs are, no migration, and with the auth delete last any failure leaves a retryable account (every step is idempotent). **Fail closed, two exceptions:** a failed step returns 500 with a step message ("wasn't deleted" for the guard and Stripe, which also says the plan may already be cancelled; "only partly deleted, try again" after). Exceptions, logged as warnings: a Stripe search *refused for good* (400/403; a 429 or 5xx still fails the step), so a key without search can't block every deletion; and no Stripe key when the profile has no customer (with one, it refuses). Google/Zoom grants are not revoked at the provider, same as the existing Disconnect; our encrypted copies are deleted. `bun run typecheck` now covers the module and its test. **Not covered yet (PRIV-2, decide next):** (1) the `stripe.*` Sync Engine mirror keeps the deleted customer's email/name, invoices and charges (the open-source engine's `customer.deleted` only updates `id/object/deleted`; confirm on prod's dashboard integration), Stripe itself keeps invoices/charges (its Redaction Jobs API is preview; tax-record retention is a legal call), and founder coupons + promotion codes carry the email in their name/metadata; (2) **private items in other people's workspaces outlive the account**: owner-only calendar and email accounts, private contacts, calendars. Private buckets there (and, depending on cascade order, private notes) are handed to that workspace's owner by the PERM `share_member_removed` trigger, which the membership cascade fires (read from the code; not live-probed); (3) a deleted co-host seat leaves the other owner's collective link paused (flagged off today; PERM-8b should handle a co-host vanishing); (4) a user deleted in the Supabase dashboard skips all of this. → [docs/testing/t-maciej-delete-account-erasure.md](../testing/t-maciej-delete-account-erasure.md) · [docs/gotchas.md](../gotchas.md) §Supabase

- **2026-07-11 · Workspace role hierarchy + transfer-ownership (follow-up to DF-24) landed** (`bun run verify` 1041 green; skeptical-senior validator on the authz logic; **all 12 authz paths round-trip-verified against prod**, rolled back clean). **Designer decision:** the `owner` tier must mean something — **only the owner manages admins**; an **admin** manages only members *below* admin (editor/viewer) and can neither remove/demote/promote another admin nor grant the admin role. Plus a **transfer-ownership** op the account-deletion effort needs (an owner must hand off before deleting). Ratified/built: **(a) Three SECURITY DEFINER ops** (migration `20260711180000_workspace_roles_transfer.sql`, **applied to prod + verified**): `workspace_op_remove_member` (now also raises `only the workspace owner can remove an admin`), `workspace_op_set_member_role(member,role,perm_notes,perm_tasks)` (role+perms in one authz-checked write — validates `p_role ∈ {admin,member,viewer}`, blocks changing the owner/self, and for a non-owner caller blocks both *managing an admin target* and *granting admin*), and `workspace_op_transfer_ownership(member)` (owner-only; sets `workspaces.owner_id`, promotes the target to `owner`, demotes the caller to `admin`). All determine owner via the authoritative `workspaces.owner_id`, not a role string. **(b) `updateMemberPermissions` now routes through `workspace_op_set_member_role`** — the old direct client `UPDATE workspace_members … WHERE id=other` was RLS-blocked (own-row write RLS), so changing another member's role silently failed before; the RPC both fixes that AND adds the hierarchy. **(c) The client mirror of the rules is a pure, tested module** [`member-permissions.ts`](../../src/features/workspaces/member-permissions.ts) (`canManageMember`/`assignableRolesFor`/`canTransferOwnership`, 6 tests) — the modal filters role options (admins never see "Admin"), gates the ⋯ menu (an admin sees none on a peer admin), and shows an owner-only "Make owner" item behind a confirm dialog. Keep this module and the SQL ops in lockstep. **(d) Transfer demotes the old owner to admin** (not stranded) — exactly the hand-off account-deletion will call before deleting the owner's account; the demote is an **UPSERT** (a `trg_workspaces_add_owner_member` trigger backfills owner memberships today, but the upsert survives that trigger ever changing). **(e) Validator-driven:** the modal's **Invite + pending-invites + MCP-keys sections are now OWNER-ONLY** (was owner||admin), because their RLS (`paid_plan_required_to_invite`, `workspace_api_keys_can_manage`) is owner-only — an admin was seeing forms the server rejects. Admins manage *existing members below them* via the per-row menu; workspace-level controls (invite/keys/billing) stay the owner's. If we later want admins to invite (as non-admin roles), that needs an admin branch in the invite INSERT policy. All three ops also got a **soft-deleted-workspace guard** (defense-in-depth). **Accepted non-fix:** transfer does NOT re-check the target's plan tier — the `free_users_max_one_workspace` limit is a *creation-time* gate, and you should be able to hand a workspace to any member (incl. a free-tier teammate); making the target own 2 workspaces via transfer is a deliberate, minor entitlement bypass. → [supabase/migrations/20260711180000_workspace_roles_transfer.sql](../../supabase/migrations/20260711180000_workspace_roles_transfer.sql) · [docs/gotchas.md](../gotchas.md) §Supabase
