- **2026-10-08 · PRIV-2a built: one SQL function erases what a deleted account leaves in other people's workspaces, and member removal is fixed** (migration [`20261008013000_account_erase_workspace_data.sql`](../../supabase/migrations/20261008013000_account_erase_workspace_data.sql), spec block 1). `account_erase_workspace_data(user, preview = true)` (only an explicit `false` deletes; NULL previews) is SECURITY DEFINER, executable only by `service_role`, runs in one transaction, decides every item from today's access before changing anything, and returns counts; PRIV-2b calls it before `auth.admin.deleteUser`. Calls made while building: **(a) Private** = no other current member passes `can_access(…, 'view')`. Trashed contacts, groups, companies, calendars and events count as private (`can_access` hides trashed rows); trashed notes and buckets are judged like live ones. **(b) Deleted with every trace**, addressed as `type:id` in every type the spine uses (`perm_can_see_entity`): grants, tags, link-suggestion declines, activity (also links activity whose payload targets the item), entities (their links and comments cascade), `exposed_notes`, `note_shares` (explicitly: no migration records its delete rule), booking references and time-block slots. **(c) New owner:** the workspace owner if they can view it, else the member with the highest level, then the earliest member grant on that item, then the earliest to join; only people who already see the item qualify, and every derived access (note inheritance, bucket→task, group→contact, contact→company) flows from it, so nobody gains visibility; the probe compares every member's access before and after. **(d)** Shared tasks in buckets that go move to the Inbox of the teammate they're assigned to (the spec's edge case; AC4's wording now matches), else of their new owner, created like the app's `ensureWebInbox`; a task there with no grant of its own is private without a search (17.7 s → 1.3 s for 1,500 such tasks with 60 members), and the follow-up `20261008040000_account_erasure_private_shortcut.sql` does the same for notes, buckets, contacts, groups and companies nobody but their creator can reach (`account_erasure_only_creator` mirrors `can_access`'s branches: keep it in step; 6,700 private items with 60 members: 22.5 s → 58 ms); tasks assigned to the user are unassigned; calendars, sets, accounts, events and email go whole. **(e) Chat:** only people still in the workspace count (chat rows outlive membership). DMs and private channels with nobody else in them go; a channel they managed alone gets the workspace owner if the owner can see it (public, or a member), else its earliest remaining member (for a public channel, else the earliest workspace member). **(f) Names:** `module_activity.actor_label` is a copy of the display name, so it is cleared on the user's remaining activity; activity only they could read (their calendar and email items, also ones removed before) is deleted, since a calendar account's entries carry its email address. Authorship ids stay as bare ids (comments, links, grants' `created_by`, roles, tags). Invitations they accepted (they hold their email) are deleted; pending ones are the inviter's and stay. **(g) `share_member_removed`** unassigns a removed member's tasks and skips the owner hand-over when the profile is already gone, so a dashboard deletion never hands private items over. The migration also unassigns, once, tasks still assigned to people removed before it (`perm_enforce_write` refused to save them). **(h) Found while building:** an owner removing a member who has a private note failed on production (since 2026-10-06): the production-only `notes_share_fields_owner_only` guard refused the hand-over's owner change while the owner was signed in. It now honours `share.bypass`, like `perm_enforce_write`. Verified on local Postgres 17 against a stub of production (`supabase/probes/account-erasure.{stub,probe}.sql`), then **applied to production on 2026-10-08** with the designer's OK (catalog, grants and a read-only preview checked). → [docs/testing/t-maciej-priv-2a-erase-workspace-data.md](../testing/t-maciej-priv-2a-erase-workspace-data.md)

- **2026-10-08 · PRIV-3: switching app analytics off, or deleting the account, deletes what PostHog holds for the person.** Both go through [`_shared/posthog-erasure.ts`](../../supabase/functions/_shared/posthog-erasure.ts): `POST https://eu.posthog.com/api/projects/<id>/persons/bulk_delete/` with the user id as distinct id and `delete_events` + `delete_recordings`. PostHog deletes the person at once and queues the events for its Sunday run. **Account deletion:** a `posthog` step runs **first** in `deleteAccount` (before Stripe), so an outage (network, 10 s timeout, 408, 429, 5xx) fails the step with everything else untouched ("Something went wrong on our side. Your account wasn't deleted", neutral because most people never shared analytics), and a retry finishes. Any other refusal (another 4xx, or a success without PostHog's summary, i.e. a wrong key, scope, project or host) is a **warning**, not a block: a broken setup must never stop every account deletion. The warning carries the user id, so the data can still be deleted by hand. No secrets, or a `POSTHOG_API_HOST` other than `https://eu.posthog.com` / `https://us.posthog.com`, means the warning `posthog_not_configured`: the key only ever goes to PostHog, and redirects are refused. `ErasureDeps.posthog` is required, so every caller (the PRIV-2c admin command too) decides it rather than skipping it by omission; a caller that leaves the field out fails the step at run time, since Edge Function entry points aren't type-checked. **Who notices a refusal:** only delete-account's logs record it, and Supabase keeps those briefly. So whoever rotates or revokes the PostHog key updates the secret in the same sitting and reruns the end-to-end check. **PRIV-3b (decided, before the production key):** a durable backlog, i.e. a service-role-only table where delete-account records an erasure that was refused, skipped or rate-limited before the auth user goes, retried on a schedule. With it, a 429 or timeout in account deletion becomes a backlog entry instead of a blocked deletion, which also removes the rate-limit coupling below. Both the validator and the security pass flagged the logs-only gap. **Switching off:** a new `analytics-forget` Edge Function (verify_jwt false, JWT checked in code) erases the caller's own person, never anyone else's. The app calls it the moment consent goes yes → no, while the person is still signed in; the function waits ~10 s before deleting, so PostHog's in-flight batch lands first ([`_shared/analytics-forget.ts`](../../supabase/functions/_shared/analytics-forget.ts)). A marker (`moduo:analytics-forget:<user id>`, one per switch-off, so an older answer can't clear a newer one) keeps the request until the function answers 200, and each later session of that person sends it again. A missing or refused PostHog setup answers **503**, not 200, so a switch-off made before the setup was fixed still happens afterwards. A yes again drops a request the server hasn't confirmed; one already sent still runs, so the few events sent during its ~10 s wait can go with the rest (over-deletion, never under-deletion). A first "no" sends nothing. Consent is per device but the PostHog person is per account: switching off on one device erases what every device sent, and a device that still says yes keeps sending. **Deleting the account** also stops this device's analytics before it signs out (`stopAnalyticsForDeletedAccount`, which records a "no" so the question doesn't come back before the sign-out lands). `app_signed_out` is tracked only when the person signs out (the auth provider's `signOut`), never on a SIGNED_OUT that auth-js fires itself, such as a refused refresh after the account was deleted elsewhere: either would recreate the erased person. Analytics also starts only once the server confirms the account: the profile read the plan tier needs at launch and sign-in (a deleted account has none, which PostgREST reports as PGRST116). Only that confirmed absence stops analytics; a failed read (offline, an outage) leaves it as it is, so a blip never resets a consenting person's PostHog identity. Otherwise another device reloading within its cached session's hour would identify the erased id and send `app_signed_in`. The app tracks only `app_signed_in`, `app_signed_out` and `$identify`, so with these two rules nothing goes out for a deleted account. The one gap left is PostHog's own lag: an event sent just before the deletion and ingested after it. **Accepted risk:** `analytics-forget` has no per-user throttle, so a signed-in user could loop it and use up PostHog's private-API rate limit, which would make account deletions fail (and retry) while it lasts. Alpha users are known; if abuse shows up or before public sign-up, add an atomic per-user ledger like the waitlist's (`20261001160000_waitlist_secure_join.sql`). **Setup (Mike, PostHog):** a personal API key with `person:write` on the Moduo project, plus the project id, as Edge Function secrets `POSTHOG_PERSONAL_API_KEY` / `POSTHOG_PROJECT_ID` (optional `POSTHOG_API_HOST`). Steps: [docs/testing/priv-3-posthog-erasure.md](../testing/priv-3-posthog-erasure.md). **Deployed 2026-10-08** after the validator, `/code-review ultra` and Claude Security passed: `delete-account` v16 and `analytics-forget` v1, `verify_jwt` false, probes green. → [supabase/functions/analytics-forget](../../supabase/functions/analytics-forget/index.ts), [src/lib/analytics.ts](../../src/lib/analytics.ts)
