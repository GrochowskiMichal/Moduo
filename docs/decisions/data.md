- **2026-10-08 · AT-1: attachment bytes go straight to a private bucket under a pending row; one ledger per workspace owner counts them; a daily `purge-deleted` function empties the trash after 30 days.** (agent, building AT-1 from [specs/attachments.md](../../specs/attachments.md); follows its decisions 1–6, 11, 12 except where stated.)
  - **Upload protocol.** `attachments_op_begin` checks edit access on the task (`can_access`, so a viewer can't add), the per-file limit and the pool, and creates a `pending` row with its object paths (`{workspace}/{id}/original.{ext}`, `…/preview.{webp|png|jpg}`; the name is display-only, never part of a path). The `storage.objects` INSERT/UPDATE policies only take a path a pending row of the same uploader names. Policies only see writes made under the person's own role, though: a signed upload URL (`createSignedUploadUrl` checks INSERT once, then its token writes for about 2 h outside RLS) could replace a file's bytes after finalize. So a trigger on `storage.objects` (`attachments_guard_object`) refuses every write to the bucket, by any path or role, that doesn't land on a pending row's path; deletes (the purge) pass. Production lets `postgres` create triggers on `storage.objects` (TRIGGER privilege; checked 2026-10-08), and every Storage policy already there is scoped to its bucket. `attachments_op_finalize` reads the stored size from `storage.objects.metadata` and fails the row on a mismatch, an object over the per-file limit or a "preview" over 10 MB. Refusals are machine codes (`attachment_too_large`, `storage_full`, …) with the numbers in the error's DETAIL as JSON, so the tile can say "340 MB — your plan allows 200 MB" without a second call. Ops need a signed-in person (Storage checks the same uploader), so API keys can't upload.
  - **What the pool counts.** `storage_usage` (one row per owner) holds the bytes of ready, undeleted files (original + preview), kept by a trigger on `attachments` and moved by a trigger on `workspaces.owner_id`. On top of that, admission counts every file that isn't ready yet (in progress, abandoned, failed) at the larger of its declared and its stored size, until the purge removes it, and one person can hold at most 50 unfinished uploads. A deleted file stops counting at once (spec). The daily purge recounts every pool from the rows, so a missed delta never outlives a day.
  - **Limits are held under the hosted upload cap, for now.** The Supabase org is on the Free plan, whose global upload limit is 50 MB and can't go higher (read with `supabase config pull` 2026-10-08), so the spec's "confirm ≥ 500 MB" fails. Until Maciej decides (Supabase Pro and a 500 MB limit, or 50 MB per file for everyone and an amended spec), `attachments__platform_file_cap()` returns 50 MiB and every per-file limit is the lower of the plan's and that, so `storage_status` never promises a size Storage would refuse. Either answer is one migration changing that function. The bucket itself says 500 MiB, the highest plan cap.
  - **The trash clock is the server's.** The app stamps `tasks.deleted_at` / `buckets.deleted_at` from the device clock; with a hard purge at 30 days a wrong or backdated clock would skip the restore window, so `trash_stamp_deleted_at` stamps `now()` on delete and keeps the stamp on later writes. Restores refuse anything trashed more than 30 days ago (`attachment_expired`; a task restore leaves such files in the trash), so a restore can't race the purge into a ready row with no bytes.
  - **Trash.** A trigger on `tasks.deleted_at` puts a task's live files in the trash with it (reason `task`, one batch id, reusing a `deleted_batch_id` on the task once TV-U6 adds one) and brings that batch back when the task is restored; a file deleted by hand earlier stays deleted. `attachments_op_restore` refuses a file trashed with its task (`restore_with_task`). `bucket` is in the reason vocabulary for TV-U6; nothing writes it yet. **No "File removed after 30 days" tombstones:** a task and its files share one 30-day clock and the purge removes the files before the tasks (a task waits while its file rows exist), so a restorable task never has purged files.
  - **Purge.** `purge-deleted` (service role, header secret `PURGE_DELETED_SECRET` compared with a Vault secret sent by pg_cron, `--no-verify-jwt`) removes objects through the Storage API, then the rows: files trashed over 30 days, uploads pending over 24 h, failed uploads, files of soft-deleted workspaces (there is no workspace restore), files whose task is gone, and objects no row names (older than a day; this is also what removes the files of an account's workspaces if `delete-account` didn't). Then tasks and buckets trashed over 30 days (links and the registry entry tombstoned like `notes__purge_ids`; a bucket waits while a task points at it), then the pool recount. `{"dry_run": true}` only counts. The schedule is its own migration (`20261008210600`), applied after a dry run. On 2026-10-08 prod had 11 tasks trashed over 30 days that the first run deletes.
  - **Alerts** are `module_activity` rows `attachments.storage_80` / `_95` (module `attachments`, entity the workspace, `notify_user_ids` = the owner, attributed to whoever uploaded), written by finalize and by restores; a jump past both sends only 95; both re-arm under 75%. They have their own mute (`storage`, Settings → Preferences). The click-through to Settings → Storage is AT-3.
  - **Elsewhere.** MCP `tasks_attachments_list` (Tasks View, the key creator's task visibility, 5-minute links); the export writes `attachments.json`, a manifest without the bytes; `delete-account` removes the files the owned workspaces' rows name (one select per 1000 files, not a Storage listing per file; a missing table counts as empty), and the purge's orphan sweep catches anything else.

- **2026-10-08 · The app never takes a Supabase session from the URL (`detectSessionInUrl: false`); sign-in is the typed 6-digit code only, and an emailed auth link at most confirms the address, never signs anyone in.** Found while fixing the booking connect CSRF: with supabase-js's defaults (implicit flow, detection on), any `#access_token=…&refresh_token=…&expires_in=…&token_type=bearer` fragment on any app URL replaced the tab's session, so anyone could send a link carrying their own token and the person who opened it worked in the sender's account (login CSRF). **What relied on URL sign-in (audit):** only Supabase's own emailed links: the dashboard "Send invitation" link (Site URL `https://app.moduo.app`, implicit fragment) and the magic-link, recovery and email-change links if a template still has `{{ .ConfirmationURL }}`. Nothing in the app does: sign-in is `signInWithOtp` + `verifyOtp` in `EmailAuthPanel`; the password sign-in/up runtime methods have no UI caller; there is no `signInWithOAuth`, recovery or email-change UI; `/join` redeems its own `?invite=` token with an Accept click after a code sign-in, and `send-workspace-invite` links there; the desktop app has no deep-link handler; calendar and Zoom connect returns use prefixed params. **Why off rather than `flowType: "pkce"`:** PKCE would also stop the CSRF and keep same-browser magic links, but auth-js would still parse every URL, the one sign-in request that works today (`signInWithOtp`) would change shape, and dashboard invites (generated server-side, so no verifier) break either way. **No `token_hash` handler** as a replacement: the hash is a credential anyone can forward, which is the same hole. **The dashboard invite link has to stay in its template.** With sign-ups off (`enable_signup = false`), GoTrue sends an unconfirmed address's code request through sign-up and refuses it ("Signups not allowed for this instance": `MagicLink` → `Signup` checks `DisableSignup` first), so an invitee can't get a code until the address is confirmed. Clicking `{{ .ConfirmationURL }}` confirms it server-side before the redirect; the app then ignores the session in the fragment and the invitee signs in with a code (the rest of the code-only design, Q13 in the transactional-email set; TX-2's Send Email Hook and TX-4's invite gate replace these templates later). A fragment that arrives is wiped from the address bar first thing at boot (`src/lib/auth-url-boot.ts`, the first import in `main.tsx`), without being read, and the sign-in page's email step says what to do ("Links don't sign you in here…", or for `#error_code=otp_expired` "That link has expired or was already used…"); an unconfirmed invitee who asks for a code first is told to click the invite link, or ask for a new invite if it expired. **If a URL callback is ever needed, it is PKCE (a code plus this browser's verifier), never the implicit fragment.** Tier 2 path (`src/lib/runtime*`). → [src/lib/auth-url.ts](../../src/lib/auth-url.ts) · gotcha in [gotchas/supabase.md](../gotchas/supabase.md) §Supabase / Auth

- **2026-10-08 · Deployed Edge Functions must match `supabase/functions/`, checked by `bun run functions:reconcile`; the Stripe Sync Engine's `stripe-webhook`, `stripe-setup` and `stripe-worker` are the only allowed exceptions.** Deleting a function's folder doesn't undeploy it: `founders-apply` stayed live after it left the repo until it was deleted by hand (2026-10-07, [billing.md](billing.md)). The check is the Edge Function sibling of `db:reconcile`, and it only reads. It lists what's deployed (the Management API when `SUPABASE_ACCESS_TOKEN` is set, otherwise the logged-in `supabase` CLI) and compares it with the function folders committed on the branch (a slug name and an `index.ts`, so `_shared/` and `deno.json` don't count; a folder that isn't committed yet doesn't count either, so it can't hide an orphan). It prints three groups: orphans, in the repo but not deployed, and the allowlisted externals. Exit 1 on an orphan, on a repo folder named like an allowlisted slug, or on an allowlisted function whose deployed entrypoint isn't the integration's own `…/source/index.ts` (something else was deployed over it, e.g. `supabase functions deploy` from `origin/main`, which still has `stripe-webhook/`). Exit 2 when it can't check, including an empty deployed list. A function in the repo but not deployed yet is reported and doesn't fail. **Limits:** names only, never code, so a stale deploy reads as in sync; the verdict is relative to the branch it runs on, so run it on an up-to-date one; and a replacement deployed with `index.ts` at the bundle root (possible through the Management API or the MCP connector) has the same entrypoint as the integration's own, so it isn't caught. To allow another integration's function, add its slug and who installed it to `KNOWN_EXTERNAL_FUNCTIONS` in [`src/lib/functions-reconcile-core.ts`](../../src/lib/functions-reconcile-core.ts). First run, 2026-10-08: 15 in both, no orphans, nothing undeployed, the three Sync Engine functions present with the integration's own entrypoints. → [scripts/functions-reconcile.ts](../../scripts/functions-reconcile.ts)

- **2026-07-29 · Prod and the migration files ARE in sync — but the repo is not a bootstrap, and that is the real debt** (OPS-2). A full reconciliation ([inventory](../reviews/ops-2-schema-reconciliation.md), re-runnable via `bun run db:reconcile`) found **0** of 193 declared objects missing from prod and **0 semantic drift** across all 110 function bodies — the EM-6 class of silent staleness is closed. The finding that matters is structural: prod has **73** applied migration versions against **42** repo files, and **22 of prod's 44 tables are created by no migration at all** (`profiles`, `workspaces`, `workspace_members`, `notes`, `calendar_events`, …). `supabase db reset` therefore cannot rebuild the database — most migrations would fail on missing tables — so there is no local/staging/preview story. **Decision deferred to the designer:** capture a `00000000000000_baseline.sql` from prod and keep the existing files as post-baseline history. Also recorded: a naive `prosrc` text hash reports 19 false drifts (prod stores compacted SQL — `('edit','admin')` vs `('edit', 'admin')`), so the comparison must normalize punctuation spacing on both sides.

- **2026-07-29 · `REVOKE … FROM PUBLIC` does not revoke `anon` on Supabase — the internal guards and a legacy invite function were anon-callable** (OPS-2 grants audit). Supabase grants `anon` EXECUTE directly, not through `PUBLIC`, so revokes naming only `PUBLIC` + `authenticated` left **15 SECURITY DEFINER functions** open to anon. **Not where you would guess:** every module’s bulk op-grant *loop* already revokes anon correctly — what omitted it were the six hand-written per-guard REVOKE pairs sitting a few hundred lines above that loop **in the same file**. The lesson is that one-off hand revokes drift from the loop pattern already present in the file. [`20260729140000_ops2_grants_hardening.sql`](../../supabase/migrations/20260729140000_ops2_grants_hardening.sql) (applied to prod, regression-probed) closes two groups: the six internal `*_op__guard*` helpers (defense in depth — a probe showed they raise rather than leak, but only an internal `IF … RAISE` stood between anon and an `email_refs` row), and **`accept_workspace_invite`**, which never read `auth.uid()` at all — it resolved the invitee by email and inserted into `workspace_members`, ignoring invite status and expiry. **Demonstrated in a rolled-back probe:** an *unauthenticated* caller using an invite already marked `revoked` drove `workspace_members` 0 → 1 with role **`admin`** (prod holds 7 non-revoked invites, which were live targets; ids are v4 UUIDs, so it needed a leaked id rather than guessing). It is legacy (pre-migration-files, superseded by DF-24's token flow) and uncalled, so it was revoked rather than repaired; **dropping it is the follow-up**. Three policy-helper functions were deliberately left anon-callable (they leak a plan tier and a workspace count) because 22 RLS policies defined for role `public` invoke them — revoking would turn anon empty-results into hard errors; scoping those policies `TO authenticated` is its own block.

- **2026-07-29 · A migration-filename collision is resolved by re-stamping the *idempotent* file, into the slot prod actually applied it in** (OPS-1, timestamp half). Two stamps were each used by two files — `20260702160000` (`companies_delete` + `user_preferences_calendar_domain`) and `20260712120000` (`df9_task_notifications` + `user_preferences_preferences_domain`) — so a fresh `supabase db reset` had an **undefined** apply order for each pair. Rule, in this order: **(1) of the pair, re-stamp the file whose SQL is provably re-runnable** — both moved files are pure `ALTER TABLE public.user_preferences ADD COLUMN IF NOT EXISTS …`, so a re-apply under a new version is a genuine no-op, whereas re-running function/trigger DDL is not free (this was the load-bearing criterion — *both* files of each pair had a prod-apply record, so "keep the stamp prod names" did not discriminate; use it only as a tie-break); **(2) pick the new stamp so the directory replays prod's REAL order** — `list_migrations` gave the ground truth (`20260702192441` calendar < `20260702200224` companies; `20260712004956` preferences < `20260713093048` df9), so both files moved *earlier* (`20260702155000`, `20260712115000`), not later. **(3) grep the docs for the old stamp** — a bare ``migration `<stamp>` `` reference silently re-points at the surviving file; four such records were orphaned by the first pass and had to be rewritten. Prod is unaffected either way: `supabase_migrations.schema_migrations` versions are generated by MCP `apply_migration` at apply time and bear no relation to the filename. Guarded by a new `src/lib/migration-order.test.ts` so `bun run verify` fails on the next collision; nothing in the repo read that directory before. → [src/lib/migration-order.test.ts](../../src/lib/migration-order.test.ts)
