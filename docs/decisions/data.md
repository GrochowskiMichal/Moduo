- **2026-07-29 · Prod and the migration files ARE in sync — but the repo is not a bootstrap, and that is the real debt** (OPS-2). A full reconciliation ([inventory](../reviews/ops-2-schema-reconciliation.md), re-runnable via `bun run db:reconcile`) found **0** of 193 declared objects missing from prod and **0 semantic drift** across all 110 function bodies — the EM-6 class of silent staleness is closed. The finding that matters is structural: prod has **73** applied migration versions against **42** repo files, and **22 of prod's 44 tables are created by no migration at all** (`profiles`, `workspaces`, `workspace_members`, `notes`, `calendar_events`, …). `supabase db reset` therefore cannot rebuild the database — most migrations would fail on missing tables — so there is no local/staging/preview story. **Decision deferred to the designer:** capture a `00000000000000_baseline.sql` from prod and keep the existing files as post-baseline history. Also recorded: a naive `prosrc` text hash reports 19 false drifts (prod stores compacted SQL — `('edit','admin')` vs `('edit', 'admin')`), so the comparison must normalize punctuation spacing on both sides.

- **2026-07-29 · `REVOKE … FROM PUBLIC` does not revoke `anon` on Supabase — the internal guards and a legacy invite function were anon-callable** (OPS-2 grants audit). Supabase grants `anon` EXECUTE directly, not through `PUBLIC`, so revokes naming only `PUBLIC` + `authenticated` left **15 SECURITY DEFINER functions** open to anon. **Not where you would guess:** every module’s bulk op-grant *loop* already revokes anon correctly — what omitted it were the six hand-written per-guard REVOKE pairs sitting a few hundred lines above that loop **in the same file**. The lesson is that one-off hand revokes drift from the loop pattern already present in the file. [`20260729140000_ops2_grants_hardening.sql`](../../supabase/migrations/20260729140000_ops2_grants_hardening.sql) (applied to prod, regression-probed) closes two groups: the six internal `*_op__guard*` helpers (defense in depth — a probe showed they raise rather than leak, but only an internal `IF … RAISE` stood between anon and an `email_refs` row), and **`accept_workspace_invite`**, which never read `auth.uid()` at all — it resolved the invitee by email and inserted into `workspace_members`, ignoring invite status and expiry. **Demonstrated in a rolled-back probe:** an *unauthenticated* caller using an invite already marked `revoked` drove `workspace_members` 0 → 1 with role **`admin`** (prod holds 7 non-revoked invites, which were live targets; ids are v4 UUIDs, so it needed a leaked id rather than guessing). It is legacy (pre-migration-files, superseded by DF-24's token flow) and uncalled, so it was revoked rather than repaired; **dropping it is the follow-up**. Three policy-helper functions were deliberately left anon-callable (they leak a plan tier and a workspace count) because 22 RLS policies defined for role `public` invoke them — revoking would turn anon empty-results into hard errors; scoping those policies `TO authenticated` is its own block.

- **2026-07-29 · A migration-filename collision is resolved by re-stamping the *idempotent* file, into the slot prod actually applied it in** (OPS-1, timestamp half). Two stamps were each used by two files — `20260702160000` (`companies_delete` + `user_preferences_calendar_domain`) and `20260712120000` (`df9_task_notifications` + `user_preferences_preferences_domain`) — so a fresh `supabase db reset` had an **undefined** apply order for each pair. Rule, in this order: **(1) of the pair, re-stamp the file whose SQL is provably re-runnable** — both moved files are pure `ALTER TABLE public.user_preferences ADD COLUMN IF NOT EXISTS …`, so a re-apply under a new version is a genuine no-op, whereas re-running function/trigger DDL is not free (this was the load-bearing criterion — *both* files of each pair had a prod-apply record, so "keep the stamp prod names" did not discriminate; use it only as a tie-break); **(2) pick the new stamp so the directory replays prod's REAL order** — `list_migrations` gave the ground truth (`20260702192441` calendar < `20260702200224` companies; `20260712004956` preferences < `20260713093048` df9), so both files moved *earlier* (`20260702155000`, `20260712115000`), not later. **(3) grep the docs for the old stamp** — a bare ``migration `<stamp>` `` reference silently re-points at the surviving file; four such records were orphaned by the first pass and had to be rewritten. Prod is unaffected either way: `supabase_migrations.schema_migrations` versions are generated by MCP `apply_migration` at apply time and bear no relation to the filename. Guarded by a new `src/lib/migration-order.test.ts` so `bun run verify` fails on the next collision; nothing in the repo read that directory before. → [src/lib/migration-order.test.ts](../../src/lib/migration-order.test.ts)
