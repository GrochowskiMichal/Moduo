- **2026-10-20 · TS-3a: the Tasks store's tables are in-memory TanStack DB collections the store drives; the snapshot reads its rows from them** → `apps/app/src/lib/sync/tanstack/kernel-mirror.ts`, `supabaseCollectionOptions({ ownerDriven: true })`, `WorkspaceStore.collection(name)` ([specs/tanstack-spine.md](../../specs/tanstack-spine.md)). The store keeps reading, landing into its kernel `SyncedCollection`, seeding from its IndexedDB copy, overlaying writes, sending the outbox and checking access, so the phases are unchanged (open tasks paint first; closed tasks, completions and comment counts follow). `changed()` hands each collection the ids its kernel table touched (`SyncedCollection.takeTouched()`; "all" after a whole read or a restore); `rendered()` lays the kernel's overlays over the collection's rows. `StoreSnapshot` and the public API are unchanged; every existing test passes untouched.

- **2026-10-20 · TS-2: the kernel is a TanStack DB collection through `supabaseCollectionOptions()`; the kernel keeps landing and the device copy** → `apps/app/src/lib/sync/tanstack/supabase-collection.ts` ([specs/tanstack-spine.md](../../specs/tanstack-spine.md)). Agent's choice, revisitable.
  - **Shape.** The options wrap one kernel `SyncedCollection` (owned by the store) and **mirror** its held rows into an in-memory collection: after every kernel step it diffs the touched ids by object identity and writes the difference in one `begin/write/commit`. Landing, delete marks, soft deletes, the lookback and the cursor stay in `kernel/`; the adapter has no landing rule of its own.
  - **Order.** Realtime subscribes first and buffers; the device copy seeds and `markReady` fires at once; the kernel delta runs once Realtime is subscribed; the buffer flushes newest-per-id by the "live" rule. With no copy, ready waits for the first whole read.
  - **No persistence plugin.** The kernel's IndexedDB copy stays the copy (TS-0 measured OPFS SQLite slower on warm open); `onChange` tells the store to write it. Access loss (`isAccessLoss` on a read error, or `utils.loseAccess()`) empties the kernel and `truncate`s the collection. Cleanup closes Realtime and drops late reads and events. `utils.catchUp()` re-reads (reconnect, a failed catch-up, which still ends the buffering) and `utils.sync(ids)` mirrors kernel changes the store made itself (access-check drops). A device copy that can't be read counts as none.
  - **TS-3c hook.** `sendChanges` gets `{ id, changes }` (only the edited fields, `changedFields()`), and its server rows land by the "answer" rule before the optimistic state drops; `utils.landServerRow` does the same for any op's answer.
  - **Rejected:** `@supabase-labs/tanstack-db` (full-row PATCH, count per read); TanStack's persisted-collection wrapper (a second copy of the rows); re-implementing landing on `collection.get` as the spike did (it lost the kernel's delete marks).

- **2026-10-08 · AT-1: attachment bytes go straight to a private bucket under a pending row; one ledger per workspace owner counts them; a daily `purge-deleted` function empties the trash after 30 days.** (agent, building AT-1 from [specs/attachments.md](../../specs/attachments.md); follows its decisions 1–6, 11, 12 except where stated.)
  - **Upload protocol.** `attachments_op_begin` checks edit access on the task (`can_access`, so a viewer can't add), the per-file limit and the pool, and creates a `pending` row with its object paths (`{workspace}/{id}/original.{ext}`, `…/preview.{webp|png|jpg}`; the name is display-only, never part of a path). The `storage.objects` INSERT/UPDATE policies only take a path a pending row of the same uploader names. Policies only see writes made under the person's own role, though: a signed upload URL (`createSignedUploadUrl` checks INSERT once, then its token writes for about 2 h outside RLS) could replace a file's bytes after finalize. So a trigger on `storage.objects` (`attachments_guard_object`) refuses every write to the bucket, by any path or role, that doesn't land on a pending row's path; deletes (the purge) pass. It share-locks that pending row, so a write racing a finalize either commits before finalize reads the size or waits and is refused (tested with two sessions on the replica). Production lets `postgres` create triggers on `storage.objects` (TRIGGER privilege; checked 2026-10-08), and every Storage policy already there is scoped to its bucket. `attachments_op_finalize` reads the stored size from `storage.objects.metadata` and fails the row on a mismatch, an object over the per-file limit or a "preview" over 10 MB. Refusals are machine codes (`attachment_too_large`, `storage_full`, …) with the numbers in the error's DETAIL as JSON, so the tile can say "340 MB — your plan allows 200 MB" without a second call. Ops need a signed-in person (Storage checks the same uploader), so API keys can't upload.
  - **What the pool counts.** `storage_usage` (one row per owner) holds the bytes of ready, undeleted files (original + preview), kept by a trigger on `attachments` and moved by a trigger on `workspaces.owner_id`. On top of that, admission counts every file that isn't ready yet (in progress, abandoned, failed) at the larger of its declared and its stored size, until the purge removes it, and one person can hold at most 50 unfinished uploads. Begins are serialized per pool (a row lock on the owner's `storage_usage`), so racing uploads can't all slip under the limit: the second waits a moment and is refused if it doesn't fit. That is stricter than the spec's "two uploads racing past the limit is a small allowed overage", with no visible cost. A deleted file stops counting at once (spec). The daily purge recounts every pool from the rows, so a missed delta never outlives a day.
  - **Limits are held under the hosted upload cap, for now.** The Supabase org is on the Free plan, whose global upload limit is 50 MB and can't go higher (read with `supabase config pull` 2026-10-08), so the spec's "confirm ≥ 500 MB" fails. **Maciej, 2026-10-08: keep 50 MB for now** (alpha, no paying users); when the org moves to Supabase Pro, set the global limit to 500 MB in Storage settings and raise the cap in one migration. Until then `attachments__platform_file_cap()` returns 50 MiB and every per-file limit is the lower of the plan's and that, so `storage_status` never promises a size Storage would refuse. Either answer is one migration changing that function. The bucket itself says 500 MiB, the highest plan cap.
  - **The trash clock is the server's.** The app stamps `tasks.deleted_at` / `buckets.deleted_at` from the device clock; with a hard purge at 30 days a wrong or backdated clock would skip the restore window, so `trash_stamp_deleted_at` stamps `now()` on delete and keeps the stamp on later writes. Nothing trashed more than 30 days ago comes back: a file restore answers `attachment_expired`, a task or bucket restore `trash_expired` (it's the purge's by then), so a restore can't race the purge into a ready row with no bytes. Pool rows are always locked in `owner_id` order (the recount, ownership transfers) so they can't deadlock.
  - **Trash.** A trigger on `tasks.deleted_at` puts a task's live files in the trash with it (reason `task`, one batch id, reusing a `deleted_batch_id` on the task once TV-U6 adds one) and brings that batch back when the task is restored; a file deleted by hand earlier stays deleted. `attachments_op_restore` refuses a file trashed with its task (`restore_with_task`). `bucket` is in the reason vocabulary for TV-U6; nothing writes it yet. **No "File removed after 30 days" tombstones:** a task and its files share one 30-day clock and the purge removes the files before the tasks (a task waits while its file rows exist), so a restorable task never has purged files.
  - **Purge.** `purge-deleted` (service role, header secret `PURGE_DELETED_SECRET` compared with a Vault secret sent by pg_cron, `--no-verify-jwt`) removes objects through the Storage API, then the rows: files trashed over 30 days, uploads pending over 24 h, failed uploads, files of soft-deleted workspaces (there is no workspace restore), files whose task is gone, and objects no row names (older than a day; this is also what removes the files of an account's workspaces if `delete-account` didn't). Then tasks and buckets trashed over 30 days (links and the registry entry tombstoned like `notes__purge_ids`; a bucket waits while a task points at it), then the pool recount. `{"dry_run": true}` only counts. The schedule is its own migration (`20261008210600`), applied after a dry run. On 2026-10-08 prod had 11 tasks trashed over 30 days that the first run deletes.
  - **Alerts** are `module_activity` rows `attachments.storage_80` / `_95` (module `attachments`, entity the workspace, `notify_user_ids` = the owner, attributed to whoever uploaded), written by finalize and by restores; a jump past both sends only 95; both re-arm under 75%. They have their own mute (`storage`, Settings → Preferences). The click-through to Settings → Storage is AT-3.
  - **Elsewhere.** MCP `tasks_attachments_list` (Tasks View, the key creator's task visibility, 5-minute links); the export writes `attachments.json`, a manifest without the bytes; `delete-account` removes the files the owned workspaces' rows name (one select per 1000 files, not a Storage listing per file; a missing table counts as empty), and the purge's orphan sweep catches anything else.
