## #315 · [TV-D5] Live updates (Realtime)

### 1. What it does

- **Status:** open, not a draft; 29 files (+1,949 / −101).
- **The client:**
  - `tasks/realtime.ts`: one ref-counted channel per workspace on five tables, which sends `resync` on rejoin, on `online` and on coming back to the window;
  - `tasks/live.ts`: the newest server `updated_at` wins, and a `LiveGate` holds changes while the module's own calls are in flight;
  - wiring in `use-tasks-module.ts`, and `applyLiveTags` in the tag store.
- **Migrations:** `20261008223000` adds the publication. `20261008224500` adds a `zz_stamp_updated_at` trigger on tasks, buckets and tags.
  - **Both are applied on prod** (the stamp as version `20261008220401`, per TV-D3's stub). **Neither file is on `origin/maciej`,** so `local:reset` diverges from prod.
  - The filename order already replays prod's apply order, so nothing needs re-stamping.
- **Gates:**
  - `verify` is green (2,490 tests);
  - the validator ran 5 rounds;
  - `/code-review high` and the security scan (0 findings) ran;
  - **`/code-review ultra` (Tier 2) is still pending.**
- **Conflicts with `maciej`:** five ledger docs only.

### 2–3. First brick, or cement?

**Both. §6.6 itself names TV-D5 as the store's live layer.** What decides it is *where the data lands*, not *how it arrives*.

| Piece | Under §6.6 |
| --- | --- |
| The publication and the server stamp (already live) | **Brick.** A clock that only moves forward is what "rows changed since" delta sync keys on |
| `realtime.ts` | **Brick:** the store's socket, unchanged |
| The pure half of `live.ts`: `parseLiveChange`, `timestampMicros`, `isNewer`, upsert, `mergeQueue`, `swapTemp` | **Brick:** the store's merge reducer |
| `applyLiveTags` / the TV-T1 tag store | **Brick and the pattern.** It's already a workspace-wide store outside React, with pending ops on top: the shape the task store needs |
| `LiveGate` + `trackTaskCalls` | **Interim.** It holds the whole module while any call is in flight; the store replaces it with per-row pending edits ("roll back that one field") |
| `resync` → `loadImpl(quiet)`, a full `tasks.list` | **Cement.** Replaced by delta sync |
| Changes landing in each `useTasksModule`'s own state (the four route pages), while about six other readers still list everything with no live updates (notification centre, dashboard, quick capture, contacts enrich, capture command, settings export) | **Cement.** The store unifies these |

**No decided call contradicts it.** Two follow-ons:
- **13–19 and 53a:** TV-D7 adds projects, sections, statuses and areas to the publication and the stamp trigger.
- **TV-D7's bulk updates:** they would re-stamp and broadcast every row, so disable the trigger in that transaction (the PR's own gotcha).

**Side effect to note:**
- A quiet refetch bumps `loadStamp`, which re-runs the client's repeat catch-up (`use-tasks-module.ts`, the catch-up effect). That's the path behind **P0 #2**'s same-day reopen, and with this PR it runs on every return to the window, not only on page loads.
- **The fix:** while merging, guard it with a one-line `if (!quiet)`, or land P0 #2 (§6.2) first.

**Notes for the store block:**
- The stamp is taken before commit, so a delta cursor needs a few seconds of overlap.
- task_queue and tag_links hard-delete, so they need tombstones or a full re-read.
- If teams outgrow `postgres_changes`, database Broadcast is the path.
