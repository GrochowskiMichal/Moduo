# Session 11 — System-level audit (control matrix, fonts, icons, accent, motion, primitives, Notes canary)


## Control-sizing & stackability matrix — Moduo Tasks module

The Tasks module has no enforced control-height ladder, so controls that sit in the same row are stitched from three independent sizing systems: (1) shadcn primitives that bind to the density tokens (`Button`/`SelectTrigger` → `--ctrl-h*`; `Input` → fixed `--ctrl-h`), (2) bespoke fixed-px icon-buttons and inline inputs (`size-5/6/7`, `h-7/h-8`) that DON'T track density, and (3) three separately hand-rolled segmented toggles (ViewSwitcher, rail ModeToggle, execute ModeToggle) that each compute their own height a different way. The single most visible defect is the Plan header right cluster: a 26px "New task"/Filter/Group-Select trio sits beside a ~32px ViewSwitcher — a 6px baseline mismatch on the most-looked-at row of the module. Inside the detail panel, every date/number field is force-set to `h-8` (32px, raw, density-frozen) while the Status/Bucket/Priority/Energy/Repeat Selects beside/above them are `size="sm"` (26px) — a permanent 6px step inside one form. `Input` has no size variant, which is the root cause of the seven `h-7 px-1.5 py-0` and six `h-8` overrides (each a raw-px, density-breaking, token-bypassing patch). The fix is one explicit 4-rung ladder, a sized `Input`, and a single `SegmentedToggle` primitive that all three switchers adopt — these become the reusable controls Notes inherits.

### Proposed system
- **Control-height ladder (4 rungs, density-aware)**: Define exactly four rungs, each a token + a fully-specified style bundle so any two controls on a rung stack pixel-perfect. RUNG XS = --ctrl-h-sm (26/24/22 by density): font text-xs→bump to text-sm(13) for legibility, radius rounded-md, px = --pad-x-sm (12/10/8), icon size-3.5(14), icon-only box = the rung height square. RUNG SM = --ctrl-h (32/30/26): font text-sm(13), radius rounded-md, px-3(12) text / px-2 icon, icon size-4(16), icon-only box square. RUNG MD = a NEW 36px-default rung (between --ctrl-h and --ctrl-h-lg; reuse --ctrl-h-lg's compact value or add --ctrl-h-md 36/34/30): font text-sm(14), radius rounded-md, px-4(16), icon size-4(16). RUNG LG = --ctrl-h-lg (40/36/32): font text-base(14-15), radius rounded-lg, px-6(24), icon size-4. ROW rung = --row-h (36/32/28) for list/rail/queue rows; --row-h-sm (28/26/24) for nested/subtask rows. Rule: a control and its label/value/icon must all be derived from the same rung's bundle; no raw h-*/size-* px in component code.
  why: One ladder with paired font+icon+radius+padding per rung is the only way to guarantee stackability. Today height, font and icon are chosen independently (26px button carries 12px text; 32px input carries 13px), so even controls that happen to match height mismatch type. Binding every property to a single rung token means dense mode scales the whole control coherently. | applies: Button, Select, Input, IconButton, SegmentedToggle, Badge-as-trigger across Tasks; Notes canary adopts the identical rung tokens so its toolbar/inspector controls drop in at the same heights.
- **Input size variant (parity with Button/Select)**: Add size?: 'sm' | 'md' to Input mirroring SelectTrigger: heightVar = size==='sm' ? var(--ctrl-h-sm) : var(--ctrl-h); sm uses px = --pad-x-sm, md uses px-3. Add a `bare` (borderless/transparent) variant for the inline-editor + capture-title cases so they stop hand-setting border-0 bg-transparent px-0 shadow-none. Replace all 7 `h-7 px-1.5 py-0` and 6 `h-8` usages with <Input size='sm'> / <Input> / <Input variant='bare'>.
  why: The absence of an Input size is the single root cause of 13 raw-px overrides and the detail-form 6px step. Giving Input the same size API as Select makes Input↔Select↔Button on the same rung align automatically and removes every density-freezing override. | applies: All inline editors (rail rename/add, row title, subtask add), all popover date/number fields, capture title (bare), detail-panel date/number/duration fields. Notes inherits the same sized Input for its property fields.
- **SegmentedToggle primitive (one component, replaces 3 bespoke)**: New src/components/ui/segmented-toggle.tsx (wrap shadcn ToggleGroup, or Tabs in a button-group skin). Props: size ('sm'|'md'), items [{value,label?,icon?}], value, onValueChange, ariaLabel. Container: rounded-md bg-muted, inset p-0.5 (sm) / p-1 (md); segment height = rung height minus inset so outer == --ctrl-h(-sm); segment radius = container radius minus inset (rounded-sm); active = bg-background text-foreground shadow-sm; font-display; icon size-4. Storybook story required (DS rule 5).
  why: ViewSwitcher, rail ModeToggle and execute ModeToggle are three hand-rolls of one pattern at three heights — collapsing them to one primitive fixes the header stackability defect (toggle finally equals the sm controls beside it) and gives Notes/Mail a ready segmented control. Inset-aware radius math is specified once instead of re-derived per copy. | applies: Plan header List/Board switcher, rail Plan/Execute, execute Pomodoro/Duration; future Notes view switchers.
- **IconButton primitive (ladder-mapped square)**: New src/components/ui/icon-button.tsx (Button size='icon' already gives square via aspect-square; expose size 'sm'|'md' → box = --ctrl-h-sm / --ctrl-h, icon size-3.5 / size-4, plus a 'ghost-quiet' variant: opacity-0 group-hover:opacity-100 transition-opacity, rounded-md, hover:bg-accent). Tooltip required for icon-only (a11y rule). Replace bespoke size-5/6/7 flex icon-buttons (rail add/menu, dialog close, attach, commit, remove) with it.
  why: Five hand-rolled icon-button sizes (16/20/24/28) with identical 16px icons means padding and alignment are accidental. A ladder-mapped IconButton guarantees an icon-button matches the text control on the same rung and standardizes the quiet hover-reveal pattern used all over the rail/detail panel. | applies: Rail section-add + bucket-menu, capture DialogClose + Paperclip, detail subtask-commit + dependency-remove, anywhere a quiet trailing action appears. CompleteToggle stays bespoke (it's a checkbox affordance, not enumerated shadcn) but should pull its 16px box from the same scale token.
- **Select default font = display (kill the repeated override)**: Either change SelectTrigger's base to font-display, or add a `chrome` prop. Tasks uses font-display on the trigger in 5 places to express chrome; bake the intended default so call sites stop overriding. (Confirm with Maciej whether Select value text should be display app-wide or only in chrome contexts.)
  why: Repeating className='font-display' on every Tasks Select is a smell: the primitive ships the wrong default for chrome. Centralizing it removes 5 overrides and prevents drift where one call forgets the override and silently renders body font (masked today by the global Pilat bug, but real once that's fixed). | applies: All SelectTriggers in chrome (group/columns control, detail-panel property selects).
- **Per-row stackability contract (the canary check)**: Codify: any flex row that places >=2 interactive controls must declare a single rung for the row; lint/review check = no two direct-child controls with different size props or different h-* in one items-center flex. Reference rows to fix first: (a) Plan header right cluster → all rung SM (or all XS) incl. the SegmentedToggle; (b) detail Scheduled/Due grid + Priority/Energy + Status/Bucket → all rung SM Inputs+Selects; (c) capture footer Create button vs the pill row above it.
  why: Stackability is a per-row property, not a per-control one — the defects are all 'two controls, two rungs, one row'. Making the row the unit of the contract is what catches them in review and is the rule Notes will be held to. | applies: Every control row in Tasks; the Notes toolbar/inspector as the canary that proves the rungs travel.

## Font-token correctness (display vs body) — Tasks module

The Tasks module mostly honors the DESIGN_SYSTEM typography contract — buttons, select triggers, eyebrow/section labels, page/section headings, mode-toggle tabs, and inline title-edit all carry font-display; metadata, counters, subtask progress, breadcrumbs, error copy, and the detail-panel description correctly carry font-sans (body). But the contract itself is internally contradictory and the primitive base classes leak: (1) the Label primitive bases to font-sans while the contract says control labels are display — Tasks dodges this by hand-rolling its own Field eyebrow with font-display, so the primitive and the usage disagree. (2) The two description fields disagree with each other: capture-modal forces font-display on the description Textarea (capture-modal.tsx:204) while the detail-panel description Textarea (task-detail-panel.tsx:264) inherits the body base — same content role, opposite token, and the DESIGN_SYSTEM text explicitly (and wrongly, for long-form content) lists "the capture description" as Primary/display. (3) Several genuine body roles carry NO explicit font and therefore fall through to the global '*' Pilat bug instead of an intended token: tag names (tag-chip.tsx:39), activity-log lines (task-detail-panel.tsx:561-566), and every empty-state string ("Nothing here yet.", "Drop tasks here", "Nothing yet."). (4) The biggest design question — task titles use font-display (task-row.tsx:192, task-card.tsx:240, execute-view.tsx:153, detail title input:229), which is per-contract but reads heavier than Linear/Todoist/TickTick, all of which set list-row task titles in the body font. (5) Timer digits (execute-view.tsx:170) and the 2xl Focus-done numeral correctly use tabular-nums but there is no contract role for large numeric/timer display — they default to font-display by author choice, which is defensible but undocumented. Net: the rendered result is masked by the Pilat '*' bug, so none of this is visible today, but the intended-token map has real holes and one self-contradiction that must be resolved before Notes inherits the same primitives.

### Proposed system
- **Typography role table (canonical, lint-encodable)**: Two families only: DISPLAY = font-display (chrome/structure), BODY = font-sans (content/values/long-form), MONO = font-mono (code & keycaps only). Role → token map: page/view heading → display; section/eyebrow label → display + text-2xs uppercase tracking-wide; dialog title → display; control label (Field eyebrow) → display + text-2xs; button text → display (primitive base); menu/select TRIGGER chrome → display; segmented-control / tab label → display; task title (row, card, hero, edit input) → SINGLE decision, see ladder below; select VALUE text → follows trigger (display) UNLESS the value is free user content, then body; task description / long-form body → BODY (font-sans); metadata / counters / dates / badges / row-meta / breadcrumb → body (+ tabular-nums when numeric); tag name → body; activity-log text → body; empty-state copy → body; large numeric / timer display → body + tabular-nums by default (NEW role, see below); keycap → mono. Encode as: 'any text node under src/features|components must carry exactly one of font-display|font-sans|font-mono, OR descend from a primitive whose base sets one — no node may rely on the global * fallback.'
  why: The global '*' Pilat rule currently masks every missing token; a lint rule that forbids relying on inheritance from '*' makes the intended token explicit everywhere and survives the eventual removal of the '*' bug. One table generalizes cleanly to Notes. | applies: All src/features/tasks/ui/*.tsx and the shared primitives (Label, Select, Input, Textarea, Badge, TagChip). ## Icon system consistency — src/features/tasks/ui/*.tsx (lucide-react)

The Tasks module is 100% lucide-react (no custom/non-lucide icons, verified by grep) and stroke width is left at lucide's default 2 everywhere except one deliberate override (the completion check at strokeWidth 3). That much is healthy. The problem is the SIZE axis: every icon hard-codes its own size class with no shared ladder, producing 44 uses of size-3.5 (14px), 24 of size-4 (16px), 9 of size-3 (12px), plus scattered size-5/6/12/2.5/2/1.5. Because nothing is bound to the control-height or row-height tokens, the same conceptual rung renders at different icon sizes (e.g. Inbox is size-3 inside a Badge in one row but size-3.5 inside a Select/menu in another; the rail's All/Today/Inbox leading icons are size-4 while the section-collapse chevrons one group below are size-3.5). Worse, icon size does NOT track density: row-h and ctrl-h shrink from comfortable→dense via tokens, but every icon stays a literal 14/16px, so at data-density=dense (26px controls, 28px rows — the Linear target) the icons are optically oversized, and at comfortable they're slightly small. Several interactive icon-only buttons also violate the CLAUDE.md tooltip rule (Paperclip uses native title=, the two capture X buttons and the rail New-bucket + and the Execute reset button have aria-label but no Tooltip). The fix is a token-bound ICON-SIZE LADDER keyed to the control/row ladder, applied through the primitives (Button/Badge/Select already have the [&_svg] hooks — they just need to read an --icon-* token instead of the literal size-4), so icons recolor with shade/accent and rescale with density for free, and the same ladder carries verbatim to Notes.

## Micro-interaction & motion system — Moduo Tasks module

The motion token set in tokens.css §12 (--motion-instant/fast/base/slow/slower + --ease-out/in-out/in/spring, with a reduced-motion block that zeroes the durations) is well-designed but DEAD: across the entire src/ tree the tokens are referenced in exactly one file (global.css) and zero times in any task UI component. Every animation in Tasks goes through one of two token-bypassing paths instead: (a) bare Tailwind transition-colors / transition-opacity utilities, which run at the browser default (~150ms, linear ease) — a raw-duration/raw-easing bug per CLAUDE.md repeated in ~20 places; or (b) shadcn overlays (Dialog/Popover/Dropdown/Tooltip/Select/ContextMenu) built on tw-animate-css, whose animate-in/out resolve to `var(--tw-duration,.15s) var(--tw-ease,ease)` — a hardcoded 150ms LINEAR curve because nothing sets --tw-duration/--tw-ease. Because nothing routes through --motion-*, the tokens' reduced-motion zeroing never fires for Tasks; the only reduced-motion handling in global.css covers two decorative illustration keyframes, so transitions and overlays ignore the user's preference entirely. On top of the systemic bypass there are concrete defects and gaps: the task-row meta chips use `hidden group-hover:flex`, so hovering a row INSERTS the Schedule/Due chips and shoves the title left (content-shift jank — the named defect); check-off, commit/queue-add, drag-drop (dropAnimation={null}), detail-panel selection swap (instant key remount), tag add/remove, and timer tick/complete all have NO feedback whatsoever. The fix is to (1) make the tokens load-bearing by wiring --tw-duration/--tw-ease on overlay primitives and replacing bare transition utilities with token-bound ones, (2) convert reveal-on-hover from layout (hidden/flex) to opacity so geometry is reserved, and (3) add a small, restrained set of polish moments (check-off pop, queue-add settle) — no AI sparkle/gradient.

### Proposed system
- **Motion token contract (confirm + extend, make load-bearing)**: Keep the five durations and four eases exactly as in tokens.css §12. Assign semantic roles: --motion-instant(0) = state with no perceived motion (e.g. selected-cursor in dense lists if desired); --motion-fast(100) = hover/press/reveal feedback (color fills, opacity reveals, press); --motion-base(180) = enter/exit of overlays, panels, chips, drop-settle (the default); --motion-slow(320) = larger surface transitions (mode/view body swap, detail-panel cross-fade); --motion-slower(500) = reserved, ambient only. Easing roles: --ease-out for all ENTER and for hover/press (content arriving/responding); --ease-in for pure EXIT where used; --ease-in-out for moves between two on-screen states (sliding pill, cursor); --ease-spring ONLY for the two sanctioned emphasis moments (check-off pop, queue-add settle) — never on routine UI. Add a thin bridge so the tokens are the single source of truth: set `--tw-duration: var(--motion-base); --tw-ease: var(--ease-out);` on the overlay content primitives (and per-primitive overrides: tooltip → --motion-fast) so tw-animate-css inherits the tokens instead of its 150ms/linear default. Add a global `@media (prefers-reduced-motion: reduce)` rule that also sets `--tw-duration:0ms` and neutralizes transition-duration for the transition utilities, so reduced-motion finally covers overlays + transitions, not just the two illustration keyframes.

### Open questions
- Spring budget: do we sanction the --ease-spring on BOTH check-off and queue-add, or keep check-off as the single 'delight' moment and make queue-add a plain ease-out settle? (More springs = livelier but less Linear-quiet.)
- Detail-panel selection swap on j/k: cross-fade every keystroke risks feeling laggy during fast scanning. Do we cross-fade always, only on click/non-adjacent jumps, or skip animation when navigation is rapid (debounced)?
- Center body swap (list↔board↔execute): is a cross-fade desired, or does Maciej prefer an instant switch for keyboard-first snappiness, reserving motion only for entering Execute (the focus 'mode shift')?
- Reduced-motion philosophy: when a user prefers reduced motion, do we kill ALL motion (including the check-off pop) and fall back to color/opacity, or keep ultra-short (~80ms) fades so feedback still registers? CLAUDE.md says honor it globally — confirm 'honor' means zero, not 'reduce'.
- Timer tick: leave the per-second digit as a hard swap (current, fine), or invest in a tabular digit roll? The roll is more 'premium' but adds complexity for a low-traffic surface.
- Should the motion system ship as token-bound Tailwind utility classes (e.g. a `motion-hover`/`motion-enter` recipe) or as documented inline `duration-[var(--motion-*)] ease-[var(--ease-*)]` patterns? The former is more reusable for Notes; the latter avoids new abstractions.

## Notes-as-canary portability scan

Notes is a genuinely strong canary because the debt is *cleanly localized*. The chrome that already lives outside the Lexical editor — sidebar tree rows, section headers, breadcrumb header, right rail (Relation Graph / Tags / Close Relations), TagInput, Badge, ContextMenu — is already token-correct, uses `--row-h`/`--ctrl-h-lg`, and carries zero `src/tw` shim usage. ### Proposed system
- **Popover-Command menu (slash menu adoption)**: Rebuild SlashCommandPlugin's portal as shadcn Command inside Popover (src/components/ui/command.tsx + popover.tsx). Container: bg-popover, border-border, rounded-lg, shadow via --shadow-lg, min-w 17.5rem (280px stays as one-off geometry but surface props tokenized). Rows = CommandItem (inherits --row-h-sm height, text-sm, rounded-md, data-[selected]:bg-accent). Group headers = CommandGroup heading (reuse SECTION_TITLE recipe: text-2xs uppercase tracking-wider text-muted-foreground). Selected state must derive from --accent (not #202020) so it recolors per accent. Keep the bespoke keyboard-nav + slash-token detection logic (Lexical-specific) but render through Command.
  why: DS rule 4 mandates wrapping shadcn for Command/Popover. This single swap kills ~15 raw-hex/arbitrary violations and makes the most-used Notes affordance recolor with the 8 accents and match every other menu in the app. | applies: Notes slash menu; the same Popover-Command pattern is what Tasks' command/quick-add palettes should use, proving the menu primitive ports.
- **FieldShell + PropertyRow (right-rail Tags / future note properties)**: FieldShell: a labeled container — label (SECTION_TITLE recipe) above a control that is border-border, bg-muted, rounded-md, focus-within:ring-2 ring-ring, min-height --ctrl-h. PropertyRow: a label-on-left / value-on-right row pinned to --row-h, used when note metadata (tags, created/updated, relations) is shown as properties. Tags field renders TagChip (v2) chips inside FieldShell instead of TagInput's secondary Badges.
  why: Notes' right rail currently hand-assembles 'section title + control' three times (Relation Graph, Tags, Close Relations). Extracting FieldShell/PropertyRow lets Notes and Tasks' detail panel share the exact same field scaffolding and proves the property primitive ports beyond Tasks. | applies: Notes right rail (Tags, Close Relations); Tasks task-detail-panel property rows; later Mail/Calendar inspectors.
- **TagChip v2 (cross-module tag display)**: Adopt src/components/tag-chip.tsx (already token-routed via data-label → label tokens, no raw color) as the single tag renderer everywhere. Notes' TagInput keeps its input/commit/paste logic but renders committed tags as <TagChip onRemove> rather than Badge variant=secondary. Display contexts (Close Relations could show shared tags) use <TagChipList max=3>.
  why: tag-chip.tsx's own header comment already designates Notes as a future adopter. Unifying tag rendering is the highest-signal, lowest-risk canary: identical data, one visual language, hue-tinted and accent-independent. | applies: Notes right-rail Tags + TagInput internals; Tasks rows/cards/detail (already adopted); Mail labels later.
- **Editor type + surface tokens (Lexical chrome)**: Title input: font-display, text-3xl (or a dedicated --text-title), text-foreground, transparent bg, no raw hex. ContentEditable: text-base, leading-relaxed (token), text-foreground; placeholder text-muted-foreground. Editor container: rely on the FeaturePanelsShell bg-card wrapper — drop the inner bg-[#111111]. Keep .notes-* block theme as-is (already token-driven). Geometry padding (the 22px gutter) may stay as a single prose-gutter token (--pad-prose) but never as a color/font bypass.
  why: The block-level theme proves tokens work for Lexical; the title/body/container are the last raw-hex holdouts and the most visible. Tokenizing them makes the editor follow theme + all data-shade presets, which is the whole point of the shade work in MEMORY. | applies: Notes LexicalNoteEditor title/body/container; any future Lexical surface (Mail compose, doc comments).
- **Embed card frame (Card + Badge + IconButton)**: Embedded* frames use Card (bg-card, border-border, rounded-lg). The 'Mindmap' type label becomes <Badge variant=secondary> (or an outline badge). Loading/empty states use bg-muted + text-muted-foreground. Any embed controls (open/remove) use the rebuilt IconButton (square, --ctrl-h-sm, rounded-md, icon size 16, tooltip required). ReactFlow's internal canvas background may remain a literal (3rd-party canvas, allowed like SVG assets), but all React-rendered chrome around it is tokenized.
  why: Embeds are Notes-specific in *content* but their *frame* is a generic card-with-header — exactly the kind of thing shared primitives should own. Proves Card/Badge/IconButton port into decorator nodes. | applies: Notes EmbeddedMindmap + EmbedNode chrome; future embeds (task/board/calendar embeds).
- **Motion system adoption**: Replace ad-hoc transitions (transition-all on slash rows, transition 100ms/120ms ease literals) with the motion tokens: menu open = --motion-fast + --ease-out; row hover/selection = --motion-instant/fast; checkbox/embed state = --motion-base. Reduced-motion already zeroes these globally.
  why: Slash rows use transition-all (animates layout — janky) and the picker cells use literal 100ms. Routing through motion tokens makes Notes honor prefers-reduced-motion correctly and gives the canary a consistent feel with Tasks. | applies: Notes slash menu, table/embed pickers, checklist toggle; mirrors Tasks row/menu motion.

### Open questions
- Title typography: should the note title use font-display (Pilat Extended, matching app headings) or stay body-weight like Notion/Todoist content-first editors? This is a taste call that sets the tone for the whole editor — Linear-style would lean display+tight, Todoist-style would lean body.
- Slash menu: full shadcn Command rebuild now, or a phase-1 'tokenize-in-place' (swap hex→tokens, keep the bespoke portal) to de-risk the Lexical caret-anchoring logic, with the full Command/Popover swap deferred to phase 2? The anchoring math is the only fragile part.
- TagInput vs TagChip ownership: should TagInput (the editable wrapper) itself be promoted to a shared primitive that internally renders TagChip, so Notes/Tasks/Mail all get identical add+display behavior — or does Tasks intentionally keep a different add UX (TagPicker popover) and only the *display* chip unifies?
- Does the relation graph (XYFlow) count as Notes-specific-and-frozen for this rebuild, or should its node styling adopt the same Card/TagChip language so a node visually matches a Close-Relations row? Currently it's token-driven but bespoke.
- Embed frame controls: do embeds need an explicit IconButton toolbar (open / remove / refresh) as part of this pass, or is the read-only frame sufficient until embeds get first-class editing?
